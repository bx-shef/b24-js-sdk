```ts-type
initializeB24Frame(options?: {
  version?: ApiVersion
  restrictionParams?: Partial<RestrictionParams>
  httpOptions?: TypeHttpOptions
  keepAuthFresh?: boolean | KeepAuthFreshParams
}): Promise<B24Frame>
```

Функция `initializeB24Frame` инициализирует объект [`B24Frame`](/docs/entry-points/frame/), с помощью которого работают приложения Битрикс24.

Она управляет процессом инициализации и обрабатывает возможные ошибки соединения.

::note
Повторные вызовы поддерживаются, пока инициализация не завершена: все вызывающие используют один общий промис, поэтому одновременные вызовы ожидают один обмен, а готовое значение возвращается сразу. **Побеждает первый вызов**: `options` более позднего вызова игнорируются, возвращается уже созданный фрейм. Передавайте `restrictionParams` / `httpOptions` при первой инициализации приложения, а не там, где вызов может оказаться вторым.
::

::caution
Если приложение открыто **вне** iframe Битрикс24 (прямой URL, сервер разработки, экран установки), в `window.name` нет `DOMAIN`/`APP_SID`. Тогда промис **сразу отклоняется** с `SdkError` (`code: JSSDK_CLIENT_SIDE_WARNING`, `status: 500`), а не зависает — включая всех одновременных вызывающих, которые делят этот промис, — и более поздний вызов может повториться, когда приложение запущено внутри Битрикс24. Всегда используйте `await` внутри `try/catch`.

Каждый вызов возвращает один и тот же фрейм, пока он не уничтожен. После `$b24.destroy()` следующий вызов создаёт новый. До [#486](https://github.com/bitrix24/b24jssdk/issues/486) возвращался уничтоженный фрейм, который уже не слышит портал, поэтому любой вызов на нём зависал.
::

**Параметры**

- **`options?`** — необязательная конфигурация:
  - **`restrictionParams?: Partial<RestrictionParams>`** — настройка лимитов и повторов, передаётся HTTP-транспортам фрейма (те же параметры, что у [`setRestrictionManagerParams`](/docs/tools/limiters/)). Без неё используются значения по умолчанию. Пример: `initializeB24Frame({ restrictionParams: { retryOnNetworkError: false } })`.
  - **`httpOptions?: TypeHttpOptions`** — настройки axios, применяются поверх значений SDK по умолчанию для обоих транспортов и без изменений передаются в конструктор. Главный ключ — `adapter`: в браузере SDK запрашивает `fetch`, потому что иначе axios перебирал бы `['xhr', 'http', 'fetch']` и по порядку списка выбрал бы XHR. Пример: `initializeB24Frame({ httpOptions: { adapter: 'xhr' } })`. См. [Настройка экземпляра axios](/docs/tools/core-http/#настройка-экземпляра-axios).
  - **`keepAuthFresh?: boolean | KeepAuthFreshParams`** — поддерживать токен доступа живым, пока вкладка открыта. **По умолчанию выключено.** Передайте `true` для значений по умолчанию или объект, чтобы настроить расписание. См. [Сохранение токена актуальным](#сохранение-токена-актуальным).
  - **`version?: ApiVersion`** — зарезервировано; тип его принимает, но фрейм пока не использует, поэтому сейчас он ни на что не влияет.

**Возвращаемое значение**

- **`Promise<B24Frame>`**: промис, который при успешной инициализации разрешается объектом [`B24Frame`](/docs/entry-points/frame/).

## Использование

```ts
import { initializeB24Frame } from '@bxshefby/b24jssdk'
```

## Сохранение токена актуальным

SDK обновляет токен доступа только на **пути запроса**: перед вызовом, если
токен уже истёк, и ещё раз, если портал ответил `401`. (Действующий токен
используется как есть — обычный вызов не стоит обновления.) Это покрывает
приложение, которое общается с Битрикс24 через `$b24`, и ничего больше.

Приложение, которое само читает токен, не покрыто:

```ts
const $b24 = await initializeB24Frame()

// The token goes to your own backend — no `$b24` request is ever made,
// so nothing in the SDK ever refreshes it.
const auth = $b24.auth.getAuthData()
await fetch('/api/orders', {
	headers: { 'X-B24-Auth': auth === false ? '' : auth.access_token }
})
```

Оставьте такую страницу открытой и не трогайте её. Через `AUTH_EXPIRES` секунд
`getAuthData()` начнёт возвращать `false`, и каждый вызов вашего бэкенда будет
отвечать `401` или `403`. Ничего не менялось и ничего не сломалось — просто
срок жизни токена закончился, а обновить его было некому.

`keepAuthFresh` запускает таймер за вас:

```ts
const $b24 = await initializeB24Frame({ keepAuthFresh: true })
```

Когда он включён:

- токен обновляется **до** истечения — с запасом, а не по факту
  `getAuthData() === false`;
- проверка повторяется каждый раз, когда вкладка становится видимой: таймеры
  фоновой вкладки замедляются, а у замороженной не выполняются вовсе, поэтому
  один таймер вернулся бы к мёртвому токену;
- обновление, которого уже ждёт вызов, **не** повторяется — поддержка токена
  использует уже идущее;
- неудачное обновление никогда не выбрасывается в ваше приложение. Это состояние,
  а не исключение: импульс пишет в логгер SDK (молчит, пока вы его не
  подключили) и пробует снова, **увеличивая паузу** — 30 с, 1 мин, 2 мин, 4 мин,
  8 мин, затем каждые 10 мин. Родительское окно, которое ушло на другую страницу
  или отказывает, не стоит сообщения каждые 30 секунд всё время жизни вкладки.

Обновление токена фрейма **не тратит REST-вызов** — это `postMessage`
родительскому окну Битрикс24. Остановка автоматическая: `$b24.destroy()`
останавливает импульс вместе со всем остальным.

::caution
Передавайте параметр при **первом** `initializeB24Frame()` приложения. Все
вызывающие делят один промис, и побеждают опции первого, поэтому второй вызов с
`keepAuthFresh: true` молча получит фрейм первого вызова без импульса — а это
тот самый тихий сбой, который параметр призван предотвратить. Если вы включаете
его из композабла или плагина, убедитесь, что именно этот код инициализирует
фрейм.
::

### Почему он не включён по умолчанию

Он меняет то, когда ваше приложение обращается к родительскому окну, а Битрикс
предупреждает, что приложение, которое обновляет токен слишком часто, может
быть заблокировано автоматически. Приложение, все запросы которого идут через
`$b24`, и так получает свежий токен при каждом вызове и ничего не выигрывает от
таймера. Включайте его, когда токен покидает SDK или когда приложение должно
оставаться открытым и простаивать.

### Настройка расписания

```ts-type
type KeepAuthFreshParams = {
  marginMs?: number  // default 300000 — 5 minutes
  minDelayMs?: number // default 30000  — 30 seconds
  maxDelayMs?: number // default 600000 — 10 minutes
}
```

- **`marginMs`** — за сколько до истечения обновление становится нужным.
  Импульс целится в *истечение минус это значение*, поэтому спит ту часть жизни
  токена, когда делать нечего.
- **`minDelayMs`** / **`maxDelayMs`** — нижняя и верхняя границы этого сна.
  Начиная с 15 минут до истечения действует верхняя граница: со значениями по
  умолчанию импульс спит все 10 минут и проверяет снова.
  - Нижнюю границу нельзя снизить. `minDelayMs` может только **поднять** её
    выше 30 секунд — ошибка на порядок иначе дала бы тысячи сообщений в секунду,
    а слишком частое обновление как раз и грозит автоблокировкой.
  - `maxDelayMs` ниже действующей нижней границы поднимается до неё, поэтому
    `{ maxDelayMs: 10_000 }` само по себе означает верхнюю границу 30 секунд, а
    не 10.

```ts
// A portal handing out short-lived tokens: refresh 2 minutes ahead and never
// sleep longer than 2 minutes.
const $b24 = await initializeB24Frame({
	keepAuthFresh: { marginMs: 120_000, maxDelayMs: 120_000 }
})
```

Срок истечения, который SDK не может прочитать (отсутствует, ноль, не конечное
число), считается **наступившим**: лишний `postMessage` ничего не стоит по
сравнению с упущенным единственным шансом обновить токен.

Обновление, которое прошло успешно, но не дало запаса — токен, весь срок жизни
которого короче `marginMs`, так что он снова нужен в момент получения, —
считается неудачей и замедляется так же. Иначе сообщение отправлялось бы каждые
30 секунд, пока вкладка открыта, а параметр как раз старается этого не делать.
