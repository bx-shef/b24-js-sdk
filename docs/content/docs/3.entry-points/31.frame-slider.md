## Методы

### openSliderAppPage

```ts-type
async openSliderAppPage(params: object = {}): Promise<unknown>
```

Метод `openSliderAppPage`{lang="ts-type"} открывает текущее приложение в новом слайдере, передавая произвольные параметры.

Как это работает:

* **Передача данных:** вы вызываете метод и передаёте объект с параметрами (например, `place`, `action` или `id`).
* **Обработка в приложении:** на стороне приложения эти параметры удобнее всего перехватывать в middleware. Так можно решить, какой маршрут показать пользователю, до отрисовки страницы.
* **Бесшовная навигация:** пользователь видит новый слайдер с нужным содержимым, а логика перенаправления скрыта внутри приложения.

Настройки слайдера передаются ключами с префиксом `bx24_`. В частности, `bx24_title` задаёт заголовок слайдера; когда портал открывает слайдер, он также отражает этот заголовок на вкладке браузера (`document.title`). Поэтому, в отличие от [`parent.setTitle`](/docs/entry-points/frame-parent/#settitle) (он обновляет только `#pagetitle` в макете), этот путь меняет заголовок вкладки браузера:

```ts
$b24.slider.openSliderAppPage({ bx24_title: 'My title' }).catch(() => {})
```

#### Когда промис завершается

Измерено на облачном портале ([#486](https://github.com/bitrix24/b24jssdk/issues/486)):

* Промис завершается, когда слайдер **закрыт**, а не когда он открылся, — по крестику ✕ портала или через `closeSliderAppPage()`. Пока слайдер открыт, промис остаётся в ожидании.
* Он всегда разрешается пустой строкой `''`. Из открытого фрейма этим способом ничего не возвращается; передавайте результаты через свой бэкенд или `appOption`.
* Поэтому `await` блокирует ваш код, пока пользователь не закроет слайдер. Если слайдер нужно только открыть, не ожидайте промис:

```ts
declare function reloadList(): void

$b24.slider.openSliderAppPage({ bx24_title: 'Deal', place: 'deal', id: 42 })
  .then(() => reloadList()) // the user has closed the slider
  .catch(() => {})
```

Промис не завершается никогда в таких случаях:

* Вызывающую страницу перезагрузили, пока слайдер был открыт. Ответ приходит в новый документ, который о нём не знает.
* Экземпляр `$b24` уничтожен. Начиная с #486 `initializeB24Frame()` после `destroy()` создаёт новый фрейм; раньше он возвращал уничтоженный, и любой вызов на нём зависал.

Не измерялось: настольное приложение Битрикс24 и мобильные клиенты.

Параметры, кроме `bx24_*`, попадают в открытый фрейм как `placement.options`. Данные до 8 КБ доходили целыми; меньшего ограничения не найдено.

#### Что портал делает с вашими параметрами

Три факта, которые стоит знать до того, как строить решение вокруг этого вызова:
каждый из них уже уводил кого-то по неверному пути.

* **Портал заново открывает ваш собственный зарегистрированный URL обработчика**,
  а не путь портала. Путь портала открывает [`openPath`](#openpath), и если указать
  в нём страницу приложения, на стороне портала будет 404. Такой сбой похож на
  «слайдеры не могут показывать страницы приложений», но это не так.
* **Всё из переданного объекта пересылается в новый фрейм как
  `PLACEMENT_OPTIONS`.** Поэтому `place` — обычный параметр вызова, а **не**
  зарегистрированная встройка (placement): `placement.bind` для него не нужен, и
  назвать его можно как угодно.
* **У `bx24_width` есть практическая нижняя граница.** Ниже вашей собственной
  мобильной точки перелома настольный слайдер молча показывает мобильную вёрстку.

Маршрутизация на нужный экран после открытия фрейма — задача вашего приложения.
Участие SDK заканчивается, когда параметр доставлен.

#### Маршрутизация на нужный экран в Nuxt

Скопируйте шаблон ниже. Он длиннее простого `return navigateTo(target)`, потому
что две его строки нужны, чтобы пережить случай, который при сбое не возвращает
никакой ошибки.

::warning
Перенаправление, **возвращённое** из route middleware, не переживает первую
навигацию, если входной маршрут **предварительно отрендерен (prerender)**. Портал
открывает ваш фрейм со строкой запроса (`DOMAIN`, `PROTOCOL`, `LANG`, `APP_SID`);
для предварительно отрендеренной страницы, открытой с запросом, Nuxt гидратируется
на голом пути, а затем восстанавливает исходный URL на `app:suspense:resolve`,
напрямую присваивая `router.currentRoute.value` — в обход навигационных
охранников и перезаписывая то, куда вас перенаправил middleware. Слайдер остаётся
на странице, которую открыл портал, и **ни одной ошибки не сообщается**.
::

Это не ограничено `nuxt generate`. `nuxt build` выполняет prerender любого
маршрута из `nitro.prerender.routes`, а при `crawlLinks: true` — и всего, что
достижимо по ссылке, поэтому приложение, которое выглядит как обычное SSR-развёртывание,
всё равно может содержать предварительно отрендеренную точку входа слайдера. Не
важно, отдаёт ли файл статический веб-сервер или сам Nitro; важно лишь, несёт ли
страница предварительно отрендеренные данные.

<!-- @check-ignore: Nuxt auto-imports (defineNuxtRouteMiddleware, navigateTo, onNuxtReady) plus two app-level helpers — none resolvable in the docs typecheck context -->
```ts
export default defineNuxtRouteMiddleware(async (to) => {
  if (import.meta.server) return

  const { $initializeB24Frame } = useNuxtApp()
  const $b24 = await $initializeB24Frame()

  // `options` values are `unknown` — the portal decides what it puts there, so
  // narrow before passing it on. This is the anti-pattern the skill warns about.
  const rawPlace = $b24.placement.options['place']
  const target = routeForPlace('string' === typeof rawPlace ? rawPlace : '')
  if (!target || isSamePath(to.path, target)) return

  // Take the query from the ADDRESS BAR, not from `to.query`: a prerendered page
  // hydrates on the bare path, so `to` carries no query at all and the target
  // screen would lose `place` along with the portal's own parameters.
  const dest = { path: target, query: Object.fromEntries(new URLSearchParams(location.search)) }

  const nuxtApp = useNuxtApp()

  // Live navigation inside an already running app — the ordinary way works.
  if (!nuxtApp.isHydrating) return navigateTo(dest, { replace: true })

  // First navigation of a freshly opened slider frame: navigate once the app is
  // ready, when Nuxt has already restored the initial URL.
  onNuxtReady(() => {
    void nuxtApp.runWithContext(async () => {
      const router = useRouter()
      // The user may have navigated away while we waited for an idle moment.
      if (!isSamePath(router.currentRoute.value.path, to.path)) return
      // `router.replace`, not `navigateTo`: the latter, when it catches another
      // navigation in progress, RETURNS a route object instead of navigating —
      // and here nobody would apply it.
      const failure = await router.replace(dest)
      if (failure) console.warn('slider redirect failed', failure.type)
    })
  })
})
```

`replace: true` важен: страница, которую открыл портал, — не шаг пользователя, и
«назад» внутри слайдера не должно возвращать на неё.

`isSamePath` должен терпимо относиться к завершающему слэшу. Статический сервер
отдаёт `/app/`, а маршрутизатор разрешает `/app`, и строгое `!==` каждый раз
отменяет перенаправление.

::warning
Перенос всей строки запроса дальше переносит и `APP_SID` — идентификатор сессии
портала для этого фрейма. Это сделано намеренно — целевому экрану нужны параметры
портала, — но значение попадает в запись истории маршрутизатора и в
`route.fullPath`. Если вы отправляете `fullPath`, текущий URL или навигационную
цепочку в сервис аналитики или отчётов об ошибках, вырезайте его там. Копируйте
только нужные ключи, если остальные приложению не требуются.
::

От того, откуда запущена навигация, зависит результат. Измерено на Nuxt 4.5 со
статически сгенерированным приложением, фрейм открыт по адресу
`/app?place=app-options`:

| Откуда запущена навигация | Результат |
|----|----|
| `return navigateTo(target)` в middleware | URL не изменился, ошибка не сообщается |
| `router.replace` / `navigateTo` в `app:mounted` | `NavigationFailure: aborted` (тип 8) |
| `navigateTo` из `onNuxtReady` | работает |

`onNuxtReady` подключается к тому же `app:suspense:resolve`, но подписывается
позже и откладывает выполнение до `requestIdleCallback`, поэтому срабатывает после
восстановления. Других поддерживаемых способов нет: `redirectCode` читается только
на сервере, `abortNavigation` не умеет перенаправлять, а `external: true` означает
полную перезагрузку приложения.

#### Слайдер открывается, но показывает главную страницу

Один симптом, несколько несвязанных причин, и ни одна не вызывает ошибку.
Проверяйте по порядку:

1. **Параметр дошёл?** Выведите в лог **имена ключей** `$b24.placement.options` и
   значение одного только `place` — не весь объект. В нём могут быть параметры
   запроса портала, в том числе `APP_SID`, а собственное правило этого
   репозитория — значение, похожее на учётные данные, никогда не попадает в
   логгер (см. [AGENTS.md](https://github.com/bx-shef/b24-js-sdk/blob/main/AGENTS.md)
   и правило линтера `local/no-credential-in-logger`). Рядом выводите, в каком
   фрейме вы находитесь (`window.location.pathname`, `$b24.placement.placement`):
   ваш код работает и в основном окне, и во фрейме слайдера, а в основном окне
   `place` законно отсутствует — без идентификатора фрейма совершенно нормальная
   строка «нет place» из основного окна читается как сбой слайдера.
2. **Значение прочитано правильно?** `options['place']` имеет тип
   `unknown`{lang="ts-type"}, поэтому сузьте его перед использованием — и помните,
   что регистр ключей определяет портал, а не соглашение. См. [опции встройки](/docs/entry-points/frame-placement/#options).
3. **Маршрутизация действительно сработала?** Логируйте получившийся URL *после*
   навигации, а не решение перейти. Верное решение и навигация, которой молча не
   произошло, одинаково выглядят в логе, где записано только первое. Для
   предварительно отрендеренного маршрута Nuxt см. предупреждение выше.
4. **Запрос пережил перенаправление?** Если ваше приложение читает `place` ещё и из
   URL фрейма, перенаправление, которое теряет запрос, не даёт целевому экрану
   понять, что он в слайдере, — и «Отмена» открывает вторую копию приложения вместо
   того, чтобы свернуть слайдер.

Шаги 2 и 3 воспроизводятся **без портала**: запустите собранное приложение
локально и откройте `/<ваша-страница>?place=<ваш-place>`, читая `place` из запроса
как запасной вариант. К Битрикс24 маршрутизация не имеет отношения.

### closeSliderAppPage

```ts-type
async closeSliderAppPage(): Promise<void>
```

Просит портал закрыть слайдер с приложением. Это та же команда, что
[`parent.closeApplication()`](/docs/entry-points/frame-parent/#closeapplication),
с теми же оговорками — прочитайте этот раздел, прежде чем проектировать закрытие.

::warning
Измерено на облачном портале ([#486](https://github.com/bitrix24/b24jssdk/issues/486)): после `closeSliderAppPage()` портал падает при завершении закрытия, поэтому этот промис не завершается никогда, а страница портала остаётся недоступной для кликов, пока её не перезагрузят. Промис `openSliderAppPage` у открывшей стороны при этом завершается. По возможности давайте пользователю закрывать слайдер крестиком ✕ портала.
::

### openPath

```ts-type
async openPath(url: URL, width: number = 1640): Promise<StatusClose>
```

Открывает указанный путь внутри портала в слайдере.

Обрабатывает ошибки, связанные с использованием на мобильных устройствах, и может открыть URL в новой вкладке, если слайдер не поддерживается.

Возвращает [`StatusClose`{lang="ts-type"}](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/types/slider.ts)

| Параметр | Тип | Описание |
|----|----|----|
| `url` | `URL`{lang="ts-type"} | URL, который нужно открыть. |
| `width` | `number`{lang="ts-type"} | Ширина слайдера, число в диапазоне от `1640` до `900`. |

Этот пример показывает вызов слайдера Битрикс24 и обработку результата его закрытия.

Главное:

* **Обработка завершения:** после закрытия слайдера SDK возвращает статус. Это позволяет запускать последующие операции, например заново инициализировать данные приложения.

::warning
В некоторых случаях Битрикс24 открывает интерфейс не в слайдере, а в новой вкладке браузера.

* **Ограничение:** закрытие отдельной вкладки стандартными средствами JS определить практически невозможно.
* **Решение:** параметр `isOpenAtNewWindow` в ответе jsSdk позволяет определить, что вместо слайдера открыта вкладка, и правильно настроить логику приложения.
::

### getUrl

```ts-type
getUrl(path: string = '/'): URL
```
Возвращает `URL`{lang="ts-type"} относительно доменного имени и пути.

```ts
$b24 = await initializeB24Frame()
// ...
const url = $b24.slider.getUrl('/settings/configs/userfield_list.php')
```

### getTargetOrigin

```ts-type
getTargetOrigin(): string
```

Возвращает адрес Битрикс24 (например, `https://your_domain.bitrix24.com`).
