## Обзор

`rest.documentation.openapi` — это метод REST v3, который возвращает **собственный** документ
[OpenAPI 3.0.0](https://spec.openapis.org/oas/v3.0.0) портала — единое
машиночитаемое описание каждого метода REST API v3, существующего **на этом
конкретном портале**, с полями тела запроса (и примерами значений) и
конвертом ответа для каждого из них.

Это **источник истины** о доступности методов v3. SDK намеренно
**не** хранит жёстко заданный список методов v3 (такой список отставал
от сервера и блокировал допустимые методы); вместо этого `$b24.actions.v3.*` отправляет любой метод
на сервер и позволяет ему решать. Когда нужно узнать, *что на самом деле есть* —
какие методы, какие поля, — спросите об этом сам портал этим вызовом.

::note
Документ перечисляет методы, которые есть **на этом портале**. Его содержимое зависит от
установленных модулей и сборки, поэтому два портала отвечают по-разному — всегда считайте
его специфичным для портала, а не глобальным каталогом. Измерено: коробочная сборка
опубликовала **147** методов в 8 модулях, облачный портал — **245**, а второй
облачный портал — **220** с другим набором, включая изменённые поля запроса
у методов, присутствующих на обоих.

**Присутствие в списке — не разрешение.** Метод, присутствующий в документе, всё равно завершается
`BITRIX_REST_V3_EXCEPTION_INSUFFICIENTSCOPEEXCEPTION` (403), если у токена нет
нужной области доступа, — поэтому документ нельзя использовать как проверку прав. Он также не
фильтруется по вашим правам: расширение вебхука с 10 областей до 15 не
изменило его вовсе. Области доступа публикуются отдельно — через `rest.scope.list`.
::

::warning
Этот метод отвечает **без обычного конверта**: документ OpenAPI приходит
на верхнем уровне, без обёртки `result` и без блока `time`. SDK заворачивает его
обратно в `result`, чтобы приведённые ниже фрагменты работали, но необработанный HTTP-клиент увидит
сам документ как тело ответа.
::

## Вызов через SDK

Это обычный вызов v3 — без специального помощника:

```ts
const response = await $b24.actions.v3.call.make<{ openapi: string }>({
  method: 'rest.documentation.openapi'
})

if (!response.isSuccess) {
  console.error(new Error(`Error: ${response.getErrorMessages().join('; ')}`))
} else {
  const doc = response.getData()?.result
  console.log(`OpenAPI ${doc?.openapi}`) // e.g. "3.0.0"
}
```

## Опубликовано ли данное действие? Случай `*.aggregate`

Поскольку `paths` содержит по одной записи на метод, фильтр по суффиксу отвечает на вопрос
«публикует ли этот портал действия такого рода вообще» одним вызовом. Агрегация —
случай, который возникает постоянно, ведь `actions.v3.aggregate.make` помечен `@experimental`
именно потому, что в поставке нет ничего, что его использует:

```ts
const response = await $b24.actions.v3.call.make<{ paths?: Record<string, unknown> }>({
  method: 'rest.documentation.openapi'
})

const aggregates = Object.keys(response.getData()?.result?.paths ?? {})
  .filter(path => path.endsWith('.aggregate'))
  .map(path => path.replace(/^\//, ''))

console.log(aggregates.length === 0 ? '(none)' : aggregates.join(', '))
```

На четырёх измеренных порталах это выводит `(none)`: ни один поставляемый модуль не подключает
серверный трейт агрегации, поэтому
[`Aggregate.make()`](/docs/working-with-the-rest-api/choosing-the-right-method/)
не к чему применить, и ответом остаётся клиентская свёртка поверх `CallList`. Спросите свой
портал, а не считайте это постоянным: механизм поставляется и работает, а модуль может
подключиться к нему в любой версии.

## Как выглядит документ

Стандартный объект OpenAPI 3.0.0. На практике важны такие части:

| Поле | Что содержит |
|----|----|
| `openapi` | строка версии спецификации, например `"3.0.0"` |
| `info` | `{ title: "Bitrix24 REST V3 API", version }` |
| `tags` | одна запись **на модуль** — `humanresources`, `mail`, `main`, `note`, `rest`, `tasks`, `timeman`, … |
| `paths` | одна запись **на метод**, ключ — `/method.name` (например, `/tasks.task.list`) |

Каждый `paths['/method.name']` содержит операции `post` (и `get`) с
массивом `tags` (модуль-владелец), JSON Schema `requestBody`, описывающей
допустимые параметры — часто с полем `example` с реальными названиями полей, —
и схему `responses` для конверта `{ result }`.

```ts
// Shape (abridged) — the fields you read in practice
type OpenApiDoc = {
  openapi: string // e.g. "3.0.0"
  info: { title: string, version: string } // title: "Bitrix24 REST V3 API"
  tags: Array<{ name: string, description: string }> // one entry per module
  paths: Record<string, {
    // keyed by "/method.name", e.g. "/tasks.task.list"
    post?: {
      tags?: string[] // the owning module
      requestBody?: { content: { 'application/json': { schema: unknown } } }
    }
    get?: { tags?: string[] }
  }>
}
```

## Почему это важно для ИИ-агентов

Документ — самый чистый способ для LLM или генератора кода работать с
порталом **без догадок**:

- **Обнаружение** — перечислите, какие именно методы v3 существуют, прежде чем генерировать
  вызов, а не выдумывайте название метода, которое вернёт
  `METHODNOTFOUNDEXCEPTION`.
- **Верные поля** — читайте настоящие названия `select` и параметров из схемы `requestBody`
  каждого метода (и её `example`), а не придумывайте их.
- **Типизация / генерация кода** — передайте схему генератору, чтобы получить типизированные
  обёртки, или сузьте `$b24.actions.v3.call.make<T>()` нужным `T`.
- **Учёт портала** — поскольку ответ зависит от портала, агент может подстроиться
  под реально установленные модули, а не под общее допущение. Области доступа — отдельный вопрос,
  на который документ не отвечает; сочетайте его с `rest.scope.list`,
  где портал их публикует.

::tip
Документ большой (часто **100 КБ+**) и **только для чтения** — он не
меняется между вызовами в рамках сессии. Получите его **один раз**, кэшируйте и работайте
с кэшированным объектом. Не запрашивайте его при каждом взаимодействии.
::

## Обработка ошибок

`rest.documentation.openapi` — обычный вызов v3, поэтому он следует стандартному
контракту `AjaxResult` — всегда проверяйте `isSuccess`{lang="ts-type"}, прежде чем читать
документ:

```ts
const response = await $b24.actions.v3.call.make<{ openapi: string }>({
  method: 'rest.documentation.openapi'
})

if (!response.isSuccess) {
  // e.g. the token lacks the scope, or the portal is unreachable
  console.error(new Error(`Error: ${response.getErrorMessages().join('; ')}`))
} else {
  const doc = response.getData()?.result
  console.log(`OpenAPI ${doc?.openapi}`)
}
```

## Примеры

### Список всех доступных методов

```ts
const response = await $b24.actions.v3.call.make<{
  paths: Record<string, unknown>
}>({ method: 'rest.documentation.openapi' })

const methods = Object.keys(response.getData()?.result?.paths ?? {})
  .map(path => path.replace(/^\//, '')) // "/tasks.task.list" → "tasks.task.list"

console.log(`${methods.length} v3 methods available`)
```

### Методы, сгруппированные по модулям

```ts
type OpenApiDoc = {
  paths: Record<string, { post?: { tags?: string[] } }>
}

const doc = (await $b24.actions.v3.call.make<OpenApiDoc>({
  method: 'rest.documentation.openapi'
})).getData()?.result

const byModule = new Map<string, string[]>()
for (const [path, ops] of Object.entries(doc?.paths ?? {})) {
  const moduleName = ops.post?.tags?.[0] ?? 'unknown'
  const list = byModule.get(moduleName) ?? []
  list.push(path.replace(/^\//, ''))
  byModule.set(moduleName, list)
}

console.log([...byModule.keys()]) // ['humanresources', 'mail', 'main', 'note', 'rest', 'tasks', 'timeman', …]
```

### Проверка существования конкретного метода

```ts
const doc = (await $b24.actions.v3.call.make<{ paths: Record<string, unknown> }>({
  method: 'rest.documentation.openapi'
})).getData()?.result

const exists = Boolean(doc?.paths?.['/note.collection.list'])
console.log(`note.collection.list on v3: ${exists}`)
```

## Альтернативы и рекомендации

* **Для полей одной сущности**: [`<entity>.field.list`](/docs/working-with-the-rest-api/discovering-entity-fields/) —
  более дешёвая половина того же вопроса. Этот документ говорит, *какие методы существуют*;
  тот — *какие поля есть у этой сущности*, и несёт `filterable`, `editable`
  и `requiredGroups`, которых в схеме запроса здесь вообще нет.
* **Справочник Apidocs**: публичный [справочник REST API v3](https://apidocs.bitrix24.com/api-reference/rest-v3/index.html)
  описывает методы в человекочитаемом виде; `rest.documentation.openapi` — его
  *программный, специфичный для портала* аналог.
* **Для вызова обнаруженного метода**: используйте [`Call`](/docs/working-with-the-rest-api/call-rest-api-ver3/),
  [`CallList`](/docs/working-with-the-rest-api/call-list-rest-api-ver3/) /
  [`FetchList`](/docs/working-with-the-rest-api/fetch-list-rest-api-ver3/) или нативные
  [`CallTail`](/docs/working-with-the-rest-api/call-tail-rest-api-ver3/) /
  [`FetchTail`](/docs/working-with-the-rest-api/fetch-tail-rest-api-ver3/),
  когда метод публикует действие `tail`.
* **Какие методы листают страницы нативным курсором**: отфильтруйте те же `paths`
  по суффиксу — `Object.keys(doc.paths).filter(path => path.endsWith('.tail'))`. Такие
  методы публикуют немногие, поэтому это стоит проверить, прежде чем обращаться к
  [`CallTail`](/docs/working-with-the-rest-api/call-tail-rest-api-ver3/).
* **Выбор между v2 и v3**: см. [Выбор подходящего метода](/docs/working-with-the-rest-api/choosing-the-right-method/).
