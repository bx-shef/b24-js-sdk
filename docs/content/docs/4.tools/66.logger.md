## Уровни журналирования

Уровни журналирования расположены по возрастанию серьёзности — от **подробной отладки** (0) до **критических сбоев** (7).
Фильтрация работает по принципу включения: при заданном уровне записываются сообщения этого уровня и всех более высоких.

| Уровень | Значение | Когда использовать | Практический пример |
|---------|----------|-------------------|-------------------|
| **DEBUG** | 0 | Подробная отладочная информация для разработчиков<br>**По умолчанию при разработке** | `Loaded 1523 records in 45ms` |
| **INFO** | 1 | Информация о штатной работе приложения<br>Отслеживание бизнес-логики | `User #123 added item to cart` |
| **NOTICE** | 2 | Важные, но не критичные события<br>Успешные операции с последствиями | `System settings changed by administrator` |
| **WARNING** | 3 | Потенциальные проблемы<br>Приложение работает, но требует внимания | `Cache almost full (95%)` |
| **ERROR** | 4 | Ошибки выполнения, требующие вмешательства<br>Часть функциональности недоступна | `Failed to connect to database` |
| **CRITICAL** | 5 | Отказ критических компонентов<br>Требуют срочного вмешательства в рабочее время | `Payment gateway unavailable for more than 5 minutes` |
| **ALERT** | 6 | Серьёзные проблемы, требующие немедленного решения | `Disk space exhausted at 99%` |
| **EMERGENCY** | 7 | Система неработоспособна<br>Наивысшая срочность | `Server farm completely unavailable` |

### Как работает фильтрация по уровню

```ts
import { Logger, ConsoleHandler, LogLevel } from '@bxshefby/b24jssdk'

// Example 1: ERROR level
const $logger = new Logger('app');
$logger.pushHandler(new ConsoleHandler(LogLevel.ERROR));

// These logs WILL be output:
$logger.error('Loading error', {}); // ✓ level 4 >= 4
$logger.critical('Critical error'); // ✓ level 5 >= 4
$logger.alert('Alert'); // ✓ level 6 >= 4
$logger.emergency('Emergency'); // ✓ level 7 >= 4

// These logs WILL NOT be output:
$logger.debug('Debug'); // ✗ level 0 < 4
$logger.info('Info'); // ✗ level 1 < 4
$logger.warning('Warning'); // ✗ level 3 < 4
```

## Основные типы и интерфейсы

**LogRecord**
Структура записи журнала:

```ts-type
{
  channel: string,              // Logger channel name
  level: LogLevel,              // Numeric level
  levelName: LogLevelName,      // Level name (e.g., 'DEBUG')
  message: string,              // Message text
  context: Record<string, any>, // Contextual data
  extra: Record<string, any>,   // Additional data (added by processors)
  timestamp: Date               // Timestamp
}
```

**LoggerInterface**
Основной интерфейс логгера:

```ts-type
log(level: LogLevel, message: string, context?: Record<string, any>): Promise<void>
debug(message: string, context?: Record<string, any>): Promise<void>
info(message: string, context?: Record<string, any>): Promise<void>
notice(message: string, context?: Record<string, any>): Promise<void>
warning(message: string, context?: Record<string, any>): Promise<void>
error(message: string, context?: Record<string, any>): Promise<void>
critical(message: string, context?: Record<string, any>): Promise<void>
alert(message: string, context?: Record<string, any>): Promise<void>
emergency(message: string, context?: Record<string, any>): Promise<void>
```

**Handler**
Обработчик журнала:

```ts-type
handle(record: LogRecord): Promise<boolean>  // Process record
isHandling(level: LogLevel): boolean         // Check level support
shouldBubble(): boolean                      // Whether to continue chain
setFormatter(formatter: Formatter): void     // Set formatter
getFormatter(): Formatter | null             // Get formatter
```

**Formatter** для преобразования LogRecord:

```ts-type
format(record: LogRecord): any
```

**Processor** для изменения LogRecord:

```ts-type
(record: LogRecord) => LogRecord
```

## Основные классы

**AbstractLogger**
Абстрактный базовый класс с вспомогательными методами (debug, info и т. д.).

**Logger**
Основная реализация логгера:

```ts-type
constructor(channel: string)                 // Create logger with specified channel
pushHandler(handler: Handler): this          // Add handler
popHandler(): Handler | null                 // Remove last handler
setHandlers(handlers: Handler[]): this       // Set list of handlers
pushProcessor(processor: Processor): this    // Add processor
log(level, message, context): Promise<void>  // Main logging method
```

**NullLogger**
Заглушка для случаев, когда журналирование не нужно. Ничего не делает.

## Фабрика логгеров

**LoggerFactory**
Статические методы для создания логгеров:

```ts-type
createNullLogger(): LoggerInterface
createForBrowser(channel: string, isDevMode: boolean = false): LoggerInterface
createForBrowserDevelopment(channel: string, level: LogLevel = LogLevel.DEBUG): LoggerInterface
createForBrowserProduction(channel: string, level: LogLevel = LogLevel.ERROR): LoggerInterface
forcedLog(logger, action, message, context): Promise<void>  // Forced logging
```

## Процессоры

Процессоры изменяют записи журнала перед обработкой:

**Встроенные процессоры:**

- `memoryUsageProcessor` — добавляет использование памяти
- `pidProcessor` — добавляет идентификатор процесса

**Создание собственного процессора:**

```ts
import { Processor } from '@bxshefby/b24jssdk'

const customProcessor: Processor = (record) => {
  record.extra.customField = 'value'
  return record
}
```
## Форматтеры

**AbstractFormatter**
Базовый класс форматтера с поддержкой форматирования даты.

**LineFormatter**
Форматирует журнал в строку с поддержкой шаблонов:

```ts-type
// Default: '[{channel}] {levelName}: {message} {context} {extra} {date}'
new LineFormatter(formatString, dateFormat)
```

_Доступные подстановки:_

- `{channel}` — название канала
- `{levelName}` — название уровня
- `{message}` — сообщение
- `{context}` — контекст в JSON
- `{extra}` — дополнительные данные в JSON
- `{timestamp}` — метка времени unix
- `{date}` — дата в заданном формате

**JsonFormatter:** форматирует журнал в строку JSON.

**TelegramFormatter:** форматирует запись журнала для [отправки в Telegram](https://core.telegram.org/bots/api#html-style). Поддерживает HTML-разметку с экранированием специальных символов.

## Обработчики

**AbstractHandler**
Базовый класс обработчика с поддержкой уровня журналирования и всплытия (bubbling).

**ConsoleHandler**
Выводит журнал в консоль браузера с оформлением для разных уровней.

**ConsoleV2Handler**
Улучшенная версия ConsoleHandler с более читаемым выводом.

**MemoryHandler**
Хранит журнал в памяти (удобно для тестов и отладки):

```ts
import { MemoryHandler, LogLevel } from '@bxshefby/b24jssdk'

const handler = new MemoryHandler(LogLevel.DEBUG, { limit: 1000 })
const records = handler.getRecords() // Get all records
handler.clear() // Clear records
```

**ConsolaAdapter**
Адаптер для [Consola](https://github.com/unjs/consola).

**WinstonAdapter**
Адаптер для [Winston](https://github.com/winstonjs/winston).

**StreamHandler**
Обработчик потоков Node.js для записи журнала в потоки.

**TelegramHandler**
[Отправляет журнал](/docs/tools/logger-telegram/) в чат Telegram. В среде, похожей на браузерную (основной поток или любой Web, Shared или Service Worker), он ничего не отправляет и вместо этого предупреждает в консоли, потому что запрос содержал бы токен бота. На сервере отправляет сообщение через Telegram Bot API.

## Использование

### Простой пример
```ts
import { LoggerFactory } from '@bxshefby/b24jssdk'

const devMode = !!(typeof import.meta !== 'undefined' && (import.meta.dev || import.meta.env?.DEV))
const $logger = LoggerFactory.createForBrowser('Example:getCrmItem', devMode)
$logger.info('User logged in', { userId: 123 })
```

### Расширенная настройка

```ts
import { Logger, ConsoleV2Handler, LineFormatter, LogLevel, memoryUsageProcessor, pidProcessor } from '@bxshefby/b24jssdk'

const $logger = new Logger('app')
const handler = new ConsoleV2Handler(LogLevel.DEBUG)
handler.setFormatter(new LineFormatter('[{levelName}] {message}'))

$logger
  .pushHandler(handler)
  .pushProcessor(memoryUsageProcessor)
  .pushProcessor(pidProcessor)

$logger.warning('Low memory', { freeMemory: '10MB' })
```

### Создание собственного обработчика

<!-- @check-ignore: AbstractHandler is not re-exported from the SDK main index -->
```ts
import { AbstractHandler, LogRecord } from '@bxshefby/b24jssdk'

class CustomHandler extends AbstractHandler {
  async handle(record: LogRecord): Promise<boolean> {
    // Send to server, write to file, etc.
    return true // Returns true if record was processed
  }
}
```

## Особенности

1. **Асинхронность**: все методы журналирования возвращают Promise.
2. **Цепочка обязанностей**: обработчики вызываются последовательно.
3. **Всплытие (bubbling)**: если обработчик возвращает `true`, а `shouldBubble() === false`, цепочка прерывается.
4. **Каналы**: записи группируются по каналам для фильтрации.
5. **Контекст**: поддержка структурированных данных через параметр `context`.
6. **Изоляция от вашего кода**: сбойный обработчик или процессор не может нарушить
   журналируемую операцию — см. ниже.

## Изоляция сбоев

`Logger.log()` никогда не выбрасывает исключение и не отклоняет промис. Обработчик или процессор,
который завершился сбоем, пропускается, а остальные обработчики по-прежнему получают запись.

Это важно, потому что журналирование работает по принципу «отправил и забыл». SDK вызывает логгер как
простой оператор, без `await` — `this.getLogger().info('post/response', { … })`.
Неожиданно отклонённый промис — это **необработанное отклонение (unhandled rejection)**, и Node
по умолчанию завершает на нём процесс. Обработчики выполняют реальный ввод-вывод — Telegram,
записываемый поток, сторонний адаптер, — поэтому отклонение — обычное эксплуатационное событие:
недоступная конечная точка, закрытый поток, переполненный диск. Без изоляции сбой Telegram
мог бы уронить серверное приложение, которое всего лишь подключило этот обработчик.

Каждый сбой выводится в `console.warn` без дедупликации, поэтому видно, как часто сбоит получатель.
Сообщение уходит в `console`, а не через логгер: если направить сбой журналирования обратно
в логгер, который только что отказал, получится рекурсия.

Ограничение, о котором стоит знать: изоляция охватывает сбои внутри логгера, но не аргументы, которые
вы для него собираете. Аргументы вычисляются в месте вызова до того, как будет достигнут `log()`,
поэтому выражение, которое выбрасывает исключение при сборке `context`,
всё равно выбросит его в вашем коде.

### Собственный логгер

Если вы передаёте собственную реализацию в `setLogger(...)`, **каждый метод журналирования
должен возвращать промис.** Это не вопрос стиля — на этом держится работа SDK.

Каждое из примерно 90 мест вызова журнала в SDK написано по принципу «отправил и забыл» и говорит об этом явно —
`this.getLogger().info('post/response', { … }).catch(() => {})`.
Завершающий `.catch(() => {})` объявляет, что «результат здесь не важен».
Без него необработанное отклонение становится **unhandled rejection**, на котором Node
по умолчанию завершает процесс. Но `.catch` есть только у промиса: метод, возвращающий
`undefined`, вызывает `TypeError: ... .catch is not a function` в каждом месте журналирования
в SDK — деталь журналирования превращается в сломанную операцию.

TypeScript контролирует это за вас, поскольку `LoggerInterface` объявляет каждый уровень как
`Promise<void>`. Риск есть в чистом JavaScript или за `as any`:

```ts
// Correct — an async method always returns a promise, even if it throws inside
class MyLogger {
  async info(message: string, context?: Record<string, any>) {
    await fetch('https://logs.example.com/ingest', {
      method: 'POST',
      body: JSON.stringify({ message, context })
    })
  }
  // ...and every other level
}
```

`setLogger(...)` при установке логгера выполняет поверхностную проверку и предупреждает в
`console`, если какого-то уровня нет или он не вызывается. Сами ваши методы он намеренно не вызывает,
чтобы посмотреть, что они возвращают: это породило бы лишние записи журнала просто от установки
логгера, — поэтому метод, который существует, но возвращает не промис, не будет обнаружен.
Возвращать промисы — ваша часть контракта.

## Рекомендации по использованию

**Разработка**

- Используйте `LoggerFactory.createForBrowserDevelopment` с уровнем `DEBUG`
- Добавляйте процессоры для отладочной информации

**Продакшен**

- Используйте `LoggerFactory.createForBrowserProduction` с уровнем `ERROR` или выше
- Ограничивайте число обработчиков ради производительности
- Подумайте о собственных обработчиках для отправки журнала на сервер

**Контекст**

<!-- @check-ignore: illustrative snippet — orderId, userId, error are not declared -->
```ts
// Good:
$logger.error('Failed to process order', {
  orderId: 123,
  userId: 456,
  error: error.message
})

// Bad:
$logger.error(`Failed to process order ${orderId} for user ${userId}: ${error.message}`)
```
