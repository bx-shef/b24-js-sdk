## Обзор

SDK маскирует фиксированный набор ключей, содержащих учётные данные, прежде чем данные запроса попадут в приёмник логгера или объект ошибки. Маскировщик ([`redact.ts`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/redact.ts)) — единый источник истины, общий для всего SDK.

На **HTTP-уровне** (начиная с v1.1.2) он удаляет эти ключи из любой полезной нагрузки запроса, прежде чем она попадёт:

- в **контекст логгера** записей уровня info `post/send`, `post/response`, `post/catchError` (и в запись отладки более низкого уровня `http request starting` / `_logRequest`);
- в поле `requestInfo.params` в [`AjaxError`](#ajaxerror--tojson--tostring), которое видят потребители через `AjaxError.toString()` / `toJSON()`.

Тот же маскировщик — с несколькими исправлениями безопасных проекций — защищает и поверхности с учётными данными **вне** HTTP-уровня: клиент Pull, канал `postMessage` фрейма и сообщения об ошибках хука. См. [Поверхности вне HTTP](#поверхности-вне-http) ниже.

Это значит, что при подключении собственного логгера через `B24Hook.setLogger(...)`, `B24Frame.setLogger(...)` или `B24OAuth.setLogger(...)` **не нужно** добавлять собственное маскирование для стандартных ключей учётных данных, перечисленных ниже, — SDK уже удаляет их на выходе.

Пользовательские поля, которые добавляете вы, **не** покрываются. Всё, что вы поместили в `params` под нестандартным ключом (например, `mySecretField`), попадает в логгер без изменений. См. [Что SDK не скрывает](#что-sdk-не-скрывает).

## Что SDK скрывает автоматически

Единый источник истины — [`packages/jssdk/src/core/http/redact.ts`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/redact.ts).

```ts
// packages/jssdk/src/core/http/redact.ts
export const SENSITIVE_PARAM_KEYS: readonly string[] = [
  'auth',
  'password',
  'token',
  'secret',
  'access_token',
  'refresh_token',
  'client_secret',
  'application_token',
  'sessid',
  'key',
  'signature'
]
```

Везде, где встречается любой из этих ключей, — совпадение **без учёта регистра**, поэтому `Auth` / `TOKEN` / `Access_Token` тоже перехватываются, — значение заменяется на `'***REDACTED***'` (экспортируемая `REDACTED_PLACEHOLDER`) до сериализации полезной нагрузки для журнала или сохранения в объекте ошибки.

Обход заходит на **два уровня** во вложенные объекты и массивы. Это охватывает форму пакета `{ cmd: [{ method, params: { ...creds... } }, ...] }`, где учётные данные лежат в `cmd[i].params.<key>`, а также плоские одноуровневые формы вроде `{ data: { token } }`. Всё, что глубже, **не** обходится: держите секреты ближе к верху полезной нагрузки, если хотите, чтобы они перехватывались, или маскируйте их в месте вызова.

Переданное значение не обязано быть объектом. **Массив** или простая **строка** на верхнем уровне обходятся на тех же условиях — это важно, потому что `post/response` журналирует `response.data?.result`, а пакет `restApi:v3` отвечает там массивом. До v2.3.0 маскировщик возвращал любой не-объектный ввод без изменений, поэтому такие ответы попадали в журнал незамаскированными (#487).

Маскировщик также сканирует **строковые значения** на пары учётных данных в строке запроса (`<key>=<value>`) и маскирует значение на месте. Это охватывает сериализованную форму пакетной команды `cmd[i] = 'method?auth=<token>&…'`, где учётные данные — это текст, а не ключ объекта. Маскируется только пара `key=value`, ключ которой — один из канонических, и требуется граница запроса (`?` / `&` / начало строки), поэтому `=` в позиции значения не затрагивается.

Маскировщик также скрывает **секретный сегмент URL вебхука Битрикс24** — `/rest/<userId>/<secret>/` — везде, где такой URL встречается в строке. Этот секрет — не ключ и не пара `key=value`, поэтому ни один из двух проходов выше его не видит.

Он попадает в журнал, потому что маскировщик работает и над **телами ответов**, и над отправленными вами параметрами, а метод портала может *вернуть* такой URL: `rest.deferredbatch.downloadresult` отвечает `downloadUrl`, построенным из вызывающего вебхука.

Покрыты обе формы: `/rest/<id>/<secret>/` для `restApi:v2` и `/rest/api/<id>/<secret>/` для `restApi:v3`. Сегмент может также завершать строку или сопровождаться `?` или `#`, потому что `.../rest/1/<secret>` без завершающей косой черты — это форма, которую принимает `B24Hook.fromWebhookUrl`.

От избыточного маскирования его удерживает остальная часть формы: идентификатор пользователя — цифры, секрет не содержит точки и состоит не менее чем из восьми символов, и это должен быть целый сегмент пути. Имя метода REST содержит точки (`crm.item.list`), а короткое слово пути (`batch`, `profile`) короче минимальной длины, поэтому ни то, ни другое не маскируется — ослепить журналы само по себе было бы дефектом. Сопоставление не учитывает регистр, а дефис и подчёркивание допускаются внутри секрета, хотя Битрикс24 выдаёт буквенно-цифровые: SDK не контролирует ни регистр, в котором приходит скопированный URL, ни формат, который портал может выдать в следующий раз. Хост и идентификатор пользователя остаются читаемыми.

Запись `key` намеренно широка: она маскирует любое свойство с именем `key` (и любую пару `?key=…` в запросе), а не только значения, похожие на ключ API. В REST Битрикс24 `key` — параметр учётных данных, поэтому выбор консервативный: учтите, что поле с именем `key`, не являющееся учётными данными, тоже будет показано как `***REDACTED***` в ваших журналах.

Запись `signature` (добавлена в #43 для HMAC канала Pull) широка так же: маскируется любое свойство с именем `signature` и любая пара `?signature=…` в запросе. В push/pull Битрикс24 `signature` — это HMAC канала, поэтому такая широта принята: поле с именем `signature`, не являющееся учётными данными, тоже будет отображаться как `***REDACTED***`.

### Места HTTP-вызовов, использующие маскировщик

| Где | Канал журнала | Уровень | Источник |
| --- | --- | --- | --- |
| `post/send` (отправляемый запрос) | контекст логгера `params` | `info` | [`abstract-http.ts:554`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/abstract-http.ts#L554) |
| `post/response` (тело успешного ответа) | контекст логгера `result` | `info` | [`abstract-http.ts:573`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/abstract-http.ts#L573) |
| `post/catchError` (ошибка axios) | контекст логгера `responseData` | `info` | [`abstract-http.ts:575`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/abstract-http.ts#L575) |
| `http request starting` (`_logRequest`) | контекст логгера `params` | `debug` | [`abstract-http.ts:887`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/abstract-http.ts#L887) |
| конструктор `AjaxError` | `requestInfo.params` (виден через `toJSON()` / `toString()`) | — | [`ajax-error.ts:128`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/ajax-error.ts#L128) |

Остальные места журналирования в [`abstract-http.ts`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/abstract-http.ts) (`http request attempt`, `http request successful`, `http request failed`, `http refreshing auth token`, `http auth error detected`, журналы ожидания повтора) содержат только `requestId`, `method`, `api`, `attempt`, `duration` и код, сообщение и статус `AjaxError` — ни одно из них не затрагивает `params` или URL вебхука, поэтому вопросов маскирования у них нет.

Записываемые данные также **ограничены по длине**: `params` в `post/send`, `result` в `post/response` и `responseData` в `post/catchError` обрезаются до префикса в 100 символов плюс `...`, как только превышают 300 символов, чтобы большое тело (HTML-страница с ошибкой, большой дамп валидации) не затопило подключённый приёмник логгера. Ограничение применяется **после** маскирования, поэтому не влияет на то, что замаскировано, — только на объём записи (#236).

Ограничение также **тотально**: помощник принимает любое значение и приводит его к строке, поэтому полезная нагрузка, которую нечего сериализовать, записывается как литерал `undefined` (или `null`) вместо исключения. Это важно, потому что эти аргументы вычисляются сразу — до того, как их увидит логгер, и независимо от уровня журнала, — поэтому `TypeError` здесь распространился бы из самого *запроса*, а не только из журналирования. До такого состояния доходят два реальных ответа: тело успеха v3 без конверта `result` (`rest.documentation.openapi` отвечает голым документом OpenAPI) и ошибка axios вообще без `response` (сбой сети, тайм-аут, CORS) (#338).

Маскирование **не зависит от уровня**: оно выполняется над данными до передачи логгеру, поэтому действует независимо от того, фильтрует ли ваш обработчик по `DEBUG`, `INFO`, `ERROR` или любому другому уровню.

### Поверхности вне HTTP

Аудит #43 распространил ту же защиту на поверхности с учётными данными, которые находятся вне HTTP-уровня. Они не проходят через `post/*`, поэтому защищены в собственных местах вызова:

| Поверхность | Что несло учётные данные | Как защищено |
| --- | --- | --- |
| **Pull** — `logMessage` (журналы info `onPull*Event`), предупреждение об ошибке `broadcastMessages`, отладка `attachCommandHandler` | заданные приложением `params` / `extra` могут содержать ключ, похожий на учётные данные (например, `signature` канала) | пропускаются через `redactSensitiveParams` перед записью |
| **Pull** — журналы ошибок JSON-RPC `unknown id` / `unknown rpc packet` / `unknown rpc command in batch` | непрозрачный серверный кадр может нести `signature` | пропускаются через `redactSensitiveParams` |
| **Pull** — консольный журнал `CHANNEL_EXPIRE` «new config for … channel set» | приводил к строке объект `TypeChanel`, включающий его `signature` | вместо объекта выводит `[updated]` |
| **Pull** — нераспознаваемый «сырой» кадр | сырые байты могут содержать `signature` | записывает только `byteLength` кадра, но не его содержимое |
| **Frame** — отладочный журнал «init data» в `B24Frame.init()` | данные рукопожатия `data` несут `AUTH_ID` / `REFRESH_ID` / `MEMBER_ID` и хранилища `*_OPTIONS` приложения | записывает проекцию по фиксированному списку допустимых полей (`PLACEMENT` / `LANG` / `INSTALL` / `IS_ADMIN` / `FIRST_RUN`) |
| **Frame** — входящий `MessageManager._runCallback` | `event.data` несёт обновлённые `AUTH_ID` / `REFRESH_ID` | записывает только `id` обратного вызова и `origin`, но не полезную нагрузку |
| **Frame** — исходящий `MessageManager.send` | собранная строка `cmd` несёт сериализованные значения `setAppOption` / `setUserOption` | записывает только `command` и ключ обратного вызова, но не строку `cmd` |
| **Hook** — ошибки разбора и форматирования `B24Hook.fromWebhookUrl` | URL вебхука содержит секрет в пути (`/rest/<userId>/<secret>/`) | выбрасываемые сообщения общие и никогда не повторяют URL |

Кеш конфигурации Pull в `localStorage` (push `jwt` и подписи каналов) сохраняется только на время жизни клиента: `PullClient.destroy()` удаляет его при остановке, а устаревшая запись вытесняется при загрузке. Пока клиент работает, кеш остаётся **документированным принятым** компромиссом общего источника (он избавляет от обращения за конфигурацией при каждом переподключении) — см. [#242](https://github.com/bitrix24/b24jssdk/issues/242).

## URL вебхука не попадает в журнал

Полный URL вебхука (`https://<portal>/rest/<userId>/<secret>/<method>.json`) раньше попадал в журнал info `post/send`. Начиная с v1.1.2 записывается только само имя метода REST (например, `user.current`, `crm.item.add`); места `post/response` и `post/catchError` никогда не содержали URL и остаются такими. `AjaxQuery` (форма `requestInfo` в `AjaxError`) больше вообще не типизирует поле `url` — см. [`ajax-result.ts:12-16`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/ajax-result.ts#L12-L16), — поэтому будущее изменение не сможет случайно вернуть утечку через отображение ошибки.

Архивы журналов версий SDK `>= 1.1.0, < 1.1.2` с подключённым собственным логгером могут содержать шаблон URL вебхука (`/rest/{userId}/{secret}/`) или шаблон токена авторизации (`"auth":"..."`), которые с v1.1.2 больше не создаются. Шаблоны для проверки, что ваши приёмники чисты, см. в разделе [Проверка архивов журналов](#проверка-архивов-журналов) ниже.

## AjaxError — `toJSON` / `toString`

`AjaxError` принимает `requestInfo`, содержащий переданные вызывающей стороной `params`. Конструктор пропускает эти `params` через тот же маскировщик, поэтому перечисленные выше ключи учётных данных не сохраняются в объекте ошибки — ни в выводе `toJSON()`, ни в строковой форме, ни в любой строке журнала, куда затем попадает ошибка.

```ts-type
// Что вы получите из AjaxError.toJSON().requestInfo.params,
// что бы ни передал вызывающий:
{
  ID: 42,
  access_token: '***REDACTED***',
  auth: '***REDACTED***'
}
```

## Что SDK не скрывает

SDK знает канонические ключи, перечисленные выше, и сопоставляет их **без учёта регистра** по точному имени ключа. Маскировщик **не** удалит:

- **Пользовательские поля полезной нагрузки, которые вы придумали** — например, `mySecretField`, `apiKeyHeader`, `x_internal_token`, любое поле, ключа которого нет в [`SENSITIVE_PARAM_KEYS`](#что-sdk-скрывает-автоматически).
- **Учётные данные внутри строковых значений, кроме канонических пар строки запроса** — пара `<канонический-ключ>=<значение>` внутри строки (например, пакетной `cmd[i]`) **маскируется**, а секрет не в форме `key=value` — голый токен, вставленный в `description`, или ключ запроса в скобках или кодированный вроде `auth[application_token]=…` — нет.
- **Данные глубже двух уровней** — всё глубже `cmd[i].params.<key>` обход пропускает, не заходя внутрь.
- **Учётные данные в пути URL, не принадлежащего Битрикс24** — проход по пути сопоставляет форму собственного вебхука Битрикс24. Вопрос «есть ли учётные данные где-то в пути» неразрешим, поэтому сторонний URL, который их несёт, не покрывается.
- **Само тело ответа, помимо учётных данных** — оно *маскируется*, но маскирование не означает исключения. Ответ портала — пользовательские данные, и он записывается в `post/response` на уровне `info`. Если ваш приёмник не должен его хранить, фильтруйте на приёмнике.
- **Текст портала внутри `AjaxError.validation`** — массив `restApi:v3`, называющий поля, не прошедшие проверку (#423). Каждая запись **пропускается** через маскировщик на тех же условиях, что и `requestInfo.params`, поэтому ключ с именем `token` или `password` внутри строки маскируется. Маскирование не может охватить собственные формулировки портала: сообщение о валидации, которое цитирует отправленное значение, остаётся таким, каким его написал портал, — как это уже происходит в `message`, который включает `toJSON()`. `validation` тоже включается в `toJSON()`, но только когда портал его прислал, поэтому ошибка без него сериализуется точно так же, как до появления этого поля.
- **Заголовки запроса, включая тот, который задаёт сам SDK.** В серверном `B24OAuth` пакет `restApi:v3` несёт токен доступа в заголовке `Authorization: Bearer <token>`, а не в теле, а заголовок, который вы настраиваете через собственные опции axios, лежит рядом с ним. В браузере тот же пакет несёт его вместо этого в **URL** запроса (`?auth=<token>`), потому что политика CORS портала этот заголовок не разрешает, — поэтому ваш собственный логгер, записывающий URL запросов, его перехватит. SDK URL не журналирует. Маскировщик затрагивает только `params`; заголовок он никогда не видит, как и локальное правило ESLint `no-credential-in-logger`. Ничто в SDK не помещает заголовок в контекст логгера — это намеренный инвариант с тестом, а не случайность, — но токен всё же находится в `AxiosError.config.headers`, поэтому прочитайте следующий пункт, прежде чем журналировать объект ошибки.

::warning
**Не журналируйте `err.originalError` напрямую.** `AjaxError` (через базовый [`SdkError`](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/sdk-error.ts#L15)) предоставляет публичное поле `originalError`, которое при транспортных сбоях содержит **сырой** `AxiosError`. Его `AxiosError.config.url` содержит полный URL вебхука (`/rest/{userId}/{secret}/method.json`), а `AxiosError.config.headers` может содержать `Authorization`. SDK не маскирует ни то, ни другое — они никогда не были в `params`. Используйте `err.code`, `err.status`, `err.message` или `err.requestInfo` (который **маскируется**) и никогда не сериализуйте `err.originalError` целиком в любой приёмник логгера.

Это относится и к ошибкам, которые вы достаёте из **результата**, а не только к перехваченным: для мягких кодов ошибок SDK возвращает `AjaxResult` вместо выбрасывания исключения, а `AjaxError` внутри `result.getErrors()` несёт тот же `originalError`. Поле неперечисляемое, поэтому расширение (spread) или `JSON.stringify()` ошибки до него по-прежнему не доберётся, — но чтение по имени доберётся на любом из путей.
::

Удаление перечисленного выше — **ответственность вызывающей стороны**. Либо не помещайте секреты в нестандартные ключи и нестандартные каналы журнала с самого начала, либо маскируйте их в обработчике или процессоре вашего собственного логгера.

## Рекомендуемый шаблон: подключение собственного логгера

Безопасный шаблон — оставить маскирование SDK на месте и надстроить собственный приёмник сверху, а не заменять маскирование на стороне SDK самодельным, расположенным после него.

<!-- @check-ignore: full example — sendToRemoteAggregator is a placeholder, not declared -->
```ts
import {
  B24Hook,
  Logger,
  ConsoleV2Handler,
  LogLevel
} from '@bxshefby/b24jssdk'

const b24 = new B24Hook({ /* … */ })

const $logger = new Logger('app')
$logger.pushHandler(new ConsoleV2Handler(LogLevel.INFO))

// Необязательный страховочный процессор: скрывает *собственные* ключи, о которых
// SDK не знает. Стандартные ключи (auth / token / …) уже вычищены
// до этого места.
$logger.pushProcessor((record) => {
  if (record.context?.params && typeof record.context.params === 'string') {
    record.context.params = record.context.params.replace(
      /"mySecretField":"[^"]*"/g,
      '"mySecretField":"***REDACTED***"'
    )
  }
  return record
})

b24.setLogger($logger)
```

Чего **следует избегать**:

<!-- @check-ignore: anti-pattern illustration — b24 and sendToRemoteAggregator are undeclared placeholders -->
```ts
// НЕ ДЕЛАЙТЕ ТАК — пересылка контекста без проверки отправляет произвольные
// данные вызывающего во внешний приёмник, а обход LoggerInterface
// через `as any` скрывает, что обработчик обязан реализовать все 8
// методов уровней (log / debug / info / notice / warning / error /
// critical / alert / emergency). Неполная реализация молча теряет
// записи на нереализованных уровнях.
b24.setLogger({
  async info(message, context) {
    await sendToRemoteAggregator({
      msg: message,
      // `context.params` в `post/send` — уже очищенная *строка*,
      // но собственная обёртка действия может вызвать этот `info` с
      // сырым объектом `params` (или с `error`, чей `originalError` —
      // неочищенный `AxiosError`). Не пересылайте `context`
      // вслепую — выбирайте нужные поля.
      ctx: context
    })
  }
  // ...остальные 7 методов опущены — только приведение ниже даёт
  // скомпилировать неполный интерфейс; в настоящем коде реализуйте
  // `LoggerInterface` полностью (или наследуйте `AbstractLogger`).
} as any)
```

Три конкретных вида сбоев, от которых нужно защититься:

1. **Журналирование исходного объекта запроса самостоятельно.** Если ваша обёртка захватывает `params` до вызова SDK и журналирует их, маскировщик SDK на этой копии не запускается. Всегда маскируйте и в собственном пути журналирования.
2. **Обращение к `err.originalError` / `err.cause`.** `requestInfo.params` в `AjaxError` очищены, поэтому `String(err)` и `JSON.stringify(err)` безопасны сами по себе. Но если вы журналируете `err.originalError`, вы можете смотреть на сырой `AxiosError`, чей `config.url` по-прежнему содержит полный URL вебхука. См. блок с предупреждением в разделе [Что SDK не скрывает](#что-sdk-не-скрывает).
3. **Пользовательские или глубоко вложенные секреты в `post/response`.** Канал `post/response` теперь пропускает `response.data.result` через тот же маскировщик, поэтому канонические ключи учётных данных на глубине ≤ 2 маскируются. Но секрет под **пользовательским** ключом или глубже двух уровней по-прежнему доходит до вашего приёмника — действуют те же ограничения, что и везде (см. [Что SDK не скрывает](#что-sdk-не-скрывает)).

## Проверка архивов журналов

Просканируйте архивы журналов, чтобы убедиться, что в них нет шаблонов учётных данных, — это полезная регулярная проверка, особенно если ваша система передаёт журналы стороннему агрегатору или хранит их долго.

**URL вебхука в журналах запросов** — grep (Linux/macOS) / ripgrep / PowerShell:

```bash
grep -rEi '/rest/[0-9]+/[a-zA-Z0-9]+/' /var/log/myapp/
rg -i '/rest/\d+/[a-zA-Z0-9]+/' /var/log/myapp/
```

```powershell
Select-String -Path 'C:\logs\myapp\*.log' -Pattern '/rest/\d+/[a-zA-Z0-9]+/'
```

**Ключи учётных данных в сериализованных параметрах** — grep (Linux/macOS) / ripgrep / PowerShell:

```bash
grep -rE '"(auth|password|token|secret|access_token|refresh_token|client_secret|application_token|sessid)":\s*"[^"]+"' /var/log/myapp/
rg '"(auth|password|token|secret|access_token|refresh_token|client_secret|application_token|sessid)":\s*"[^"]+"' /var/log/myapp/
```

```powershell
Select-String -Path 'C:\logs\myapp\*.log' -Pattern '"(auth|password|token|secret|access_token|refresh_token|client_secret|application_token|sessid)":\s*"[^"]+"'
```

Замените `/var/log/myapp/` (или `C:\logs\myapp\`) своими настоящими путями к журналам. Типичные приёмники для проверки: захват stdout (журналы Docker, systemd journal, PM2), файлы, записанные через `StreamHandler`, и сторонние агрегаторы (Datadog, Logtail, Splunk, Papertrail и др.).

Шаблон URL вебхука создавался записями `post/send` в версиях SDK `>= 1.1.0, < 1.1.2` при подключённом собственном логгере. Шаблоны ключей учётных данных могли появляться в `post/send` в любой версии этого диапазона, где соответствующий ключ присутствовал в параметрах запроса. Оба подавляются SDK начиная с v1.1.2.

`client_secret`, `application_token` и `sessid` добавлены в маскировщик в v1.3 — включите их (выше) при сканировании архивов с конечных точек, передающих эти параметры. Канонический список также охватывает `key`, который опущен в шаблонах выше, потому что `"key":` слишком часто встречается, чтобы искать его без сильного шума, — просканируйте его вручную, если ваша интеграция использует `key` как учётные данные.

`signature` добавлен в #43 для HMAC канала push/pull. Архивы старых версий с подключённым собственным логгером и активным клиентом Pull могут содержать `"signature":"…"` — ищите `"signature":\s*"[^"]+"`, если вы использовали сервер Pull, помня, что он (как и `key`) может давать много шума.

Если любой из шаблонов найден в ваших архивах, смените затронутые учётные данные: удалите и создайте заново вебхук, чтобы получить новый секрет, или отзовите и выпустите заново токен OAuth или Frame.
