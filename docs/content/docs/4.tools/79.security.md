## Обзор

Эта страница — для серверов, которые предоставляют **публичную HTTP-конечную точку, куда Битрикс24 отправляет POST-запросы**:

- **Приёмники исходящих событий** — приложение, которое регистрирует события через `event.bind` (`ONCRMDEALADD`, `ONCRMDEALUPDATE`, …) и обрабатывает их, как в [рецепте обработчика вебхука](/docs/examples/webhook-handler/).
- **OAuth-приложения** — приложение из маркетплейса, которое обрабатывает обратные вызовы `ONAPPINSTALL` / `ONAPPUPDATE` / `ONAPPUNINSTALL` и хранит учётные данные каждого портала, как в [рецепте установки OAuth](/docs/examples/oauth-install/).

У обоих одна и та же модель угроз: URL доступен любому, а Битрикс24 аутентифицирует каждую доставку с помощью `application_token` в полезной нагрузке. Два приёма делают эти конечные точки корректными и безопасными. Они не зависят от транспорта SDK — они находятся в вашем HTTP-обработчике, — поэтому описаны здесь, а не на странице действия.

::note
Маскирование учётных данных внутри SDK — отдельный вопрос, см. [Журналирование и маскирование учётных данных](/docs/tools/logging/). Эта страница — о слое **обработки запросов** вокруг SDK.
::

## Приём 1 — сначала ответьте 200, потом проверяйте

Битрикс24 не вызывает ваш обработчик в реальном времени: он ставит события в очередь на отдельном сервере и **следит за тем, как быстро отвечает ваш обработчик**. Обработчик, который выполняет проверку или обработку *до* ответа, отвечает медленно, и Битрикс24 начинает доставлять ему события с **более низким приоритетом** (более длинные паузы между вызовами). **Автоматического повтора нет**: если обработчик завершился ошибкой или превысил время ожидания, Битрикс24 фиксирует сбой и больше это событие не отправляет — «второго шанса нет» (см. [обзор событий](https://apidocs.bitrix24.com/api-reference/events/index.html)). Таким образом, медленный или падающий обработчик и снижает скорость доставки, **и** молча теряет события.

Решение — порядок: сначала отправьте `2xx`, затем проверяйте и обрабатывайте. Подтверждение уходит быстро (вы не попадаете под штраф за медленный обработчик), а проверка и обработка его больше не блокируют. Если потеря события недопустима, не полагайтесь на живую доставку — используйте [офлайн-события](https://apidocs.bitrix24.com/api-reference/events/offline-events.html) как надёжный канал.

```ts
import { type Request, type Response } from 'express'

// Stand-ins for your real verification / processing logic.
function verifyOrigin(req: Request): boolean { return Boolean(req.body?.auth) }
async function handleEvent(payload: unknown): Promise<void> { /* … */ }

// WRONG — verify + process run BEFORE the 200 reply.
async function onWebhookWrong(req: Request, res: Response) {
  if (!verifyOrigin(req)) return  // may be slow, may throw
  await handleEvent(req.body)     // if this throws, the next line never runs…
  res.sendStatus(200)             // …so the ack never goes out — the event is
                                  // lost (no retry) and the slow path gets you
                                  // deprioritized
}
```

```ts
import { type Request, type Response } from 'express'

function verifyOrigin(req: Request): boolean { return Boolean(req.body?.auth) }
async function handleEvent(payload: unknown): Promise<void> { /* … */ }

// CORRECT — acknowledge first, verify + process after.
async function onWebhook(req: Request, res: Response) {
  const payload = req.body

  res.sendStatus(200)             // 1. reply immediately — fast ack avoids the
                                  //    slow-handler penalty

  if (!verifyOrigin(req)) return  // 2. drop spoofed / stale events (already acked)
  await handleEvent(payload)      // 3. safe: Bitrix24 already has its 200
}
```

[Рецепт обработчика вебхука](/docs/examples/webhook-handler/) отвечает небольшим JSON-подтверждением — `res.status(200).json({ status: 'ok' })`, — которое эквивалентно `res.sendStatus(200)`; подойдёт любой вариант, если он отправляется первым.

У подтверждения до обработки есть следствие, которое нужно учесть: доставка **как минимум однократная (at-least-once)**. Битрикс24 повторяет ответ не из `2xx` до 24 часов, а обработчик, который отвечает уже после того, как портал перестал ждать, увидит то же событие снова. Если ваш обработчик что-то *записывает*, сделайте запись идемпотентной, а не рассчитывайте на одну доставку — в `restApi:v3` передавайте [`idempotencyKey`](/docs/actions/call/#idempotency-key), выведенный из события, чтобы повторная доставка воспроизводила сохранённый ответ, а не создавала вторую запись. Рецепт 7 делает именно так.

## Приём 2 — проверяйте application_token за постоянное время

Битрикс24 включает `application_token` в блок `auth` каждого события. Это общий секрет, который доказывает, что запрос действительно пришёл с вашего портала: без его проверки любой, кто узнает URL, может воспроизводить произвольные события.

Сравнивайте его функцией **постоянного времени**. Обычный `===` (или `!=`) возвращает результат, как только встретит первый отличающийся байт, поэтому злоумышленник может восстановить токен по одному символу, измеряя задержку ответа. `crypto.timingSafeEqual` в Node сравнивает за постоянное время, но **выбрасывает исключение, если длины двух буферов различаются**, — поэтому сначала проверьте длину:

Помощник приведён здесь полностью, потому что его стоит прочитать, прежде чем доверять. Сами рецепты импортируют одну общую копию из [`lib/crypto.ts`](https://github.com/bitrix24/b24jssdk/blob/main/skills/b24jssdk-recipes/lib/crypto.ts), а не носят каждый свою: сравнение за постоянное время, которое разошлось в одном из нескольких форков, — это уязвимость, выглядящая как рефакторинг.

```ts
import { type Request, type Response } from 'express'
import { timingSafeEqual } from 'node:crypto'

// Constant-time compare. `timingSafeEqual` throws on a length mismatch, so the
// length pre-check is what turns that throw into a plain `false`. It does not
// hide the length — the early return is length-dependent — but a token's length
// is not the secret. Do not "fix" that by padding: you would then be comparing
// the padding rather than the token.
function safeEqual(a: string, b: string): boolean {
  const ab = Buffer.from(a, 'utf8')
  const bb = Buffer.from(b, 'utf8')
  if (ab.length !== bb.length) return false
  return timingSafeEqual(ab, bb)
}

const expectedApplicationToken = process.env.B24_APPLICATION_TOKEN ?? ''

// Called AFTER res.sendStatus(200) (Pattern 1). Returns false → drop the event.
function verifyEvent(req: Request, _res: Response): boolean {
  const incomingToken = req.body?.auth?.application_token ?? ''
  return safeEqual(incomingToken, expectedApplicationToken)
}
```

Храните ожидаемый токен отдельно (переменная окружения вроде `B24_APPLICATION_TOKEN`, полученная из консоли разработчика Битрикс24 → Локальное приложение → `application_token`) и закрывайтесь при отказе (fail closed), если она не задана.

### Удаление OAuth: проверяйте до удаления

То же правило критично для обратного вызова **удаления**. `ONAPPUNINSTALL` удаляет сохранённые учётные данные портала, поэтому, если удалять без проверки, любой, кто может обратиться к `/uninstall`, сотрёт токены портала, просто угадав его `member_id`. Всегда сравнивайте входящий `application_token` с тем, что вы записали при установке, за постоянное время, прежде чем что-либо удалять:

```ts
import { type Request, type Response } from 'express'

// `safeEqual` is the constant-time helper from Pattern 2 above.
declare function safeEqual(a: string, b: string): boolean
declare function getCredentials(memberId: string): Promise<{ applicationToken: string } | null>
declare function deleteCredentials(memberId: string): Promise<void>

async function handleUninstall(req: Request, res: Response) {
  res.sendStatus(200)  // reply first — Pattern 1 applies to uninstall too

  const memberId = req.body?.auth?.member_id ?? ''
  const receivedToken = req.body?.auth?.application_token ?? ''
  if (!memberId || !receivedToken) return

  const stored = await getCredentials(memberId)
  if (!stored) return  // idempotent — nothing to delete

  // ALWAYS verify application_token before deleting. Without this check, anyone
  // who reaches /uninstall could wipe a portal's tokens by guessing member_id.
  if (!safeEqual(stored.applicationToken, receivedToken)) return

  await deleteCredentials(memberId)
}
```

## Приём 3 — проверяйте URL порталов, которые несёт событие установки

Установка — единственный обратный вызов, который **не может** проверить вызывающего, и никакая осторожность этого не изменит: `application_token` *выдаётся* событием установки, поэтому у обработчика при первом обращении не с чем сравнивать. Битрикс24 не присылает предварительно согласованного секрета с `ONAPPINSTALL`. Это ограничение платформы.

Поэтому вопрос не в том, как отклонить поддельную установку — это невозможно, — а в том, чего она *стоит*. Это целиком зависит от того, что вы делаете с тремя полями, которые она несёт.

| Поле | Что значит доверие к нему |
| --- | --- |
| `client_endpoint` | Куда уходит каждый последующий вызов REST для этого портала. Поддельный позволяет читать ваши бизнес-данные и отвечать вместо Битрикс24. |
| `server_endpoint` | Куда SDK при каждом обновлении токена отправляет POST с `client_id`, **`client_secret`** и `refresh_token`. Поддельный раскрывает **общий для приложения** секрет — всех порталов, а не только того, чей `member_id` угадали. |
| `domain` | С чем сверяются два других поля и что будет написано в ваших журналах. |

О `server_endpoint` стоит подумать дважды, и именно его легче всего ошибочно проверить в обратную сторону: **это не портал.** В облаке это общий сервер токенов — `oauth.bitrix.info` — для всех порталов, поэтому проверка, требующая его совпадения с `domain`, отклоняет каждую легитимную облачную установку.

Что проверить перед сохранением:

- только `https:` и без учётных данных, встроенных в URL;
- `client_endpoint` на том же хосте, что и `domain`. Для этого не нужен список, поэтому проверка работает и для портала на собственной инфраструктуре, хост которого никто не мог перечислить;
- `domain` и `server_endpoint` — каждый по своему списку разрешённых, причём оба списка должны настраиваться. Коробочный Битрикс24 живёт на том домене, который выбрал владелец, и сам является своим сервером токенов, поэтому жёстко заданные суффиксы `*.bitrix24.*` отклоняют каждую легитимную установку на собственной инфраструктуре. Указание одного известного хоста *надёжнее* суффикса по умолчанию, а не слабее;
- записывайте причину в журнал и ничего не отвечайте. Если сообщать вызывающей стороне, какая проверка сработала, конечная точка превращается в оракул для поиска такой, которая пройдёт.

С этим худшее, чего добьётся поддельная установка, — повреждённая запись: вызовы этого портала будут завершаться ошибкой, что заметно и устранимо. Без этого — утечка учётных данных.

**Ничто из этого не делает конечную точку безопасной для небрежного открытия.** Это по-прежнему неаутентифицированная запись в ваше хранилище, поэтому защитите её сетевым средством: списком разрешённых диапазонов исходящих адресов Битрикс24 или секретным сегментом пути.

[Рецепт 12](/docs/examples/oauth-install/) реализует это в `skills/b24jssdk-recipes/lib/portal-url.ts`.

## Контрольный список

**Каждая конечная точка-приёмник событий** (обработчики `event.bind`):

- Обслуживайте обработчик по **HTTPS** на общедоступном URL — Битрикс24 вызывает его со своих серверов, а `application_token` передаётся в теле запроса, поэтому обычный HTTP раскрыл бы его при передаче.
- Отвечайте `2xx` **до** проверки или обработки (приём 1).
- Требуйте переменную окружения `application_token` и **закрывайтесь при отказе**, если она не задана.
- Сравнивайте входящий `application_token` через `safeEqual` (приём 2), никогда через `===`.
- При несовпадении отбрасывайте событие, а не возвращайте ошибку (верните уже отправленный `2xx`; не раскрывайте, какая проверка не прошла).
- Никогда не журналируйте `application_token` (или «сырой» блок `auth`). Журналируйте решение, а не секрет.

**OAuth-приложения** (обратные вызовы установки и удаления), дополнительно:

- Сохраняйте `application_token` вместе с токенами при установке.
- При удалении проверяйте `application_token` **до** удаления учётных данных.
- Отсутствующую запись считайте идемпотентным успехом (без ошибки — её уже нет).
- Храните токены с ограниченными правами (режим файла `0o600` или хранилище с изоляцией по арендаторам).
- **Проверяйте URL порталов перед сохранением** (приём 3) и защитите `/install` сетевым средством.
- **Считайте ненадёжным и `member_id`.** Он приходит на ту же неаутентифицированную конечную точку, а затем становится ключом в вашем хранилище и значением в журналах. Проверяйте его форму до того и другого: перевод строки в нём подделывает строку журнала, которая выглядит как настоящая установка для другого портала, а длина ничем не ограничена. Отдельно: не используйте простой литерал объекта как ключ хранилища в памяти: `__proto__` — сеттер, поэтому запись молча отбрасывается, а `constructor` / `toString` находятся как унаследованные функции при поиске, который должен был ничего не вернуть. У `Map` или `Object.create(null)` такого свойства нет; у типа записи — есть.
