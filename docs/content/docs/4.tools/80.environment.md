## Обзор

`getEnvironment()`{lang="ts-type"} сообщает, выполняется ли код в браузере, воркере, Node.js или в среде, которую SDK не может классифицировать. Он возвращает член перечисления `Environment`{lang="ts-type"}. Оба экспортируются из `@bxshefby/b24jssdk` и используются внутри, чтобы отделять браузерное поведение (DOM, `localStorage`, обмен сообщениями с iframe) от серверных контекстов.

```ts
import { getEnvironment, Environment } from '@bxshefby/b24jssdk'

if (getEnvironment() === Environment.BROWSE) {
  // browser-only code (DOM, localStorage, …)
}
```

## Сигнатура метода

```ts-type
enum Environment {
  UNKNOWN = 'unknown',
  BROWSE = 'browser',
  WORKER = 'worker',
  NODE = 'node'
}

getEnvironment(): Environment
isBrowserLikeRuntime(): boolean
```

## Ключевые понятия

- **Порядок определения.** `getEnvironment()` сначала проверяет браузер, проверяя `window` и `window.document`; если есть оба, возвращает `Environment.BROWSE`. Затем Node — через `process.versions.node`. Только потом он спрашивает, **является** ли эта область областью воркера — `globalThis instanceof WorkerGlobalScope`, — и возвращает `Environment.WORKER`; всё остальное — `Environment.UNKNOWN`.
- **Node проверяется раньше воркера, и у этого выбора есть цена с обеих сторон.** Среды, которые сообщают **оба** признака, — воркер Deno и Cloudflare Worker с `nodejs_compat` — это серверы, где запускать вебхук законно; назвать их похожими на браузер значило бы без причины убрать учётные данные из заголовков и на каждом вызове предупреждать, что закрытый секрет утёк. Цена в обратную сторону: **браузерный** воркер, который сообщает версию Node, читается как сервер. Это достижимо — `process@0.11.10` оставляет `process.versions` пустым, но `unenv`, полифил за Nitro и Nuxt, отвечает `{ node: '22.14.0' }`, — и вот что это стоит, начиная с худшего: [`TelegramHandler`](/docs/tools/logger-telegram/) отправил бы запрос, поместив токен бота в URL из кода, который может прочитать кто угодно; заголовок `Authorization` в пакете OAuth `restApi:v3`, который предзапрос портала отклоняет (путь, уже описанный как не работающий из браузера); отсутствие предупреждения о клиентской стороне; и `User-Agent`, который браузер всё равно отбрасывает. Определение среды не заменяет отказ от доставки секрета на клиент.
- **Это `instanceof`, а не проверка «определено ли имя»** — спецификация помещает этот конструктор в цепочку прототипов настоящего воркера, поэтому вопрос, является ли им *эта* область, точен. Он уже проверки по имени, но не герметичен: в цепочке Cloudflare `workerd` есть `WorkerGlobalScope`, и он ускользает только потому, что предоставляет второй, не идентичный конструктор как глобальную привязку. С `nodejs_compat` и свежей датой совместимости он сообщает версию Node и классифицируется как `NODE`; на более старой дате или без `nodejs_compat` это `UNKNOWN`. Ни то ни другое не похоже на браузер, а это и есть важный результат.
- **Bun Web Worker сообщает `NODE`**, поскольку сообщает версию Node, а Node проверяется первым, — и Bun в любом случае нигде не определяет `WorkerGlobalScope`. Имя не самое подходящее, но безвредное: ничто там не навязывает правила браузера, ради которых существует этот член.
- **Член для браузера — `BROWSE`, его значение — `'browser'`.** Сравнивайте с членом перечисления (`Environment.BROWSE`), а не с голой строкой, чтобы переименование оставалось типобезопасным.
- **`BROWSE` означает наличие DOM — воркер не `BROWSE`.** У воркера нет `window.document`, поэтому код, защищённый проверкой `BROWSE`, там не должен выполняться. Но другие правила браузера в нём действуют: CORS, запрещённые заголовки запроса и сборка, которую может прочитать кто угодно. Когда важно именно это, нужно спрашивать `isBrowserLikeRuntime()` — он `true` и для `BROWSE`, и для `WORKER`, и именно по нему собственный транспорт SDK решает, что **не** должен отправлять заголовок `Authorization` или `User-Agent`.
- **`UNKNOWN` охватывает всё остальное.** Edge- и бессерверные среды и другие хосты, не прошедшие ни одну из трёх проверок, попадают в `Environment.UNKNOWN` — считайте это «предполагайте отсутствие браузерных глобальных объектов». Cloudflare Worker без `nodejs_compat` — одна из таких сред.

## Обработка ошибок

`getEnvironment()` никогда не выбрасывает исключение. Проверки `window` и `process` — это защиты `typeof`, поэтому отсутствующий глобальный объект приводит к переходу к следующей ветке, а не к `ReferenceError`. Проверка воркера — это `instanceof`, который при глобальном объекте, не являющемся конструктором, выбрасывает `TypeError`; она обёрнута в `try / catch`, отвечающий `false`{lang="ts-type"}, поэтому странная среда не приведёт к сбою при импорте.

## Примеры

Ветвление между браузером, воркером и Node.js:

```ts
import { getEnvironment, Environment } from '@bxshefby/b24jssdk'

switch (getEnvironment()) {
  case Environment.BROWSE:
    // Safe to touch the DOM / localStorage here
    break
  case Environment.WORKER:
    // No DOM here — but the browser's rules still apply, so treat this code as
    // public. See isBrowserLikeRuntime() below.
    break
  case Environment.NODE:
    // Server-side path (e.g. read env vars, use a webhook client)
    break
  default:
    // Environment.UNKNOWN — an unrecognised host; avoid browser and Node-specific globals
    break
}
```

Отличить отсутствие DOM от отсутствия браузера:

```ts
import { getEnvironment, isBrowserLikeRuntime, Environment } from '@bxshefby/b24jssdk'

// "Can I touch the DOM?" — false in a worker.
const hasDom = getEnvironment() === Environment.BROWSE

// "Do the browser's rules apply?" — true in a worker, and the question to ask
// before shipping a secret or setting a forbidden header.
const isPublicCode = isBrowserLikeRuntime()
```

Защита браузерного кода до его выполнения:

```ts
import { getEnvironment, Environment } from '@bxshefby/b24jssdk'

function isBrowser(): boolean {
  return getEnvironment() === Environment.BROWSE
}

if (isBrowser()) {
  // window / document are available
}
```

## Альтернативы и рекомендации

- **Используйте `getEnvironment()` для грубого ветвления «где я запущен».** Для более тонких проверок браузера, ОС и возможностей (Chrome или Safari, iOS, касания, доступность `localStorage`) используйте [`Browser`](/docs/tools/browser/).
- **Предпочитайте его разовым проверкам `typeof window`.** Централизованное определение сохраняет ветвление между браузером и Node согласованным и совпадает с проверками, которые SDK выполняет внутри.
- **Для всего, кроме DOM, спрашивайте `isBrowserLikeRuntime()`, а не `=== BROWSE`.** Воркер — не сервер: секрет вебхука, попавший в его сборку, так же публичен, как и в основном потоке, а заголовок, запрещённый браузером, там тоже отбрасывается.
- **Среда, определённая как `WORKER`, считается публичным кодом.** Если у вас сервер, который просто предоставляет API Worker, это означало бы учётные данные вне заголовков, отсутствие `User-Agent` и предупреждение «этот вебхук находится на клиентской стороне» на каждом вызове, — поэтому проверка спрашивает, *является* ли глобальный объект областью воркера, а не существует ли имя. Если вы столкнулись со средой, где она по-прежнему отвечает неверно, пожалуйста, откройте issue.
- **Относитесь к `UNKNOWN` консервативно.** Если вы не можете подтвердить браузер, избегайте доступа к DOM и `localStorage` — многие методы `Browser` предполагают существование этих глобальных объектов и вне браузера могут выбросить исключение.
