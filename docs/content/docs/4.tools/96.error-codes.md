Неудачный вызов доходит до вас одним из двух способов, и разница — в **способе доставки, а не в серьёзности**:

- **Жёсткая** — промис отклоняется, и SDK выбрасывает `AjaxError`{lang="ts-type"} (или подкласс). Обрабатывайте её в `try / catch`.
- **Мягкая** — промис выполняется; ошибка упакована в возвращённый `AjaxResult`{lang="ts-type"}, а `response.isSuccess === false`. Обрабатывайте её через `if`.

Два вопроса это разделение **не** решает. Оно не влияет на повторы: любой 4xx, кроме 408 и 429, прекращает повторы независимо от этого, как и закреплённый код любого из двух видов. А *не перечисленный* код ведёт себя как жёсткий: всё, что не классифицировано как мягкое, выбрасывается.

Всё остальное (сетевые ошибки, 5xx, коды ограничения частоты) подчиняется стратегии повторов, описанной в разделе [Лимитеры](/docs/tools/limiters/).

## Таблицы — не каталог

В двух таблицах ниже перечислены коды, классификация которых **закреплена**. Это не весь набор кодов, которые может прислать портал.

Код `restApi:v3` выводится из класса исключения, которое его выбросило, поэтому набор, который способна выдать сборка, растёт с каждым модулем портала. На одной сборке для коробки измерено не менее **39 различных кодов v3**; в закреплённом списке мягких — **девять**. Остальные сегодня выбрасываются, включая `INVALIDPAGINATIONEXCEPTION`, `UNKNOWNFILTEROPERATOREXCEPTION` и `INVALIDORDEREXCEPTION`, которые представляют ту же ошибку вызывающей стороны в том же запросе с тем же HTTP 400, что и закреплённые мягкими `INVALIDSELECTEXCEPTION` и `INVALIDFILTEREXCEPTION`.

**Не сопоставляйте по префиксу `BITRIX_REST_V3_EXCEPTION_` и не выводите код, отрезая его.** Модули поставляют собственные исключения v3 с короткими кодами без префикса — `NOTE_SEARCH_QUERY_TOO_SHORT`, `NOTE_FILE_TOO_LARGE`, `CRM_EMAIL_INVALID_REQUEST` и другие. Сопоставляйте по строке целиком или не сопоставляйте вовсе. По `message`, который локализован, сопоставлять нельзя никогда.

## Классификация по категории (`restApi:v3`)

Вместо того чтобы наращивать список, SDK принимает решение по **самому ответу**: ошибка, пришедшая в конверте ошибки v3 с HTTP **4xx, кроме 401, 408 и 429**, считается мягкой независимо от кода. Настройки для этого не нужны — это и есть поведение.

```ts
// const $b24 = ...
const response = await $b24.actions.v3.call.make({
  method: 'main.eventlog.list',
  params: { pagination: { limit: 0 } }
})

// Reached for any 4xx the portal reports, not only the nine pinned codes.
if (!response.isSuccess) {
  console.log(response.getErrorMessages().join('; '))
}
```

Порядок решения фиксирован: код из списка жёстких выбрасывается; код из списка мягких — мягкий; затем правило категорий; затем, как и прежде, выбрасывается. Поэтому закреплённая классификация — включая ваши собственные `hardErrorCodes` / `softErrorCodes` — всегда приоритетнее категории.

Чего правило **не** затрагивает:

- **5xx** — вызывающая сторона на них повлиять не может, поэтому «повторить, затем выбросить» остаётся верным.
- **401** — им занимается путь обновления авторизации.
- **408 и 429** — два повторяемых 4xx; ошибка, которая ещё повторяется, пока не классифицирована.
- **`restApi:v2`** — плоское тело ошибки не является конвертом v3. Решение принимается по телу, которое действительно пришло, а не по версии клиента, поскольку шлюз перед контроллером v3 может ответить в плоской форме.

**403 — мягкая** намеренно. Отказ в разрешении — то, на что вызывающая сторона может отреагировать, а `…ACCESSDENIEDEXCEPTION` уже закреплён мягким: исключить 403 целиком значило бы, что один 403 возвращается, а соседний выбрасывается.

Один 403 закреплён жёстким вопреки этому правилу: `BITRIX_REST_V3_EXCEPTION_INSUFFICIENTSCOPEEXCEPTION`. Он означает, что в OAuth-разрешении приложения не хватает области доступа (scope) — это ошибка конфигурации, а не проверка прав для отдельной записи, — а v2-написание того же условия, `insufficient_scope`, всегда выбрасывалось. Это разные строки, поэтому без закрепления формы v3 один и тот же сбой доставлялся бы в v2 одним способом, а в v3 другим.

::caution
**Изменено в 3.0.0.** В линейке `2.x` это правило включалось по желанию через параметр `classifyV3ErrorsByCategory`; в `3.0.0` оно стало поведением, а параметра больше нет. Это меняет способ доставки ошибки: ошибка v3 с кодом 4xx, которая выбрасывалась в `2.x`, теперь возвращается как результат, поэтому `try / catch` вокруг вызова перестаёт срабатывать, и управление проваливается в ветку успеха. Перенесите эту обработку в `if (!response.isSuccess)` — см. [руководство по миграции](/docs/getting-started/migration/v3/#поведение-ошибки-v3-классифицируются-по-категории-ответа).
::

## Закреплённые жёсткие коды (выбрасываются)

Эти коды проходят по пути отклонения промиса и правилом категорий никогда не смягчаются. Оберните вызовы в `try / catch`, если нужно обрабатывать их централизованно.

| Код | Значение |
|----|----|
| `ERR_BAD_REQUEST` | Некорректный запрос — обычно нужно исправить вызывающий код. |
| `JSSDK_UNKNOWN_ERROR` | Внутренняя ошибка SDK неизвестной формы. |
| `100` | Общий прежний код 100. |
| `INTERNAL_SERVER_ERROR` | Серверная ошибка 500. |
| `ERROR_UNEXPECTED_ANSWER` | Битрикс24 вернул тело, которое SDK не смог разобрать. |
| `PORTAL_DELETED` | Портала больше не существует. |
| `ERROR_BATCH_METHOD_NOT_ALLOWED` | В пакете есть метод, который нельзя вызывать внутри пакета. |
| `ERROR_BATCH_LENGTH_EXCEEDED` | В пакете больше 50 команд. Используйте `batchByChunk`. |
| `NO_AUTH_FOUND` | Отсутствуют учётные данные. |
| `INVALID_REQUEST` | Битрикс24 отклонил форму запроса. |
| `OVERLOAD_LIMIT` | Достигнут лимит перегрузки тарифа (отличается от ограничения частоты). |
| `expired_token` | Срок действия токена доступа OAuth истёк, а обновление не удалось. |
| `invalid_token` | Токен доступа OAuth недействителен — отозван, повреждён или выдан для другого приложения. В отличие от `expired_token`, обновление не помогает; приложению нужно получить новое разрешение. |
| `BITRIX_REST_V3_EXCEPTION_INSUFFICIENTSCOPEEXCEPTION` | REST v3: в OAuth-разрешении приложения нет области доступа, нужной этому методу. Написание `insufficient_scope` в v3; закреплён, чтобы правило категорий не смягчало его при 403. |
| `ACCESS_DENIED` | Пользователю отказано в доступе. |
| `INVALID_CREDENTIALS` | Секрет вебхука или учётные данные OAuth недействительны. |
| `user_access_error` | У пользователя нет доступа к ресурсу. |
| `insufficient_scope` | Область доступа токена OAuth слишком узкая для вызова. |
| `ERROR_MANIFEST_IS_NOT_AVAILABLE` | Не удалось получить манифест приложения. |
| `allowed_only_intranet_user` | Конечной точке нужен пользователь интранета. |
| `NOT_FOUND` | Ресурс не существует. |
| `INVALID_ARG_VALUE` | У одного из аргументов значение, отклонённое Битрикс24. |
| `PULL_DISABLED` | `PullClient.start()` — сервер Push & Pull на портале отключён. |
| `PULL_DISPOSED` | `PullClient.start()` вызван после `destroy()` — создайте новый экземпляр. |
| `JSSDK_FRAME_DISPOSED` | Команда фрейма всё ещё ожидала ответа родительского окна, когда выполнился `B24Frame.destroy()` — отвечать на неё теперь некому. |
| `JSSDK_FRAME_BAD_PAYLOAD` | Родительское окно ответило на команду фрейма полезной нагрузкой, не являющейся допустимым JSON. |
| `JSSDK_FRAME_APP_SID_NOT_INIT` | `getAppSid()` до завершения рукопожатия фрейма — родитель так и не передал `appSid`. |
| `JSSDK_FRAME_INSTALL_ALREADY_FINISHED` | `installFinish()` вызван вне режима установки — защищайте вызов проверкой `isInstallMode`. |
| `JSSDK_FRAME_REFRESH_AUTH_TIMEOUT` | `refreshAuth()` — родительское окно не ответило в течение 10 секунд (медленно отвечает, ушло на другую страницу или заблокировано). Прежний токен сохраняется; повторите вызов. |
| `JSSDK_FRAME_REFRESH_AUTH_BAD_RESPONSE` | `refreshAuth()` — родительское окно ответило без пригодного `AUTH_EXPIRES`. Прежний токен сохраняется и не перезаписывается непригодным; повторите вызов. Сообщение называет поле, но никогда не показывает его значение. |
| `JSSDK_HOOK_URL_EMPTY` | `B24Hook.fromWebhookUrl()` — URL пуст. |
| `JSSDK_HOOK_URL_INVALID` | `B24Hook.fromWebhookUrl()` — URL не разбирается. Сообщение никогда не повторяет URL: он содержит секрет. |
| `JSSDK_HOOK_URL_NOT_HTTPS` | `B24Hook.fromWebhookUrl()` — вебхуки требуют HTTPS. |
| `JSSDK_HOOK_URL_MALFORMED` | `B24Hook.fromWebhookUrl()` — путь не имеет вид `/rest/<userId>/<secret>` или `/rest/api/<userId>/<secret>`. |
| `JSSDK_HOOK_URL_USER_ID_NOT_NUMERIC` | `B24Hook.fromWebhookUrl()` — сегмент userId не числовой (в переставленном URL там оказывается секрет; сообщение его никогда не повторяет). |
| `JSSDK_OAUTH_TOKEN_REFRESH_FAILED` | Сервер OAuth ответил на обновление токена полезной нагрузкой с ошибкой. |
| `JSSDK_OAUTH_TOKEN_REFRESH_BAD_STATUS` | Обновление токена вернуло статус, отличный от 200 (передаётся как `status`). |
| `JSSDK_OAUTH_TOKEN_REFRESH_NO_DATA` | Обновление токена не вернуло данных авторизации. |
| `JSSDK_OAUTH_IS_ADMIN_NOT_INIT` | `isAdmin` прочитан до того, как `B24OAuth.initIsAdmin()` его заполнил. |
| `JSSDK_OAUTH_PROFILE_FAILED` | Вызов `profile` в основе `initIsAdmin()` завершился ошибкой; описание содержит текст ошибки портала. |
| `JSSDK_HELPER_NOT_INIT` | Обращение к аксессору `useB24Helper()` до `initB24Helper()`. |
| `JSSDK_HELPER_PULL_CLIENT_NOT_INIT` | Обращение к аксессору Pull до `usePullClient()`. |
| `JSSDK_PULL_PUBLIC_IDS_UNAVAILABLE` | `PullClient.sendMessage()` не смог определить каналы получателей, поэтому отправлять было некому. Обычная причина — не сбой: `pull.channel.public.list` не входит в REST-интерфейс приложений, а клиент Pull приложения, как задокументировано, работает только на приём — бэкенд публикует через `pull.application.event.add`. Не возникает, когда каналы всех получателей уже есть в кеше и не истекли — стартовый конфигурационный вызов заполняет этот кеш из `publicChannels`, где есть собственный канал текущего пользователя, поэтому отправка самому себе часто вообще обходится без поиска. **Никогда** не возникает у `sendMessageToChannels()`, который принимает идентификаторы каналов от вызывающей стороны и поиск не выполняет. До 3.0.0 этот сбой завершался как успех, и сообщение молча терялось. |
| `JSSDK_PULL_SEND_REFUSED` | `PullClient.sendMessage()` / `sendMessageToChannels()` передал кадр транспорту, а тот его не принял — WebSocket не открыт или у long-polling нет пути публикации. Конкретная причина есть в журнале коннектора. Учтите, что отсутствие этой ошибки — не подтверждение доставки: оно означает, что транспорт принял кадр, а long-polling не ждёт ответа. Когда принятый кадр затем никуда не уходит, причина обычно вообще не ошибка, а **код закрытия** WebSocket: сообщается, что сервер push отклоняет кадр, закрывая соединение, а не отвечая. `CloseReasons`{lang="ts-type"} называет их: `WRONG_REQUEST_DATA`{lang="ts-type"} (4013), `NO_CHANNELS_FOUND`{lang="ts-type"} (4017), `PRIVATE_CHANNEL_NOT_ALLOWED`{lang="ts-type"} (4020), `INVALID_CHANNEL_SIGNATURE`{lang="ts-type"} (4021) и другие. Они никогда не доходят до вызывающей стороны как ошибка, а только в событии `close` сокета. До 3.0.0 отказ возвращался как `false`, который вызывающая сторона должна была заметить. |
| `JSSDK_PULL_PUBLISHING_DISABLED` | Отправка предпринята на портале, где не включена клиентская публикация (`publish_enabled`). Публикуйте из бэкенда через `pull.application.event.add`. До 3.0.0 здесь выбрасывалась голая `Error` без кода, по которому можно ветвиться. |
| `JSSDK_HTTP_INVALID_IDEMPOTENCY_KEY` | `idempotencyKey` — не 1–255 печатаемых символов ASCII (`0x21-0x7E`). Только `restApi:v3` — транспорт v2 отбрасывает ключ с предупреждением. Выбрасывается до отправки запроса; сообщение никогда не повторяет ключ. |
| `JSSDK_HTTP_IDEMPOTENCY_KEY_BROWSER` | `idempotencyKey` в вызове `restApi:v3` из браузера. CORS-предзапрос портала не разрешает заголовок `Idempotency-Key`, поэтому кросс-доменный запрос с ним отклоняется (#573). Выбрасывается до отправки чего-либо; выполняйте идемпотентные записи с сервера. |
| `JSSDK_HTTP_REDIRECT_BLOCKED` | Перенаправление ответило на запрос, у которого действующий `maxRedirects` равен `0` — по умолчанию это пакет `restApi:v3` или вызов `restApi:v3` с `idempotencyKey` на не-вебхук-транспорте, несущий токен доступа, который перенаправление на поддомен унесло бы с собой; задайте `maxRedirects: 0` сами — и сюда попадёт каждый ответ со статусом 0. Возникает там, где отказ иначе незаметен: в адаптере `fetch` ответ непрозрачен (статус 0, пустое тело), и axios его разрешает. Вне браузера тот же отказ приходит как обычный 301; при конфигурации по умолчанию транспорт вебхука сюда вообще не попадает, поскольку вебхук не отправляет токен и поэтому никогда не несёт `maxRedirects: 0`. Детерминирован, поэтому не повторяется. Укажите SDK конечный URL. |

## Закреплённые мягкие коды (возвращаются в `AjaxResult`)

Эти коды не выбрасываются — они появляются в `result.getErrors()` (и `getErrorMessages()`). Сначала проверяйте `isSuccess`. При включённом правиле категорий к ним присоединяется много других кодов v3, не перечисленных здесь.

| Код | Значение |
|----|----|
| `ERROR_ENTITY_NOT_FOUND` | REST v2: строка сущности не существует. |
| `BITRIX_REST_V3_EXCEPTION_ACCESSDENIEDEXCEPTION` | REST v3: отказано в доступе. |
| `BITRIX_REST_V3_EXCEPTION_INVALIDJSONEXCEPTION` | REST v3: полезная нагрузка не является допустимым JSON. |
| `BITRIX_REST_V3_EXCEPTION_INVALIDFILTEREXCEPTION` | REST v3: некорректный фильтр. |
| `BITRIX_REST_V3_EXCEPTION_INVALIDSELECTEXCEPTION` | REST v3: некорректный `select` — **или** пакет, тело которого не является списком команд. Портал читает каждый элемент верхнего уровня тела пакета как команду и требует у каждой `method` и `query`, поэтому один элемент без `query` или лишний элемент, вообще не являющийся командой, приводит к сбою всего пакета с этим кодом. Куда передаются учётные данные, зависит от среды выполнения, и браузер — самый неудобный случай: см. [ограничения BatchV3](/docs/actions/batch/#ограничения). |
| `BITRIX_REST_V3_EXCEPTION_ENTITYNOTFOUNDEXCEPTION` | REST v3: сущность не существует. |
| `BITRIX_REST_V3_EXCEPTION_METHODNOTFOUNDEXCEPTION` | REST v3: метод не существует. |
| `BITRIX_REST_V3_EXCEPTION_UNKNOWNDTOPROPERTYEXCEPTION` | REST v3: неизвестное свойство DTO. |
| `BITRIX_REST_V3_EXCEPTION_VALIDATION_REQUESTVALIDATIONEXCEPTION` | REST v3: проверка на уровне запроса не пройдена. `error.validation[]` содержит подробности по полям. |
| `BITRIX_REST_V3_EXCEPTION_VALIDATION_DTOVALIDATIONEXCEPTION` | REST v3: проверка на уровне DTO не пройдена. |

## Коды, запускающие повторы

Этих кодов нет в каталоге выше — они обнаруживаются [`RestrictionManager`](/docs/tools/limiters/) и запускают автоматические повторы с задержкой:

- HTTP 503 / `QUERY_LIMIT_EXCEEDED` — ограничение частоты.
- HTTP 429 / `OPERATION_TIME_LIMIT` — лимит времени операций. Ошибка ограничения частоты v3 (`BITRIX_REST_V3_EXCEPTION_RATELIMITEXCEPTION`) тоже приходит как 429 и классифицируется здесь, только по статусу — см. [Три слоя выдают ошибку ограничения](/docs/tools/limiters/#три-слоя-выдают-ошибку-ограничения-а-не-два).
- Любой другой временный код → экспоненциальная задержка с джиттером.

`OVERLOAD_LIMIT` — третий из этих слоёв. Он есть во встроенном списке жёстких кодов, но это не решает, что с ним произойдёт: сопоставители по статусу выполняются первыми, поэтому при 503, с которым он задокументирован, его забирает ветка ограничения частоты, и он **повторяется**. Перечисление в списке жёстких кодов решает только то, как он доставляется после исчерпания повторов.

После `maxRetries` (по умолчанию `3`) SDK сдаётся и показывает исходную ошибку с её настоящим кодом (например, `QUERY_LIMIT_EXCEEDED`) — выбрасывает для жёстких кодов или возвращает в `AjaxResult` для мягких.

::caution
Сейчас `NETWORK_ERROR` и `REQUEST_TIMEOUT` **не** входят в список жёстких, а значит, неидемпотентные вызовы (например, `crm.documentgenerator.document.add`) могут повторяться после тайм-аута на стороне сервера и создавать дубликаты. Если вы с этим столкнулись, подумайте об обёртке вызова собственным ключом идемпотентности на вашей стороне.
::

## Работа с `AjaxError`

Обе группы появляются как [`AjaxError`{lang="ts-type"}](https://github.com/bitrix24/b24jssdk/blob/main/packages/jssdk/src/core/http/ajax-error.ts) (подкласс `SdkError`{lang="ts-type"}). Полезные свойства:

```ts-type
class AjaxError extends SdkError {
  readonly code: string
  readonly message: string
  readonly status: number
  readonly requestInfo?: { method?: string, params?: TypeCallParams, requestId?: string, url?: string }
}
```

Шаблон единой обработки:

```ts
import { AjaxError } from '@bitrix24/b24jssdk'

async function callWithUnifiedErrorHandling(method: string, params: Record<string, unknown>, requestId: string) {
  try {
    const response = await $b24.actions.v3.call.make({ method, params, requestId })
    if (!response.isSuccess) {
      for (const error of response.getErrors()) {
        if (error instanceof AjaxError) {
          // Soft error
          console.warn(error.code, error.requestInfo?.method)
        }
      }
      return null
    }
    return response.getData()
  } catch (error) {
    if (error instanceof AjaxError) {
      // Hard error
      console.error('SDK threw', error.code, error.status)
    }
    throw error
  }
}
```

## Коды закрытия Pull

Это не коды ошибок, и до вызывающей стороны они никогда не доходят как ошибка. Сервер push отклоняет кадр, **закрывая WebSocket** с числовым кодом и строкой причины, поэтому они приходят только в событии `close` сокета. `CloseReasons`{lang="ts-type"} называет их.

::note
Числа — это то, что даёт событие `close`. Что каждое из них **означает**, известно из аудита собственных исходников сервера push, а не из опубликованной документации, поэтому считайте описания ниже обоснованным руководством, а не контрактом.
::

Перечисление содержит оба направления. Коды ниже `4010`{lang="ts-type"} отправляет **клиент**, когда `PullClient` сам завершает соединение (`NORMAL_CLOSURE`{lang="ts-type"}, `CHANNEL_EXPIRED`{lang="ts-type"}, `CONFIG_EXPIRED`{lang="ts-type"}, `STUCK`{lang="ts-type"} и остальные) — они никогда не указывают на отклонённое сообщение.

| Код | Имя | Что означает |
| --- | --- | --- |
| 4013 | `WRONG_REQUEST_DATA`{lang="ts-type"} | Кадр не декодировался или не содержал запросов. |
| 4014 | `REQUEST_COMMAND_NOT_ALLOWED`{lang="ts-type"} | Не `incomingMessages` и не `channelStats`. |
| 4015 | `WRONG_REQUEST_COMMAND`{lang="ts-type"} | Нет обработчика команды. |
| 4016 | `TOO_MANY_MESSAGES`{lang="ts-type"} | Более 100 сообщений в одном пакете. |
| 4017 | `NO_CHANNELS_FOUND`{lang="ts-type"} | Сообщение никому не адресовано. |
| 4018 | `TOO_MANY_CHANNELS`{lang="ts-type"} | Более 100 каналов в одном запросе. |
| 4019 | `INVALID_CHANNEL_ID`{lang="ts-type"} | Проверка доверенного соединения; из браузера недостижима. |
| 4020 | `PRIVATE_CHANNEL_NOT_ALLOWED`{lang="ts-type"} | Клиент не может публиковать в приватный канал. |
| 4021 | `INVALID_CHANNEL_SIGNATURE`{lang="ts-type"} | Подпись канала не прошла проверку. |

Ещё три кода находятся в том же числовом диапазоне и относятся к **уровню соединения**: они говорят, что соединение непригодно, а не что отклонено конкретное сообщение: `WRONG_CHANNEL_ID`{lang="ts-type"} (4010), `NO_PUBLIC_CHANNEL_ID`{lang="ts-type"} (4012) и `TOO_MANY_CONNECTIONS`{lang="ts-type"} (4029). Проверка «это 401x» неверно классифицировала бы все три, поэтому используйте `isFrameRefusalCloseCode()`{lang="ts"}.

::caution
**Код закрытия — доказательство, когда он приходит. Его отсутствие ничего не доказывает о закодированном вами сообщении.** Поле, записанное под номером, которого сервер не объявляет, пропускается: кадр разбирается, рассылается и не несёт ничего полезного — без закрытия, без ошибки, без какого-либо признака.

Учтите границу этого, потому что она работает и в обратную сторону. Сообщение, правильно сформированное, но *семантически* неверное, порождает код закрытия — отсутствие получателей даёт `4017`{lang="ts-type"}, приватный канал — `4020`{lang="ts-type"}, неверная подпись — `4021`{lang="ts-type"}. Поэтому сначала стоит проверить таблицу выше; молчаливый прогон не снимает подозрений только с самого кодирования.
::
