## Обзор

Система состоит из нескольких компонентов, которые работают совместно, чтобы не превышать лимиты API и обеспечивать стабильную работу.

```ts-type
┌─────────────────────────────────────────────┐
│            RestrictionManager               │
│  (Coordinator of all types of restrictions) │
└─────┬──────────────┬──────────────┬─────────┘
      │              │              │
      ▼              ▼              ▼
┌──────────┐  ┌────────────┐  ┌─────────────┐
│ Rate     │  │ Operating  │  │ Adaptive    │
│ Limiter  │  │ Limiter    │  │ Delayer     │
└──────────┘  └────────────┘  └─────────────┘
```

### Интерфейсы и типы

#### ILimiter (базовый интерфейс)

```ts-type
interface ILimiter {
  getTitle(): string
  setConfig(config: any): Promise<void>
  setLogger(logger: LoggerInterface): void
  getLogger(): LoggerInterface
  canProceed(requestId: string, method: string, params?: any): Promise<boolean>
  waitIfNeeded(requestId: string, method: string, params?: any): Promise<number>
  updateStats(requestId: string, method: string, data: any): Promise<void>
  reset(): Promise<void>
  getStats(): Record<string, any>
}
```

#### RestrictionParams

```ts-type
interface RestrictionParams {
  rateLimit?: RateLimitConfig      // Rate limiting settings
  operatingLimit?: OperatingLimitConfig  // Operation time limit settings
  adaptiveConfig?: AdaptiveConfig  // Adaptive delay settings
  maxRetries?: number              // Maximum number of request retries (default: 3). Except for `batch` requests
  retryDelay?: number              // Base delay between retries in ms (default: 1000)
  retryOnNetworkError?: boolean    // Retry on `NETWORK_ERROR` / `REQUEST_TIMEOUT` (HTTP 408) (default: true).
                                   // Set to `false` for non-idempotent calls — see "Non-idempotent calls" below.
  hardErrorCodes?: string[]        // Extra codes to throw immediately (merged with built-in hard list).
  softErrorCodes?: string[]        // Extra codes to return as AjaxResult with error (merged with built-in soft list).
}
```

## Компоненты системы

### 1. RateLimiter (ограничение частоты запросов)

**Назначение**: реализует алгоритм «дырявого ведра» (Leaky Bucket) для ограничения частоты запросов.

#### RateLimiter — конфигурация

```ts-type
interface RateLimitConfig {
  burstLimit: number    // Bucket capacity (maximum number of simultaneous requests)
  drainRate: number     // Leak rate (requests per second)
  adaptiveEnabled: boolean  // Enable adaptive management
}
```

#### RateLimiter — принцип работы

1. **Система токенов**: каждый запрос расходует один токен.
2. **Автоматическое пополнение**: токены пополняются со скоростью `drainRate`.
3. **Адаптивное управление**:
  * при частых ошибках лимиты автоматически снижаются на 20%;
  * при стабильной работе лимиты постепенно восстанавливаются;
  * минимальные значения: `drainRate = 0.5`{lang="ts-type"}, `burstLimit = 5`{lang="ts-type"}.

### 2. OperatingLimiter (ограничение времени операций)

**Назначение**: контролирует суммарное время выполнения операций в скользящем окне.

#### OperatingLimiter — конфигурация

```ts-type
interface OperatingLimitConfig {
  windowMs: number      // Time period in milliseconds (default: 600000 = 10 minutes)
  limitMs: number       // Maximum execution time in milliseconds (default: 480000 = 480 seconds)
  heavyPercent: number  // Threshold for heavy request notifications (%)
}
```

#### OperatingLimiter — принцип работы

1. **Скользящее окно**: отслеживается время выполнения за последние 10 минут.
2. **Учёт по методам**: статистика ведётся отдельно для каждого метода.
3. **Запас надёжности**: в расчётах используется `limitMs - 5000`{lang="ts-type"} (запас 5 секунд).
4. **Блокировка**: при достижении лимита выполнение блокируется до сброса статистики.

#### OperatingLimiter — особенности

- Пакет засчитывается на метод `batch` — так его учитывает портал, — а не распределяется по методам внутри него.
- Автоматическая очистка устаревших данных (> windowMs + 10 секунд).
- Журналирование тяжёлых запросов при превышении `heavyPercent`{lang="ts-type"}.

::warning
**Портал на собственной инфраструктуре (self-hosted) по умолчанию вообще не ограничивает частоту REST, поэтому этому лимитеру там делать нечего.** Счётчики `operating` / `operating_reset_at` приходят только пока активен собственный `LoadLimiter` портала, а в коробке он читает опцию модуля `rest` `load_limiter_active` — по умолчанию `N`, и ничто в продукте её не записывает. Этот же переключатель управляет и **принудительным применением**: `LoadLimiter::is()` сразу возвращает `false`, когда лимитер неактивен, то есть портал вызовы тоже не отклоняет. Тихий `OperatingLimiter` поэтому просто совпадает с порталом, а не что-то упускает. `RateLimiter` и `AdaptiveDelayer` не затронуты и продолжают действовать.
::

Это также означает, что у коробки нет защиты от неконтролируемой интеграции, которая перегружает REST. Если она нужна, [включите лимитер осознанно](#включение-лимитера-времени-операций-на-self-hosted-портале), но сначала прочитайте, чего это стоит: вы включаете принудительное ограничение, а не телеметрию.

#### Что означают счётчики, когда они приходят

Измерено на `main 26.700.0` / `rest 26.500.0`. Портал на собственной инфраструктуре находится в одном из трёх состояний, и среднее — ловушка:

| Состояние портала | `operating` | `operating_reset_at` | Можно использовать как бюджет |
|---|---|---|---|
| `load_limiter_active` не задан (по умолчанию `N`) | отсутствует | отсутствует | Нет — и ничего не ограничивается |
| `load_limiter_active = Y`, соединение не настроено | присутствует, **никогда не накапливается** | **отсутствует** | **Нет — и это не выглядит поломкой** |
| `load_limiter_active = Y` + рабочее соединение | накапливается между запросами | срок действия корзины | Да |

Среднее состояние опасно, и не по той причине, о которой вы подумали бы. `operating` там **не** постоянный ноль: это сумма, накопленная *в пределах текущего запроса*, поэтому быстрый вызов показывает `0` лишь потому, что уложился в `minimalFixTime` портала, равный 0,1 с, а пакет из 50 команд показывает правдоподобные `0.16`. В трёх одинаковых запусках пакета значения были `0.16`, затем `0`, затем `0.157` — число, которое меняется, выглядит настоящим и никогда не растёт. Клиент, который регулирует нагрузку по нему, никогда не начнёт её регулировать.

Как это становится достижимым: достаточно переключить одну опцию, а соединение само не появляется. Сюда же приводит и сломанное соединение: `getConnectionResource()` обнуляет ресурс, когда `isConnected()` не равно `true`, поэтому опечатка в имени соединения или остановленный Redis молча возвращают портал в это состояние, и в ответе REST об этом нет никакого сигнала.

::note
Поэтому SDK никогда не подставляет `operating: 0`, когда счётчиков нет. Выдуманный ноль перевёл бы каждый портал в среднее состояние — уверенно неверное вместо честно слепого.
::

#### Свойства бюджета портала, которых не видно по числам

Измерено на той же сборке, и каждое из них противоречит разумному предположению:

- **Бюджет ведётся по методу, а не по порталу или учётным данным.** Портал строит ключ как `sha1(тип авторизации | учётные данные | метод)`. Измерение: когда бюджет `batch` стоял на `1.228`, `tasks.task.list` в тот же момент показывал `0` — в обеих версиях API. Общепортальную цифру «REST израсходован на 60% бюджета» по этим числам получить нельзя, а пакет засчитывается на `batch`, а не на методы внутри него.
- **Пакет тратит вдвое меньше времени, чем занимает.** Портал применяет `BATCH_TIME_WEIGHT`, равный `0.5`. Подтверждено дважды — внутри запроса и через соединение. SDK не нужно это компенсировать: число, которое он читает, уже взвешено.
- **Окно — 600 секунд, а не 420.** Это десять 60-секундных корзин. `420` — это *порог* в пределах этого окна, который на коробке можно переопределить через `load_limiter_second_limit`; в облаке то же переопределение задаётся переменной функциональности.
- **Вызов короче 0,1 с вообще не учитывается.**
- **`operating_reset_at` — ненадёжный срок.** Портал добавляет его только тогда, когда время сброса приходит истинным значением, поэтому в среднем состоянии таблицы выше его нет совсем — это измерено. Когда он есть, это срок действия сохранённых корзин: фиксированная точка, которая остаётся на месте между запросами, а не сдвигается вперёд с каждым из них. Чтение исходников модуля подсказывает третий случай, когда ничего не сохранено и значение вычисляется как `начало этого запроса + 600`; этот случай не наблюдался, поэтому считайте присутствующее значение подсказкой, а не обещанием.
- **`Retry-After` никогда не отправляется.** Поиск по всему модулю `rest` не находит ни одного упоминания, и ни один ответ за пятнадцать минут постоянной нагрузки его не содержал. SDK нечего учитывать, и он его не ищет.

Каждый проверенный нами облачный портал отправляет счётчики — и в `restApi:v2`, и в `restApi:v3`.

#### Что на самом деле делает длительная нагрузка

Измерено на облачном портале, потому что путь принудительного применения там — тот же класс с тем же коннектором, что и на настроенной коробке; в облаке он просто всегда включён.

Два запуска пакетов по 50 команд: шесть, затем четырнадцать параллельных потоков, пятнадцать минут и примерно 11 000 запросов (около полумиллиона подкоманд). **Ни одного отказа**: ни `429`, ни `503`, ни `OVERLOAD_LIMIT`, ни заголовка `Retry-After` или `X-RateLimit-*` ни в одном ответе — измерение подтверждает то, что уже подсказывал поиск по исходникам модуля.

Интересно то, что сделал счётчик:

| Нагрузка | Поведение `operating` |
|---|---|
| одиночные вызовы | замирает после первого — каждый следующий вызов укладывается в порог 0,1 с и ничего не добавляет |
| 6 параллельных потоков пакетов | устойчиво растёт, затем **выходит на плато около 266 с** и держится там |
| 14 параллельных потоков пакетов | колеблется между ~270 и ~383, выше не поднимается |

Плато — это скользящее окно, достигшее установившегося режима: после этого оно отбрасывает данные так же быстро, как нагрузка их добавляет. Оба плато лежат **ниже порога в 420 секунд**, а удвоение параллелизма почти не сдвинуло потолок. Значит, на портале такого размера лимит времени операций не просто трудно достичь — при лёгкой, но частой нагрузке он недостижим по построению, и `OperatingLimiter` никогда не будет иметь повода что-либо задерживать.

Это стоит знать до настройки `operatingLimit`: если ваши вызовы короткие, бюджет, который вы моделируете, портал применять не будет. Ограничения, с которыми вы действительно столкнётесь, — это ограничения частоты запросов.

::note
Форма отказа в сетевом обмене поэтому по-прежнему не наблюдалась — не из-за недостатка попыток. То, что выбрасывает портал, прочитано в его исходниках: `restApi:v2` выбрасывает `OPERATION_TIME_LIMIT` с HTTP 429, `restApi:v3` — исключение ограничения частоты с тем же статусом. Поэтому классификация SDK для v3 429 оставлена как есть, а не изменена на основе предположения — см. [Три слоя выдают ошибку ограничения, а не два](#три-слоя-выдают-ошибку-ограничения-а-не-два).
::

::caution
**Не используйте `time.duration` и `time.processing` для измерения времени на этой сборке.** `CRestServer` объявляет `timeStart` / `timeProcessStart` / `timeProcessFinish` как `int` и присваивает им `microtime(true)`, поэтому дробная часть молча отбрасывается. `duration` завышается до целой секунды (измерено: 0,29, 0,45, 0,42 с на трёх конвертах пакетов), а `processing` квантуется до целых секунд и почти для каждого вызова равен `0`. Заголовок `X-Bitrix-Rest-Time` строится из тех же двух значений — по измерениям, на обычном успешном вызове он равен `0.0000000000`. SDK измеряет длительность собственных запросов монотонными часами и ни одно из этих полей не читает.
::

### Включение лимитера времени операций на self-hosted портале

Шаги ниже выполнялись на реальном портале в этом порядке. Они предназначены для **владельца коробки**, а не для кода приложения: ничто здесь не меняет поведение SDK.

::warning
Вы включаете **принудительное ограничение**, а не телеметрию. Каждый вебхук и каждое OAuth-приложение на портале начинают подчиняться бюджету времени операций по методам. Интеграция, которая тихо жила выше него, начнёт сбоить в день включения. Включайте в спокойное окно и сутки наблюдайте за 429, прежде чем ему доверять.
::

**1. Redis для него, привязанный к loopback.** Memcached не подойдёт: лимитер вызывает `exists`, `setEx`, `ttl`, `del`, `incrByFloat`, `expireAt` и «сырой» `MGET` — это интерфейс phpredis. Коробке, у которой движок кеша — memcached, всё равно нужно отдельно объявить Redis.

```
bind 127.0.0.1 -::1
protected-mode yes
port 6379
save ""
appendonly no
maxmemory 128mb
maxmemory-policy allkeys-lru
```

Постоянное хранение намеренно выключено: счётчики — это скользящее десятиминутное окно, у каждого ключа есть TTL, а потеря их при перезапуске лишь делает лимитер мягче. `allkeys-lru` выбран по той же причине — при нехватке памяти отбрасывать счётчики, а не отказывать в записи. Пароля нет, потому что нет слушателя вне loopback; не открывайте порт в файрволе.

**2. Объявите соединение** в `bitrix/.settings.php` в разделе `connections` → `value`. Сначала скопируйте файл: синтаксическая ошибка там роняет весь портал.

```php
'cache.redis' => [
    'className' => \Bitrix\Main\Data\RedisConnection::class,
    'host' => '127.0.0.1',
    'port' => 6379,
    'persistent' => false,
],
```

**3. Проверьте пул, прежде чем что-либо включать.** Сначала вызовите `getResource()`, затем `isConnected()` — соединение ленивое, и при обратном порядке проверки совершенно исправное соединение сообщает `false`.

```php
$c = \Bitrix\Main\Application::getInstance()->getConnectionPool()->getConnection('cache.redis');
$r = $c->getResource();
echo get_class($r), ' ', var_export($c->isConnected(), true), ' ', var_export($r->ping(), true);
```

Этот шаг обязателен. Неверное имя или остановленный Redis оставляют вас в среднем состоянии таблицы выше, и ничто в ответе REST этого не сообщает.

**4. Включите.**

```php
\Bitrix\Main\Loader::includeModule('rest');
\Bitrix\Main\Config\Option::set('rest', 'load_limiter_active', 'Y');
\Bitrix\Main\Config\Option::set('rest', 'load_limiter_connection_name', 'cache.redis');
```

**5. Убедитесь, что накопление идёт, а не предполагайте это.** Вызывайте один метод повторно и следите, растёт ли `time.operating` между ответами. Значение, которое меняется, но не растёт, означает, что шаг 3 не удался.

**Чтобы откатить**, верните обе опции в `'N'` и `''`.

#### Эксплуатационные заметки

- **Единственная настройка — `load_limiter_second_limit`**, которая заменяет порог в 420 секунд. `BAN_DURATION` — закрытая константа в 300 секунд, и настроить её нельзя. Если значение по умолчанию слишком жёсткое для легитимной интеграции, поддерживаемый путь — поднять эту опцию; отключать лимитер не следует.
- **Блокировки не попадают в журнал исключений портала.** Исключение ограничения частоты в v3 помечено так, чтобы пропускать журнал. Вместо этого следите в журнале доступа веб-сервера за ответами 429 по пути `/rest/`. Включите лимитер — и портал начнёт отклонять запросы, не оставляя следа там, куда администратор смотрит в первую очередь.
- **Сбой Redis работает «открытым».** Ничего не накапливается, порог не достигается, и REST продолжает обслуживать запросы. Это правильное направление отказа, но молча умерший Redis выглядит точно так же, как здоровый ненагруженный портал.

### 3. AdaptiveDelayer (адаптивные задержки)

**Назначение**: динамически рассчитывает задержки на основе опыта выполнения предыдущих запросов.

#### AdaptiveDelayer — конфигурация

```ts-type
interface AdaptiveConfig {
  enabled: boolean        // Enable adaptive delays
  thresholdPercent: number // Activation threshold (% of operating limit)
  coefficient: number     // Delay multiplier (0.01 = 1% of remaining blocking time)
  maxDelay: number        // Maximum delay in milliseconds
}
```

#### AdaptiveDelayer — алгоритм расчёта задержки

```html
If operating of current method > (limitMs × thresholdPercent / 100):
  If operating_reset_at > current time:
    Delay = (operating_reset_at - current time) × coefficient
  Otherwise:
    Delay = 7000 ms (default value)
  
  Final delay = min(calculated, maxDelay)
```

#### AdaptiveDelayer — особенности

* Пакет задерживается по бюджету `batch`, по которому его учитывает портал, а не по самому загруженному методу внутри него.
* Не блокирует выполнение, а только добавляет задержку.
* Использует статистику из OperatingLimiter.

### 4. RestrictionManager (главный координатор)

**Назначение**: управляет всеми видами ограничений и обработкой ошибок.

#### Порядок применения ограничений

1. **Проверка лимита операций**: проверяет лимит времени операций.
2. **Адаптивная задержка**: при необходимости применяет адаптивную задержку.
3. **Ограничение частоты**: проверяет и применяет ограничение частоты (цикл для параллельных запросов).

#### Обработка ошибок

```ts-type
// Determining error type, in the order they are tested
#isRateLimitError(error): boolean          // 503 or QUERY_LIMIT_EXCEEDED
#isOperatingLimitError(error): boolean     // 429 or OPERATION_TIME_LIMIT
#isNonRetryableClientError(error): boolean // HTTP 4xx (except 429 / 408)
#isNeedThrowError(error): boolean          // Critical errors (no point in retrying)
```

#### Три слоя выдают ошибку ограничения, а не два

Два описанных выше сопоставителя делят случаи на две части, но у портала **три** места, где вызов отклоняется из-за нагрузки:

| Слой | Где возникает | Форма в сетевом обмене | Как SDK его классифицирует |
|---|---|---|---|
| `OVERLOAD_LIMIT` | слой авторизации, до разбора версии URL | плоская ошибка старого формата, на **любом** URL — и `restApi:v2`, и `restApi:v3` | входит во встроенный список жёстких кодов, но решает статус: при 503, который [справочник ошибок](/docs/actions/errors/) для него документирует, первой его забирает ветка ограничения частоты и повторяет запрос |
| `QUERY_LIMIT_EXCEEDED` | облачный слой (в исходниках для собственной инфраструктуры не встречается) | плоская ошибка старого формата | ограничение частоты — `RateLimiter.handleExceeded()` |
| `RATELIMITEXCEPTION` | сам слой v3 | HTTP **429**, конверт v3, код `BITRIX_REST_V3_EXCEPTION_RATELIMITEXCEPTION` | лимит **времени операций**, только по HTTP-статусу |

Стоит прямо сказать о двух вещах.

Ошибка ограничения частоты v3 сейчас обрабатывается веткой лимита времени операций, потому что `#isOperatingLimitError()` сопоставляет `status === 429` само по себе. Последствия заметны, но не опасны: в строке журнала указан `OPERATION_TIME_LIMIT`, ожидание берётся из статистики времени операций (на портале на собственной инфраструктуре её нет, поэтому это фиксированный минимум 10 секунд), а `RateLimiter` не узнаёт, что его ограничили, и не сокращает собственный бюджет.

И присутствие кода в списке жёстких кодов не решает, что с ним произойдёт: два сопоставителя по статусу проверяются до этой проверки, поэтому `OVERLOAD_LIMIT` при 503 повторяется как ограничение частоты, а перечисление в списке жёстких кодов действует только для формы, которая не несёт статуса.

Первое из этого оставлено так намеренно. Переклассификация требует знать, какой слой отвечает первым на URL v3 под нагрузкой и отправляет ли портал `Retry-After`, который стоит соблюдать вместо нашей задержки, — SDK сегодня такой заголовок не читает. Оба вопроса требуют измерения на одноразовом портале, поскольку блокировка на собственной инфраструктуре длится фиксированные 300 секунд. Гадание обменяло бы неверную метку на неверное расписание повторов. См. [#459](https://github.com/bitrix24/b24jssdk/issues/459).

#### Стратегия повторов

1. **Для ошибок лимитов**: экспоненциальная задержка с учётом номера попытки.
2. **Для клиентских ошибок (HTTP 4xx, кроме 429 / 408)**: без повторов — ответ `4xx` детерминирован, поэтому повтор не может изменить результат. Ошибка выходит из цикла повторов с первой попытки; затем применяется обычная классификация жёстких и мягких ошибок (выбрасывается как `AjaxError` или для мягких кодов возвращается внутри `AjaxResult`). `429` повторяется как ограничение частоты или времени операций; `408` (тайм-аут запроса) остаётся временной ошибкой.
3. **Для остальных ошибок**: базовая задержка с джиттером (±10%).
4. **Критические ошибки**: без повторов.

## Обновление параметров

`setRestrictionManagerParams` **заменяет указанные вами параметры и сохраняет остальные**. Вызовите его дважды — второй вызов не отменяет первый:

```ts
import { ParamsFactory } from '@bitrix24/b24jssdk'

// const $b24 = ...
await $b24.setRestrictionManagerParams({
  ...ParamsFactory.getDefault(),
  retryOnNetworkError: false,
  hardErrorCodes: ['MY_APP_BAD_PAYLOAD']
})

// Later, elsewhere. `retryOnNetworkError` and `hardErrorCodes` survive.
await $b24.setRestrictionManagerParams({ maxRetries: 5 })
```

::caution
**Слияние поверхностное: вложенные блоки заменяются целиком.** `rateLimit`, `operatingLimit` и `adaptiveConfig` не сливаются по полям — передав один, вы передаёте *все* его поля; если опустить блок, он остаётся нетронутым.

TypeScript контролирует это за вас: у `RateLimitConfig` и его собратьев нет необязательных полей, поэтому `{ rateLimit: { burstLimit: 7 } }` — ошибка компиляции. Из JavaScript или за приведением типа это отклоняется уже во время выполнения — ошибкой `JSSDK_LIMITER_INVALID_CONFIG_BLOCK`, в которой названы пропущенные поля. До лимитера не доходит ничего недостроенного.

Глубокое слияние позволило бы наполовину заданному блоку объединиться со старым в пару чисел, которую никто не выбирал. Чтобы изменить одно поле, разверните текущий блок:

```ts
import { ApiVersion, ParamsFactory } from '@bitrix24/b24jssdk'

// const $b24 = ...
const client = $b24.getHttpClient(ApiVersion.v3)
const current = client.getRestrictionManagerParams()

// `$b24.setRestrictionManagerParams` writes to EVERY API version, while the
// block above came from one client. Go through the same client when you mean
// to change only that one.
await client.setRestrictionManagerParams({
  ...current,
  rateLimit: { ...(current.rateLimit ?? ParamsFactory.getDefault().rateLimit!), burstLimit: 7 }
})
```

`getRestrictionManagerParams()` возвращает **копию**, включая вложенные блоки, поэтому прочитанное — это снимок, а не живое состояние лимитера. Учтите, что значения в нём — те, что действуют *сейчас* (лимитер частоты сам снижает `drainRate`, пока адаптивно ограничивает), а не обязательно те, что вы задали последними.
::

**Сброс значения** требует явного значения, поскольку пропущенный ключ теперь означает «не трогать»: передайте `hardErrorCodes: []`, чтобы опустошить список, или значение поля по умолчанию, чтобы его восстановить. Развёртывание `...ParamsFactory.getDefault()` сбрасывает всё, что фабрика *называет*, но в нём нет ключей `hardErrorCodes` и `softErrorCodes`, поэтому эти два остаются. Называйте их сами, когда хотите их очистить.

До [#479](https://github.com/bitrix24/b24jssdk/issues/479) этот метод **заменял всю конфигурацию**, поэтому частичное обновление молча сбрасывало все не упомянутые параметры, в том числе вложенные блоки, которые затем доходили до своих лимитеров как `undefined`. По этой причине примеры в документации сначала разворачивают `...ParamsFactory.getDefault()`; это по-прежнему хороший способ описать полную политику в одном месте.

## Долгие запросы и неидемпотентные вызовы

В SDK по умолчанию задан тайм-аут axios 30 секунд, а неудачные запросы повторяются до `maxRetries` раз. Оба значения не подходят для **долгих** **неидемпотентных** REST-методов — канонический пример `crm.documentgenerator.document.add`, который может формировать документ по шаблону 10–60 секунд и стал причиной исходного обращения [issue #24](https://github.com/bitrix24/b24jssdk/issues/24).

### Почему по умолчанию всё идёт не так

Когда сервер отвечает дольше тайм-аута axios, происходит следующее:

1. Клиент открывает запрос, сервер начинает обработку.
2. Срабатывает тайм-аут axios, SDK получает `REQUEST_TIMEOUT` (`code: ECONNABORTED`).
3. `REQUEST_TIMEOUT` считается временной ошибкой — SDK повторяет запрос.
4. Сервер, не зная, что клиент сдался, завершает первый запрос и **сохраняет документ**. Затем принимает повтор и сохраняет **ещё один**.
5. После `maxRetries` попыток SDK выбрасывает исходную ошибку (с её настоящим кодом), и у вызывающей стороны в CRM остаётся 2–3 дубликата.

Тот же риск есть у любого неидемпотентного метода: `crm.deal.add`, `crm.contact.add`, `disk.folder.uploadfile`, `tasks.task.add`, любой собственный REST-метод, создающий состояние.

### Рекомендуемая конфигурация

Используйте этот шаблон для любого вызова, который создаёт сущность, независимо от ожидаемой длительности:

```ts
import { ApiVersion, ParamsFactory } from '@bitrix24/b24jssdk'

// const $b24 = ...

// 1. Raise the timeout so the client actually waits for a slow operation.
const clientAxios = $b24.getHttpClient(ApiVersion.v2).ajaxClient
clientAxios.defaults.timeout = 120_000 // default is 30_000

// 2. Disable retries on transport errors so a client-side timeout never
//    creates duplicate entities on the server.
await $b24.setRestrictionManagerParams({
  ...ParamsFactory.getDefault(),
  retryOnNetworkError: false
})

// Now safe for non-idempotent calls.
const result = await $b24.actions.v2.call.make({
  method: 'crm.documentgenerator.document.add',
  params: { templateId: 42, entityTypeId: 2, entityId: 6014, values: {} }
})
```

::note
**Одного шага недостаточно.** Долгий тайм-аут без `retryOnNetworkError: false` всё равно порождает дубликаты в нестабильной сети (сервер ответил, но ответ не дошёл). Флаг без тайм-аута срабатывает слишком рано на запросах, которые завершились бы за 35–40 секунд.
::

### Точечное применение — переопределение для одного вызова

Если строгое поведение нужно только для конкретного участка кода, создайте для этого вызова новый `B24Hook`, а не изменяйте глобальный:

```ts
import { B24Hook, ParamsFactory } from '@bitrix24/b24jssdk'
import { ApiVersion } from '@bitrix24/b24jssdk'

const $b24Strict = B24Hook.fromWebhookUrl(hookUrl, {
  restrictionParams: {
    ...ParamsFactory.getDefault(),
    retryOnNetworkError: false
  }
})
$b24Strict.getHttpClient(ApiVersion.v2).ajaxClient.defaults.timeout = 120_000

await $b24Strict.actions.v2.call.make({ method: 'crm.deal.add', params: {/*…*/} })
```

### Крайняя мера — отключить все повторы

Если вы не можете позволить себе ни одного повтора ни при каких обстоятельствах (например, платёжная операция), задайте `maxRetries: 1`:

```ts
import { ParamsFactory } from '@bitrix24/b24jssdk'

await $b24.setRestrictionManagerParams({
  ...ParamsFactory.getDefault(),
  maxRetries: 1
})
```

Это влияет на каждый класс ошибок, а не только на транспортные, поэтому применяйте с осторожностью.

## Настройка классификации ошибок

SDK группирует коды ошибок REST в три категории:

1. **Жёсткие ошибки** — выбрасываются сразу как `AjaxError`. Без повторов. Используются для фатальных условий (сбои авторизации, неверные аргументы, удалённые порталы).
2. **Мягкие ошибки** — возвращаются внутри `AjaxResult` как полезная нагрузка с ошибкой и **не** выбрасываются. Используются для кодов, которые вызывающий код обычно проверяет как часть обычного потока управления (например, `ENTITY_NOT_FOUND`, ошибки валидации v3).
3. **Всё остальное** — возможность повтора определяется HTTP-статусом. Клиентские ошибки (HTTP `4xx`, кроме `429` и `408`) **никогда не повторяются** — они детерминированы, поэтому SDK завершает работу сразу с первой попытки независимо от того, перечислен ли код ошибки. Временные условия (`5xx`, `429`, `408`, сетевые ошибки) повторяются до `maxRetries` раз с задержкой и джиттером.

Встроенные списки охватывают стандартный REST-интерфейс Битрикс24. Если ваше приложение использует собственные REST-методы (например, из локального приложения или обработчика встройки (placement)), которые возвращают свои коды ошибок со статусом не из `4xx`, эти коды будут **повторяться по умолчанию** — а это неверно для неидемпотентных бизнес-ошибок.

Расширьте классификацию через `hardErrorCodes` и `softErrorCodes`:

```ts
import { ParamsFactory } from '@bitrix24/b24jssdk'

// const $b24 = ...

await $b24.setRestrictionManagerParams({
  ...ParamsFactory.getDefault(),

  // These will throw immediately instead of being retried:
  hardErrorCodes: [
    'DOCUMENT_GENERATOR_ALREADY_IN_QUEUE', // business code: don't retry
    'MY_APP_INVALID_PAYLOAD'               // custom REST: caller fix needed
  ],

  // These will be returned in AjaxResult instead of thrown:
  softErrorCodes: [
    'MY_APP_VALIDATION_FAILED'             // expected via normal flow
  ]
})
```

### Классификация ошибок `restApi:v3` по категории

Расширение списков помогает только для кодов, которые вы уже знаете, а в `restApi:v3` знать их все нельзя: код выводится из класса исключения, которое его выбросило, поэтому набор растёт с каждым модулем портала. На одной сборке для коробки измерено не менее **39 различных кодов v3** против **девяти** во встроенном списке мягких, — поэтому классификация зависит от даты поставки модуля, а не от вида ошибки. `INVALIDSELECTEXCEPTION` мягкая, а `INVALIDPAGINATIONEXCEPTION` — та же ошибка вызывающей стороны в том же запросе с тем же HTTP 400 — выбрасывается.

Поэтому SDK принимает решение по ответу, и настраивать ничего не нужно.

Ошибка, пришедшая в конверте ошибки v3 с HTTP **4xx, кроме 401, 408 и 429**, считается мягкой независимо от кода. Закреплённые коды — встроенные списки и ваши собственные — по-прежнему приоритетнее этого правила; 5xx не затрагивается, как и `restApi:v2`, чьё плоское тело ошибки не является конвертом v3.

::caution
**Изменено в 3.0.0.** В линейке `2.x` это включалось по желанию через параметр `classifyV3ErrorsByCategory`, по умолчанию `false`; в `3.0.0` правило стало поведением, а параметра больше нет. Ошибка v3 с кодом 4xx, которая выбрасывалась в `2.x`, теперь возвращается как результат, поэтому `try / catch`, написанный под прежнее поведение, перестаёт срабатывать, и управление проваливается в ветку успеха. Перенесите эту обработку в `if (!response.isSuccess)`. Подробности — в [кодах ошибок](/docs/tools/error-codes/#классификация-по-категории-restapiv3), шаги миграции — в [руководстве по 3.0.0](/docs/getting-started/migration/v3/#поведение-ошибки-v3-классифицируются-по-категории-ответа).
::

::note
**Слияние, а не замена.** Коды, которые вы задаёте, добавляются к встроенным спискам. Можно только **добавлять** коды — встроенные (коды авторизации, `INTERNAL_SERVER_ERROR`, коды валидации v3 и т. д.) остаются на месте. Это защищает от случайного отключения важных предохранителей, таких как обнаружение `expired_token`.
::

Встроенные списки доступны как статические поля для справки:

```ts
import { RestrictionManager } from '@bitrix24/b24jssdk'

console.log(RestrictionManager.BUILT_IN_HARD_ERROR_CODES)
console.log(RestrictionManager.BUILT_IN_SOFT_ERROR_CODES)
```

Один встроенный жёсткий код выбрасывает сам SDK, а не портал, и он — исключение из описанной выше истории с повторами: `JSSDK_HTTP_REDIRECT_BLOCKED` приходит со `status: 0`{lang="ts-type"}, поэтому `retryOnNetworkError` им не управляет — отказ в перенаправлении детерминирован, а каждый повтор заново отправлял бы запрос с токеном доступа на хост, который хочет его перенаправить. Будучи встроенным и жёстким, он также приоритетнее `softErrorCodes`: указание его там не превращает его в возвращаемую ошибку. См. [коды ошибок](/docs/tools/error-codes/).

## Глобальная область действия `setRestrictionManagerParams` на уровне экземпляра

`setRestrictionManagerParams()` изменяет **весь экземпляр `$b24`**: он перенастраивает единственный `RestrictionManager`, общий для каждого запроса, который проходит через этот экземпляр. Это **не** переопределение для одного вызова.

На сервере это ловушка, когда один экземпляр `$b24` разделяется между параллельными запросами (типичный шаблон: синглтон уровня модуля, который используют многие HTTP-обработчики). Изменение параметров для одного запроса меняет их для **всех выполняющихся запросов** этого экземпляра.

```ts
import { ParamsFactory } from '@bitrix24/b24jssdk'

// ⚠️ ANTI-PATTERN: shared $b24, concurrent handlers
// Request A — a non-idempotent create that wants retries OFF:
await $b24.setRestrictionManagerParams({
  ...ParamsFactory.getDefault(),
  retryOnNetworkError: false
})
await $b24.actions.v2.call.make({
  method: 'crm.deal.add',
  params: { fields: { TITLE: 'Deal A' } }
})

// Request B — running concurrently on the SAME $b24 — now ALSO sees
// retryOnNetworkError: false, even though it never asked for it. And if
// Request B calls setRestrictionManagerParams first, Request A's create
// silently runs with B's params. Last writer wins, globally.
```

Поскольку изменение глобально, а изоляции по запросам нет, два параллельных потока `createDeal` могут затереть конфигурацию ограничения частоты и повторов друг друга.

### Безопасные шаблоны

1. **Отдельный экземпляр `$b24` для неидемпотентных и нестандартных потоков.** Создайте отдельный экземпляр (или передайте `restrictionParams` при создании) для участка кода, которому нужно другое поведение, чтобы он никогда не делил состояние с основным пулом:

   ```ts
   import { B24Hook, ParamsFactory, ApiVersion } from '@bitrix24/b24jssdk'

   const $b24Strict = B24Hook.fromWebhookUrl(hookUrl, {
     restrictionParams: {
       ...ParamsFactory.getDefault(),
       retryOnNetworkError: false
     }
   })
   $b24Strict.getHttpClient(ApiVersion.v2).ajaxClient.defaults.timeout = 120_000

   await $b24Strict.actions.v2.call.make({
     method: 'crm.deal.add',
     params: { fields: { TITLE: 'Deal A' } }
   })
   ```

2. **Задавайте параметры ограничений один раз при запуске**, а не для каждого запроса. Считайте их конфигурацией экземпляра, а не настройкой для одного вызова.

3. **`Idempotency-Key` (только `restApi:v3`).** Передайте `idempotencyKey` в вызове — строку, называющую одну бизнес-операцию и выведенную из ваших собственных идентификаторов (`deal-${orderId}-create`), чтобы повтор в другом процессе дал тот же ключ. `crypto.randomUUID()`, записанный в месте вызова, этого не даёт: перезапущенный процесс создаст новый и запишет дубликат. Портал сохраняет успешный ответ под этим ключом на 24 часа и воспроизводит его при повторе с тем же ключом и телом, так что дубликат вообще не создаётся; `AjaxResult.isIdempotentReplay()` отличает воспроизведение от свежей записи. Ответ сохраняется **только при успехе**, поэтому это дополняет `retryOnNetworkError: false`, а не заменяет его. См. [Call REST API v3 → Idempotency-Key](/docs/actions/call-rest-api-ver3/#idempotency-key).

4. **Идемпотентность на уровне приложения.** В `restApi:v2`, где портал игнорирует заголовок, добавьте собственную защиту от повторов (ключ дедупликации или уникальное бизнес-поле, проверяемое перед вставкой), чтобы дублирующий вызов не имел последствий, даже если повтор проскочит.

## Рекомендации по использованию

Конфигурации для разных сценариев:

```ts
import { ParamsFactory } from '@bitrix24/b24jssdk'

// const $b24 = ...

// Default parameters
$b24.setRestrictionManagerParams( ParamsFactory.getDefault() )

// Batch processing
$b24.setRestrictionManagerParams( ParamsFactory.getBatchProcessing() )

// Real-time
$b24.setRestrictionManagerParams( ParamsFactory.getRealtime() )

// By tariff plan
$b24.setRestrictionManagerParams( ParamsFactory.fromTariffPlan('enterprise') )

// Dynamic configuration change
$b24.setRestrictionManagerParams({
  ...ParamsFactory.getDefault(),
  rateLimit: {
    burstLimit: 30,  // Temporary reduction in case of problems
    drainRate: 1,
    adaptiveEnabled: true
  }
})
```
