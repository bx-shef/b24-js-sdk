## Обзор

SDK предоставляет пять примитивов для работы с REST API Битрикс24, и все они вызываются через `b24.actions.v{2,3}.<primitive>.make(options)`. Они похожи, но сильно различаются по стоимости. Неверный выбор — самая частая причина медленных приложений и обращений вроде «почему мой дашборд заваливает очередь?», поэтому эта страница нужна, чтобы принять решение за 30 секунд.

Выбор определяют три оси:

1. **Один вызов или несколько?** Один метод REST или сразу несколько.
2. **Ограниченный объём или нет?** Известно ли заранее, что результатов не больше 50, или их может быть 50 000?
3. **Всё сразу или потоком?** Нужны ли все записи в памяти для агрегации или их можно обрабатывать по мере поступления?

::caution{title="⚠️ Не используйте устаревшие сокращения"}
Сокращения уровня экземпляра в `AbstractB24` (`b24.callMethod()`, `b24.callBatch()`, `b24.callListMethod()`, `b24.fetchListMethod()`, `b24.callBatchByChunk()`) **удалены в 3.0.0** — они не учитывали разделение версий API, поэтому нельзя было указать, какой протокол имеется в виду. Вызывайте действие явно: `b24.actions.v2.call.make({…})` / `b24.actions.v3.batch.make({…})` и т. д. Как переписать код, включая случай, который не является простой заменой, см. в [руководстве по миграции](/docs/getting-started/migration/v3/).
::

## Матрица решений

| Ваша ситуация | Что использовать |
|---|---|
| Один метод, одна запись (`crm.deal.get`, `tasks.task.get`) | [`Call`](/docs/actions/call/) |
| Один списочный метод, до нескольких тысяч записей, нужен полный массив в памяти | [`CallList`](/docs/actions/call-list/) |
| Один списочный метод, десятки тысяч записей, обработка порциями (выгрузка в CSV, ETL) | [`FetchList`](/docs/actions/fetch-list/) |
| Несколько **разных** методов, которые нужно выполнить за одно обращение (загрузка плитки дашборда) | [`Batch`](/docs/actions/batch/) |
| Много вызовов одной формы (массовое создание, обновление или удаление более 50 элементов) | [`BatchByChunk`](/docs/actions/batch-by-chunk/) |
| Тысячи вызовов, которые можно выполнить в фоне на портале (v3, если позволяет тариф) | [`DeferredBatch`](/docs/actions/deferred-batch/) |

Затем выберите версию API: для любого метода, [доступного в v3](https://apidocs.bitrix24.com/api-reference/rest-v3/index.html), предпочитайте **v3** (лучше фильтрация, больше страницы, оптимизация на стороне сервера), а для всего остального — **v2**. `Call.make()` в v2 даже выводит предупреждение, если вы вызываете метод, подходящий для v3, — это сигнал к миграции.

## Компромиссы по методам

### `Call.make()`

**Используйте, когда** нужна ровно одна запись или одна серверная операция (`update`, `add`, `delete`).

**Избегайте, когда** вы оборачиваете его в цикл `for` с `await` — это сигнал перейти на `Batch` или `BatchByChunk`. Цикл из N вызовов `Call.make()` — это N обращений; `Batch` сворачивает до 50 из них в одно. `BatchByChunk` сворачивает любое число в `ceil(N / 50)` обращений.

### `CallList.make()`

**Используйте, когда** набор результатов достаточно мал, чтобы держать его в памяти, и вы будете делать с ним что-то сквозное (сортировка, группировка, агрегация, удаление дубликатов, передача в библиотеку графиков).

**Избегайте, когда** нужен лишь небольшой срез — передайте `select` и `filter`, чтобы сузить результат, вместо получения всего. Метод всегда получает каждую страницу, подходящую под ваш фильтр; запрос «дай первые 10» без фильтра расточителен.

### `FetchList.make()`

**Используйте, когда** результат не ограничен (или может быть таким) и записи можно обрабатывать, как только они пришли: выгружать в CSV, помещать в очередь, записывать в базу данных, отправлять по WebSocket.

**Избегайте, когда** нужна агрегация по записям, требующая весь набор в памяти, — `CallList` проще. Генератор отдаёт порции по `50` (v2) или по `options.limit` с учётом ограничения метода (v3 — ограничение задаётся методом, а не глобальным `1000`); ваш код ниже по потоку должен обработать каждую порцию до отправки следующего запроса, поэтому тяжёлая синхронная работа между порциями замедляет весь обход.

### `CallTail.make()` / `FetchTail.make()` (только v3)

**Используйте, когда** метод v3 публикует нативное действие `tail` (keyset-курсор) — например, `main.eventlog.tail`. В отличие от `CallList` / `FetchList`, которые *эмулируют* курсор, внедряя условие `[idField, '>', n]` в `filter`, они управляют нативным параметром сервера `cursor: { field, value, order, limit }`. `CallTail` возвращает один массив; `FetchTail` — асинхронный генератор.

**Избегайте, когда** метод предоставляет только `list` (тогда используйте `CallList` / `FetchList`). Подводные камни: поле курсора **не должно** встречаться в `filter` (сервер его отклоняет), оно автоматически добавляется в `select`, а `order: 'DESC'` требует явного `initialValue`.

### `Aggregate.make()` (только v3)

**Используйте, когда** нужны итоги на стороне сервера (`sum` / `avg` / `min` / `max` / `count` / `countDistinct`) для метода v3, предоставляющего действие `*.aggregate`, вместо получения всех строк и свёртки в памяти. Передайте `select` (список полей по функциям или словарь `{ field: alias }`) и необязательный `filter`; результат — корзины, ключами которых служат функция, а затем поле; псевдоним, если вы его передаёте, называет столбец внутри запроса портала и в ответе никогда не появляется. Значения приходят **строками**, а для `sum` или `avg` по строкам, которым ничего не соответствует, — как `null`.

Действие помечено **`@experimental`** — не потому, что контракт неясен (он измерен), а потому, что в поставке нет ничего, что его использует; см. доступность ниже.

**Каждое агрегируемое поле должно быть доступно для фильтрации в сущности**, а это не то же самое, что быть доступным для выбора. Спросите [`<entity>.field.list`](/docs/actions/discovering-entity-fields/): у каждого поля есть собственный флаг `filterable`, и агрегировать можно только поля, где он равен `true`{lang="ts-type"}. Это куда строже, чем кажется: в `tasks.task` для фильтрации доступно ровно **одно** поле из девяноста пяти, тогда как для сортировки — девятнадцать. Поле, доступное для выбора, но не для фильтрации, отвечает **мягкой** ошибкой `BITRIX_REST_V3_EXCEPTION_VALIDATION_REQUESTVALIDATIONEXCEPTION` с названием этого поля в `validation[].field` — ориентируйтесь на код и поле, а не на сообщение, которое локализуется.

**Избегайте, когда** у метода нет endpoint `*.aggregate` — **ни один поставляемый модуль его не публикует** ни на одном из четырёх проверенных порталов. Ожидание релиза не обязательно поможет: серверный механизм (`AggregateOrmActionTrait`) уже поставляется и работает, поэтому не хватает модуля, который его подключит, — по одному модулю за раз. Используйте `CallList` и свёртку на клиенте, а у своего портала спросите одним вызовом — `rest.documentation.openapi`, затем найдите пути, оканчивающиеся на `.aggregate`.

### `Batch.make()`

**Используйте, когда** одно действие пользователя зависит от данных из нескольких разных методов. Типичный пример — плитка дашборда, которой нужны профиль пользователя, число его открытых сделок и закреплённые задачи: три разных метода, одно обращение.

**Избегайте, когда** один и тот же метод повторяется 50 и более раз. Именно для этого нужен `BatchByChunk`, а `Batch` отклонит больше 50 команд. Также избегайте, когда нужны именованные ключи результата *и* больше 50 вызовов — `BatchByChunk` намеренно принимает только массив кортежей или массив объектов (именованные команды ломаются на границах порций).

### `BatchByChunk.make()`

**Используйте, когда** у вас произвольное число команд одной формы — массовые миграции, массовое `create` / `update` / `delete`, выгрузка деталей по id для тысяч связанных записей.

**Избегайте, когда** у вас лишь несколько вызовов — `Batch` проще и даёт именованные результаты. Также избегайте, когда нужно транзакционное поведение — `BatchByChunk` **не** атомарен. Если порция 7 из 30 завершилась ошибкой, порции 1–6 уже применены; порции 8–30 могут выполниться или нет в зависимости от `isHaltOnError`.

### `DeferredBatch.make()` (`restApi:v3`)

**Используйте, когда** у вас тысячи команд и можно подождать: портал принимает их все одним вызовом, выполняет как фоновое задание, а SDK возвращает декодированные строки, сообщая о ходе выполнения через `onStatus`. Один запрос на запуск вместо одного на каждые 50 команд.

**Избегайте, когда** на тарифе портала нет отложенных пакетов (`FEATURE_NOT_AVAILABLE_ON_CURRENT_PLAN`) — используйте `BatchByChunk` — или когда результат нужен в том же запросе, а команд не больше 50 — используйте `Batch`.

## Ограничения в одной таблице

| Метод | Макс. вызовов | Макс. страница | Возвращает | Выбрасывает исключение на первой ошибке? |
|---|---|---|---|---|
| `Call.make()` | 1 | н/д | `AjaxResult<T>` | Нет (проверьте `isSuccess`) |
| `CallList.make()` | не ограничено (постранично) | 50 (v2) / по методу (v3) | `Result<T[]>` | Нет |
| `FetchList.make()` | не ограничено (потоком) | 50 (v2) / по методу (v3) | `AsyncGenerator<T[]>` | Да — `SdkError` |
| `Batch.make()` | 50 | н/д | `CallBatchResult<T>` | Настраивается через `isHaltOnError` |
| `BatchByChunk.make()` | не ограничено (порциями по 50) | н/д | `Result<T[]>` | Настраивается через `isHaltOnError` |
| `DeferredBatch.make()` (v3) | тысячи в одном задании (измерено 5000) | н/д | `Result<T[]>` | Нет (проверьте `isSuccess`); выбрасывает только при неверно сформированных `calls` |

## Типичные антипаттерны

- **`b24.callMethod()` / `b24.callBatch()` / `b24.callListMethod()` / `b24.fetchListMethod()` / `b24.callBatchByChunk()`.** Удалены в 3.0.0. Используйте соответствующий `b24.actions.v{2,3}.<primitive>.make({…})` — соответствие и три отличия `callListMethod` от `callList.make` описаны в [руководстве по миграции](/docs/getting-started/migration/v3/).
- **`for (const id of ids) await b24.actions.v2.call.make(...)`.** N идентификаторов — это N обращений. Используйте `actions.v2.batch.make`, если `ids.length ≤ 50`, иначе `actions.v2.batchByChunk.make`.
- **`actions.v2.callList.make → actions.v2.callList.make → actions.v2.callList.make` для связанных сущностей.** Это причина большинства медленных дашбордов. Получите родительский список один раз (`actions.v2.callList.make` или `actions.v2.fetchList.make`), а затем загружайте связанные записи одним `actions.v2.batch.make` на каждые 50 идентификаторов.
- **Пользовательский `order` в `actions.v{2,3}.callList.make` / `actions.v{2,3}.fetchList.make`.** Постраничная выборка по курсору требует `order: { idKey: 'ASC' }`. Любой переданный пользователем `order` удаляется с предупреждением во время выполнения (см. [Ограничения](/docs/actions/fetch-list/#ограничения)). Чтобы сузить срез, используйте `filter`.
- **`actions.v{2,3}.batch.make` с именованными командами для более чем 50 элементов.** Либо разбейте вручную на несколько вызовов `batch.make`, либо перейдите на `actions.v{2,3}.batchByChunk.make` и примите упорядоченные результаты.
- **Смешивание методов только v2 и методов v3 в одном вызове `actions.v3.batch.make`.** SDK не проверяет методы заранее — каждая команда уходит на endpoint пакета v3, сервер отклоняет не-v3 метод, а пакет v3 прерывается на первой ошибке. Разделите пакет по версиям API или используйте `actions.v2.batch.make`.
