## Обзор

`CallTailV3.make()`{lang="ts-type"} обходит **tail**-метод `restApi:v3` — метод, который листает страницы по собственному keyset-курсору сервера, — и возвращает все записи одним массивом.

::caution
**Прежде чем использовать его, убедитесь, что ваш метод публикует tail-endpoint.** Это отдельный метод, не совпадающий со списочным аналогом, и он есть у немногих модулей: из десяти правдоподобных кандидатов на облачном портале в сентябре 2026 года ответил только `main.eventlog.tail`, остальные вернули `METHODNOTFOUNDEXCEPTION`.

Спросите портал, а не полагайтесь на эту выборку. `rest.documentation.openapi` возвращает все публикуемые им методы v3 с ключом по пути:

```ts
const doc = await $b24.actions.v2.call.make<{ paths: Record<string, unknown> }>({
  method: 'rest.documentation.openapi',
  params: {}
})

const tails = Object.keys(doc.getData()?.result?.paths ?? {})
  .filter(path => path.endsWith('.tail'))
```

См. [Обнаружение методов v3](/docs/actions/discovering-v3-methods/), чтобы узнать, что ещё содержит этот документ.

Для всех остальных случаев используйте [`CallList`{lang="ts-type"}](/docs/actions/call-list/), который приходит к тому же результату, эмулируя курсор на обычном списочном методе.
::

```ts
// Базовое использование
const response = await $b24.actions.v3.callTail.make({
  method: 'main.eventlog.tail',
  params: {
    select: ['id', 'auditTypeId']
  },
  cursorField: 'id',
  customKeyForResult: 'items'
})
```

### Чем он отличается от CallList

Два обходчика приходят в одно место разными путями, и эта разница определяет, что может содержать `filter`.

| | `callList` / `fetchList` | `callTail` / `fetchTail` |
|---|---|---|
| Постраничная выборка | **Эмулируется** — дописывает `[cursorIdKey, '>', cursor]`{lang="ts-type"} в ваш `filter` | **Нативная** — отправляет `cursor: { field, value, order, limit }`{lang="ts-type"}, `filter` передаётся без изменений |
| `order` | Зарезервирован обходчиком | Ваш, через `order: 'ASC' \| 'DESC'`{lang="ts-type"} |
| Форма `filter` | Только массив, потому что обходчику нужно его расширять | Массив **или** голая логическая группа |
| Работает с | Любым списочным методом | Только с методом, который реализует `tail` |

Поскольку списочные обходчики должны дописывать условие в ваш фильтр, они принимают только форму массива. Tail-обходчики ничего не добавляют, поэтому голая группа `FilterV3.or(...)`{lang="ts-type"} здесь является допустимым фильтром целиком.

### Когда использовать CallTailV3.make()

1. **Метод публикует endpoint `tail`**, и вам нужен собственный курсор сервера, а не эмулированный.
2. **Небольшие и средние объёмы данных**, которые целиком помещаются в памяти. Для большой выгрузки используйте [`FetchTail`{lang="ts-type"}](/docs/actions/fetch-tail/), который отдаёт данные постранично.

## Сигнатура метода

```ts-type
make<T = unknown>(
  options: ActionCallTailV3
): Promise<Result<T[]>>
```

### Параметры

| Параметр | Тип | Обязательный | Описание |
|----|----|----|----|
| **`method`** | `string`{lang="ts-type"} | Да | Tail-метод `restApi:v3`, например `main.eventlog.tail`. Указание метода `.list` не работает — см. [Если указать списочный метод](#если-указать-списочный-метод). |
| **`params`** | `Omit<TypeCallParamsV3, 'pagination' \| 'order' \| 'cursor' \| 'filter'> & { filter?: TypeFilterV3 \| FilterV3Group }`{lang="ts-type"} | Нет | Параметры запроса. `pagination`, `order` и `cursor` зарезервированы — курсором управляет обходчик, а направление берёт из `order` ниже. `filter` принимает форму массива `restApi:v3` или голую логическую группу. |
| **`cursorField`** | `string`{lang="ts-type"} | Нет | Поле, по которому сервер листает страницы. По умолчанию `'id'`. Оно должно быть **уникальным, полностью упорядоченным и скалярным** — см. [Выбор поля курсора](#выбор-поля-курсора). Оно также должно читаться в ответе: к явному `select` оно добавляется автоматически, а если `select` не указан и `cursorField` не по умолчанию, выводится предупреждение. |
| **`order`** | `'ASC' \| 'DESC'`{lang="ts-type"} | Нет | Направление обхода. По умолчанию `'ASC'`; строчные буквы тоже принимаются. `'DESC'` требует `initialValue` — см. ниже. |
| **`initialValue`** | `number \| string`{lang="ts-type"} | Нет | Значение курсора, с которого начинается первая страница. По умолчанию `0`, что подходит для числового поля по возрастанию. **Обязательно для `'DESC'`** — это SDK проверяет. Нужно также для любого нечислового поля, и там SDK *не* проверяет: значение по умолчанию `0` — число и будет отправлено как есть. |
| **`customKeyForResult`** | `string`{lang="ts-type"} | Нет | Ключ, под которым строки лежат в конверте ответа. По умолчанию `'items'`. |
| **`requestId`** | `string`{lang="ts-type"} | Нет | Идентификатор для трассировки, передаётся как `bx24_request_id`. Ничего не дедуплицирует. |
| **`limit`** | `number`{lang="ts-type"} | Нет | Строк на страницу. По умолчанию `50`. **Это запрос, а не гарантия** — каждый метод применяет собственный максимум, и короткая страница не означает конец данных. |
| **`maxPages`** | `number`{lang="ts-type"} | Нет | Верхняя граница числа прочитанных страниц. По умолчанию `10000`; должно быть положительным целым числом, иначе при вызове возникает `JSSDK_ACTION_INVALID_MAX_PAGES`. Достижение границы не отбрасывает прочитанное: строки возвращаются вместе с `JSSDK_ACTION_MAX_PAGES_EXCEEDED`, поэтому проверяйте `isSuccess`. |
| **`signal`** | `AbortSignal`{lang="ts-type"} | Нет | Отменяет обход, проверяется перед каждым запросом. Уже прочитанные страницы возвращаются вместе с `JSSDK_ACTION_ABORTED`. |
| **`progress`** | `(p: { pages: number, rows: number }) => void`{lang="ts-type"} | Нет | Вызывается после каждой страницы с накопленными счётчиками. Это счётчики, а не процент: keyset-выборка не запрашивает общее число. |

### Возвращаемое значение

`Promise<Result<T[]>>`{lang="ts-type"} — разрешается в [`Result<T[]>`{lang="ts-type"}](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/result.ts) со всеми прочитанными строками.

- `.getData(): T[] | null | undefined`{lang="ts-type"} — строки. По типу значение может быть пустым, поэтому в примерах ниже используется `?.length ?? 0`; завершённый обход всегда задаёт массив, пусть и пустой.
- `.isSuccess: boolean`{lang="ts-type"} — `false`, если достигнута граница или портал вернул мягкую ошибку посреди обхода; уже прочитанные строки при этом остаются. Не каждый сбой приходит таким образом — см. [Обработка ошибок](#обработка-ошибок).
- `.getErrorMessages(): string[]`{lang="ts-type"} — сообщения.

## Ключевые понятия

### Выбор поля курсора

Обход запрашивает строки строго после последнего увиденного значения, поэтому поле должно само задавать весь порядок. Три требования:

- **Уникальность.** Условие — строго «больше», поэтому строки, у которых то же значение, что и у последней строки, на границе страниц никогда не запрашиваются — это следует из условия, а не из измерения. `id` — безопасное значение по умолчанию не случайно.
- **Скалярность.** Число или строка. Обход читает значение прямо из ответа, поэтому поле с объектом или массивом не может служить курсором.
- **Читаемость.** Значение должно приходить в ответе, иначе продвигаться не по чему. SDK сам добавляет поле к явному `select`; если `select` нет, а поле не по умолчанию, выводится предупреждение, потому что SDK не знает набор полей сервера по умолчанию.

::caution
**Ошибка здесь молча усекает результат.** Ни одно из трёх условий не вызывает ошибку. Поле курсора, которого нет в ответе или которое не скалярное, считается *отсутствием курсора*: обход останавливается на этом месте и завершается **успешно** с уже полученными страницами. Неуникальное поле ещё хуже — оно теряет отдельные строки на границах страниц, и ничто не отмечает пропуск.

Единственный сигнал — запись уровня `warning` в журнале, и только когда страница была полной. Поэтому если обход возвращает подозрительно круглое число строк — например, ровно одну страницу, — проверьте `cursorField`, прежде чем верить результату.
::

Для нечислового поля передайте также `initialValue`: значение по умолчанию — число `0`, и SDK этого не проверяет.

### Поле курсора не должно встречаться в `filter`

Сервер упорядочивает и листает страницы по этому полю и отклоняет фильтр по нему. Измерено на `main.eventlog.tail`:

```json
{ "error": { "code": "BITRIX_REST_V3_EXCEPTION_INVALIDFILTEREXCEPTION",
             "message": "Cursor field id cannot be used…" } }
```

SDK предупреждает до запроса, а не заставляет вас узнавать об этом от портала:

```text
callTail.make: the cursor field "id" must not appear in `filter` — the server
orders and pages by it and will reject a filter on the same field
(INVALIDFILTEREXCEPTION). Remove it from `filter`.
```

Проверка заходит внутрь логических групп, поэтому поле, спрятанное внутри `FilterV3.or(...)`{lang="ts-type"}, тоже находится.

### Поле курсора добавляется в `select`

Обход продвигается, читая `cursorField` из последней строки, поэтому поле должно приходить в ответе. Если вы передаёте `select`, SDK добавляет поле курсора, когда его там нет. Если `select` не передан вообще, а поле курсора — не `id` по умолчанию, выводится предупреждение: SDK не знает набор полей сервера по умолчанию.

### `order: 'DESC'` требует `initialValue`

Обход по убыванию листает страницы по условию `field < value`, поэтому первое значение по умолчанию `0` не подошло бы ни под одну строку. SDK отклоняет такой вызов сразу, а не возвращает молча пустой результат:

```ts
// Throws JSSDK_CORE_B24_CALL_TAIL_DESC_REQUIRES_INITIAL_VALUE
await $b24.actions.v3.callTail.make({
  method: 'main.eventlog.tail',
  cursorField: 'id',
  order: 'DESC',
  customKeyForResult: 'items'
})
```

Передайте значение, которое сортируется после всех строк. Для числового поля это максимум типа; для поля даты и времени — временная метка ISO-8601 в далёком будущем **с указанием часового пояса** (защита от курсора, идущего назад, сравнивает только значения даты и времени с одинаковым поясом, поэтому несовпадение тихо отключает защиту); для любой другой строки — значение, которое сортируется последним.

```ts
const response = await $b24.actions.v3.callTail.make({
  method: 'main.eventlog.tail',
  cursorField: 'id',
  order: 'DESC',
  initialValue: Number.MAX_SAFE_INTEGER,
  customKeyForResult: 'items'
})
```

## Обработка ошибок

| Код | Когда |
|---|---|
| `JSSDK_ACTION_V3_TAIL_FILTER_INVALID` | `filter` был объектным диалектом `restApi:v2`, например `{ '>id': 100 }`{lang="ts-type"}. Отклоняется здесь, а не на один запрос позже, где портал сообщает об этом формулировкой, никогда не называющей диалект. |
| `JSSDK_CORE_B24_CALL_TAIL_DESC_REQUIRES_INITIAL_VALUE` | `order: 'DESC'`{lang="ts-type"} без `initialValue`. |
| `JSSDK_ACTION_CURSOR_STALLED` | Курсор вернулся равным только что отправленному — сервер отвечает той же страницей. При обходе tail обычные причины — `cursorField` не является полем, по которому сервер листает страницы, или его значения не уникальны, а также метод, который вообще не реализует `tail`. |
| `JSSDK_ACTION_CURSOR_WENT_BACKWARDS` | Курсор перешёл на значение, которое обход уже прошёл. При `order: 'DESC'`{lang="ts-type"} проверьте, что `initialValue` — самое новое значение, а не самое старое. |
| `JSSDK_ACTION_MAX_PAGES_EXCEEDED` | Достигнут предел числа страниц. Прочитанные строки возвращаются вместе с ошибкой — проверяйте `isSuccess`, не считайте возвращённый список полным. |
| `JSSDK_ACTION_INVALID_MAX_PAGES` | `maxPages` не было положительным целым числом. Возникает до любого запроса. |
| `JSSDK_ACTION_ABORTED` | Сработал `signal`. Обрабатывается как предел: прочитанное возвращается вместе с ошибкой. |

**Две из них возвращаются, пять отклоняются.** Только последние две — границы, которые задаёте вы, поэтому уже собранные строки верны и возвращаются вместе с ошибкой. Остальные четыре — отклонённый фильтр, отсутствующий `initialValue`, застрявший или идущий назад курсор — отклоняют промис, потому что результата, который стоило бы сохранять, нет. Поэтому одного `isSuccess` недостаточно:

```ts
try {
  const response = await $b24.actions.v3.callTail.make({
    method: 'main.eventlog.tail',
    cursorField: 'id',
    customKeyForResult: 'items'
  })

  // Reached the ceiling or was aborted: the rows are here and are correct.
  if (!response.isSuccess) {
    console.warn(response.getErrorMessages(), response.getData()?.length ?? 0)
  }
}
catch (error) {
  // Filter refused, a bad `maxPages`, DESC without `initialValue`, or the
  // cursor stopped advancing.
  console.error(error)
}
```

Мягкая ошибка портала посреди обхода тоже попадает в `Result`, а не выбрасывается, поэтому `isSuccess` охватывает и этот случай.

Полную таблицу см. в разделе [Коды ошибок и их обработка](/docs/actions/errors/).

### Если указать списочный метод

Списочный метод не реализует курсор, и — измерено на `main.eventlog.list` — портал **молча игнорирует параметр `cursor`**, а не отклоняет его. На этом методе неизвестный ключ верхнего уровня игнорировался так же, поэтому ничто в ответе не сообщает, что обход не листает страницы. Ведут ли себя так все списочные методы v3, не измерялось; достаточно одного такого, чтобы это имело значение, потому что симптом неотличим от работающего обхода, пока страницы не начнут повторяться.

До появления защиты курсора такой обход бесконечно повторял первую страницу. Теперь он останавливается:

```ts
// Throws JSSDK_ACTION_CURSOR_STALLED — main.eventlog.list has no tail
await $b24.actions.v3.callTail.make({
  method: 'main.eventlog.list',
  cursorField: 'id',
  customKeyForResult: 'items'
})
```

Если вы хотели обойти списочный метод, используйте [`CallList`{lang="ts-type"}](/docs/actions/call-list/).

## Примеры

### Чтение журнала событий, сначала самые старые

```ts
const response = await $b24.actions.v3.callTail.make<{ id: number }>({
  method: 'main.eventlog.tail',
  params: { select: ['id', 'auditTypeId'] },
  cursorField: 'id',
  customKeyForResult: 'items',
  limit: 100
})

if (!response.isSuccess) {
  console.warn(response.getErrorMessages())
}

console.log(`rows: ${response.getData()?.length ?? 0}`)
```

### Фильтрация голой логической группой

Списочные обходчики требуют форму массива, потому что расширяют её. Tail передаёт фильтр без изменений, поэтому группа сама по себе принимается:

```ts
import { FilterV3 } from '@bxshefby/b24jssdk'

const response = await $b24.actions.v3.callTail.make({
  method: 'main.eventlog.tail',
  params: {
    filter: FilterV3.or(
      ['auditTypeId', '=', 'MAIN_EVENTLOG'],
      ['auditTypeId', '=', 'MAIN_LOGIN']
    ),
    select: ['id', 'auditTypeId']
  },
  cursorField: 'id',
  customKeyForResult: 'items'
})
```

### Полный скрипт

```ts
import { B24Hook, SdkError } from '@bxshefby/b24jssdk'

const $b24 = B24Hook.fromWebhookUrl('https://your-portal.bitrix24.com/rest/1/SECRET')

try {
  const response = await $b24.actions.v3.callTail.make<{ id: number }>({
    method: 'main.eventlog.tail',
    params: { select: ['id', 'auditTypeId'] },
    cursorField: 'id',
    customKeyForResult: 'items'
  })

  if (!response.isSuccess) {
    console.warn(response.getErrorMessages())
  }

  console.log(`rows: ${response.getData()?.length ?? 0}`)
}
catch (error) {
  if (error instanceof SdkError) {
    console.error(`the walk could not run: ${error.code}`)
  }
  throw error
}
```

Пустой результат — обычный ответ, а не сбой: `isSuccess` равен `true`, а массив пуст. Учтите, что неверный `customKeyForResult` выглядит точно так же — обходчик считает ключ, который не нашёл, «отсутствием данных», — поэтому при молча пустом обходе первым делом проверьте ключ.

## Альтернативы и рекомендации

- [`FetchTail`{lang="ts-type"}](/docs/actions/fetch-tail/) — тот же обход в виде асинхронного генератора, для наборов данных, слишком больших для хранения целиком.
- [`CallList`{lang="ts-type"}](/docs/actions/call-list/) — для обычных списочных методов, то есть почти для всех.
- [Фильтрация](/docs/actions/filtering/) — диалекты фильтра и то, какой обходчик какой принимает.
