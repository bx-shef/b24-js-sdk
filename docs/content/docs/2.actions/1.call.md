## Обзор

::::rest-api-version-only
#rest-api-ver2
Для вызова методов REST API версии 2 используйте `CallV2.make()`{lang="ts-type"}.

#rest-api-ver3
Для вызова методов REST API версии 3 используйте `CallV3.make()`{lang="ts-type"}.
::::

Метод возвращает `Promise` с объектом `AjaxResult`{lang="ts-type"}, который содержит данные ответа, статус и методы работы с ошибками.

::::rest-api-version-only
#rest-api-ver2
```ts
// Базовое использование
import { EnumCrmEntityTypeId } from '@bxshefby/b24jssdk'

const response = await $b24.actions.v2.call.make({
  method: 'crm.item.get',
  params: {
    entityTypeId: EnumCrmEntityTypeId.contact,
    id: 123
  },
  requestId: 'unique-request-id'
})
```

#rest-api-ver3
```ts
// Базовое использование
const response = await $b24.actions.v3.call.make({
  method: 'tasks.task.get',
  params: {
    id: 123
  },
  requestId: 'unique-request-id'
})
```

### Параметры

Объект `options` содержит следующие свойства:

::::rest-api-version-only
#rest-api-ver2
| Параметр | Тип | Обязательный | Описание |
|----|----|----|----|
| **`method`** | `string`{lang="ts-type"} | Да | Название метода REST API (например, `crm.item.get`, `tasks.task.get`). |
| **`params`** | `TypeCallParams`{lang="ts-type"} | Нет | Объект с параметрами, передаваемыми в метод REST API. |
| **`requestId`** | `string`{lang="ts-type"} | Нет | Уникальный идентификатор запроса для отслеживания и отладки — передаётся в query-параметре `bx24_request_id`. Он ничего не дедуплицирует; для этого есть `idempotencyKey` (restApi:v3). |

#rest-api-ver3
| Параметр | Тип | Обязательный | Описание |
|----|----|----|----|
| **`method`** | `string`{lang="ts-type"} | Да | Название метода REST API (например, `tasks.task.get`, `tasks.task.add`). |
| **`params`** | `TypeCallParams`{lang="ts-type"} | Нет | Объект с параметрами, передаваемыми в метод REST API. |
| **`requestId`** | `string`{lang="ts-type"} | Нет | Уникальный идентификатор запроса для отслеживания и отладки — передаётся в query-параметре `bx24_request_id`. Он ничего не дедуплицирует; для этого есть `idempotencyKey` (restApi:v3). |

### Возвращаемое значение

`Promise<AjaxResult<T>>`{lang="ts-type"} — промис, который разрешается в объект [`AjaxResult`{lang="ts-type"}](https://github.com/bx-shef/b24-js-sdk/blob/main/packages/jssdk/src/core/http/ajax-result.ts).

Этот объект предоставляет:

::::rest-api-version-only
#rest-api-ver2
- `.getData(): SuccessPayload<T> | undefined`{lang="ts-type"} — возвращает конверт успешного ответа `{ result: T, time?: PayloadTime }` или `undefined`, если запрос завершился ошибкой. Сначала проверьте `.isSuccess`. Поле `time` необязательное: оно есть не в каждом ответе, и SDK его не выдумывает.
- `.isSuccess: boolean`{lang="ts-type"} — признак успешного выполнения запроса.
- `.getErrorMessages(): string[]`{lang="ts-type"} — массив сообщений об ошибках.

#rest-api-ver3
- `.getData(): SuccessPayload<T> | undefined`{lang="ts-type"} — возвращает конверт успешного ответа `{ result: T, time?: PayloadTime }` или `undefined`, если запрос завершился ошибкой. Сначала проверьте `.isSuccess`. Поле `time` необязательное: оно есть не в каждом ответе, и SDK его не выдумывает.
- `.isSuccess: boolean`{lang="ts-type"} — признак успешного выполнения запроса.

  Результат, который портал строит как словарь по ключам, может прийти как **пустой массив**,
  если записей нет: `main.like.reactions` отвечает `{"like":1}` и `[]`,
  когда данных нет (измерено в #570). SDK передаёт значение без изменений,
  поэтому типизируйте `T` так, чтобы допускались оба варианта, либо нормализуйте через
  `Array.isArray(value) ? {} : value`.
- `.getErrorMessages(): string[]`{lang="ts-type"} — массив сообщений об ошибках.
::::

## Обработка ошибок

::::rest-api-version-only
#rest-api-ver2
Всегда проверяйте результат через `isSuccess` и обрабатывайте ошибки:

<!-- @check-ignore: top-level return in error-handling illustration -->
```ts
const response = await $b24.actions.v2.call.make({
  method: 'some.method',
  params: { /* some_params */ },
  requestId: 'unique-request-id'
})

if (!response.isSuccess) {
  // Обработка ошибки
  console.error(new Error(`Error: ${response.getErrorMessages().join('; ')}`))
  return
}

// Работа с успешным результатом
const data = response.getData()?.result
```

#rest-api-ver3
SDK не хранит на клиенте список методов v3: `CallV3.make()`{lang="ts-type"} отправляет любой переданный вами метод на endpoint v3, а решение принимает сервер. Если метод не относится к v3, сервер отвечает `METHODNOTFOUNDEXCEPTION` как **мягкой ошибкой** (`response.isSuccess === false`{lang="ts-type"}, сообщение — в `getErrorMessages()`{lang="ts-type"}); SDK заранее исключение не выбрасывает. Для устаревших методов используйте `CallV2.make()`{lang="ts-type"}, а что есть в v3, смотрите на [`apidocs.bitrix24.com`](https://apidocs.bitrix24.com/api-reference/rest-v3/index.html) (или через `rest.documentation.openapi` самого портала).

Для успешных запросов всегда проверяйте `isSuccess` и обрабатывайте ошибки:

<!-- @check-ignore: top-level return in error-handling illustration; `some.method` is a placeholder, not a portal method -->
```ts
const response = await $b24.actions.v3.call.make({
  method: 'some.method',
  params: { /* some_params */ },
  requestId: 'unique-request-id'
})

if (!response.isSuccess) {
  // Обработка ошибки
  console.error(new Error(`Error: ${response.getErrorMessages().join('; ')}`))
  return
}

// Работа с успешным результатом
const data = response.getData()?.result
```

## Что возвращает запись

**Форма ответа зависит от модуля.** Измерены три модуля, и ни два из них не совпадают:

| модуль | `add` | `update` |
|----|----|----|
| стандартные ORM-трейты | `{ result: { id: 22 } }`{lang="ts-type"} | `{ result: true }`{lang="ts-type"} |
| `tasks.task` | `{ result: { item: { … } } }`{lang="ts-type"} | `{ result: { result: true } }`{lang="ts-type"} |
| `note.collection` | `{ result: { item: { … } } }`{lang="ts-type"} | `{ result: { item: { … } } }`{lang="ts-type"} |

Основания для каждой строки разные по природе, и это стоит знать, прежде чем
на них опираться. Первая строка — модуль, собранный специально для этих проверок без
собственного кода действий, поэтому он показывает поведение фреймворка по умолчанию, и
собственные типы ответов фреймворка говорят то же: `AddResponse` объявляет одно свойство,
`public int $id`, а `UpdateResponse` наследует `BooleanResponse`. Вторая строка
измерена здесь. Третья приведена так, как её наблюдал автор #465, и на этой сборке не
перемерена. Две последние строки — модули, объявляющие собственный ответ,
причём `tasks.task.update` вкладывает булево значение на уровень глубже, чем трейт.

Поэтому общего правила нет, есть только контракт конкретного метода, который нужно прочитать. Вызывающий код,
обращающийся к `result.id` после `add`, может получить идентификатор, объект или
`undefined`{lang="ts-type"} — смотрите, что документирует вызываемый вами метод, и
типизируйте вызов соответственно.

`*.delete` везде, где измерялось, отвечал `{ result: true }`{lang="ts-type"}, а `*.get` —
`{ result: { item: { … } } }`{lang="ts-type"}. В таблице выше показан весь
конверт, поэтому `getData()` после `add` через трейт
вернёт `{ id: 22 }`, а не само число `22`.

::warning
**Неверный тип отклоняется не всегда.** Измерено на коробочной сборке: `select`,
переданный строкой там, где объявлен массив, получил ответ HTTP 200, а число, переданное
там, где объявлена строка, было принято и сохранено. Строка, которую нельзя превратить в
число, *отклоняется* с ошибкой `BITRIX_REST_V3_EXCEPTION_INVALIDJSONEXCEPTION`. То есть
валидация неравномерная, но не отсутствует, и ошибка типа может проявиться позже в виде странных
данных, а не в момент вызова.
::

## Долгие запросы

::::rest-api-version-only
#rest-api-ver2
Тяжёлые неидемпотентные методы, такие как `crm.documentgenerator.document.add`,
регулярно превышают таймаут axios по умолчанию — 30 секунд. При таймауте SDK
по умолчанию повторяет запрос, из-за чего на сервере могут появиться **дубликаты
сущностей** (см. [issue #24](https://github.com/bitrix24/b24jssdk/issues/24)).

#rest-api-ver3
Неидемпотентные методы, которые создают или сохраняют данные, например
`tasks.task.add`, на загруженном портале могут превысить таймаут axios по умолчанию — 30 секунд.
При таймауте SDK по умолчанию повторяет запрос, из-за чего на сервере могут появиться
**дубликаты сущностей** (см. [issue #24](https://github.com/bitrix24/b24jssdk/issues/24)).
::::

Для любого метода, который создаёт или сохраняет данные, увеличьте таймаут axios
и отключите повторы при транспортных ошибках:

::::rest-api-version-only
#rest-api-ver2

```ts
// const $b24 = ...
$b24.getHttpClient(ApiVersion.v2).ajaxClient.defaults.timeout = 120_000
await $b24.setRestrictionManagerParams({
  ...ParamsFactory.getDefault(),
  retryOnNetworkError: false
})

await $b24.actions.v2.call.make({
  method: 'crm.documentgenerator.document.add',
  params: {/*…*/}
})
```

```ts
import { ApiVersion, ParamsFactory } from '@bxshefby/b24jssdk'

// const $b24 = ...
```

### Idempotency-Key

Настройки выше не дают SDK создать дубликат. `Idempotency-Key`
позволяет остановить дубликат **порталу**, и это закрывает случаи, которых SDK
не видит: ваш собственный код, другой процесс или пользователь, который выполнил одну и ту же операцию
дважды.

#### Четыре способа, как на самом деле появляется дубликат

| Что делает пользователь или система | Без ключа | С ключом |
| --- | --- | --- |
| Двойной клик по *Создать сделку* или нетерпеливое второе нажатие в медленной мобильной форме | Две сделки | Второй вызов воспроизводит первый ответ — тот же id |
| Запрос завершается по таймауту, SDK повторяет его, но портал уже записал элемент ([issue #24](https://github.com/bitrix24/b24jssdk/issues/24)) | Две записи, а вызывающий код видит только вторую | Одна запись; повтор воспроизводит её |
| Воркер очереди (BullMQ, cron, Lambda) падает после записи, но до отметки задания выполненным, и задание запускается снова | Две записи | Одна запись |
| Битрикс24 доставляет исходящее событие дважды (доставка событий — как минимум один раз), а ваш обработчик создаёт что-то на каждое событие | Две записи | Одна запись |
| Импорт из бухгалтерской системы, магазина или журнала телефонии перезапускают после частичного сбоя по строкам, которые уже загружены | Все уже загруженные строки ещё раз | Каждая строка один раз, сколько бы раз ни запускался импорт |

Первые два случая закрывают также `retryOnNetworkError: false` и увеличенный таймаут.
Последние три они не затрагивают вовсе: дубликат приходит от
*другого процесса* или *другого запуска*, который ничего не знает о политике повторов первого.
Именно этот пробел закрывает ключ.

#### Массовый импорт и повторная синхронизация

Здесь ключ окупается, потому что в импорте уже есть то,
что иначе трудно придумать: **собственный идентификатор исходной системы**.
У договора в бухгалтерской системе есть GUID, у заказа в магазине — номер заказа, у звонка — id звонка.
Этот идентификатор *и есть* ключ, поэтому повторный запуск
импорта не создаёт дубликатов, и вести учёт на вашей стороне не нужно:

```ts
declare const rows: Array<{ externalId: string, title: string }>
declare const responsibleId: number
// const $b24 = ...

for (const row of rows) {
  await $b24.actions.v3.call.make({
    method: 'tasks.task.add',
    // `creatorId` and `responsibleId` are required by tasks.task.add — a
    // fields object with only a title is refused by validation.
    params: { fields: { title: row.title, creatorId: responsibleId, responsibleId } },
    // The source system's id, prefixed by the operation. Re-run the import
    // tomorrow and every row that already loaded is replayed, not rewritten.
    idempotencyKey: `import-task-${row.externalId}`
  })
}
```

Это заменяет схему «чтение перед каждой записью»: найти строку
с внешним id и создавать, только если ничего не нашлось. Такая схема стоит одного
лишнего вызова на строку, требует пользовательского поля для поиска и всё равно подвержена гонке: два
пересекающихся запуска оба видят «нет» и оба создают. Ключ переносит
решение на портал, где оно принимается один раз.

Два ограничения определяют, можно ли этим пользоваться, и оба легко пропустить:

* **У `batch` нет ключа.** Поэтому массовая загрузка без дубликатов — это
  цикл одиночных вызовов, а не пакет: вы платите пропускной способностью за гарантию.
  Учитывайте это при планировании запуска и смотрите [Лимитеры](/docs/tools/limiters/).
* **Только методы `restApi:v3`.** Портал учитывает заголовок только по пути
  `/rest/api/`, поэтому запись должна существовать в v3 — см. ниже.

#### Что это покрывает сейчас

Endpoint v3 — не копия v2: он публикует собственные модули, и набор
того, что через него можно *создать*, пока невелик. На облачном портале,
измеренном 2026-11-26 (1389 методов, 25 модулей), создающих методов много:
`crm.deal.add`, `crm.lead.add`, `crm.contact.add`, `crm.company.add`, `tasks.task.add`,
`tasks.task.result.add`, `note.document.add`, `catalog.product.add`,
`humanresources.node.add` и другие. На замере 2026-09-05 (245 методов, 14 модулей)
CRM-сущностей в v3 не было совсем; на коробке по замеру 2026-09-05 (147 методов, 8 модулей)
их тоже не было (нового замера коробки нет).

**Наличие создания `crm.*` в v3 зависит от портала.** На облаке оно есть, на коробке — по замеру
сентября нет. Проверяйте `rest.documentation.openapi` своего портала, а не предполагайте.
Где CRM-запись идёт через `crm.*` в `restApi:v2` (классическая интеграционная запись:
бухгалтерская система создаёт контрагентов, магазин создаёт лиды, телефония создаёт записи
звонков), заголовок игнорируется. Транспорт v2 отбрасывает
ключ и пишет предупреждение в журнал, чтобы вы не считали, что защита есть.

Для таких записей остаётся тот способ, который эта возможность заменяет в других местах:
сохраните идентификатор исходной системы в поле сущности и проверяйте его
перед вставкой — именно так делает
[рецепт синхронизации с ERP](https://github.com/bx-shef/b24-js-sdk/blob/main/skills/b24jssdk-recipes/examples/04-erp-sync.ts).
Что публикует портал, не предполагайте, а спрашивайте через
`rest.documentation.openapi`.

#### Выбор ключа

В этом вся практика, и ошибка делает возможность бесполезной:

**Ключ должен идентифицировать операцию, а не попытку.** Две попытки
одной и той же бизнес-операции должны нести *один и тот же* ключ, иначе ничего не дедуплицируется.

Самая частая ошибка — `crypto.randomUUID()` в месте вызова.
Это работает при двойном клике внутри одного запущенного процесса и при собственном повторе
SDK — оба используют одну переменную. Но это не помогает при упавшем
воркере или повторно доставленном событии, потому что перезапущенный процесс создаёт новый
UUID и пишет вторую запись.

Два рабочих варианта:

```ts
interface QueueJob { orderId: number, idempotencyKey?: string }
declare const job: QueueJob
declare const jobs: { save: (job: QueueJob) => Promise<void> }

// A. Derive the key from the operation. Nothing to store: the same inputs
//    always produce the same key, in any process, after any restart.
const keyFromOperation = `deal-${job.orderId}-create`

// B. Mint a random key once, and persist it *before* the call, alongside the
//    job. A retry of that job reads the key back rather than making a new one.
job.idempotencyKey ??= crypto.randomUUID()
await jobs.save(job)
```

Вариант A обычно проще, и именно он нужен обработчику события: событие,
доставленное дважды, оба раза несёт один и тот же id события, поэтому
`` `deal-from-event-${event.id}` `` уже является правильным ключом.

Ещё два ограничения на саму строку: это должны быть 1–255 печатаемых ASCII-символов
(иначе SDK выбросит `JSSDK_HTTP_INVALID_IDEMPOTENCY_KEY` до отправки
запроса), и она должна быть уникальной для каждой *операции*, поскольку ключ, использованный для другой записи,
отклоняется, а не дедуплицируется. Добавляйте к ключам префикс операции, чтобы
`deal-42-create` и `deal-42-close` не пересекались.

#### Использование

```ts
// const $b24 = ...
declare const orderId: number
const idempotencyKey = `deal-${orderId}-create`

const response = await $b24.actions.v3.call.make<{ item: { id: number } }>({
  method: 'tasks.task.add',
  params: { fields: { title: 'Ship it', creatorId: 1, responsibleId: 1 } },
  idempotencyKey
})

if (response.isIdempotentReplay()) {
  // The portal had already executed this operation: nothing new was written,
  // and the body below is the stored response from the first time. Useful for
  // deciding whether to send the "task created" notification a second time.
}

// The key the portal echoed back — a confirmation for your log, not a
// discovery: you already know the key you sent.
console.log(response.getIdempotencyKey())

console.log(response.getData()?.result.item.id)
```

Портал хранит успешный ответ по ключу 24 часа. Повтор с **тем же ключом и тем же телом** возвращает сохранённый ответ
вместо повторного выполнения метода и помечает его
`Idempotent-Replayed: true` — это и читает `isIdempotentReplay()`. Тот же
ключ с **другим** телом отклоняется с HTTP 422
`BITRIX_REST_V3_EXCEPTION_IDEMPOTENCYKEYREUSEDEXCEPTION`.

Измерено на рабочем портале (issue #570):

* **«То же тело» означает совпадение байт в байт.** Портал хэширует необработанное тело запроса,
  поэтому тот же JSON с одним лишним пробелом — это *другое* тело, и вы получите 422.
  Собирайте вызов заново из тех же данных, а не из повторно сериализованной копии.
* **Сохраняется только успешный ответ (HTTP 200).** Неудачный вызов
  не воспроизводится: повтор с тем же ключом выполняется снова.
* **В OAuth-приложении SDK не помещает токен в тело.** Токен доступа
  меняется примерно раз в час, а ключ живёт 24 часа; токен в теле
  превратил бы повтор после обновления в 422. Поэтому вызов с
  `idempotencyKey` отправляет токен в заголовке `Authorization` — на сервере, где
  такой вызов только и может выполняться (см. ниже). Такой вызов не следует HTTP-редиректам, поскольку редирект
  унёс бы токен с собой: endpoint с редиректом завершается ошибкой
  `JSSDK_HTTP_REDIRECT_BLOCKED`, поэтому указывайте в SDK конечный URL. Вебхука
  это не касается: его секрет находится в URL.

Срок хранения 24 часа и область действия ключа — контракт портала.

::warning
**Недоступно в браузере** (измерено, [#573](https://github.com/bitrix24/b24jssdk/issues/573)).
CORS preflight портала разрешает только `origin, content-type, accept`, поэтому
браузер не отправит `Idempotency-Key`; заголовок `Idempotent-Replayed` он тоже не отдаёт,
а форм ключа в query или теле портал не принимает. Поэтому SDK
отказывается принимать `idempotencyKey` в браузере (`B24Frame` или клиентский `B24OAuth`)
с ошибкой `JSSDK_HTTP_IDEMPOTENCY_KEY_BROWSER` до отправки чего-либо. Выполняйте
идемпотентные записи на сервере.
::

Три момента, которые нужно знать, прежде чем на это полагаться:

* **SDK никогда не генерирует ключ.** Портал ограничивает дедупликацию связкой
  вебхук или приложение × пользователь × метод, поэтому ключ, созданный внутри одного процесса,
  ничего не значит для другого процесса, повторяющего ту же операцию. Только ваш код знает,
  к какой операции относится вызов, поэтому только ваш код может её назвать.
* **Ответ сохраняется только при успехе.** После ошибки повтор с тем же
  ключом выполняет метод снова. Ключ не заменяет
  `retryOnNetworkError: false` для долгой записи; это вторая линия защиты.
  Используйте оба средства для записи, которая вам важна.
* **Срок действия — 24 часа.** Дедупликация защищает повтор через минуты
  или часы, но не задание, воспроизведённое на следующей неделе. Для более длинного окна
  по-прежнему нужна ваша запись о том, что операция выполнена.
* **`restApi:v2` игнорирует заголовок.** Портал учитывает его только по пути
  `/rest/api/`, поэтому транспорт v2 отбрасывает ключ и пишет предупреждение в журнал, а не
  отправляет ключ, который, как вы бы считали, вас защищает.

Только одиночные вызовы: [`Batch`](/docs/actions/batch/)
не принимает ключ. Механизм называет одну операцию, а пакет — это много операций, и
воспроизводит ли ключ на пакете v3 весь пакет целиком, не измерялось, поэтому SDK
этого не предлагает, а не гадает.

Механизм принадлежит порталу, а не SDK; справочное описание — в
[Bitrix24 REST v3 → «Повторный вызов без дублей»](https://apidocs.bitrix24.ru/api-reference/rest-v3.html).

## Какой HTTP-адаптер используется

В **браузере** SDK просит axios использовать адаптер `fetch`. Если оставить выбор axios,
он перебирает `['xhr', 'http', 'fetch']` и берёт первый *поддерживаемый* вариант, поэтому
везде, где есть `XMLHttpRequest` — в окне, выделенном воркере, общем воркере, —
он выбирает **XHR** и до `fetch` не доходит. Это выбор по порядку в списке,
а не по достоинствам.

Вне браузера ничего не запрашивается, и решает axios: в Node нет
`XMLHttpRequest`, поэтому и так выбирается `http`, и он там подходит.

Указать адаптер можно самому при создании:

```ts
import { B24Hook } from '@bxshefby/b24jssdk'

const b24 = B24Hook.fromWebhookUrl(
  'https://your-portal.bitrix24.com/rest/1/SECRET',
  { httpOptions: { adapter: 'xhr' } }
)
```

Приложение во фрейме передаёт его в [`initializeB24Frame()`](/docs/entry-points/frame-initialize-b24-frame/), которая пересылает его без изменений, — а браузер как раз то место, где это важнее всего, потому что именно там изменился адаптер.

`httpOptions` объединяется с собственными настройками axios по умолчанию в SDK, поэтому любой
указанный вами ключ имеет приоритет — `adapter` просто тот, ради которого это сделано. Опция предоставляет узкий срез
`AxiosRequestConfig`{lang="ts-type"} (`TypeHttpOptions`{lang="ts-type"}), который проверяется при создании, а не только компилятором: ключи, нужные SDK, чтобы достучаться до портала, —
`baseURL`, `transformRequest`, `paramsSerializer` и `validateStatus` — в него не входят,
а ключ вне списка отбрасывается при создании с записью его имени в журнал. `headers` тоже не предлагается — тип его отвергает, — хотя
транспорт всё же объединяет заголовок, дошедший до него из нетипизированного кода, как и с #144. Эти настройки остаются доступны через
[`ajaxClient.defaults`](/docs/tools/core-http/#настройка-экземпляра-axios).

::warning
**Одно поведение меняется вместе с адаптером, и только на одном узком пути.** `maxRedirects`
читает `fetch` (как `redirect: 'manual'`), а XHR игнорирует его полностью. SDK
устанавливает его там, где токен доступа OAuth передаётся в строке запроса, чтобы этот токен
не ушёл по редиректу, — в браузере это **только пакет `restApi:v3` или
вызов `restApi:v3` с `idempotencyKey` на не-вебхук транспорте** (а также
скачивание файла результата `actions.v3.deferredBatch` на любом транспорте), но не обычный вызов, — если только вы не
задали `maxRedirects: 0` сами в `httpOptions`, что относит любой ответ со статусом 0 в ту же категорию. На `fetch` эта защита срабатывает там, где
раньше была бездействующей: развёртывание с редиректом получает непрозрачный ответ — статус 0,
пустое тело — вместо того, чтобы молча пройти переход с приложенными учётными данными.
Axios разрешает такой ответ, а не отклоняет его, поэтому SDK сам выбрасывает
`JSSDK_HTTP_REDIRECT_BLOCKED`; без этого отклонённый запрос выглядел бы
как пустой успех. Защита работает как задумано, но это изменение поведения,
а не отсутствие эффекта.
::
