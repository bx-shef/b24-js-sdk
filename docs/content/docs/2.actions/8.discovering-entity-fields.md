## Обзор

Большинство сущностей `restApi:v3` публикуют пару методов метаданных:

- `<entity>.field.list` — все поля сущности в виде списка дескрипторов;
- `<entity>.field.get` — одно поле по `name`.

Это значительная часть поверхности v3: **458 из 1389 методов**, которые публикует измеренный на 2026-11-26
облачный портал, относятся к этому семейству — 33%. Оно есть у большинства модулей: `crm` 208,
`catalog` 66, `biconnector` 28, `tasks` 26, `rest` 22, `main` 20, `disk` 14, `note` 12,
`vibecodeconnector` 10, `bizprocdesigner` 9, `sign` 9, `humanresources` 8, `mail` 6 и меньше у остальных.
На замере 2026-09-05 (245 методов, 14 модулей) их было 91.

::note
[Обнаружение методов v3](/docs/actions/discovering-v3-methods/) отвечает на вопрос
**какие методы существуют** на портале — одним документом, который получают один раз и кэшируют.
Эта страница отвечает на вопрос **какие поля есть у этой сущности** — небольшой и дешёвый вызов, который можно делать
для каждой сущности и который несёт также флаги по полям, которых нет в документе OpenAPI.
::

## Вызов через SDK

Обычный вызов v3 — без специального помощника:

```ts
const response = await $b24.actions.v3.call.make<{
  items: Array<{ name: string, type: string, sortable: boolean, filterable: boolean }>
}>({ method: 'tasks.task.field.list' })

const fields = response.getData()?.result?.items ?? []
const sortable = fields.filter(field => field.sortable).map(field => field.name)
```

Строки приходят в **`result.items`**. `<entity>.field.get` вместо этого отвечает одним
дескриптором в **`result.item`**:

```ts
const response = await $b24.actions.v3.call.make<{
  item: { name: string, type: string, sortable: boolean }
}>({ method: 'tasks.task.field.get', params: { name: 'title' } })
```

Оба принимают необязательный `select`, который сужает ключи **дескриптора**: передайте
`select: ['name', 'sortable']`, и каждая строка вернётся только с этими двумя ключами.

## Что содержит дескриптор

| Ключ | Что означает |
| --- | --- |
| `name` | Название поля для использования в `select`, `filter` и `order`. |
| `type` | `string`{lang="ts-type"}, `integer`{lang="ts-type"}, `datetime`{lang="ts-type"}, … |
| `title` / `description` | Человекочитаемые подписи. `description`{lang="ts-type"} часто равно `null`{lang="ts-type"}. |
| `filterable` | Можно ли использовать поле в `filter` — **и в агрегатном `select`**; см. ниже. |
| `sortable` | Можно ли использовать его в `order`. |
| `editable` | Можно ли его записывать. |
| `requiredGroups` | Операции, для которых поле обязательно, например `['add']`{lang="ts-type"}. |
| `multiple` / `elementType` | Является ли значение списком и каким. |
| `validationRules` | Ограничения на стороне портала, если поле их объявляет. |

**Три из них нигде больше не встречаются.** `filterable`, `editable` и `requiredGroups`
отсутствуют в схеме запроса документа OpenAPI, поэтому на вопросы *«можно ли по этому полю фильтровать?»* и
*«что нужно передать в `add`?»* ответ есть только здесь.

::warning
**`sortable` и `filterable` независимы — не выводите одно из другого.** В `main.eventlog` они
случайно называют одни и те же пять полей (`id`, `timestampX`, `auditTypeId`,
`userId`, `guestId` из тринадцати), из-за чего совпадение выглядит как правило. Это не так:
в `tasks.task` поле `title` имеет `sortable: true` и `filterable: false`, а фильтровать вообще можно ровно одно поле
из девяноста пяти — `id`, тогда как сортировать — девятнадцать. Богатый
`order` рядом с голым `filter` — нормальное состояние сущности v3, а не неисправность портала.
В `restApi:v2` та же сущность прекрасно фильтруется по `RESPONSIBLE_ID`, `STATUS` и `GROUP_ID`;
это различие между двумя API, а не то, что нужно обходить.
::

::note
**`filterable` также разрешает агрегацию, чего название флага не подсказывает.**
Поле, которое доступно для выбора и совершенно нормально приходит из `list`, всё равно
отклоняется агрегатным `select`, если по нему нельзя фильтровать, — портал проверяет
один и тот же атрибут для обоих случаев. Измерено: отказ — это **мягкий** сбой
(`isSuccess`{lang="ts-type"} равен `false`{lang="ts-type"}, а не исключение — 4xx в
конверте `restApi:v3`) с кодом
`BITRIX_REST_V3_EXCEPTION_VALIDATION_REQUESTVALIDATIONEXCEPTION` и названием
поля в `validation[].field`{lang="ts-type"}. Сопоставляйте по коду и полю:
сообщение локализуется. С учётом указанного выше соотношения это реальное ограничение на то,
что можно попросить сущность v3 посчитать, —
см. [Выбор подходящего метода](/docs/actions/choosing-the-right-method/).
::

`requiredGroups` равно `null`{lang="ts-type"}, а не пустому массиву, если поле
не обязательно ни для чего, — проверяйте это перед перебором.

::note
**Источник истины — флаг, и набор меняется.** Какие поля сущность помечает
`filterable` или `sortable`, решает модуль Битрикс24, которому принадлежит сущность, и это
меняется от версии модуля к версии. Справочная документация указывает текущий
ответ для каждого метода — например, `tasks.task.list` в `restApi:v3`
[документирует `id` как единственный поддерживаемый фильтр](https://apidocs.bitrix24.com/api-reference/tasks/tasks-task-list-rest-v3.html)
— но на ваш запрос отвечает портал, с которым вы работаете. Читайте флаг, а не
предполагайте, особенно в коде, который должен продолжать работать при обновлениях портала.
::

## Зачем делать этот вызов

Поле v3, не помеченное `Filterable` или `Sortable`, отклоняется — портал не
игнорирует условие молча. Оба отказа измерены на двух сущностях. Оба приходят
**мягкими**: 4xx в конверте `restApi:v3` не выбрасывается как исключение, поэтому проверяйте
`isSuccess`{lang="ts-type"}, а не оборачивайте эти вызовы в `try`/`catch`.

```ts
// у `title` `filterable: false` — ответ будет HTTP 400
await $b24.actions.v3.call.make({
  method: 'tasks.task.list',
  params: { filter: [['title', '=', 'x']], select: ['id'] }
})
```

```json
{
  "error": {
    "code": "BITRIX_REST_V3_EXCEPTION_VALIDATION_REQUESTVALIDATIONEXCEPTION",
    "validation": [{ "field": "title", "message": "…requires the `Filterable` attribute…" }]
  }
}
```

Сортировка по полю с `sortable: false` отвечает так же, называя `Sortable` — измерено
на `main.eventlog.list` с сортировкой по `description`, одному из тринадцати полей, которые этот метод
возвращает:

```json
{
  "error": {
    "code": "BITRIX_REST_V3_EXCEPTION_VALIDATION_REQUESTVALIDATIONEXCEPTION",
    "validation": [{ "field": "description", "message": "…`EventLogDto`…`Sortable`…" }]
  }
}
```

То, что поле **возвращается**, ничего не говорит о том, можно ли по нему фильтровать или сортировать.

::warning
`message` **локализуется** — портал отвечает на языке портала. Сопоставляйте по
`error.code` и `validation[].field`, но никогда по тексту.
::

Поэтому полезная привычка такова: **сначала прочитайте поля, потом стройте запрос**.

```ts
const meta = await $b24.actions.v3.call.make<{
  items: Array<{ name: string, filterable: boolean, sortable: boolean }>
}>({ method: 'tasks.task.field.list', params: { select: ['name', 'filterable', 'sortable'] } })

const fields = meta.getData()?.result?.items ?? []
const canFilterOn = new Set(fields.filter(field => field.filterable).map(field => field.name))

// На замеренном портале у `tasks.task` ровно одно фильтруемое поле: `id`.
if (canFilterOn.has('deadline')) {
  // …и только потом отправлять фильтр по `deadline`
}
```

## Названия полей

**Названия полей `restApi:v3` — в camelCase.** Измерено на двух сущностях и 108
дескрипторах — `tasks.task` (95) и `main.eventlog` (13) — ни одно из 108 не начинается с
заглавной буквы: `id`, `title`, `creatorId`, `responsibleId`, `startPlan`, `storyPoints`,
`timestampX`, `auditTypeId`.

`restApi:v2` — наоборот: `ID`, `TITLE`, `RESPONSIBLE_ID`.

Именно поэтому у SDK такие значения по умолчанию для постраничной выборки, и это правило, а не
особенность отдельного метода:

| | `idKey` по умолчанию |
| --- | --- |
| `actions.v3.callList` / `fetchList` | `'id'`{lang="ts-type"} |
| `actions.v2.callList` / `fetchList` | `'ID'`{lang="ts-type"} |

`cursorIdKey` существует для методов, которые пишут идентификатор **по-разному в запросе и
в ответе**. В `restApi:v2` известный случай — `tasks.task.list`: он возвращает
`id` в нижнем регистре, но фильтрует по `ID` в верхнем, поэтому обход с настройками по умолчанию читает
курсор из несуществующего поля, не продвигается и бесконечно повторяет первую страницу.

```ts
// restApi:v2 `tasks.task.list` — без `cursorIdKey` обход не закончится
const response = await $b24.actions.v2.callList.make({
  method: 'tasks.task.list',
  params: { select: ['ID', 'TITLE'] },
  idKey: 'id',
  cursorIdKey: 'ID',
  customKeyForResult: 'tasks'
})
```

В `restApi:v3` тот же метод не требует переопределения — запрос и ответ совпадают по `id`.

::tip
Если обход возвращает строки, но одни и те же снова и снова, проверьте это в первую очередь.
Спросите у `<entity>.field.list`, как ответ называет свой идентификатор.
::

## Доступность

Почти повсеместно, но не везде. На облачном портале (замер 2026-11-26) **19** методов `.list` публикуются
без соответствующего `.field.list` — это `crm.*.field.custom.list` и `crm.*.field.custom.enum.list`
(`company`, `contact`, `deal`, `lead`, `quote`, `smartinvoice`), `forum.message.field.custom.*`,
`crm.company.bankrequisite.list`, `crm.contact.bankrequisite.list`,
`humanresources.access.permission.list`, `humanresources.node.communication.list` и `rest.scope.list`.
Считайте отсутствие метода метаданных обычным делом: проверьте `isSuccess` и вернитесь к документу
OpenAPI или к документированным названиям полей.

Числа здесь **специфичны для портала**, как и вся остальная поверхность v3 — измеренные порталы
опубликовали 147 (коробка, 2026-09-05), 220, 245 (2026-09-05) и 1389 (2026-11-26) методов в сумме. Читайте их как порядок величины,
а не как контракт.

## Альтернативы и рекомендации

- **Поля одной сущности с флагами** — `<entity>.field.list`. Небольшой и дешёвый вызов для каждой сущности
  и единственный источник `filterable` / `editable` / `requiredGroups`.
- **Вся поверхность методов** —
  [`rest.documentation.openapi`](/docs/actions/discovering-v3-methods/).
  Один документ, часто 100 КБ и больше; получите его один раз и кэшируйте.
- **Ни то, ни другое** — для `restApi:v2` по-прежнему применяются классические методы `crm.item.fields` / `*.fields`;
  это семейство относится к v3.
