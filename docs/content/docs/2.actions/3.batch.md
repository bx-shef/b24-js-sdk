## Обзор

::::rest-api-version-only
#rest-api-ver2
Используйте `BatchV2.make()`{lang="ts-type"}, чтобы выполнить до 50 команд REST API в одном запросе. Это особенно полезно, когда нужно получить или обновить большой объём данных, сократив число сетевых запросов и соблюдая ограничения REST API.

```ts
// Базовое использование
import { EnumCrmEntityTypeId } from '@bxshefby/b24jssdk'

const response = await $b24.actions.v2.batch.make({
  calls: [
    ['crm.item.get', { entityTypeId: EnumCrmEntityTypeId.contact, id: 1 }],
    ['crm.item.get', { entityTypeId: EnumCrmEntityTypeId.contact, id: 2 }]
  ],
  options: {
    isHaltOnError: true,
    returnAjaxResult: true,
    requestId: 'unique-request-id'
  }
})
```

#rest-api-ver3
Используйте `BatchV3.make()`{lang="ts-type"}, чтобы выполнить до 50 команд REST API в одном запросе, сократив число сетевых обращений.

::note
**Число 50 — это предел SDK, а не портала.** 51 команда, отправленная прямо на endpoint пакета v3, получила ответ HTTP 200 с 51 результатом (измерено на коробочной сборке), — то есть реальная граница v3 выше 51 и не опубликована. SDK ограничивает v3 тем же числом, которое применяет `restApi:v2` (`CRestUtil::BATCH_MAX_LENGTH = 50`, по исходникам портала), что делает разбиение на порции одинаковым во всех версиях, а пакет избыточной длины — понятной ошибкой на стороне клиента, а не неизвестной ошибкой на стороне сервера. Для более чем 50 команд используйте [`BatchByChunk`](/docs/actions/batch-by-chunk/).
::

```ts
// Базовое использование
import { EnumCrmEntityTypeId } from '@bxshefby/b24jssdk'

const response = await $b24.actions.v3.batch.make({
  calls: [
    ['tasks.task.get', { id: 1 }],
    ['tasks.task.get', { id: 2 }]
  ],
  options: {
    isHaltOnError: true,
    returnAjaxResult: true,
    requestId: 'unique-request-id'
  }
})
```
::::

## Сигнатура метода

::::rest-api-version-only

```ts-type
make<T = unknown>(
  options: ActionBatchV2

```

#rest-api-ver3
```ts-type
make<T = unknown>(
  options: ActionBatchV3
): Promise<CallBatchResult<T>>
```
::::

### Параметры

Объект `options` содержит следующие свойства:

| Параметр | Тип | Обязательный | Описание |
|----|----|----|----|
| **`calls`** | `BatchCommandsArrayUniversal \| BatchCommandsObjectUniversal \| BatchNamedCommandsUniversal`{lang="ts-type"} | Да | Команды, которые нужно выполнить в пакете. Поддерживается несколько [форматов](#форматы-команд-optionscalls). |
| **`options`** | `IB24BatchOptions`{lang="ts-type"} | Нет | [Дополнительные опции](#параметры-пакетного-запроса-optionsoptions) выполнения пакетного запроса. |

### Форматы команд (`options.calls`)

#### 1. Массив кортежей (`BatchCommandsArrayUniversal`)
<!-- @check-ignore: partial snippet — calls array literal, not a valid statement -->
```ts
calls: [
  ['method1', params1],
  ['method2', params2],
  // ...
]
```

#### 2. Массив объектов (`BatchCommandsObjectUniversal`)
<!-- @check-ignore: partial snippet — object array literal, not a valid statement -->
```ts
calls: [
  { method: 'method1', params: params1 },
  { method: 'method2', params: params2 },
  // ...
]
```

#### 3. Объект с именованными командами (`BatchNamedCommandsUniversal`)
```ts-type
calls: {
  command1: { method: 'method1', params: params1 },
  command2: ['method2', params2],
  // ...
}
```

::::rest-api-version-only
#rest-api-ver3
::warning
**Аргументы команды указываются в `params`; название на уровне протокола у портала — `query`.** Элемент пакета v3
уходит по сети как `{ method, query, as, parallel }` — именно это показывают
справочник самого портала и каждый пример `curl`, — а SDK сам превращает
`params` в `query`. Если записать в команде `query`, аргументы
не прочитает никто: команда уйдёт с пустым `query`, который портал
**принимает**.

Измерено на `main.eventlog.list` с `select: ['id']` и `pagination: { limit: 2 }`:
с `params` портал вернул **2 строки по 1 полю**; тот же запрос с `query`
вернул **50 строк по 13 полей** — всю страницу по умолчанию, без
`select` и без лимита. HTTP 200 в обоих случаях, никаких ошибок. Фильтр,
записанный таким образом, даёт неверный ответ, а не сбой, поэтому заметить нечего.

TypeScript отклоняет это в свежем литерале объекта. Но он не видит тот же литерал,
сначала присвоенный переменной, команды, построенные из объекта конфигурации, `JSON.parse`
или обычный JavaScript, поэтому SDK предупреждает и во время выполнения: одна строка
на пакетный запрос с названием проигнорированных ключей и команд, которые их несли.
Предупреждение выводится, только когда аргументы действительно потеряны, — у команды без
`params` или у команды с `query`. Ваши собственные `id` или `label` рядом с заполненным
`params` не затрагиваются.
::
::::

### Параметры пакетного запроса (`options.options`)

| Опция | Тип | По умолчанию | Описание |
|----|----|----|----|
| **`isHaltOnError`** | `boolean`{lang="ts-type"} | `true` | Останавливать ли выполнение на первой ошибке. |
| **`returnAjaxResult`** | `boolean`{lang="ts-type"} | `false` | Возвращать ли объект `AjaxResult` вместо данных. |
| **`requestId`** | `string`{lang="ts-type"} | — | Уникальный идентификатор запроса для отслеживания и отладки — передаётся в query-параметре `bx24_request_id`. Он ничего не дедуплицирует; для этого есть `idempotencyKey` (restApi:v3). |

::warning
Эти опции указываются **внутри** `options`. Если передать их свойствами верхнего уровня аргумента, они **не применяются**: TypeScript отклоняет такой литерал, а вызывающий код, которого компилятор не видит (обычный JavaScript или литерал, расширенный через переменную), получает предупреждение в журнале с названием флага и местом, куда его нужно поместить. До этого (#426) всё происходило молча, и хуже всего приводил к последствиям `returnAjaxResult`, потерянный таким образом: `isSuccess` у обычных данных равен `undefined`, поэтому пакет, в котором все команды выполнились успешно, выглядит как пакет, где все команды завершились ошибкой.
::

### Возвращаемое значение

Форма результата выбирается по аргументам, и перегрузки определяют, что вы получите, —
без приведения типов и ручного сужения:

| `calls` | `options.returnAjaxResult` | разрешается в |
| --- | --- | --- |
| именованные команды (запись) | отсутствует / `false` | `Result<Record<string, T>>`{lang="ts-type"} — данные по имени команды |
| именованные команды (запись) | `true` | `Result<Record<string, AjaxResult<T>>>`{lang="ts-type"} |
| массив команд (кортежи **или** объекты) | отсутствует / `false` | `Result<T[]>`{lang="ts-type"} — данные по позиции |
| массив команд (кортежи **или** объекты) | `true` | `Result<AjaxResult<T>[]>`{lang="ts-type"} |

`T` во всех строках — это данные **одной команды**, а не коллекции.

::::rest-api-version-only
#rest-api-ver2
::warning
**Аргументы команды указываются в `params`.** Если записать их под `query`, их
не прочитает никто: команда v2 уходит по сети как `method?<querystring>`, собранная
из `params`, то есть отправляется вообще без аргументов, а портал отвечает HTTP
200 со значениями метода по умолчанию.

Измерено на `user.get` с `filter: { ACTIVE: 'N' }` на портале, где единственный
пользователь активен: с `params` портал вернул **0 строк** — фильтр сработал, — а тот же
запрос с `query` вернул **1 строку**: активного пользователя, которого фильтр должен был исключить.
Это неверный ответ, а не сбой.

`query` — это написание `restApi:v3` в запросе, поэтому именно его выбирает вызывающий код;
в v2 это просто ключ, который парсер не читает.

TypeScript отклоняет его в свежем литерале объекта. Но он не видит тот же литерал,
сначала присвоенный переменной, команды, построенные из объекта конфигурации, `JSON.parse`
или обычный JavaScript, поэтому SDK предупреждает и во время выполнения: одна строка
на пакетный запрос с названием проигнорированных ключей и команд, которые их несли.
Предупреждение выводится, только когда аргументы действительно потеряны, — у команды без
`params` или у команды с `query`. Ваши собственные `id` или `label` рядом с заполненным
`params` не затрагиваются.
::
::::

::note
Массив *объектов* команд (`[{ method, params }]`) отвечает **по индексу**, как и
форма с кортежами. По имени отвечает форма записи (`{ name: { method, params } }`) — выбор делается по
контейнеру, а не по тому, как выглядят элементы.
::

::caution
Когда `returnAjaxResult` — это `boolean`, который компилятор не может прочитать как литерал
(переменная, а не `true` или `false`, записанные на месте), ни одна перегрузка не может
решить за вас, и вызов разрешается в объединение
`CallBatchResult<T>`{lang="ts-type"}. Это честно, но не удобно: сузьте
тип самостоятельно или передавайте флаг литералом.
::

## Данные элемента результата

::::rest-api-version-only
#rest-api-ver2
Каждый `result` отдельной команды возвращается ровно так, как его доставил REST API,
включая `null`, когда нижележащий метод законно не возвращает данных
(например, `im.chat.get`, вызванный с `ENTITY_TYPE`, который не соответствует
ни одному чату).

```ts
const response = await $b24.actions.v2.batch.make<{ ID: number } | null>({
  calls: {
    chatGet: {
      method: 'im.chat.get',
      params: { ENTITY_TYPE: 'UNKNOWN', ENTITY_ID: 'UNKNOWN' }
    }
  },
  options: { returnAjaxResult: true, requestId: 'chat-get' }
})

// Без приведения типов и без `@check-ignore`: именованные команды плюс `returnAjaxResult: true`
// дают запись из `AjaxResult`, и перегрузки выводят это из
// аргументов (#518).
const chatGet = response.getData()!.chatGet!
if (chatGet.getData()?.result === null) {
  // метод вернул null — подходящего чата нет
} else {
  console.log(chatGet.getData()?.result.ID)
}
```

::note
До v1.1.1 результат `null` приводился к `{}`, что ломало защитные проверки типов для nullable-значений
на стороне вызывающего кода (см. [issue #23](https://github.com/bitrix24/b24jssdk/issues/23)).
Если типизируете generic для методов, которые могут вернуть `null`, объявляйте его как
`T | null`{lang="ts-type"}.
::

#rest-api-ver3

Если типизируете generic для методов, которые могут вернуть `null`, объявляйте его как

## Ограничения

Пакет `restApi:v3` работает по принципу **«всё или ничего»**:

* Ошибки отдельных команд не возвращаются. Если любая команда в пакете
  завершается ошибкой, весь пакет завершается ошибкой, а внешний
  `response.getErrorMessages()` содержит эту ошибку (эти ошибки); `getData()` возвращает пустой словарь.
* `time` у каждого `AjaxResult` — это время всего пакета, а не отдельной команды.
  Лимитер **не** относит длительность пакета к отдельным методам —
  он начисляет пакет на `batch`, так его тарифицирует портал. (`restApi:v2`
  ведёт себя так же; раньше он распределял это значение по методам внутри
  пакета, чего портал никогда не делал.)

::note
**Пакет v3 теперь может ждать, чего раньше никогда не делал.** До 3.0.0 операционный
бюджет читался из ключей, которые записывал только путь пакета v2, поэтому пакет v3 никогда
не задерживался и не отступал из-за операционного времени. Теперь, когда бюджет читается
по `batch`, возможны два следствия: пакет может быть задержан перед отправкой, когда этот
бюджет почти исчерпан, а повтор после `OPERATION_TIME_LIMIT` ждёт сообщённого
времени сброса, а не фиксированные десять секунд. Оба применяются к `batchByChunk`
на каждой порции, поэтому длинный обход порциями под нагрузкой может занять заметно больше времени —
в этом и смысл: портал всё равно отклонил бы эти вызовы. Ни одно из них не включается на портале, который
далёк от своего бюджета, а [измерения](/docs/tools/limiters/#что-на-самом-деле-делает-длительная-нагрузка)
говорят, что таких порталов большинство.
::
* Если в успешном ответе v3 отсутствует запись результата для команды (что
  указывает на некорректный ответ API), SDK выбрасывает
  `JSSDK_INTERACTION_BATCH_STRATEGY_V3_EMPTY_COMMAND_RESPONSE`{lang="ts-type"}.

::caution
**Пакет `restApi:v3` не работает из браузера.** В v3 команды *и есть*
тело запроса — голый JSON-массив, — поэтому в нём нет места для учётных данных OAuth: портал читает
каждый элемент верхнего уровня как команду и требует `method` и `query` у каждой. На сервере — везде, где нет браузера или воркера, — SDK вместо этого переносит токен в заголовок
`Authorization: Bearer`. Браузер так не может: портал
отвечает на CORS preflight заголовком `Access-Control-Allow-Headers: origin,
content-type, accept`, поэтому запрос, просящий этот заголовок, вообще
не ушёл бы.

Поэтому браузер отправляет учётные данные в **строке запроса** —
`?auth=<token>`, добавляемой только для этой формы запроса. Портал читает её через
тот же словарь, что и `auth` в теле (`CRestUtil::getRequestData()` объединяет строку запроса
с телом), а параметр в строке запроса ничего не стоит на preflight, который
запрос уже делает из-за `Content-Type`. Принятие подтверждено измерением на рабочем
портале.

Это единственное место, где SDK помещает токен OAuth в URL. Он не виден тем,
кто не мог прочитать его и раньше — в приложении во фрейме токен живёт
в собственном JavaScript страницы, а каждый не пакетный вызов несёт его в теле запроса, —
но он попадает в журнал доступа веб-сервера портала и в его диагностический журнал,
пока администратор его включил. Если для вашего развёртывания это важно, выполняйте пакет
на собственном бэкенде через `B24OAuth` или `B24Hook` либо используйте
[`BatchV2.make()`](/docs/actions/batch/),
если методы существуют в `restApi:v2`.

`B24Hook` ничего не добавляет: его секрет уже находится в пути URL.

В тот день, когда `authorization` появится в списке разрешённых заголовков портала, браузер пойдёт
тем же путём через заголовок, каким сегодня идёт сервер.
::
::::

## Передача данных между командами (`$ref` / `$refArray`)

Пакет v3 может передавать вывод одной команды в `params` более поздней. Задайте
исходной команде псевдоним `as`, а затем сошлитесь на неё маркером `$ref` (одно значение)
или `$refArray` (поле, собранное по `items[]` источника). **Подстановку выполняет
сервер** — SDK просто передаёт маркер. Для построения маркеров используйте
помощник `BatchRefV3` (он проверяет путь на клиенте):

```ts
import { BatchRefV3 as R } from '@bxshefby/b24jssdk'

const response = await $b24.actions.v3.batch.make({
  calls: [
    { method: 'tasks.task.list', as: 'tasks', params: { select: ['id'] } },
    {
      method: 'tasks.task.list',
      // сервер развернёт это в `['id', 'in', [<id, собранные из tasks.items>]]`
      params: { select: ['id', 'title'], filter: [['id', 'in', R.refArray('tasks.id')]] }
    }
  ]
})
```

* `R.ref('alias.path.to.field')` → `{ $ref: '…' }` — одно значение. В контекст попадают только `item`
  (get) и `items` (list/tail); результат `add` или `update` не попадает, какой бы формы он ни был в модуле: `$ref` на
  `add` был отклонён с HTTP 400, `INVALIDSELECTEXCEPTION` на измеренной коробочной сборке.

  ::note
  **Что возвращают `add` и `update`, определяет модуль — измерены три, и ни два
  не совпадают.** Стандартные ORM-трейты отдают идентификатор и булево значение
  (`{ result: { id: 22 } }`{lang="ts-type"} / `{ result: true }`{lang="ts-type"});
  `tasks.task` отдаёт из `add` весь объект, а из `update` — булево значение, вложенное на уровень
  глубже (`{ result: { result: true } }`{lang="ts-type"}); модуль в
  облачной песочнице отдал весь объект из обоих. Полная таблица — на
  [странице вызова](/docs/actions/call/#что-возвращает-запись).
  ::
* `R.refArray('alias.field')` → `{ $refArray: '…' }` — собирает `field` по
  `items[]` псевдонима. Путь должен содержать точку.
* Неверный путь или неразрешённая ссылка завершает пакет ошибкой
  `BITRIX_REST_V3_EXCEPTION_INVALIDSELECTEXCEPTION`.
* **Только v3.** Эти маркеры не подставляются в пакете v2
  (`actions.v2.batch.make`) — там они становятся буквальными значениями фильтра и
  молча дают неверные или пустые результаты.
::::

## Обработка ошибок

::::rest-api-version-only
#rest-api-ver2
Всегда проверяйте результат через `isSuccess` и обрабатывайте ошибки:

<!-- @check-ignore: top-level return in error-handling illustration -->
```ts
const response = await $b24.actions.v2.batch.make({
  calls: [
    { method: 'crm.item.get', params: { entityTypeId: EnumCrmEntityTypeId.contact, id: 1 } },
    { method: 'crm.item.get', params: { entityTypeId: EnumCrmEntityTypeId.contact, id: 2 } }
  ],
  options: {
    isHaltOnError: true,
    returnAjaxResult: true,
    requestId: 'unique-request-id'
  }
})

if (!response.isSuccess) {
  // Обработка ошибки
  console.error(new Error(`Error: ${response.getErrorMessages().join('; ')}`))
  return
}

// Работа с успешным результатом
const data = response.getData()
```

Проверка `isSuccess` охватывает **два** разных сбоя:

- **Ошибки отдельных команд** — конверт пакета выполнен успешно, но отдельные команды завершились ошибкой. Проверьте каждый `AjaxResult` в `getData()` или используйте `getErrorsByKey()`, чтобы увидеть, какая команда не выполнилась.
- **Ошибки уровня конверта (мягкие)** — весь пакет завершается ошибкой до возврата результатов команд, например из-за серверного кода валидации (`BITRIX_REST_V3_EXCEPTION_VALIDATION_*`). Тогда внешний `Result` имеет `isSuccess === false`, ошибки находятся в `getErrorMessages()` / `getErrors()`, а `getData().result` пуст. Если этот код относится к валидации,
`AjaxError` также называет поле, которое не прошло проверку, — см.
[Какое поле не прошло проверку](/docs/actions/errors/#какое-поле-не-прошло-проверку-ajaxerrorvalidation).

Одна проверка `if (!response.isSuccess)` обрабатывает оба случая.

#rest-api-ver3
SDK больше не проверяет методы пакета заранее по клиентскому списку v3: каждая команда отправляется на endpoint пакета v3, и каждую проверяет сервер. Команда, которая называет метод не из v3, возвращается как серверная ошибка для этой команды (и, по семантике пакета v3, ошибка прерывает пакет). Используйте [`BatchV2.make()`](/docs/actions/batch/), если в пакете есть устаревшие методы, либо разделите смешанные пакеты по версиям API.

Для успешных запросов всегда проверяйте `isSuccess` и обрабатывайте ошибки:

<!-- @check-ignore: top-level return in error-handling illustration -->
```ts
const response = await $b24.actions.v3.batch.make({
  calls: [
    { method: 'tasks.task.get', params: { id: 1 } },
    { method: 'tasks.task.get', params: { id: 2 } }
  ],
  options: {
    isHaltOnError: true,
    returnAjaxResult: true,
    requestId: 'unique-request-id'
  }
})

if (!response.isSuccess) {
  // Обработка ошибки
  console.error(new Error(`Error: ${response.getErrorMessages().join('; ')}`))
  return
}

// Работа с успешным результатом
const data = response.getData()
```

#rest-api-ver3
### Получение нескольких задач

<!-- @check-ignore: full example — processResult callback and BatchCommands tuple inference not in scope -->
```ts [BatchTasks.ts]
import type { AjaxResult, Result } from '@bxshefby/b24jssdk'
import { AjaxError, B24Hook, LoggerFactory, SdkError } from '@bxshefby/b24jssdk'

type TaskItem = {
  id: number
  title: string
}

const devMode = !!(typeof import.meta !== 'undefined' && (import.meta.dev || import.meta.env?.DEV))
const $logger = LoggerFactory.createForBrowser('Example:batchTasks', devMode)
const $b24 = B24Hook.fromWebhookUrl('https://your_domain.bitrix24.com/rest/1/webhook_code/')

async function getMultipleItems(itemIds: number[], requestId: string): Promise<TaskItem[]> {
  if (itemIds.length < 1 || itemIds.length > 50) {
    throw new SdkError({
      code: 'MY_APP_GET_PROBLEM',
      description: `The number of elements must be between 1 and 50`,
      status: 404
    })
  }

  const calls = itemIds.map(id => [
    'tasks.task.get',
    {
      id,
      select: ['id', 'title']
    }
  ])

  const response = await $b24.actions.v3.batch.make<{ item: TaskItem }>({
    calls,
    options: {
      isHaltOnError: true,
      returnAjaxResult: true,
      requestId
    }
  })

  if (!response.isSuccess) {
    throw new Error(`Problem: ${response.getErrorMessages().join('; ')}`)
  }

  const resultData = (response as Result<AjaxResult<{ item: TaskItem }>[]>).getData() ?? []
  const results: TaskItem[] = []
  resultData.forEach((resultRow) => {
    if (resultRow.isSuccess) {
      const item = resultRow.getData()?.result.item
      if (item) {
        results.push(item)
      }
    }
  })

  return results
}

// Использование
const requestId = 'batch/tasks.task.get'
try {
  const itemIds = [1, 2, 3]
  const items = await getMultipleItems(itemIds, requestId)
  
  $logger.info(`Retrieved ${items.length} items`, {
    expected: itemIds.length,
    retrieved: items.length,
    items: items.map(c => ({ id: c.id, title: c.title }))
  })
} catch (error) {
  if (error instanceof AjaxError) {
    $logger.critical(error.message, { requestId, code: error.code })
  } else {
    $logger.alert('Problem', { requestId, error })
  }
}
```

## Альтернативы и рекомендации

::::rest-api-version-only
#rest-api-ver2
* **Для последовательных запросов**: используйте [`Call`](/docs/actions/call/) для одиночных вызовов.
* **Для работы со списками**: используйте [`CallList`](/docs/actions/call-list/) для получения больших объёмов данных.
* **Для пошаговой обработки**: используйте [`FetchList`](/docs/actions/fetch-list/) для обработки данных по мере поступления.
* **Чтобы выполнить больше команд (более 50)**: используйте [`BatchByChunk`](/docs/actions/batch-by-chunk/), который автоматически разбивает команды на порции по 50.
* **На стороне клиента (в браузере):** используйте встроенный объект [`B24Frame`](/docs/getting-started/installation/vue/#инициализация).

#rest-api-ver3
* **Для последовательных запросов**: используйте [`Call`](/docs/actions/call/) для одиночных вызовов.
* **Для работы со списками**: используйте [`CallList`](/docs/actions/call-list/) для получения больших объёмов данных.
* **Для пошаговой обработки**: используйте [`FetchList`](/docs/actions/fetch-list/) для обработки данных по мере поступления.
* **Чтобы выполнить больше команд (более 50)**: используйте [`BatchByChunk`](/docs/actions/batch-by-chunk/), который автоматически разбивает команды на порции по 50.
* **На стороне клиента (в браузере):** `B24Frame` **не может выполнить пакет `restApi:v3`** — см. [Ограничения](#ограничения). Используйте `actions.v2.batch.make` во фрейме или перенесите пакет на собственный бэкенд (`B24OAuth` / `B24Hook`).
::::
