## Обзор

`FetchTailV3.make()`{lang="ts-type"} обходит **tail**-метод `restApi:v3` через собственный keyset-курсор сервера и отдаёт каждую страницу по мере поступления, поэтому набор данных, больший объёма памяти, можно обрабатывать по одной странице.

Это потоковый аналог [`CallTail`{lang="ts-type"}](/docs/actions/call-tail/); всё про курсор, формы фильтра и ошибки у них одинаково и полностью описано на той странице. Ниже — только отличия.

::caution
**Сначала убедитесь, что метод существует.** Tail-endpoint отделён от своего списочного аналога, и публикуют его немногие модули — см. [как спросить портал](/docs/actions/call-tail/#обзор). Для обычного списочного метода используйте [`FetchList`{lang="ts-type"}](/docs/actions/fetch-list/).
::

```ts
for await (const page of $b24.actions.v3.fetchTail.make<{ id: number }>({
  method: 'main.eventlog.tail',
  params: { select: ['id', 'auditTypeId'] },
  cursorField: 'id',
  customKeyForResult: 'items',
  limit: 100
})) {
  // `page` — одна страница сервера, уже разобранная
  console.log(`Processing ${page.length} items`)
}
```

### Когда использовать FetchTailV3.make()

1. **Большие выгрузки и миграции** — строки передаются дальше и могут освобождаться, а не накапливаться.
2. **Ранний выход** — `break` из цикла, и дальнейшие запросы не выполняются.
3. **Осмысленный прогресс** — вы видите каждую страницу, как только она пришла.

Используйте [`CallTail`{lang="ts-type"}](/docs/actions/call-tail/) вместо него, когда весь результат помещается в памяти и с одним массивом работать проще.

## Сигнатура метода

```ts-type
make<T = unknown>(
  options: ActionFetchTailV3
): AsyncGenerator<T[]>
```

Опции те же, что у [`CallTail`{lang="ts-type"}](/docs/actions/call-tail/#параметры): `method`, `params`, `cursorField`, `order`, `initialValue`, `customKeyForResult`, `requestId`, `limit`, `maxPages` и `signal`.

Обратного вызова `progress` здесь нет, и он не нужен — тело цикла выполняется один раз на страницу, то есть несёт тот же сигнал, что и обратный вызов.

Два правила с той страницы действуют здесь без изменений, и их легко упустить, если вы пришли от списочных обходчиков: **поле курсора не должно встречаться в `filter`** (сервер его отклоняет), а `filter` может быть формой массива **или голой логической группой `FilterV3`** — списочные обходчики принимают только массив, потому что должны его расширять. О том, каким должно быть само поле, см. [Выбор поля курсора](/docs/actions/call-tail/#выбор-поля-курсора).

### Возвращаемое значение

`AsyncGenerator<T[]>`{lang="ts-type"} — отдаёт один массив на страницу сервера. **Пока вы его не используете, ничего не происходит**: первый запрос выполняется на первой итерации, поэтому генератор, который создан, но ни разу не перебран, не отправляет трафик вовсе. Именно здесь срабатывают и все проверки — если обернуть в `try` только вызов `make(...)`, ничего не будет перехвачено.

Пустой результат отдаёт **ни одной страницы**, поэтому тело цикла не выполняется ни разу. Неверный `customKeyForResult` выглядит так же, потому что ключ, который обходчик не нашёл, читается как «нет данных», — проверьте ключ, прежде чем делать вывод, что на портале ничего не было.

## Обработка ошибок

Здесь всё **выбрасывается как исключение**, и это отличие от `callTail`, под которое стоит писать код.

| Код | Когда |
|---|---|
| `JSSDK_ACTION_V3_TAIL_FILTER_INVALID` | `filter` был объектным диалектом `restApi:v2`. Возникает на первой итерации, до любого запроса. |
| `JSSDK_CORE_B24_FETCH_TAIL_DESC_REQUIRES_INITIAL_VALUE` | `order: 'DESC'`{lang="ts-type"} без `initialValue`. Обратите внимание на сегмент `FETCH_TAIL`: `callTail` выбрасывает вариант с `CALL_TAIL`, поэтому сравнивайте точную строку. |
| `JSSDK_CORE_B24_FETCH_TAIL_METHOD_API_V3` | Портал вернул мягкую ошибку посреди обхода. Это ошибка, которую вы увидите чаще всего, и в ней настоящая асимметрия: `callTail` включает тот же сбой в свой `Result`. |
| `JSSDK_ACTION_CURSOR_STALLED` | Курсор вернулся равным только что отправленному. Обычно `cursorField` не является полем, по которому сервер листает страницы, или у метода вообще нет endpoint `tail`. |
| `JSSDK_ACTION_CURSOR_WENT_BACKWARDS` | Курсор перешёл на значение, которое уже пройдено. При `DESC` проверьте, что `initialValue` — самое новое значение. |
| `JSSDK_ACTION_MAX_PAGES_EXCEEDED` | Достигнут предел числа страниц. |
| `JSSDK_ACTION_INVALID_MAX_PAGES` | `maxPages` не было положительным целым числом. Возникает на первой итерации, до любого запроса. |
| `JSSDK_ACTION_ABORTED` | Сработал `signal`. |

### Чем это на самом деле отличается от CallTail

Три из них доходят до вас по-разному:

- `JSSDK_ACTION_MAX_PAGES_EXCEEDED` и `JSSDK_ACTION_ABORTED` — границы, которые задаёте *вы*, поэтому `callTail` возвращает собранные строки вместе с ошибкой. Генератор так не может — он уже отдал все прочитанные страницы;
- мягкую ошибку портала `callTail` сообщает в `Result`, а здесь она приходит как `JSSDK_CORE_B24_FETCH_TAIL_METHOD_API_V3`.

Остальные выбрасываются из **обоих** обходчиков: `await callTail.make(...)` без `try` отклоняется на застрявшем курсоре точно так же, как цикл ниже.

`callTail` разрешает `Result` и прикрепляет к нему ошибку, связанную с границей, поэтому прочитанные строки сохраняются. Генератор так не может — он уже передал все прочитанные страницы, — поэтому **выбрасывает исключение**:

```ts
try {
  for await (const page of $b24.actions.v3.fetchTail.make({
    method: 'main.eventlog.tail',
    cursorField: 'id',
    customKeyForResult: 'items'
  })) {
    console.log(`Processing ${page.length} items`)
  }
}
catch (error) {
  // Уже выданные страницы обработаны. Если для вашего потребителя это небезопасно,
  // откатите их здесь — см. примечание ниже.
  throw error
}
```

::caution
**Страница, которая была отдана, уже доставлена.** Если обход остановился с `JSSDK_ACTION_CURSOR_STALLED` или `JSSDK_ACTION_CURSOR_WENT_BACKWARDS`, страницы, которые ваш цикл уже обработал, могут содержать дубликаты — сервер повторялся. Потребитель, который их сохранил, должен это откатить. Это противоположность `JSSDK_ACTION_MAX_PAGES_EXCEEDED` и `JSSDK_ACTION_ABORTED`, где прочитанное верно, но неполно.
::

## Что ещё отличается от CallTail

### Ранняя остановка

Выход из цикла останавливает обход; следующие страницы не запрашиваются.

```ts
let seen = 0

for await (const page of $b24.actions.v3.fetchTail.make<{ id: number }>({
  method: 'main.eventlog.tail',
  cursorField: 'id',
  customKeyForResult: 'items'
})) {
  seen += page.length
  if (seen >= 500) {
    break
  }
}
```

Для границы, которую обеспечивает SDK, а не проверяете вы сами, передайте `maxPages` или `signal`.

## Примеры

### Потоковая выгрузка, сначала самые старые

```ts
import { SdkError } from '@bxshefby/b24jssdk'

let pages = 0
let rows = 0

try {
  for await (const page of $b24.actions.v3.fetchTail.make<{ id: number }>({
    method: 'main.eventlog.tail',
    params: { select: ['id', 'auditTypeId'] },
    cursorField: 'id',
    customKeyForResult: 'items',
    limit: 100
  })) {
    rows += page.length
    console.log(`page ${++pages}, ${rows} rows`)
  }
}
catch (error) {
  if (error instanceof SdkError) {
    console.error(`walk stopped: ${error.code}`)
  }
  throw error
}
```

### Сначала самые новые

Обходу по убыванию нужна явная точка старта, потому что сервер листает страницы по условию `field < value`:

```ts
for await (const page of $b24.actions.v3.fetchTail.make<{ id: number }>({
  method: 'main.eventlog.tail',
  cursorField: 'id',
  order: 'DESC',
  initialValue: Number.MAX_SAFE_INTEGER,
  customKeyForResult: 'items'
})) {
  console.log(`Processing ${page.length} items`)
}
```

Без `initialValue` обход выбрасывает `JSSDK_CORE_B24_FETCH_TAIL_DESC_REQUIRES_INITIAL_VALUE`, а не уходит пустым. `Number.MAX_SAFE_INTEGER` подходит для числового поля; для даты и времени или любой другой строки см. [что передавать вместо этого](/docs/actions/call-tail/#order-desc-требует-initialvalue). Ошибка возникает на первой итерации, а не при создании генератора — пока вы его не используете, ничего не выполняется.
