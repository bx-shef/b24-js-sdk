## Обзор

Если нужно обрабатывать большие объёмы данных из списочных методов REST API версии 3 по частям (порциями), используйте `FetchListV3.make()`{lang="ts-type"}.

Метод реализует быстрый алгоритм перебора больших наборов данных без загрузки всех данных в память сразу. Каждая итерация возвращает следующую страницу (порцию) результатов, пока не будут получены все данные.

```ts
// Basic usage
const generator = $b24.actions.v3.fetchList.make({
  method: 'main.eventlog.list',
  params: {
    filter: [
      ['userId', '=', 1]
    ],
    select: ['id', 'userId']
  },
  idKey: 'id',
  customKeyForResult: 'items',
  requestId: 'unique-request-id',
  limit: 600
})

for await (const chunk of generator) {
  // Process chunk (e.g., save to database, analyze, etc.)
  console.log(`Processing ${chunk.length} items`)
}
```

### Когда использовать FetchListV3.make()

1. **Очень большие объёмы данных**: число записей составляет тысячи или десятки тысяч.
2. **Потоковая обработка**: данные нужно обрабатывать по мере поступления.
3. **Долгие операции**: обработка каждой записи занимает много времени.

## Сигнатура метода

```ts-type
make<T = unknown>(
  options: ActionFetchListV3
): AsyncGenerator<T[]>
```

### Параметры

Объект `options` содержит следующие свойства:

| Параметр | Тип | Обязательный | Описание |
|----|----|----|----|
| **`method`** | `string`{lang="ts-type"} | Да | Название метода REST API, который возвращает список данных (например, `tasks.task.list`, `main.eventlog.list`). |
| **`params`** | `Omit<TypeCallParamsV3, 'pagination' \| 'order' \| 'filter'> & { filter?: TypeFilterV3 }`{lang="ts-type"} | Нет | Параметры запроса, кроме `pagination` и `order`, а `filter` сужен до формы массива `restApi:v3` (см. [Ограничения](#ограничения)). Параметр `pagination` зарезервирован, потому что метод получает все данные за один вызов. Параметр `order` зарезервирован, потому что постраничная выборка по курсору требует сортировки строго по `cursorIdKey` (по умолчанию равен `idKey`) по возрастанию — см. [Ограничения](#ограничения). Для управления выборкой используйте `filter` и `select`. |
| **`idKey`** | `string`{lang="ts-type"} | Нет | Название поля с идентификатором **в том виде, как оно встречается в каждом элементе ответа**; его значение задаёт курсор. По умолчанию: `'id'`. Укажите то поле идентификатора, которое возвращает метод. |
| **`cursorIdKey`** | `string`{lang="ts-type"} | Нет | Название поля, которое используется в **запросе** для `order` и фильтра страницы `[field, '>', n]`. По умолчанию равно `idKey`. В `restApi:v3` оно нужно редко: названия полей v3 — в camelCase, поэтому запрос и ответ совпадают по `id`. Указывайте его, только если метод пишет идентификатор по-разному в запросе и в ответе — выясните, как его называет ответ, через [`<entity>.field.list`](/docs/actions/discovering-entity-fields/). |
| **`customKeyForResult`** | `string`{lang="ts-type"} | Да | Пользовательский ключ, указывающий, что данные из ответа REST API нужно брать по этому полю. Например, `items` для списка элементов CRM. |
| **`requestId`** | `string`{lang="ts-type"} | Нет | Уникальный идентификатор запроса для отслеживания и отладки — передаётся в query-параметре `bx24_request_id`. Он ничего не дедуплицирует; для этого есть `idempotencyKey` (restApi:v3). |
| **`maxPages`** | `number`{lang="ts-type"} | Нет | Верхняя граница числа страниц, которые может прочитать обход. По умолчанию `10000`; должно быть положительным целым числом, иначе при вызове возникает `JSSDK_ACTION_INVALID_MAX_PAGES`. При достижении границы выбрасывается `JSSDK_ACTION_MAX_PAGES_EXCEEDED` после того, как уже прочитанные страницы были отданы, — см. [Ограничение обхода](#ограничение-обхода). |
| **`signal`** | `AbortSignal`{lang="ts-type"} | Нет | Отменяет обход. Проверяется перед каждым запросом, поэтому уже отменённый сигнал не стоит ни одного запроса. Отмена выбрасывает `JSSDK_ACTION_ABORTED`; уже отданные страницы остаются у вас. |
| **`limit`** | `number`{lang="ts-type"} | Нет | Сколько записей получать на страницу. По умолчанию `50`. **Это запрос, а не гарантия** — каждый метод применяет собственный максимум, и короткая страница не означает конец данных. Измерено: `tasks.task.list` отвечает 50 при `limit` 51, 100 и 1000, хотя доступно 60 строк. Этот обход устойчив к ограничению (см. [Ключевые понятия](#оптимизация-производительности)); самодельная постраничная выборка на `call.make` — нет. На измеренной сборке `limit: 0`{lang="ts-type"} или нечисловое значение отклонялись с `INVALIDPAGINATIONEXCEPTION`, а отрицательное давало голый 500 — это один метод на одной коробочной сборке, поэтому считайте эти коды ожидаемым поведением, а не контрактом. |

### Возвращаемое значение

`AsyncGenerator<T[]>`{lang="ts-type"} — асинхронный генератор, который возвращает порции данных в виде массивов типа `T`.

Каждая итерация генератора возвращает:

- Массив элементов (порцию) не более чем из `options.limit` записей.
- Генератор завершается, когда получены все данные.

## Ключевые понятия

### AsyncGenerator и Promise

В отличие от `CallListV3.make()`{lang="ts-type"}, который возвращает `Promise`{lang="ts-type"} со всеми данными сразу, `FetchListV3.make()`{lang="ts-type"} возвращает асинхронный генератор:

| Аспект | `CallListV3.make()` | `FetchListV3.make()` |
|----|----|----|
| **Возвращаемое значение** | `Promise<Result<T[]>>` | `AsyncGenerator<T[]>` |
| **Память** | Загружает все данные в память | Обрабатывает данные по частям |
| **Использование** | `await response.getData()` | `for await (const chunk of generator)` |
| **Подходит для** | Небольших и средних объёмов данных | Очень больших объёмов данных |

### Оптимизация производительности

Метод реализует [алгоритм, рекомендованный Битрикс24](https://apidocs.bitrix24.com/settings/performance/huge-data.html), для эффективной работы с большими объёмами данных:

1. **Фильтрация по возрастающему id**: каждый следующий запрос использует фильтр `[cursorIdKey, '>', id]` с id последнего полученного элемента (читается через `idKey`).
2. **Потоковая обработка**: данные обрабатываются по мере получения, что экономит память.
3. **Автоматическое определение конца данных**: запросы прекращаются, когда получен пустой массив или страница короче самой большой из виденных до сих пор. Остановка привязана к размеру страницы, который сервер реально возвращает, а не к запрошенному `options.limit`, поэтому метод, который молча ограничивает страницу ниже `limit` (например, `tasks.task.list` с фиксированными 50), всё равно листается по всем записям, а не останавливается после первой урезанной страницы. Короткая страница завершает обход, только когда проверен курсор, прочитанный из неё: страница, которая и короткая, *и* повторяет курсор, — это сервер, игнорирующий условие страницы, а не конец данных, и о ней сообщается как об ошибке, а не возвращается как результат.

### Структура ответа REST API v3

::note
Параметр `customKeyForResult`{lang="ts-type"} сохранён для обратной совместимости. В будущем, после анализа реального использования, будет принято решение о его необходимости.
::

В REST API версии 3 разные методы возвращают данные в одинаковых структурах:

- **Сгруппированный массив**: `{ result: { items: [...] } }`{lang="ts-type"}

Параметр `customKeyForResult`{lang="ts-type"} позволяет указать ключ, по которому данные находятся в ответе.

::note
Некоторые списочные методы v3 (например, `note.*`) также возвращают в конверте ответа поле `nextCursor`{lang="ts-type"} рядом с `items` — `{ result: { nextCursor, items: [...] } }`{lang="ts-type"}. Читать или передавать его **не нужно**: `FetchListV3.make()`{lang="ts-type"} листает страницы собственным курсором по `idKey`{lang="ts-type"} (внедряемый фильтр `[idField, '>', n]`{lang="ts-type"}) и проходит все страницы независимо от `nextCursor`{lang="ts-type"}. Поле носит информационный характер; SDK его игнорирует.
::

### Ограничения

- **Размер страницы зависит от метода, а не равен глобальным 1000**: `limit` задаёт, что вы хотите; метод решает, что отдаст. Измерено на коробочной сборке: `tasks.task.list` возвращает 50 независимо от запрошенного, и ничто в ответе не сообщает об ограничении. Обход определяет конец данных по самой большой странице, которую сервер реально вернул, поэтому проходит всё независимо от этого, — самодельный цикл на `call.make` так не умеет.
- **Сортировка фиксирована**: метод всегда сортирует по `cursorIdKey` (по умолчанию равен `idKey`) по возрастанию, потому что постраничная выборка по курсору опирается на фильтры `[cursorIdKey, '>', nextId]` для обхода набора данных. Значение `order`, переданное пользователем, нарушило бы этот инвариант, поэтому объявленное свойство `order` исключено из типа через `Omit`, хотя унаследованная сигнатура индекса `[key: string]: unknown` означает, что компилятор всё же его примет, — а любое значение, переданное во время выполнения, удаляется с записью `warning` в журнал. Чтобы сузить набор результатов, используйте `filter`.
- **`filter` должен быть в форме массива v3**: `[['id', '>', 100]]` или результат `FilterV3.build(...)`. Объектный диалект `restApi:v2` (`{ '>id': 100 }`) принимается типом `TypeCallParamsV3`{lang="ts-type"} для обратной совместимости и работает с обычным `call`, но не здесь: постраничная выборка по курсору на каждой странице дописывает `[cursorIdKey, '>', nextId]` в тот же фильтр, поэтому расширить можно только массив. Передача объекта выбрасывает `SdkError`{lang="ts-type"} с кодом `JSSDK_ACTION_V3_LIST_FILTER_NOT_ARRAY`. Раньше объект принимался, а обход падал на середине с `filter is not iterable`.
- **Курсор, который перестал продвигаться, — фатальная ошибка**: если последнее значение `idKey` на странице равно тому, по которому уже фильтруют, условие `>cursorIdKey` потеряно, и одна и та же страница будет приходить снова. Полная страница сама по себе не может завершить обход — остановка по самой большой из виденных страниц не срабатывает, — а короткая проверяется до того, как её сочтут концом данных, поэтому вместо бесконечного накопления дубликатов выбрасывается `SdkError`{lang="ts-type"} с кодом `JSSDK_ACTION_CURSOR_STALLED`. Обычная причина — `idKey` называет поле ответа, а `cursorIdKey` по умолчанию совпадает с ним: `tasks.task.list` возвращает `id` в нижнем регистре, но фильтрует по `ID` в верхнем, поэтому нужны оба (`idKey: 'id'`, `cursorIdKey: 'ID'`). Курсор, который **движется не в ту сторону**, тоже отслеживается, отдельно: сервер, чередующий две страницы, никогда не повторяет только что отправленное значение, поэтому проверка на равенство выше его не видит — обход останавливается с `JSSDK_ACTION_CURSOR_WENT_BACKWARDS`{lang="ts-type"} на первом же шаге назад. И ни одна из проверок больше не ждёт полной страницы: **короткая** страница, курсор которой не продвинулся, раньше завершала обход как конец данных, возвращая усечённый и пересекающийся результат вообще без ошибки.
- **Только для списочных методов**: предназначен только для методов, которые возвращают массивы данных.

## Обработка ошибок

Поскольку метод возвращает асинхронный генератор, ошибки обрабатываются иначе, чем в `CallListV3.make()`{lang="ts-type"}:

// @check-ignore: `some.method` is a placeholder, not a portal method
```ts
import { SdkError } from '@bitrix24/b24jssdk'

try {
  const generator = $b24.actions.v3.fetchList.make({
    method: 'some.method',
    params: { /* some_params */ },
    idKey: 'id',
    customKeyForResult: 'items',
    requestId: 'unique-request-id',
    limit: 600
  })

  for await (const chunk of generator) {
    // Process chunk (e.g., save to database, analyze, etc.)
    console.log(`Processing ${chunk.length} items`)
  }
} catch (error) {
  // Handling error
  if (
    error instanceof SdkError
    && error.code === 'JSSDK_CORE_B24_FETCH_LIST_METHOD_API_V3'
  ) {
    console.error(`${error.message}`, { code: error.code })
  } else {
    console.error('Some error', error)
  }
}
```

## Примеры

### Пошаговая обработка большого числа записей журнала событий

```ts [ProcessMainEventLogItems.ts]
import { B24Hook, LoggerFactory, Text, SdkError, AjaxError } from '@bitrix24/b24jssdk'

type MainEventLogItem = {
  id: number
  userId: number
}

const devMode = !!(typeof import.meta !== 'undefined' && (import.meta.dev || import.meta.env?.DEV))
const $logger = LoggerFactory.createForBrowser('Example:ProcessMainEventLogItems', devMode)
const $b24 = B24Hook.fromWebhookUrl('https://your_domain.bitrix24.com/rest/1/webhook_code/')

async function processMainEventLogItem(): Promise<void> {
  let batchNumber = 0
  let totalItems = 0

  const sixMonthAgo = new Date()
  sixMonthAgo.setMonth((new Date()).getMonth() - 6)
  sixMonthAgo.setHours(0, 0, 0)
  
  const requestId = 'some-main-event-log-item-list'
  
  try {
    const generator = $b24.actions.v3.fetchList.make<MainEventLogItem>({
      method: 'main.eventlog.list',
      params: {
        filter: [
          ['timestampX', '>=', Text.toB24Format(sixMonthAgo)] // created at least 6 months ago
        ],
        select: ['id', 'userId']
      },
      idKey: 'id',
      customKeyForResult: 'items',
      requestId,
      limit: 60
    })
    
    for await (const chunk of generator) {
      batchNumber++
      totalItems += chunk.length

      $logger.info(`Processing batch #${batchNumber}`, {
        batchSize: chunk.length,
        totalSoFar: totalItems
      })
      
      // Example: saving to database
      await saveToDatabase(chunk)
      
      // Example: sending to message queue
      await sendToMessageQueue(chunk)
    }
    
    $logger.notice(`Processed ${totalItems} elements in ${batchNumber} batches`)
  } catch (error) {
    if (error instanceof SdkError) {
      $logger.error(`Processing error: ${error.message}`, {
        code: error.code,
        batchNumber,
        totalItems
      })
    } else {
      $logger.error('Unknown error', { error, batchNumber, totalItems })
    }
    throw error
  }
}

// Helper functions
// Database save implementation
async function saveToDatabase(items: MainEventLogItem[]): Promise<void> {
  await new Promise(resolve => setTimeout(resolve, 100)) // Simulation
}

// Message queue send implementation
async function sendToMessageQueue(items: MainEventLogItem[]): Promise<void> {
  await new Promise(resolve => setTimeout(resolve, 50)) // Simulation
}

// Usage
try {
  await processMainEventLogItem()
} catch (error) {
  $logger.critical('A problem occurred', { error })
}
```

### Когда поля идентификатора в запросе и ответе различаются

Некоторые методы сортируют и фильтруют по одному названию поля, а возвращают другое (например, `ID` в верхнем регистре в запросе и `id` в нижнем в данных). Установите `idKey` в поле **ответа**, а `cursorIdKey` — в поле **запроса**:

// @check-ignore: `some.list` is a placeholder, not a portal method
```ts
const generator = $b24.actions.v3.fetchList.make({
  method: 'some.list',
  params: { select: ['ID', 'TITLE'] },
  idKey: 'id', // read the id from each returned item
  cursorIdKey: 'ID', // order + ["ID", ">", n] page filter in the request
  customKeyForResult: 'items'
})

for await (const chunk of generator) {
  console.log(`Got ${chunk.length} records`)
}
```

Два способа ошибиться дают разные сбои, и разница важна:

- **`idKey` нельзя прочитать из полной страницы** — вы назвали поле, которого нет в ответе. SDK выводит `warning` и прекращает листание, а не усекает результат молча; `Result` содержит то, что пришло к этому моменту, и это настоящие данные.
- **`cursorIdKey` называет поле, по которому сервер не фильтрует** — `idKey` читается нормально, поэтому обход продолжается, но условие страницы теряется, и одна и та же страница приходит бесконечно. Это выбрасывает `SdkError`{lang="ts-type"} с кодом `JSSDK_ACTION_CURSOR_STALLED`, потому что всё собранное к этому моменту — одна повторяющаяся страница.

## Альтернативы и рекомендации

* **Размер порции**: каждая порция содержит до `options.limit` записей (по умолчанию `50`; метод применяет собственный максимум, поэтому порция может быть меньше запрошенной). Большие порции означают меньше HTTP-запросов, но большую нагрузку на память на каждой итерации.
* **Оптимальная параллельность**: при обработке данных из генератора рекомендуется ограниченная параллельность (3–5 одновременных операций).
* **Обработка ошибок**: всегда обрабатывайте ошибки внутри цикла `for await...of`, чтобы не останавливать весь процесс.
* **Отслеживание хода выполнения**: добавьте журналирование прогресса для долгих операций.

* **Для последовательных запросов**: используйте [`Call`](/docs/actions/call-rest-api-ver3/) для одиночных вызовов.
* **Если метод публикует собственный endpoint `tail`** (таких мало) — используйте [`FetchTail`](/docs/actions/fetch-tail-rest-api-ver3/), который отдаёт потоком собственный курсор сервера, а не эмулированный.
* **Для пакетных операций:** используйте [`Batch`](/docs/actions/batch-rest-api-ver3/), чтобы выполнить до 50 команд в одном запросе.
* **На стороне клиента (в браузере):** используйте встроенный объект [`B24Frame`](/docs/getting-started/installation/vue/#инициализация).
* **См. также:** [Фильтрация](/docs/actions/filtering/) — как строить `filter` (и почему `order` удаляется).

## Ограничение обхода

Обход листает страницы, пока не закончатся данные. Его ограничивают три опции.

`maxPages` останавливает обход после указанного числа страниц и выбрасывает `JSSDK_ACTION_MAX_PAGES_EXCEEDED`{lang="ts-type"} с названием метода, отдав все прочитанные страницы. По умолчанию значение **10 000** — это страховка, а не политика: в `restApi:v3` это 500 000 строк при размере страницы по умолчанию 50 (и больше, только если собственный предел метода допускает больший `limit`), а при скорости выборки по умолчанию 2 запроса в секунду — примерно 83 минуты, так что бесконечный обход ограничен, и при этом никто не лишается возможности прочитать нужное. Увеличьте значение, если чтению действительно нужно больше.

Опция **выдаёт ошибку, а не усекает результат**. Короткий список, который выглядит полным, — тот сбой, который постоянно порождает весь этот класс ошибок, поэтому обход никогда не завершается молча. Уже отданные страницы остаются у вас — исключение не даёт усечённому обходу выглядеть законченным.

`signal` принимает `AbortSignal`{lang="ts-type"} и выбрасывает `JSSDK_ACTION_ABORTED`{lang="ts-type"}. Он проверяется в начале каждой итерации, поэтому уже отменённый сигнал не стоит ни одного запроса.

Потоковые обходчики не принимают `progress`: они отдают каждую страницу по мере поступления, поэтому подсчёт — это тело вашего собственного `for await`.
