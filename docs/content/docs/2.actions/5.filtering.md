## Обзор

В Битрикс24 есть **два диалекта фильтра**, и они не взаимозаменяемы: каждая версия
API принимает только свой.

- **v2** (`$b24.actions.v2.{call,callList,fetchList}.make`) использует **объект с ключами-префиксами**:
  оператор — это префикс в названии поля.
- **v3** (`$b24.actions.v3.{call,callList,fetchList}.make`) использует **массив
  троек**: `[field, operator, value]`.

Фильтр в стиле v3, переданный в действие v2, молча разбирается неверно; фильтр в стиле v2,
переданный в действие v3, возвращает `UnknownFilterOperatorException`.

## v2 — операторы-префиксы

Оператор — это префикс в названии поля. Несколько ключей объединяются через
`AND`. Два оператора для одного поля требуют двух отдельных ключей (например, диапазон).

```ts-type
filter: {
  '>=opportunity': 50000,
  '<=opportunity': 200000,
  '!stageId': 'LOST',
  '=%title': 'A%'
}
```

| Префикс | Значение | Пример |
|---|---|---|
| (нет) | точное совпадение | `{ stageId: 'NEW' }` |
| `>=` | больше или равно | `{ '>=opportunity': 50000 }` |
| `>` | больше | `{ '>id': 100 }` |
| `<=` | меньше или равно | `{ '<=opportunity': 200000 }` |
| `<` | меньше | `{ '<closeDate': '2026-01-01' }` |
| `!` | не равно | `{ '!stageId': 'LOST' }` |
| `!=` | не равно (альтернативная запись) | `{ '!=stageId': 'LOST' }` |
| `%` | LIKE (подстрока, без учёта регистра) | `{ '%title': 'supply' }` |
| `=%` | LIKE с явным шаблоном (`%` / `_`) | `{ '=%title': 'A%' }` |
| `!%` | NOT LIKE | `{ '!%title': 'test' }` |

Значение-массив означает `IN`; в сочетании с `!` получается «не входит в»:

```ts-type
filter: {
  stageId: ['NEW', 'PREPARATION', 'EXECUTING'], // IN
  '!categoryId': [4, 7]                          // NOT IN
}
```

## v3 — массив троек

Фильтр — это **массив** JSON; каждый элемент — условие `[field, operator, value]`.
Массив верхнего уровня неявно объединяется через `AND`.

```ts
filter: [
  ['stageId', '=', 'NEW'],
  ['createdTime', '>=', '2026-01-01T00:00:00+03:00'],
  ['responsibleId', 'in', [1, 2, 3]]
]
```

Условие из двух элементов `[field, value]` — сокращённая запись равенства:
`['id', 94]` означает `['id', '=', 94]`. Портал описывает и принимает её,
`TypeFilterV3` её допускает, и `FilterV3.build()` тоже её принимает, в том числе внутри
групп `FilterV3.and()` / `or()` (тип `FilterV3Shorthand`). В построителе
`FilterV3.eq('id', 94)` записывает то же условие полностью.

### Операторы v3 — всего 8

```txt
=   !=   >   >=   <   <=   in   between
```

::note
**На уровне протокола v3 нет оператора `like` / `%` / подстроки.** Поиск по подстроке
сейчас доступен только в v2 — используйте v2 с `%` или `=%`. Условие v3
`['title', 'like', 'A%']` завершается ошибкой `UnknownFilterOperatorException`.
::

- Значение `between` должно быть массивом из 2 элементов: `[min, max]`.
- Значение `in` должно быть массивом.

Формы с двумя аргументами — это синтаксический сахар:

```ts-type
['id', 42]              // same as ['id', '=', 42]
['stageId', ['A', 'B']] // same as ['stageId', 'in', ['A', 'B']]
```

Для чего-либо сложнее плоского списка предпочитайте типизированный построитель `FilterV3` — он
проверяет операторы и формы `in` / `between` на клиенте. См.
[навык b24jssdk-filtering](https://github.com/bx-shef/b24-js-sdk/blob/main/skills/b24jssdk-filtering/SKILL.md).

## Булево условие требует тела JSON

Булево значение в `filter` сохраняется, только если тело запроса — **JSON**. Если отправить его как
`application/x-www-form-urlencoded`, оно придёт строкой — `"false"`, а не
`false`{lang="ts-type"}, — и условие отбрасывается: вызов отвечает
строками, которые должен был исключить, и об ошибке ничто не сообщает.

Измерено на одном поле одного метода (`user.get`, `ACTIVE`), на одном портале, в одну
минуту — поэтому читайте это как ожидаемое поведение, а не как контракт:

| тело | `filter: { ACTIVE: true }` | `filter: { ACTIVE: false }` |
|----|----|----|
| JSON | 1 строка | **0 строк** |
| `application/x-www-form-urlencoded` | 1 строка | **1 строка** — условие проигнорировано |

Вывод несёт только столбец `false`{lang="ts-type"}. Значение `true`{lang="ts-type"}, закодированное формой, —
тоже строка `"true"`, поэтому её 1 строка — ровно то, что дало бы и проигнорированное условие: она
приведена как контроль, а не как доказательство. Происходит ли то же с числами или `null`{lang="ts-type"},
не измерялось.

**SDK отправляет JSON и указывает это явно** в каждом запросе, а не полагается на то, что
axios выберет `application/json`{lang="ts-type"} для тела-простого объекта.
Это важно, потому что экземпляр axios публичный: SDK задаёт тип содержимого для каждого
запроса, поэтому увеличение `ajaxClient.defaults.timeout` — которое
[страница вызова v3](/docs/actions/call/) советует
для долгих записей — не может случайно изменить кодировку тела. Один канал всё же
до него дотягивается: **перехватчик запросов** (request interceptor) этого экземпляра выполняется после сборки
конфигурации SDK, поэтому перехватчик, который задаёт `Content-Type`, меняет
кодировку и трафика SDK, и снова открывает именно эту проблему.

::warning
Если вы строите тот же вызов **вручную** — `curl`, тестер вебхуков, собственный HTTP-клиент, —
отправляйте его как JSON. Тело в виде формы — то место, где это проявляется, и проявляется оно
молча: строки выглядят правдоподобно, ошибки нет, а проигнорированным оказывается тот фильтр,
на который вы рассчитывали.
::

## Даты

Используйте помощник SDK `Text.toB24Format(date)` для **обоих** диалектов — он выдаёт
формат Битрикс24 `yyyy-MM-dd'T'HH:mm:ssZZ` и принимает `Date`, `DateTime` или
строку.

```ts
import { Text } from '@bxshefby/b24jssdk'

const sixMonthsAgo = new Date()
sixMonthsAgo.setMonth(sixMonthsAgo.getMonth() - 6)

// v2
const filterV2 = { '>=createdTime': Text.toB24Format(sixMonthsAgo) }

// v3
const filterV3 = [['createdTime', '>=', Text.toB24Format(sixMonthsAgo)]]
```

::note
Всегда указывайте смещение часового пояса в строках с датой — порталы Битрикс24 работают в
часовом поясе, настроенном для портала. `Text.toB24Format()` подставляет смещение за вас.
::

## Параметр `order` и списочные действия

`callList.make` и `fetchList.make` (и в v2, и в v3) **удаляют любой переданный пользователем
`order`** и принудительно сортируют по идентификатору курсора (`{ [cursorIdKey]: 'ASC' }`),
потому что листают набор данных keyset-курсором. Если передать `order`, SDK
отбросит его и выведет `warning` — значение молча игнорируется
для набора результатов.

Если нужна определённая сортировка, спуститесь на уровень `call.make` и листайте страницы вручную,
но почти всегда лучше **сузить фильтр**. Подробности — в разделе
[Ограничения CallList](/docs/actions/call-list/#ограничения).

## Какую форму `filter` принимает каждый списочный обходчик

Все четыре обходчика v3 отклоняют объектный диалект `restApi:v2` (`{ '>id': 100 }`)
на клиенте — портал разбирает фильтр v3 по позициям, поэтому словарь с ключами-префиксами операторов
не соответствует ни одной известной ему форме. Помимо этого, два семейства различаются,
потому что листают страницы по-разному.

`callList` / `fetchList` **эмулируют** курсор: на каждой странице они дописывают
`[cursorIdKey, '>', cursor]` в `filter`. Расширить можно только массив, поэтому
логическую группу — вполне допустимый сам по себе фильтр v3 — нужно оборачивать:

```ts
import { B24Hook, FilterV3, SdkError } from '@bxshefby/b24jssdk'

const b24 = B24Hook.fromWebhookUrl('https://your-portal.bitrix24.ru/rest/1/SECRET')

// ✅ wrapped in an array, so the page condition can be appended to it
await b24.actions.v3.callList.make({
  method: 'main.eventlog.list',
  params: {
    select: ['id', 'severity'],
    filter: [FilterV3.or(['severity', '=', 'ERROR'], ['severity', '=', 'WARNING'])]
  },
  idKey: 'id',
  customKeyForResult: 'items'
})

// ❌ a bare group here throws JSSDK_ACTION_V3_LIST_FILTER_NOT_ARRAY
```

[`callTail`](/docs/actions/call-tail/) /
[`fetchTail`](/docs/actions/fetch-tail/) управляют
нативным действием сервера `tail` через `cursor: { field, value, order, limit }`
и передают `filter` без изменений. Портал принимает голую логическую группу как весь
фильтр, поэтому работают обе формы:

```ts
import { B24Hook, FilterV3 } from '@bxshefby/b24jssdk'

const b24 = B24Hook.fromWebhookUrl('https://your-portal.bitrix24.ru/rest/1/SECRET')

// ✅ a bare group — forwarded verbatim as
//    { "logic": "or", "conditions": [["severity", "=", "ERROR"], ...] }
await b24.actions.v3.callTail.make({
  method: 'main.eventlog.tail',
  cursorField: 'id',
  params: {
    select: ['id', 'severity'],
    filter: FilterV3.or(['severity', '=', 'ERROR'], ['severity', '=', 'WARNING'])
  },
  customKeyForResult: 'items'
})
```

Диалект v2 отклоняется здесь, а не на один запрос позже, где
портал сообщает об этом формулировкой, которая никогда не называет диалект:

```ts
import { B24Hook, SdkError } from '@bxshefby/b24jssdk'

const b24 = B24Hook.fromWebhookUrl('https://your-portal.bitrix24.ru/rest/1/SECRET')

try {
  await b24.actions.v3.callTail.make({
    method: 'main.eventlog.tail',
    params: { select: ['id'], filter: { '>id': 100 } as never },
    customKeyForResult: 'items'
  })
} catch (error) {
  // 'JSSDK_ACTION_V3_TAIL_FILTER_INVALID' — thrown before any request is sent
  console.error((error as SdkError).code)
}
```

`as never` выше нужен только для того, чтобы пройти компилятор: `filter` в
tail-действиях имеет тип `TypeFilterV3 | FilterV3Group`, поэтому диалект v2 изначально не проходит
проверку типов.

Ещё одно правило, специфичное для tail: поле курсора **не должно** встречаться в
`filter`. Сервер упорядочивает и листает по нему и отклоняет фильтр по тому же
полю с `INVALIDFILTEREXCEPTION`, поэтому SDK выводит `warning`, когда замечает
такое, — в том числе внутри вложенной группы:

```ts
import { B24Hook, FilterV3 } from '@bxshefby/b24jssdk'

const b24 = B24Hook.fromWebhookUrl('https://your-portal.bitrix24.ru/rest/1/SECRET')

// ⚠️ warns: the cursor field "id" must not appear in `filter`
await b24.actions.v3.callTail.make({
  method: 'main.eventlog.tail',
  cursorField: 'id',
  params: { select: ['id'], filter: [FilterV3.and(['id', '>', 5])] },
  customKeyForResult: 'items'
})
```

Обёртка в массив работает во всех четырёх обходчиках, так что оборачивайте, если хотите сохранить
одну привычку, а не помнить это разделение.

Один сбой не может быть вызван формой фильтра, но его легко с ней спутать: если
курсор, прочитанный со страницы, равен только что отправленному, условие страницы было отброшено,
и обход никогда не закончится. Страница не обязана быть полной — строка, стоящая в курсоре или до него,
не может быть в ответе, учитывающем условие «строго больше», каким бы малым ни было число
вернувшихся строк, — поэтому короткая страница проверяется до того, как её сочтут концом данных. Все шесть обходчиков — эти
четыре и два списочных `restApi:v2` — выбрасывают `SdkError`{lang="ts-type"} с
кодом `JSSDK_ACTION_CURSOR_STALLED` — или `JSSDK_ACTION_CURSOR_WENT_BACKWARDS`, если сервер ходит по кругу между страницами, а не повторяет одну, — вместо того чтобы идти бесконечно. У
tail-обходчиков обычная причина — `cursorField`, не являющийся полем, по которому
сервер листает страницы, либо метод без endpoint `tail`; см.
[Выбор поля курсора](/docs/actions/call-tail/#выбор-поля-курсора). Полный способ устранения — в
[Коды ошибок и их обработка](/docs/actions/errors/).

## Бок о бок: один и тот же фильтр в v2 и v3

Здесь важен диалект, а не сущность, — и две половины ниже не могут
использовать один и тот же метод, потому что **`crm.*` существует только в `restApi:v2`**. Endpoint v3
не публикует `crm.item.*` ни на одном измеренном портале; из `crm` он публикует
только письма таймлайна. Поэтому половина v2 запрашивает открытые сделки, а половина v3 задаёт задачам
вопрос той же *формы*: группа NOT-IN, `between` и нижняя граница по дате.

v2 — открытые сделки (`stageId` не входит в `WON` / `LOSE`) с суммой от 50 000
до 200 000, созданные за последние шесть месяцев:

```ts [v2]
import { EnumCrmEntityTypeId, Text } from '@bxshefby/b24jssdk'

const sixMonthsAgo = new Date()
sixMonthsAgo.setMonth(sixMonthsAgo.getMonth() - 6)

const response = await $b24.actions.v2.callList.make({
  method: 'crm.item.list',
  params: {
    entityTypeId: EnumCrmEntityTypeId.deal,
    filter: {
      '!stageId': ['WON', 'LOSE'],
      '>=opportunity': 50000,
      '<=opportunity': 200000,
      '>=createdTime': Text.toB24Format(sixMonthsAgo)
    },
    select: ['id', 'title', 'stageId', 'opportunity']
  },
  idKey: 'id',
  customKeyForResult: 'items'
})
```

v3 — незавершённые задачи (`status` не входит в *завершена* / *отложена*) с оценкой в story points
от 5 до 20, созданные за последние шесть месяцев:

```ts [v3]
import { Text } from '@bxshefby/b24jssdk'

const sixMonthsAgo = new Date()
sixMonthsAgo.setMonth(sixMonthsAgo.getMonth() - 6)

const response = await $b24.actions.v3.callList.make({
  method: 'tasks.task.list',
  params: {
    filter: [
      // v3 has no "not in" operator — wrap `in` in a NOT group (`negative: true`).
      // The `FilterV3.not(FilterV3.in(...))` helper builds the same shape.
      // 5 = completed, 6 = deferred
      { negative: true, conditions: [['status', 'in', [5, 6]]] },
      ['storyPoints', 'between', [5, 20]],
      ['created', '>=', Text.toB24Format(sixMonthsAgo)]
    ],
    // v3 field names are camelCase — `tasks.task.field.list` is how you ask the
    // portal for the real ones rather than guessing.
    select: ['id', 'title', 'status', 'storyPoints']
  },
  idKey: 'id',
  customKeyForResult: 'items'
})
```
