## Обзор

Если нужно обрабатывать большие объёмы данных из списочных методов REST API версии 2 по частям (порциями), используйте `FetchListV2.make()`{lang="ts-type"}.

Метод реализует быстрый алгоритм перебора больших наборов данных без загрузки всех данных в память сразу. Каждая итерация возвращает следующую страницу (порцию) результатов, пока не будут получены все данные.

```ts
// Basic usage
import { EnumCrmEntityTypeId } from '@bitrix24/b24jssdk'

const generator = $b24.actions.v2.fetchList.make({
  method: 'crm.item.list',
  params: {
    entityTypeId: EnumCrmEntityTypeId.deal,
    filter: { '>opportunity': 10000 }
  },
  idKey: 'id',
  customKeyForResult: 'items',
  requestId: 'unique-request-id'
})

for await (const chunk of generator) {
  // Process chunk (e.g., save to database, analyze, etc.)
  console.log(`Processing ${chunk.length} items`)
}
```

### Когда использовать FetchListV2.make()

1. **Очень большие объёмы данных**: число записей составляет тысячи или десятки тысяч.
2. **Потоковая обработка**: данные нужно обрабатывать по мере поступления.
3. **Долгие операции**: обработка каждой записи занимает много времени.

## Сигнатура метода

```ts-type
make<T = unknown>(
  options: ActionFetchListV2
): AsyncGenerator<T[]>
```

### Параметры

Объект `options` содержит следующие свойства:

| Параметр | Тип | Обязательный | Описание |
|----|----|----|----|
| **`method`** | `string`{lang="ts-type"} | Да | Название метода REST API, который возвращает список данных (например, `crm.contact.list`, `tasks.task.list`). |
| **`params`** | `Omit<TypeCallParamsV2, 'start' \| 'order'>`{lang="ts-type"} | Нет | Параметры запроса, кроме `start` и `order`. Параметр `start` зарезервирован, потому что метод получает все данные за один вызов. Параметр `order` зарезервирован, потому что постраничная выборка по курсору требует сортировки строго по `cursorIdKey` (по умолчанию равен `idKey`) по возрастанию — см. [Ограничения](#ограничения). Для управления выборкой используйте `filter` и `select`. |
| **`idKey`** | `string`{lang="ts-type"} | Нет | Название поля с идентификатором **в том виде, как оно встречается в каждом элементе ответа**; его значение задаёт курсор. По умолчанию `'ID'` (в верхнем регистре). Для методов, которые возвращают идентификатор в нижнем регистре или в camelCase (например, `tasks.task.list` возвращает `id`), укажите `'id'`. |
| **`cursorIdKey`** | `string`{lang="ts-type"} | Нет | Название поля, которое используется в **запросе** для `order` и фильтра страницы `>`. По умолчанию равно `idKey`. Указывайте его, только когда название поля, по которому можно сортировать и фильтровать, отличается от названия поля в ответе — например, `tasks.task.list` сортирует и фильтрует по `ID`, но возвращает `id`: передайте `idKey: 'id', cursorIdKey: 'ID'`. |
| **`customKeyForResult`** | `string`{lang="ts-type"} | Нет | Пользовательский ключ, указывающий, что данные из ответа REST API нужно брать по этому полю. Например, `items` для списка элементов CRM. |
| **`requestId`** | `string`{lang="ts-type"} | Нет | Уникальный идентификатор запроса для отслеживания и отладки — передаётся в query-параметре `bx24_request_id`. Он ничего не дедуплицирует; для этого есть `idempotencyKey` (restApi:v3). |
| **`maxPages`** | `number`{lang="ts-type"} | Нет | Верхняя граница числа страниц, которые может прочитать обход. По умолчанию `10000`; должно быть положительным целым числом, иначе при вызове возникает `JSSDK_ACTION_INVALID_MAX_PAGES`. При достижении границы выбрасывается `JSSDK_ACTION_MAX_PAGES_EXCEEDED` после того, как уже прочитанные страницы были отданы, — см. [Ограничение обхода](#ограничение-обхода). |
| **`signal`** | `AbortSignal`{lang="ts-type"} | Нет | Отменяет обход. Проверяется перед каждым запросом, поэтому уже отменённый сигнал не стоит ни одного запроса. Отмена выбрасывает `JSSDK_ACTION_ABORTED`; уже отданные страницы остаются у вас. |

### Возвращаемое значение

`AsyncGenerator<T[]>`{lang="ts-type"} — асинхронный генератор, который возвращает порции данных в виде массивов типа `T`.

Каждая итерация генератора возвращает:

- Массив элементов (порцию) не более чем из `50` записей.
- Генератор завершается, когда получены все данные.

## Ключевые понятия

### Автоматическое предупреждение

При вызове методов, которые **доступны в REST API версии 3**, система автоматически выводит предупреждение в журнал:

```json
"The method {method_name} is available in restApi:v3. It's worth migrating to the new API."
```

Оно означает, что стоит рассмотреть переход на новую версию REST API.

### AsyncGenerator и Promise

В отличие от `CallListV2.make()`, который возвращает `Promise` со всеми данными сразу, `FetchListV2.make()` возвращает асинхронный генератор:

| Аспект | `CallListV2.make()` | `FetchListV2.make()` |
|----|----|----|
| **Возвращаемое значение** | `Promise<Result<T[]>>` | `AsyncGenerator<T[]>` |
| **Память** | Загружает все данные в память | Обрабатывает данные по частям |
| **Использование** | `await response.getData()` | `for await (const chunk of generator)` |
| **Подходит для** | Небольших и средних объёмов данных | Очень больших объёмов данных |

### Оптимизация производительности

Метод реализует [алгоритм, рекомендованный Битрикс24](https://apidocs.bitrix24.com/settings/performance/huge-data.html), для эффективной работы с большими объёмами данных:

1. `start: -1`: отключает подсчёт общего числа записей, что значительно ускоряет выполнение запроса.
2. **Фильтрация по возрастающему id**: каждый следующий запрос использует фильтр `>cursorIdKey` с id последнего полученного элемента (читается через `idKey`).
3. **Потоковая обработка**: данные обрабатываются по мере получения, что экономит память.
4. **Автоматическое определение конца данных**: запросы прекращаются, когда получен пустой массив или число элементов меньше размера страницы (`50`). Короткая страница завершает обход, только когда проверен курсор, прочитанный из неё: страница, которая и короткая, *и* повторяет курсор, — это сервер, игнорирующий условие страницы, а не конец данных, и о ней сообщается как об ошибке, а не возвращается как результат.

### Структура ответа REST API v2

В REST API версии 2 разные методы могут возвращать данные в разной структуре:

- **Прямой массив**: `{ result: [...] }`{lang="ts-type"}
- **Сгруппированный массив**: `{ result: { items: [...] } }`{lang="ts-type"}

Параметр `customKeyForResult`{lang="ts-type"} позволяет указать ключ, по которому данные находятся в ответе.

### Ограничения

- **Размер страницы**: фиксированное ограничение REST API Битрикс24 версии 2 — `50` записей на запрос.
- **Сортировка фиксирована**: метод всегда сортирует по `cursorIdKey` (по умолчанию равен `idKey`) по возрастанию, потому что постраничная выборка по курсору опирается на фильтр `>cursorIdKey` для обхода набора данных. Значение `order`, переданное пользователем, нарушило бы этот инвариант, поэтому объявленное свойство `order` исключено из типа через `Omit`, хотя унаследованная сигнатура индекса `[key: string]: unknown` означает, что компилятор всё же его примет, — а любое значение, переданное во время выполнения, удаляется с записью `warning` в журнал. Чтобы сузить набор результатов, используйте `filter`.
- **Условия передаются в `filter` строчными буквами, а `FILTER` нужно убрать**: метод листает страницы, записывая собственные `filter`, `order` и `start` строчными буквами, а портал оставляет только последний из двух ключей верхнего уровня, различающихся регистром. Для старых списочных методов в документации *указаны* `FILTER` / `SORT` / `ORDER` в верхнем регистре, поэтому следовать этой документации здесь — ошибка. Измерено на `user.get` с четырьмя пользователями: `FILTER: { ID: 4 }`{lang="ts-type"} возвращает всех четырёх, `filter: { ID: 4 }`{lang="ts-type"} — одного. Какой из пары окажется последним, не определено, поэтому два способа ошибиться дают противоположные сбои: если передать только `FILTER`, ваши условия теряются ([#483](https://github.com/bitrix24/b24jssdk/issues/483)), а если передать `FILTER` *и* `filter`, теряется собственный курсор обхода, и обход зависает (см. следующий пункт). Перенесите условия, а не просто добавляйте ключ в нижнем регистре рядом с ключом в верхнем. С `SORT` всё ещё хуже — на `user.get` из-за него внедрённый `order` не проходит собственную валидацию метода, и запрос завершается ошибкой `ERROR_ARGUMENT` / *"Order must be a string"*. Обо всех этих случаях сообщается через `warning`.
- **Курсор, который перестал продвигаться, — фатальная ошибка**: если последнее значение `idKey` на странице равно тому, по которому уже фильтруют, условие `>cursorIdKey` потеряно, и одна и та же страница будет приходить снова. Полная страница сама по себе не может завершить обход — остановка по `length < 50` не срабатывает, — а короткая проверяется до того, как её сочтут концом данных, поэтому вместо бесконечного накопления дубликатов выбрасывается `SdkError`{lang="ts-type"} с кодом `JSSDK_ACTION_CURSOR_STALLED`. Обычная причина — `idKey` называет поле ответа, а `cursorIdKey` по умолчанию совпадает с ним: `tasks.task.list` возвращает `id` в нижнем регистре, но фильтрует по `ID` в верхнем, поэтому нужны оба (`idKey: 'id'`, `cursorIdKey: 'ID'`). Курсор, который **движется не в ту сторону**, тоже отслеживается, отдельно: сервер, чередующий две страницы, никогда не повторяет только что отправленное значение, поэтому проверка на равенство выше его не видит — обход останавливается с `JSSDK_ACTION_CURSOR_WENT_BACKWARDS`{lang="ts-type"} на первом же шаге назад. И ни одна из проверок больше не ждёт полной страницы: **короткая** страница, курсор которой не продвинулся, раньше завершала обход как конец данных, возвращая усечённый и пересекающийся результат вообще без ошибки.
- **Только для списочных методов**: предназначен только для методов, которые возвращают массивы данных.

## Обработка ошибок

Поскольку метод возвращает асинхронный генератор, ошибки обрабатываются иначе, чем в `CallListV2.make()`{lang="ts-type"}:

```ts
import { SdkError } from '@bitrix24/b24jssdk'

try {
  const generator = $b24.actions.v2.fetchList.make({
    method: 'some.method',
    params: { /* some_params */ },
    idKey: 'id',
    customKeyForResult: 'items',
    requestId: 'unique-request-id'
  })

  for await (const chunk of generator) {
    // Process chunk (e.g., save to database, analyze, etc.)
    console.log(`Processing ${chunk.length} items`)
  }
} catch (error) {
  // Handling error
  if (
    error instanceof SdkError
    && error.code === 'JSSDK_CORE_B24_FETCH_LIST_METHOD_API_V2'
  ) {
    console.error(`${error.message}`, { code: error.code })
  } else {
    console.error('Some error', error)
  }
}
```

## Примеры

### Пошаговая обработка большого числа компаний

```ts [ProcessCrmItems.ts]
import { B24Hook, EnumCrmEntityTypeId, LoggerFactory, Text, SdkError, AjaxError } from '@bitrix24/b24jssdk'

type Company = {
  id: number
  title: string
}

const devMode = !!(typeof import.meta !== 'undefined' && (import.meta.dev || import.meta.env?.DEV))
const $logger = LoggerFactory.createForBrowser('Example:ProcessCrmItems', devMode)
const $b24 = B24Hook.fromWebhookUrl('https://your_domain.bitrix24.com/rest/1/webhook_code/')

async function processCrmItemList(): Promise<void> {
  let batchNumber = 0
  let totalItems = 0

  const sixMonthAgo = new Date()
  sixMonthAgo.setMonth((new Date()).getMonth() - 6)
  sixMonthAgo.setHours(0, 0, 0)
  
  const requestId = 'some-crm-item-list'
  
  try {
    const generator = $b24.actions.v2.fetchList.make<Company>({
      method: 'crm.item.list',
      params: {
        entityTypeId: EnumCrmEntityTypeId.company,
        filter: {
          // use some filter by title
          '=%title': 'Prime%',
          '>=createdTime': Text.toB24Format(sixMonthAgo) // created at least 6 months ago
        },
        select: ['id', 'title']
      },
      idKey: 'id',
      customKeyForResult: 'items',
      requestId
    })
    
    for await (const chunk of generator) {
      batchNumber++
      totalItems += chunk.length

      $logger.info(`Processing batch #${batchNumber}`, {
        batchSize: chunk.length,
        totalSoFar: totalItems
      })
      
      // Example: saving to database
      await saveToDatabase(chunk)
      
      // Example: sending to message queue
      await sendToMessageQueue(chunk)
    }
    
    $logger.notice(`Processed ${totalItems} elements in ${batchNumber} batches`)
  } catch (error) {
    if (error instanceof SdkError) {
      $logger.error(`Processing error: ${error.message}`, {
        code: error.code,
        batchNumber,
        totalItems
      })
    } else {
      $logger.error('Unknown error', { error, batchNumber, totalItems })
    }
    throw error
  }
}

// Helper functions

}

// Message queue send implementation

  await new Promise(resolve => setTimeout(resolve, 50)) // Simulation

// Usage

} catch (error) {
  $logger.critical('A problem occurred', { error })
}
```

### Постраничная выборка `tasks.task.list` (поле запроса ≠ поле ответа)

`tasks.task.list` сортирует и фильтрует по `ID` (в верхнем регистре), но возвращает каждую задачу с `id` в нижнем регистре. Направьте `idKey` на поле **ответа**, а `cursorIdKey` — на поле **запроса**: тогда курсор читает последний `id` со страницы и запрашивает следующую через `>ID`:

```ts [ProcessAllTasks.ts]
type TaskListItem = { id: string, title: string }

const generator = $b24.actions.v2.fetchList.make<TaskListItem>({
  method: 'tasks.task.list',
  params: {
    filter: { RESPONSIBLE_ID: 1 }, // tasks filter fields are uppercase
    select: ['ID', 'TITLE'] // selected uppercase, but the response carries lowercase id / title
  },
  idKey: 'id', // read task.id from the response
  cursorIdKey: 'ID', // order + ">ID" page filter in the request
  customKeyForResult: 'tasks'
})

let total = 0
for await (const chunk of generator) {
  total += chunk.length
}
console.log(`Processed ${total} tasks`)
```

Без `cursorIdKey` значение `idKey: 'ID'` по умолчанию нельзя прочитать из ответа в нижнем регистре, поэтому постраничная выборка остановится после первых 50 задач, а SDK выведет `warning` со ссылкой сюда.

## Альтернативы и рекомендации

* **Размер порции**: REST API Битрикс24 версии 2 всегда возвращает до 50 записей на запрос.
* **Оптимальная параллельность**: при обработке данных из генератора рекомендуется ограниченная параллельность (3–5 одновременных операций).
* **Обработка ошибок**: всегда обрабатывайте ошибки внутри цикла `for await...of`, чтобы не останавливать весь процесс.
* **Отслеживание хода выполнения**: добавьте журналирование прогресса для долгих операций.

* **Для последовательных запросов**: используйте [`Call`](/docs/actions/call-rest-api-ver2/) для одиночных вызовов.
* **Для пакетных операций:** используйте [`Batch`](/docs/actions/batch-rest-api-ver2/), чтобы выполнить до 50 команд в одном запросе.
* **На стороне клиента (в браузере):** используйте встроенный объект [`B24Frame`](/docs/getting-started/installation/vue/#инициализация).
* **См. также:** [Фильтрация](/docs/actions/filtering/) — как строить `filter` (и почему `order` удаляется).

## Ограничение обхода

Обход листает страницы, пока не закончатся данные. Его ограничивают три опции.

`maxPages` останавливает обход после указанного числа страниц и выбрасывает `JSSDK_ACTION_MAX_PAGES_EXCEEDED`{lang="ts-type"} с названием метода, отдав все прочитанные страницы. По умолчанию значение **10 000** — это страховка, а не политика: в `restApi:v2` это 500 000 строк, а при скорости выборки по умолчанию 2 запроса в секунду — примерно 83 минуты, так что бесконечный обход ограничен, и при этом никто не лишается возможности прочитать нужное. Увеличьте значение, если чтению действительно нужно больше.

Опция **выдаёт ошибку, а не усекает результат**. Короткий список, который выглядит полным, — тот сбой, который постоянно порождает весь этот класс ошибок, поэтому обход никогда не завершается молча. Уже отданные страницы остаются у вас — исключение не даёт усечённому обходу выглядеть законченным.

`signal` принимает `AbortSignal`{lang="ts-type"} и выбрасывает `JSSDK_ACTION_ABORTED`{lang="ts-type"}. Он проверяется в начале каждой итерации, поэтому уже отменённый сигнал не стоит ни одного запроса.

Потоковые обходчики не принимают `progress`: они отдают каждую страницу по мере поступления, поэтому подсчёт — это тело вашего собственного `for await`.
