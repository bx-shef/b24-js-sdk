::note
REST API версии 3 листает страницы через `pagination: { limit, page }`{lang="ts-type"}. `limit` — это **запрос**: каждый метод применяет собственный максимум, и 1000 — частое значение, а не правило: `tasks.task.list` отвечает 50 независимо от запрошенного. Поэтому страница короче `limit` не доказывает, что данные закончились.
::

## Обзор

Если нужно с максимальной эффективностью получить все записи из списочных методов REST API версии 3 и вы готовы хранить весь набор данных в памяти, используйте `CallListV3.make()`{lang="ts-type"}.

Метод автоматически обрабатывает постраничную выборку и возвращает все данные одним массивом.

::note
Для импорта, экспорта, обработки всех элементов и построения отчётов рекомендуем [`FetchList`{lang="ts-type"}](/docs/working-with-the-rest-api/fetch-list-rest-api-ver3/) — он возвращает асинхронный генератор для пошаговой обработки больших списков.
::

```ts
// Basic usage
const response = await $b24.actions.v3.callList.make({
  method: 'main.eventlog.list',
  params: {
    filter: [
      ['userId', '=', 1]
    ],
    select: ['id', 'userId']
  },
  idKey: 'id',
  customKeyForResult: 'items',
  requestId: 'unique-request-id',
  limit: 600
})
```

### Когда использовать CallListV3.make()

1. **Небольшие и средние объёмы данных**: общее число записей не превышает нескольких тысяч.
2. **Простая обработка**: нужен простой доступ ко всем данным сразу.

## Сигнатура метода

```ts-type
make<T = unknown>(
  options: ActionCallListV3
): Promise<Result<T[]>>
```

### Параметры

Объект `options` содержит следующие свойства:

| Параметр | Тип | Обязательный | Описание |
|----|----|----|----|
| **`method`** | `string`{lang="ts-type"} | Да | Название метода REST API, который возвращает список данных (например, `tasks.task.list`, `main.eventlog.list`). |
| **`params`** | `Omit<TypeCallParamsV3, 'pagination' \| 'order' \| 'filter'> & { filter?: TypeFilterV3 }`{lang="ts-type"} | Нет | Параметры запроса, кроме `pagination` и `order`, а `filter` сужен до формы массива `restApi:v3` (см. [Ограничения](#ограничения)). Параметр `pagination` зарезервирован, потому что метод получает все данные за один вызов. Параметр `order` зарезервирован, потому что постраничная выборка по курсору требует сортировки строго по `cursorIdKey` (по умолчанию равен `idKey`) по возрастанию — см. [Ограничения](#ограничения). Для управления выборкой используйте `filter` и `select`. |
| **`idKey`** | `string`{lang="ts-type"} | Нет | Название поля с идентификатором **в том виде, как оно встречается в каждом элементе ответа**; его значение задаёт курсор. По умолчанию: `'id'`. Укажите то поле идентификатора, которое возвращает метод. |
| **`cursorIdKey`** | `string`{lang="ts-type"} | Нет | Название поля, которое используется в **запросе** для `order` и фильтра страницы `[field, '>', n]`. По умолчанию равно `idKey`. В `restApi:v3` оно нужно редко: названия полей v3 — в camelCase, поэтому запрос и ответ совпадают по `id`. Указывайте его, только если метод пишет идентификатор по-разному в запросе и в ответе — выясните, как его называет ответ, через [`<entity>.field.list`](/docs/working-with-the-rest-api/discovering-entity-fields/). |
| **`customKeyForResult`** | `string`{lang="ts-type"} | Да | Пользовательский ключ, указывающий, что данные из ответа REST API нужно брать по этому полю. Например, `items` для списка элементов CRM. |
| **`requestId`** | `string`{lang="ts-type"} | Нет | Уникальный идентификатор запроса для отслеживания и отладки — передаётся в query-параметре `bx24_request_id`. Он ничего не дедуплицирует; для этого есть `idempotencyKey` (restApi:v3). |
| **`maxPages`** | `number`{lang="ts-type"} | Нет | Верхняя граница числа страниц, которые может прочитать обход. По умолчанию `10000`; должно быть положительным целым числом, иначе при вызове возникает `JSSDK_ACTION_INVALID_MAX_PAGES`. Достижение границы не отбрасывает прочитанное — собранные строки возвращаются вместе с ошибкой `JSSDK_ACTION_MAX_PAGES_EXCEEDED`, поэтому проверяйте `isSuccess` — см. [Ограничение обхода](#ограничение-обхода). |
| **`signal`** | `AbortSignal`{lang="ts-type"} | Нет | Отменяет обход. Проверяется перед каждым запросом, поэтому уже отменённый сигнал не стоит ни одного запроса. Отмена не означает потерю: уже прочитанные страницы возвращаются вместе с ошибкой `JSSDK_ACTION_ABORTED`. |
| **`progress`** | `(p: { pages: number, rows: number }) => void`{lang="ts-type"} | Нет | Вызывается после каждой собранной страницы с накопленными счётчиками. Это счётчики, а не процент: при постраничной выборке по курсору портал не возвращает общее число, поэтому знаменатель пришлось бы выдумывать. |
| **`limit`** | `number`{lang="ts-type"} | Нет | Сколько записей получать на страницу. По умолчанию `50`. **Это запрос, а не гарантия** — каждый метод применяет собственный максимум, и короткая страница не означает конец данных. Измерено: `tasks.task.list` отвечает 50 при `limit` 51, 100 и 1000, хотя доступно 60 строк. Этот обход устойчив к ограничению (см. [Ключевые понятия](#оптимизация-производительности)); самодельная постраничная выборка на `call.make` — нет. На измеренной сборке `limit: 0`{lang="ts-type"} или нечисловое значение отклонялись с `INVALIDPAGINATIONEXCEPTION`, а отрицательное давало голый 500 — это один метод на одной коробочной сборке, поэтому считайте эти коды ожидаемым поведением, а не контрактом. |

### Возвращаемое значение

`Promise<Result<T[]>>`{lang="ts-type"} — промис, который разрешается в объект [`Result<T[]>`{lang="ts-type"}](https://github.com/bitrix24/b24jssdk/blob/main/packages/jssdk/src/core/result.ts) с массивом всех полученных элементов.

Этот объект предоставляет:

- `.getData(): T[]`{lang="ts-type"} — возвращает массив всех полученных элементов.
- `.isSuccess: boolean`{lang="ts-type"} — признак успешного выполнения всех запросов.
- `.getErrorMessages(): string[]`{lang="ts-type"} — массив сообщений об ошибках.

## Ключевые понятия

### Оптимизация производительности

Метод реализует [алгоритм, рекомендованный Битрикс24](https://apidocs.bitrix24.com/settings/performance/huge-data.html), для эффективной работы с большими объёмами данных:

1. **Фильтрация по возрастающему id**: каждый следующий запрос использует фильтр `[cursorIdKey, '>', id]` с id последнего полученного элемента (читается через `idKey`).
2. **Автоматическое определение конца данных**: запросы прекращаются, когда получен пустой массив или страница короче самой большой из виденных до сих пор. Остановка привязана к размеру страницы, который сервер реально возвращает, а не к запрошенному `options.limit`, поэтому метод, который молча ограничивает страницу ниже `limit` (например, `tasks.task.list` с фиксированными 50), всё равно листается по всем записям, а не останавливается после первой урезанной страницы. Короткая страница завершает обход, только когда проверен курсор, прочитанный из неё: страница, которая и короткая, *и* повторяет курсор, — это сервер, игнорирующий условие страницы, а не конец данных, и о ней сообщается как об ошибке, а не возвращается как результат.

### Структура ответа REST API v3

::note
Параметр `customKeyForResult`{lang="ts-type"} сохранён для обратной совместимости. В будущем, после анализа реального использования, будет принято решение о его необходимости.
::

В REST API версии 3 разные методы возвращают данные в одинаковых структурах:

- **Сгруппированный массив**: `{ result: { items: [...] } }`{lang="ts-type"}

Параметр `customKeyForResult`{lang="ts-type"} позволяет указать ключ, по которому данные находятся в ответе.

::note
Некоторые списочные методы v3 (например, `note.*`) также возвращают в конверте ответа поле `nextCursor`{lang="ts-type"} рядом с `items` — `{ result: { nextCursor, items: [...] } }`{lang="ts-type"}. Читать или передавать его **не нужно**: `CallListV3.make()`{lang="ts-type"} листает страницы собственным курсором по `idKey`{lang="ts-type"} (внедряемый фильтр `[idField, '>', n]`{lang="ts-type"}) и проходит все страницы независимо от `nextCursor`{lang="ts-type"}. Поле носит информационный характер; SDK его игнорирует.
::

### Ограничения

- **Размер страницы зависит от метода, а не равен глобальным 1000**: `limit` задаёт, что вы хотите; метод решает, что отдаст. Измерено на коробочной сборке: `tasks.task.list` возвращает 50 независимо от запрошенного, и ничто в ответе не сообщает об ограничении. Обход определяет конец данных по самой большой странице, которую сервер реально вернул, поэтому проходит всё независимо от этого, — самодельный цикл на `call.make` так не умеет.
- **Сортировка фиксирована**: метод всегда сортирует по `cursorIdKey` (по умолчанию равен `idKey`) по возрастанию, потому что постраничная выборка по курсору опирается на фильтры `[cursorIdKey, '>', nextId]` для обхода набора данных. Значение `order`, переданное пользователем, нарушило бы этот инвариант, поэтому объявленное свойство `order` исключено из типа через `Omit`, хотя унаследованная сигнатура индекса `[key: string]: unknown` означает, что компилятор всё же его примет, — а любое значение, переданное во время выполнения, удаляется с записью `warning` в журнал. Чтобы сузить набор результатов, используйте `filter`.
- **`filter` должен быть в форме массива v3**: `[['id', '>', 100]]` или результат `FilterV3.build(...)`. Объектный диалект `restApi:v2` (`{ '>id': 100 }`) принимается типом `TypeCallParamsV3`{lang="ts-type"} для обратной совместимости и работает с обычным `call`, но не здесь: постраничная выборка по курсору на каждой странице дописывает `[cursorIdKey, '>', nextId]` в тот же фильтр, поэтому расширить можно только массив. Передача объекта выбрасывает `SdkError`{lang="ts-type"} с кодом `JSSDK_ACTION_V3_LIST_FILTER_NOT_ARRAY`. Раньше объект принимался, а обход падал на середине с `filter is not iterable`.
- **Курсор, который перестал продвигаться, — фатальная ошибка**: если последнее значение `idKey` на странице равно тому, по которому уже фильтруют, условие `>cursorIdKey` потеряно, и одна и та же страница будет приходить снова. Полная страница сама по себе не может завершить обход — остановка по самой большой из виденных страниц не срабатывает, — а короткая проверяется до того, как её сочтут концом данных, поэтому вместо бесконечного накопления дубликатов выбрасывается `SdkError`{lang="ts-type"} с кодом `JSSDK_ACTION_CURSOR_STALLED`. Обычная причина — `idKey` называет поле ответа, а `cursorIdKey` по умолчанию совпадает с ним: `tasks.task.list` возвращает `id` в нижнем регистре, но фильтрует по `ID` в верхнем, поэтому нужны оба (`idKey: 'id'`, `cursorIdKey: 'ID'`). Курсор, который **движется не в ту сторону**, тоже отслеживается, отдельно: сервер, чередующий две страницы, никогда не повторяет только что отправленное значение, поэтому проверка на равенство выше его не видит — обход останавливается с `JSSDK_ACTION_CURSOR_WENT_BACKWARDS`{lang="ts-type"} на первом же шаге назад. И ни одна из проверок больше не ждёт полной страницы: **короткая** страница, курсор которой не продвинулся, раньше завершала обход как конец данных, возвращая усечённый и пересекающийся результат вообще без ошибки.
- **Только для списочных методов**: предназначен только для методов, которые возвращают массивы данных.

## Обработка ошибок

Всегда проверяйте результат через `isSuccess` и обрабатывайте ошибки:

// @check-ignore: top-level return in error-handling illustration; `some.method` is a placeholder, not a portal method
```ts
const response = await $b24.actions.v3.callList.make({
  method: 'some.method',
  params: { /* some_params */ },
  idKey: 'id',
  customKeyForResult: 'items',
  requestId: 'unique-request-id',
  limit: 600
})

if (!response.isSuccess) {
  // Handling error
  console.error(new Error(`Error: ${response.getErrorMessages().join('; ')}`))
  return
}

// Working with a successful result
const data = response.getData()
```

## Примеры

### Получение всех записей журнала событий с фильтрацией

```ts [AllMainEventLogItems.ts]
import { B24Hook, LoggerFactory, Text, SdkError, AjaxError } from '@bitrix24/b24jssdk'

type MainEventLogItem = {
  id: number
  userId: number
}

const devMode = !!(typeof import.meta !== 'undefined' && (import.meta.dev || import.meta.env?.DEV))
const $logger = LoggerFactory.createForBrowser('Example:AllMainEventLogItems', devMode)
const $b24 = B24Hook.fromWebhookUrl('https://your_domain.bitrix24.com/rest/1/webhook_code/')

async function getMainEventLogItemList(requestId: string): Promise<MainEventLogItem[]> {
  const sixMonthAgo = new Date()
  sixMonthAgo.setMonth((new Date()).getMonth() - 6)
  sixMonthAgo.setHours(0, 0, 0)

  const response = await $b24.actions.v3.callList.make<MainEventLogItem>({
    method: 'main.eventlog.list',
    params: {
      filter: [
        ['timestampX', '>=', Text.toB24Format(sixMonthAgo)] // created at least 6 months ago
      ],
      select: ['id', 'userId']
    },
    idKey: 'id',
    customKeyForResult: 'items',
    requestId,
    limit: 60
  })

  if (!response.isSuccess) {
    throw new SdkError({
      code: 'MY_APP_GET_PROBLEM',
      description: `Problem ${response.getErrorMessages().join('; ')}`,
      status: 404
    })
  }

  return response.getData() ?? []
}

// Usage
const requestId = 'some-main-event-log-item-list'
try {
  const list = await getMainEventLogItemList(requestId)
  $logger.info(`List [${list?.length}]`, { requestId, list })
} catch (error) {
  if (error instanceof AjaxError) {
    $logger.critical(error.message, { requestId, code: error.code })
  } else {
    $logger.alert('Problem', { requestId, error })
  }
}
```

### Когда поля идентификатора в запросе и ответе различаются

Некоторые методы сортируют и фильтруют по одному названию поля, а возвращают другое (например, `ID` в верхнем регистре в запросе и `id` в нижнем в данных). Установите `idKey` в поле **ответа**, а `cursorIdKey` — в поле **запроса**:

// @check-ignore: `some.list` is a placeholder, not a portal method
```ts
const response = await $b24.actions.v3.callList.make({
  method: 'some.list',
  params: { select: ['ID', 'TITLE'] },
  idKey: 'id', // read the id from each returned item
  cursorIdKey: 'ID', // order + ["ID", ">", n] page filter in the request
  customKeyForResult: 'items'
})
```

Два способа ошибиться дают разные сбои, и разница важна:

- **`idKey` нельзя прочитать из полной страницы** — вы назвали поле, которого нет в ответе. SDK выводит `warning` и прекращает листание, а не усекает результат молча; `Result` содержит то, что пришло к этому моменту, и это настоящие данные.
- **`cursorIdKey` называет поле, по которому сервер не фильтрует** — `idKey` читается нормально, поэтому обход продолжается, но условие страницы теряется, и одна и та же страница приходит бесконечно. Это выбрасывает `SdkError`{lang="ts-type"} с кодом `JSSDK_ACTION_CURSOR_STALLED`, потому что всё собранное к этому моменту — одна повторяющаяся страница.

## Альтернативы и рекомендации

* **Для работы со списками:** вместо ручного управления постраничной выборкой используйте:
  * [`FetchList`](/docs/working-with-the-rest-api/fetch-list-rest-api-ver3/) — возвращает асинхронный генератор для пошаговой обработки больших списков.
* **Если метод публикует собственный endpoint `tail`** (таких мало; `main.eventlog.tail` — один из них) — [`CallTail`](/docs/working-with-the-rest-api/call-tail-rest-api-ver3/) использует собственный курсор сервера, а не эмулирует его, и принимает голую логическую группу как весь `filter`.
* **Для пакетных операций:** используйте [`Batch`](/docs/working-with-the-rest-api/batch-rest-api-ver3/), чтобы выполнить до 50 команд в одном запросе.
* **На стороне клиента (в браузере):** используйте встроенный объект [`B24Frame`](/docs/getting-started/installation/vue/#инициализация).
* **См. также:** [Фильтрация](/docs/working-with-the-rest-api/filtering/) — как строить `filter` (и почему `order` удаляется).

## Ограничение обхода

Обход листает страницы, пока не закончатся данные. Его ограничивают три опции.

`maxPages` останавливает обход после указанного числа страниц и выбрасывает `JSSDK_ACTION_MAX_PAGES_EXCEEDED`{lang="ts-type"} с названием метода. Уже прочитанные строки **не** отбрасываются — они возвращаются вместе с ошибкой, поэтому проверяйте `isSuccess`. По умолчанию значение **10 000** — это страховка, а не политика: в `restApi:v3` это 500 000 строк при размере страницы по умолчанию 50 (и больше, только если собственный предел метода допускает больший `limit`), а при скорости выборки по умолчанию 2 запроса в секунду — примерно 83 минуты, так что бесконечный обход ограничен, и при этом никто не лишается возможности прочитать нужное. Увеличьте значение, если чтению действительно нужно больше.

Опция **выдаёт ошибку, а не усекает результат**. Короткий список, который выглядит полным, — тот сбой, который постоянно порождает весь этот класс ошибок, поэтому обход никогда не завершается молча: прочитанные строки возвращаются вместе с ошибкой, а `isSuccess` равен `false`. Проверяйте его, а не длину.

`signal` принимает `AbortSignal`{lang="ts-type"} и выбрасывает `JSSDK_ACTION_ABORTED`{lang="ts-type"}. Он проверяется в начале каждой итерации, поэтому уже отменённый сигнал не стоит ни одного запроса.

`progress` вызывается после каждой собранной страницы с `{ pages, rows }`{lang="ts-type"}. Это счётчики, а не процент: при выборке по курсору общее число не читается — `restApi:v3` его не присылает, а в v2 обход его не запрашивает, — поэтому знаменатель пришлось бы выдумывать.

```ts
// const $b24 = ...
const controller = new AbortController()

const response = await $b24.actions.v3.callList.make({
  method: 'main.eventlog.list',
  params: { select: ['id', 'severity'] },
  idKey: 'id',
  customKeyForResult: 'items',
  maxPages: 200,
  signal: controller.signal,
  progress: ({ pages, rows }) => console.log(`${pages} pages, ${rows} rows`)
})
```
