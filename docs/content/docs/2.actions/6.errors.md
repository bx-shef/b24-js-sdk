## Обзор

SDK выбрасывает ошибки через два связанных класса:

- `SdkError` — выбрасывается самим кодом SDK (валидация, конфигурация, устаревшие пути, внутренние инварианты). Всегда содержит `code`, `status` (в стиле HTTP) и необязательный `originalError`. Начиная с #189 `originalError` **неперечисляемый**: он остаётся доступным как `err.originalError` для локальной отладки, но spread `{ ...err }`, `Object.keys(err)`, `JSON.stringify(err)` или захват в стиле Sentry его пропускают — поэтому необработанная транспортная ошибка (в `config` которой может быть секрет вебхука) не утечёт при обычной сериализации. Для всего, что вы записываете в журнал, используйте `code` / `status` / `message`.
::caution
**`description` у `SdkError` не очищается от секретов.** `AjaxError` пропускает свой `requestInfo` через `redactSensitiveParams`; у `SdkError` такого шага нет, потому что его описание должно быть написано самим SDK, а не собрано из входных данных. Если вы создаёте `SdkError` сами, не подставляйте в него параметры запроса, фильтр, URL или токен: один только фильтр законно содержит пользовательские данные, например искомый адрес электронной почты или номер телефона, а сообщения об ошибках попадают в журналы и отчёты о сбоях.
::

- `AjaxError extends SdkError` — выбрасывается при сбое HTTP-вызова к Битрикс24. Добавляет `requestInfo` (`method`, `requestId`, параметры запроса), чтобы сопоставлять с журналами на стороне портала, и `isV3Envelope`, который показывает, ответил ли портал в форме ошибки `restApi:v3` (`{ error: { code, message } }`), а не в плоской форме v2 — на нём основано [правило категорий](/docs/tools/error-codes/#классификация-по-категории-restapiv3), а для ошибки, которая не пришла из разобранного тела REST, он равен `undefined`. Начиная с v1.1.2 (#39), `requestInfo` **не** включает полный URL запроса, а поля с учётными данными внутри `params` скрываются — цель в том, чтобы секреты вебхуков не попадали в вывод `toJSON()` / `toString()`.

Методы, которые не выбрасывают исключений, — `Call`, `CallList`, `Batch`, `BatchByChunk` — сообщают о сбоях **на стороне портала** через `Result`/`AjaxResult`: проверьте `.isSuccess` и прочитайте `.getErrorMessages()`. `FetchList`, напротив, **выбрасывает** исключение при сбое (генератор не может завершиться частично).

Это разделение касается ошибок REST, а не любых сбоев. `CallList` и `CallTail` также выбрасывают `SdkError` в нескольких случаях, когда сам обход невозможен: `filter`, который нельзя расширить, курсор, который перестал продвигаться (`JSSDK_ACTION_CURSOR_STALLED`) или идёт назад (`JSSDK_ACTION_CURSOR_WENT_BACKWARDS`), и `maxPages`, не являющийся положительным целым числом (`JSSDK_ACTION_INVALID_MAX_PAGES`). В этих случаях промис отклоняется, а не разрешается с `Result`, поэтому, если хотите обработать оба варианта, оберните вызов в `try`/`catch` и проверяйте `isSuccess`. Ещё два условия — обход, достигший предела числа страниц (`JSSDK_ACTION_MAX_PAGES_EXCEEDED`), и обход, прерванный вызывающим кодом (`JSSDK_ACTION_ABORTED`) — применимы к `FetchList` и `FetchTail` в равной мере и являются исключением из описанного выше разделения: «жадные» обходчики *разрешаются*, возвращая прочитанные строки вместе с ошибкой, потому что эти строки верны и лишь неполны. Если вы обновляетесь внутри линейки 2.x и для вас это ново, см. [Изменения поведения внутри 2.x](/docs/getting-started/migration/within-2x/).

## Какое поле не прошло проверку: `AjaxError.validation`

`restApi:v3` сообщает об ошибке валидации массивом `validation` с названием поля, а `AjaxError` передаёт его без изменений (#423):

```ts-type
readonly validation?: ReadonlyArray<{ field?: string, message?: string }>
```

`getErrorMessages()` сводит эти сообщения в одну строку для показа. `validation` хранит их раздельно, **вместе с полем, к которому каждое относится**, — этого одно сообщение не несёт, а именно это нужно, чтобы пометить ошибочное поле ввода, а не показывать баннер:

```ts
import { AjaxError } from '@bxshefby/b24jssdk'

declare function markFieldInvalid(field?: string, message?: string): void

const response = await $b24.actions.v3.call.make({
  method: 'note.document.get',
  params: {}
})

if (!response.isSuccess) {
  for (const error of response.getErrors()) {
    if (error instanceof AjaxError && error.validation) {
      for (const detail of error.validation) {
        // detail.field → 'id'
        // detail.message → 'Обязательное поле `id` не указано'
        //                  ("Required field `id` is not specified" — the portal
        //                   answers in the portal's own language)
        markFieldInvalid(detail.field, detail.message)
      }
    }
  }
}
```

Приведённый выше вызов — живой пример, на котором это проверено: метод `restApi:v3`,
вызванный без обязательного аргумента, отвечает `400` с

```json
{"error":{"code":"BITRIX_REST_V3_EXCEPTION_VALIDATION_REQUESTVALIDATIONEXCEPTION",
  "message":"Ошибка при валидации объекта запроса",
  "validation":[{"message":"Обязательное поле `id` не указано","field":"id"}]}}
```

(`"Ошибка при валидации объекта запроса"` — «Error validating the request
object». Сообщения портала приходят на языке портала, поэтому считайте их
текстом для показа пользователю, а не тем, по чему можно сопоставлять; сопоставляйте по `code` и `field`.)

Запрос, который не проходит проверку по нескольким полям, возвращает по одной записи на поле, а
`message` сводит их все в одну строку через пробелы.

Каждая запись проходит через тот же механизм скрытия, что и `requestInfo.params`, поэтому ключ
с названием `token` или `password` внутри записи маскируется — см.
[Логирование](/docs/tools/logging).

::warning
`field` и `message` внутри записи оба **необязательные**, потому что так говорит собственная форма портала: `TypeDescriptionErrorV3` объявляет их необязательными и допускает дополнительные ключи. Обрабатывайте отсутствие `field`, а не утверждайте, что оно есть.
::

Присутствует только для `restApi:v3` и только когда портал его прислал: у `restApi:v2` аналога нет, а ошибка v3 может возникнуть по причинам, не связанным с полем. Он доходит до вас независимо от того, мягкий ли код (возвращается в `Result`) или жёсткий (выбрасывается), поскольку оба пути строят ошибку одинаково. `toJSON()` включает его, когда он есть, поэтому он сохраняется в журнале или трекере ошибок — а именно там название поля важнее всего, потому что `message` сводит *сообщения* валидации, но не `field`, к которому каждое относится.

```ts
import { SdkError, AjaxError } from '@bxshefby/b24jssdk'

try {
  // …SDK calls
}
catch (error) {
  if (error instanceof AjaxError) {
    // network / portal-side failure; error.code is the Bitrix24 code
    console.error(error.code, error.status, error.requestInfo?.method, error.requestInfo?.requestId)
  }
  else if (error instanceof SdkError) {
    // SDK-side issue; error.code starts with JSSDK_
    console.error(error.code, error.status)
  }
  else {
    throw error
  }
}
```

## Коды SdkError, которые выбрасывает SDK

Коды — это стабильные строки: сопоставляйте по ним, а не разбирайте сообщения.

| Код | Статус | Где выбрасывается | Что означает |
|---|---|---|---|
| `JSSDK_CORE_B24_NOT_INIT` | 500 | геттеры `AbstractB24` | Вы вызвали метод у экземпляра `B24`, конструктор которого не завершился. Для `B24Frame` дождитесь `initializeB24Frame()`; для `B24Hook` URL был некорректным. |
| `JSSDK_CORE_B24_HTTP_V2_NOT_INIT` | 500 | `getHttpClient(ApiVersion.v2)` | HTTP-клиент v2 не был создан (обычно ошибка конфигурации). |
| `JSSDK_CORE_B24_HTTP_V3_NOT_INIT` | 500 | `getHttpClient(ApiVersion.v3)` | То же для v3. |
| `JSSDK_CORE_B24_API_WRONG` | 500 | `getHttpClient` | Запрошена неизвестная `ApiVersion`. |
| `JSSDK_CORE_METHOD_NOT_SUPPORT_IN_API_V3` | 500 | `AjaxResult.getNext()` | `getNext()` существует только в `restApi:v2` и не может работать с клиентом v3 — v3 не присылает смещение `next`, поэтому метод выбрасывает исключение, а не возвращает `false`, что читалось бы как «последняя страница». `CallV3.make()` / `BatchV3.make()` его больше не выбрасывают — SDK отказался от списка разрешённых методов v3, поэтому неизвестный метод v3 сервер сообщает как `METHODNOTFOUNDEXCEPTION` (мягкая ошибка в результате). |
| `JSSDK_CORE_B24_FETCH_LIST_METHOD_API_V2` | 500 | генератор `FetchListV2.make()` | Запрос одной из страниц завершился ошибкой; генератор останавливается. Перехватывайте вокруг `for await`. |
| `JSSDK_CORE_B24_FETCH_LIST_METHOD_API_V3` | 500 | генератор `FetchListV3.make()` | То же для v3. |
| `JSSDK_CORE_B24_FETCH_TAIL_METHOD_API_V3` | 500 | генератор `FetchTailV3.make()` | Запрос страницы `tail` (keyset) завершился ошибкой; генератор останавливается. Перехватывайте вокруг `for await`. |
| `JSSDK_CORE_B24_FETCH_TAIL_DESC_REQUIRES_INITIAL_VALUE` / `JSSDK_CORE_B24_CALL_TAIL_DESC_REQUIRES_INITIAL_VALUE` | 500 | `FetchTailV3.make()` / `CallTailV3.make()` | Запрошен `order: 'DESC'` без `initialValue`; сервер листает страницы по `field < value`, поэтому значение `0` по умолчанию ничего не вернёт. Передайте `initialValue`. |
| `JSSDK_FILTER_V3_INVALID_FIELD` / `JSSDK_FILTER_V3_INVALID_OPERATOR` / `JSSDK_FILTER_V3_INVALID_IN` / `JSSDK_FILTER_V3_INVALID_BETWEEN` / `JSSDK_FILTER_V3_INVALID_NODE` | 400 | построитель `FilterV3` | Проверка на клиенте при построении фильтра v3: пустое название поля, оператор вне 8 допустимых, значение `in` — не непустой массив, `between` с неопределённым или null-операндом либо некорректный узел, переданный в `build()` (например, забытый spread). |
| `JSSDK_BATCH_REF_V3_INVALID_PATH` / `JSSDK_BATCH_REF_V3_INVALID_REF_ARRAY` | 400 | помощник `BatchRefV3` | Проверка на клиенте маркера `$ref` / `$refArray` пакета v3: пустой или не строковый путь либо путь `refArray` без точки (`alias.field`). |
| `JSSDK_AGGREGATE_V3_INVALID_FUNCTION` | 400 | действие `AggregateV3` | В select указана функция вне `sum`/`avg`/`min`/`max`/`count`/`countDistinct`. |
| `JSSDK_AGGREGATE_V3_INVALID_SELECT` | 400 | действие `AggregateV3` | Значение select не является ни `string[]`, ни словарём `{ field: alias }`. |
| `JSSDK_AGGREGATE_V3_EMPTY_SELECT` | 400 | действие `AggregateV3` | В select **нет ни одного агрегируемого столбца** (`{}`, `{ count: [] }`, `{ count: {} }`). На такой запрос портал отвечает голым 500, в котором нет ничего, на что можно опереться, поэтому он отклоняется до отправки. Считается весь select: пустой список рядом с непустым принимается, потому что портал его принимает. |
| `JSSDK_BATCH_REF_V3_INVALID_PATH` / `JSSDK_BATCH_REF_V3_INVALID_REF_ARRAY` | 400 | помощник `BatchRefV3` | Проверка на клиенте при построении маркера `$ref`/`$refArray` пакета v3: пустой или не строковый путь либо путь `refArray` без точки (`alias.field`). |
| `JSSDK_BATCH_TOO_LARGE` | 400 | HTTP-клиенты v2 **и** v3 | В один пакет передано больше 50 команд. В `restApi:v2` 50 — собственный предел сервера; в `restApi:v3` это предел **SDK**: портал принимает 51 команду, поэтому предел сознательно приведён в соответствие с v2, а не является границей протокола. Используйте `BatchByChunk`. |
| `JSSDK_BATCH_EMPTY` | 400 | HTTP-клиент v2 | Пустой `calls`. |
| `JSSDK_BATCH_SUB_ERROR` | 500 | обработка пакета | Обёртка для сбоя вложенного вызова внутри пакета. Проверьте результат каждого вызова. |
| `JSSDK_INTERACTION_BATCH_BUILD_STRATEGY_V3_EMPTY_COMMAND` | 400 | обработка пакета v3 | Одна команда в пакете v3 была пустой или некорректной. |
| `JSSDK_INTERACTION_BATCH_BUILD_STRATEGY_V3_EMPTY_COMMANDS` | 400 | обработка пакета v3 | Весь массив `commands` был пустым. |
| `JSSDK_INTERACTION_BATCH_STRATEGY_V2_EMPTY_COMMANDS` | 400 | обработка пакета v2 | То же для v2. |
| `JSSDK_INTERACTION_BATCH_STRATEGY_V2_EMPTY_COMMAND_RESPONSE` | 500 | обработка пакета v2 | У команды в ответе не было тела — обычно проблема на стороне портала. |
| `JSSDK_INTERACTION_BATCH_EMPTY_PROCESSING_STRATEGY` | 500 | обработка пакета | Внутренняя ошибка — не удалось найти стратегию. |
| `JSSDK_ACTION_V3_LIST_FILTER_NOT_ARRAY` | 500 | `actions.v3.callList` / `fetchList` | `filter` не был массивом. Эти действия на каждой странице дописывают в него `[cursorIdKey, '>', cursor]`, поэтому расширить можно только массив: логическая группа `FilterV3` — допустимый фильтр v3, но её нужно обернуть: `filter: [FilterV3.or(...)]`. |
| `JSSDK_ACTION_V3_TAIL_FILTER_INVALID` | 500 | `actions.v3.callTail` / `fetchTail` | `filter` был объектным диалектом `restApi:v2` (`{ '>id': 100 }`). Эти действия передают `filter` без изменений, поэтому подходит массив **или** голая логическая группа — отклоняется только диалект v2, и отклоняется здесь, а не на один запрос позже, где портал сообщает об этом формулировкой, которая никогда не называет диалект. |
| `JSSDK_ACTION_CURSOR_STALLED` | 500 | `callList` / `fetchList` (**v2 и v3**), `callTail` / `fetchTail` (v3) | Курсор вернулся равным только что отправленному — сервер отвечает той же страницей, поэтому обход никогда не закончится. Эту ошибку вызывает и **короткая** страница: строка, стоящая в курсоре или до него, не может быть в ответе, учитывающем условие «строго больше», каким бы малым ни было число вернувшихся строк, поэтому курсор проверяется до того, как короткую страницу сочтут концом данных. **Списочные обходчики**: условие страницы `>` было отброшено, почти всегда потому, что поле идентификатора в ответе и в запросе пишется по-разному — сверьте `idKey` с `cursorIdKey` (в `restApi:v2` `tasks.task.list` эта пара — `idKey: 'id'`, `cursorIdKey: 'ID'`; метод v3 пишет в нижнем регистре в обоих направлениях и переопределения не требует). **Tail-обходчики**: проверьте `cursorField` — это должно быть поле, по которому сервер листает страницы, оно должно присутствовать в `select` и продвигаться между страницами. В отличие от мягкой ошибки REST, эта **отклоняет** промис, а не разрешает его. `fetchList` / `fetchTail` к этому моменту уже отдали каждую прочитанную страницу, включая повторившуюся, поэтому потребитель `for await`, который их сохранил, должен это откатить. |
| `JSSDK_ACTION_CURSOR_WENT_BACKWARDS` | 500 | `callList` / `fetchList` (**v2 и v3**), `callTail` / `fetchTail` (v3) | Курсор сдвинулся, но не в ту сторону — на значение, которое обход уже прошёл. Именно это даёт сервер, который **чередует две страницы**, и проверка на застревание выше этого не видит: значение отличается от только что отправленного, просто оно уже использовалось, поэтому обход шёл бы бесконечно. Каждый обход здесь запрашивает строки строго после курсора — списочные обходчики дописывают `[cursorIdKey, '>', cursor]`, tail-обходчики отправляют `cursor: { field, value, order }`, — поэтому курсор, не продвигающийся в собственном направлении обхода, означает, что условие страницы не было применено. Проверьте то же, что и при застревании: `idKey` относительно `cursorIdKey` для списочного обхода, `cursorField` для tail-обхода, а при `order: 'DESC'` — что `initialValue` является самым новым значением, а не самым старым. Значения, которые SDK не может упорядочить друг относительно друга, здесь **не** сообщаются; для них остаётся проверка на равенство. Оцениваются только две формы строк, и обе лишь при одинаковой длине: цифры (идентификатор с ведущими нулями) и даты и время ISO-8601 с **одним и тем же** часовым поясом и тем же разделителем. Всё остальное — курсор, у которого изменился тип, идентификаторы без ведущих нулей, значения в разном регистре, которые регистронезависимая сортировка может упорядочить иначе, чем JavaScript, и метки времени, которые переход на летнее время упорядочивает иначе (из-за смены смещения или потому, что оно вообще не указано), — пропускается, потому что защита, останавливающая здоровый обход, хуже, чем защита, пропускающая больной. |
| `JSSDK_ACTION_MAX_PAGES_EXCEEDED` | 500 | `callList` / `fetchList` (**v2 и v3**), `callTail` / `fetchTail` (v3) | Обход прочитал `maxPages` страниц и не дошёл до конца данных. Либо чтение действительно больше предела — увеличьте `maxPages` (по умолчанию **10 000**), — либо обход не продвигается способом, которого не видят предыдущие защиты: повторяющийся курсор ловит `JSSDK_ACTION_CURSOR_STALLED`, а ходящий по кругу — `JSSDK_ACTION_CURSOR_WENT_BACKWARDS`, поэтому пределу остаётся обход, значения курсора которого SDK не может упорядочить друг относительно друга. «Жадные» обходчики (`callList` / `callTail`) возвращают прочитанные строки вместе с этой ошибкой — строки верны, лишь неполны, поэтому проверяйте `isSuccess`, а не считайте возвращённый список полным. `fetchList` / `fetchTail` вместо этого выбрасывают исключение, уже отдав каждую прочитанную страницу. |
| `JSSDK_ACTION_ABORTED` | 400 | те же шесть обходчиков | Сработал `signal`, переданный в обход. Проверяется в начале каждой итерации, поэтому уже отменённый сигнал не стоит ни одного запроса. Обрабатывается как предел выше: «жадные» обходчики возвращают прочитанное с этой ошибкой, потоковые выбрасывают исключение. |
| `JSSDK_ACTION_INVALID_MAX_PAGES` | 400 | те же шесть обходчиков | `maxPages` не было положительным целым числом. `0` означало бы «ничего не обходить», а дробный предел сработал бы на номере страницы, который никто не писал, — оба отклоняются, а не приводятся. |
| `JSSDK_INTERACTION_BATCH_ROW_FAIL` | 500 | парсер строк пакета | Не удалось разобрать одну строку пакета. |
| `JSSDK_INVALID_PARAMS` | 400 | HTTP-транспорт | Форма `params` отклонена до отправки запроса. |
| `JSSDK_PARAMS_TOO_LARGE` | 413 | HTTP-транспорт | Сериализованное тело запроса превысило ограничение по размеру. Разделите вызов. |
| `JSSDK_CALL_ALL_ATTEMPTS_EXHAUSTED` | 500 | HTTP-транспорт | Только вырожденная конфигурация (`maxRetries < 1`, ни одной попытки). При обычном исчерпании повторов вместо этого возвращается реальный код нижележащей ошибки. |
| `JSSDK_HTTP_INVALID_IDEMPOTENCY_KEY` | 500 | `_prepareRequestConfig` (транспорт v3) | `idempotencyKey` — не 1–255 печатаемых ASCII-символов (`0x21-0x7E` — без пробелов и управляющих символов). Только `restApi:v3`: endpoint v2 игнорирует заголовок, поэтому транспорт v2 отбрасывает ключ с предупреждением, а не проверяет его. Выбрасывается до отправки запроса; сообщение никогда не повторяет ключ, который вызывающий код вправе построить из бизнес-идентификаторов. |
| `JSSDK_HTTP_IDEMPOTENCY_KEY_BROWSER` | 500 | `_prepareRequestConfig` (транспорт v3) | `idempotencyKey` в браузере (среде, где действует CORS). CORS preflight портала разрешает только `origin, content-type, accept`, поэтому кросс-доменный запрос с заголовком `Idempotency-Key` отклоняется, а другие формы ключа не учитываются (измерено, #573). Выбрасывается до отправки запроса, а не как сетевая ошибка, которую цикл повторов повторил бы. |
| `JSSDK_HTTP_REDIRECT_BLOCKED` | 0 | HTTP-транспорт | Редирект ответил на запрос, у которого действующее значение `maxRedirects` равно `0`. По умолчанию это пакет `restApi:v3` или вызов `restApi:v3` с `idempotencyKey` на не-вебхук транспорте, который несёт токен доступа, а редирект унёс бы его с собой (`actions.v3.deferredBatch` тоже отклоняет редиректы при скачивании файла результата, но сообщает об этом как `JSSDK_DEFERRED_BATCH_DOWNLOAD_FAILED`), — но вызывающий код, который задаёт `maxRedirects: 0` в `httpOptions` или в `ajaxClient.defaults`, относит сюда любой ответ со статусом 0, поскольку непрозрачный ответ нельзя отличить от оборванного соединения. Возникает там, где отказ иначе был бы невидим: в адаптере `fetch` ответ — непрозрачный (статус 0, пустое тело), который axios *разрешает*, поэтому без этой ошибки отклонённый запрос выглядел бы как пустой успех. Вне браузера тот же отказ приходит как обычный 301. При конфигурации по умолчанию транспорт **вебхука** до этого кода не доходит — вебхук не отправляет токен, поэтому ни один его запрос не несёт `maxRedirects: 0`, а тот же непрозрачный ответ проявляется как `JSSDK_INTERACTION_BATCH_STRATEGY_V3_EMPTY_COMMAND_RESPONSE`; если вы зададите опцию сами, вебхук выбросит её, как любой другой клиент. Не повторяется: портал ответит на следующую попытку так же. Укажите SDK конечный URL. |
| `JSSDK_UNKNOWN_ERROR` | 500 | в разных местах | Запасной вариант, когда нет более конкретного кода. |
| `JSSDK_INTERNAL_ERROR` | 500 | `SdkError.fromException` | Код по умолчанию при оборачивании неизвестного исключения. |
| `JSSDK_INTERNAL_AJAX_ERROR` | 500 | `AjaxError.fromException` | Код по умолчанию при оборачивании неизвестной HTTP-ошибки. |
| `JSSDK_CLIENT_SIDE_WARNING` | — / 500 | `B24Hook` (браузер / воркер) · `initializeB24Frame` | Два случая. Как **записанное в журнал предупреждение** (без `status`): `B24Hook` используется в браузерной среде — основной поток или Web/Shared/Service Worker, — где общепортальному секрету вебхука не место, потому что бандл читается в любом случае. Как **отклонённый `SdkError`** (`status: 500`): `initializeB24Frame()` выполнен вне iframe Битрикс24, поэтому `window.name` не содержал `DOMAIN`/`APP_SID` — откройте приложение внутри Битрикс24 (или вставьте URL в настройки приложения). Отклонение происходит сразу, а последующий вызов может повторить попытку. |
| `JSSDK_BATCH_UNREAD_COMMAND_KEY` | — | разбор команд пакета (`AbstractInteractionBatch`) | **Предупреждение в журнале**, никогда не выбрасывается. Одна или несколько команд пакета несли ключ, который SDK не читает (читаются `method`, `params`, `as`, `parallel`), **и из-за этого потеряли аргументы**: у команды не было `params` или в ней был `query` — собственное написание `restApi:v3` на уровне протокола, которое SDK записывает за вас. Выводится **один раз на пакетный запрос** — обход `batchByChunk` предупреждает один раз на порцию, поскольку каждая порция — отдельный запрос, — с названием каждого такого ключа и позициями команд, которые его несли. Ключ рядом с заполненным `params` — ваши собственные `id`, `label`, `_meta` — не затрагивается. См. [BatchV3](/docs/actions/batch/) и [BatchV2](/docs/actions/batch/). |

## Коды на стороне REST, которые приходят как `AjaxError`

Битрикс24 возвращает их в поле `error` HTTP-ответа. SDK переносит их в `AjaxError.code` без изменений — сопоставляйте по строке.

Два протокола используют **разные словари**, и код одного никогда не появляется в другом. Таблица ниже относится к `restApi:v2`; у [`restApi:v3` свои коды](#коды-restapiv3), устроенные иначе.

| Код | HTTP-статус | Значение | Типичное решение |
|---|---|---|---|
| `expired_token` | 401 | Истёк токен доступа OAuth. | SDK обновляет токен и повторяет запрос один раз в `B24Frame` / `B24OAuth`; `B24Hook` повторяет с теми же учётными данными (обновление у него ничего не делает). |
| `invalid_token` | 401 | Токен некорректен или отозван. | Обрабатывается как `expired_token` (автоматическое обновление и один повтор); если новый токен всё равно отклоняется, ошибка выбрасывается — выполните повторную авторизацию (OAuth) или исправьте URL вебхука. |
| `AUTHORIZE_ERROR` | 403 | У вызывающего нет права выполнить это действие. | Неверная область доступа вебхука или приложения либо у пользователя нет права доступа (например, на CRM). |
| `WRONG_AUTH_TYPE` | 403 | Тип токена не соответствует endpoint (например, вебхук там, где нужен OAuth). | Используйте правильный способ аутентификации для endpoint. |
| `QUERY_LIMIT_EXCEEDED` | 503 | Достигнут лимит частоты в секунду / по методу. | Уже обрабатывается встроенным `RateLimiter` — увеличивайте `restrictionParams.maxConcurrent`, только если понимаете цену. |
| `OVERLOAD_LIMIT` | 503 | Сброс нагрузки на уровне всего портала. | Отступите. При этом статусе встроенный `RateLimiter` берёт ошибку на себя и повторяет запрос — код есть в списке жёстко заданных, но сопоставители статуса проверяются первыми, поэтому этот список действует только для формы, пришедшей без статуса. `AdaptiveDelayer` — это задержка до запроса, и в повторе ошибки он не участвует. |
| `ERROR_METHOD_NOT_FOUND` | 400 | Название метода неверно или у приложения нет области доступа, чтобы его видеть. | Проверьте написание; сверьте `SCOPE` из `app.info` с областью, которую требует метод. |
| `INVALID_REQUEST` | 400 | Неверные параметры (нет обязательного поля, неверный тип). | Проверьте `error.message` — описание Битрикс24 называет проблемное поле. |

Список не исчерпывающий — полный перечень по методам Битрикс24 публикует на [apidocs.bitrix24.com](https://apidocs.bitrix24.com/). Всё, чего здесь нет, передаётся как есть в `AjaxError.code`.

## Коды `restApi:v3`

v3 отвечает в другой форме — `{ error: { code, message } }`, а не плоской парой v2, — и с другим набором кодов. `AjaxError.isV3Envelope` показывает, в какой форме пришла конкретная ошибка.

::note
**Список механический, а не отобранный вручную.** Каждая ошибка v3 — это класс в `Bitrix\Rest\V3\Exception`, а код — его полное имя в верхнем регистре с заменой `\` на `_` — именно это делает `RestException::getRegistryCode()` и ничего больше. Поэтому `Bitrix\Rest\V3\Exception\InvalidSelectException` — это всегда `BITRIX_REST_V3_EXCEPTION_INVALIDSELECTEXCEPTION`, а класс в подпространстве имён несёт его: `Validation\RequestValidationException` превращается в `…_VALIDATION_REQUESTVALIDATIONEXCEPTION`. Знать правило полезнее, чем запоминать таблицу: портал новее этой документации ответит кодами, построенными так же.
::

| Код (после префикса `BITRIX_REST_V3_EXCEPTION_`) | HTTP-статус | Значение | Типичное решение |
|---|---|---|---|
| `ACCESSDENIEDEXCEPTION` | **401 или 403** | Смотрите на статус, а не на код — см. предупреждение ниже. | 401: учётные данные не приняты по любой причине. 403: метод или его контроллер отключён на этом портале. |
| `INSUFFICIENTSCOPEEXCEPTION` | 403 | Учётные данные действительны, но у них нет области доступа, нужной этому методу. | Расширьте области доступа вебхука или приложения; `rest.scope.list` показывает, что есть у токена. Учтите, что то, что метод **указан** в `rest.documentation.openapi`, не означает права на него — см. [Обнаружение методов v3](/docs/actions/discovering-v3-methods/). |
| `METHODNOTFOUNDEXCEPTION` | 404 | На этом портале нет такого метода v3. | Проверьте написание и то, что модуль установлен, — наборы методов v3 сильно различаются между порталами. |
| `RATELIMITEXCEPTION` | 429 | Лимит частоты. | Обрабатывается автоматическим отступлением, но веткой лимита **операционного времени**, а не `RateLimiter`: классификатор сопоставляет один только HTTP 429, и этот код не сопоставляет ничто, поэтому в журнале названо `OPERATION_TIME_LIMIT`, а `RateLimiter` так и не узнаёт, что его ограничили. См. [Три слоя порождают ошибку ограничения, а не два](/docs/tools/limiters/#три-слоя-выдают-ошибку-ограничения-а-не-два). |
| `RESTUNAVAILABLEEXCEPTION` / `MARKETSUBSCRIPTIONREQUIREDEXCEPTION` | 402 | REST или это приложение недоступно на тарифе портала. | Коммерческий вопрос, а не изменение кода. |
| `VALIDATION_REQUESTVALIDATIONEXCEPTION` | 400 | Обязательное поле запроса отсутствует или некорректно — **а также** случай, когда поле существует, но у него нет атрибута, который нужен запросу: `Filterable`, чтобы встречаться в `filter` или в агрегатном `select`, `Sortable`, чтобы встречаться в `order`. | Ответ содержит массив `validation` с названием поля — именно его предоставляет [`AjaxError.validation`](#какое-поле-не-прошло-проверку-ajaxerrorvalidation). Сопоставляйте по коду и этому полю, а не по сообщению: оно локализуется. Измерено на `tasks.task.list` и `main.eventlog.list`; см. [Обнаружение полей сущности](/docs/actions/discovering-entity-fields/). |
| `INVALIDFILTEREXCEPTION` / `UNKNOWNFILTEROPERATOREXCEPTION` | 400 | Фильтр имеет форму, которую v3 не разбирает, или называет оператор, которого у него нет. | Фильтры v3 — это позиционные тройки или логические группы, см. [Фильтрация](/docs/actions/filtering/). Объектный диалект `restApi:v2` (`{ '>id': 100 }`) к ним не относится. |
| `INVALIDSELECTEXCEPTION` / `INVALIDORDEREXCEPTION` / `INVALIDPAGINATIONEXCEPTION` | 400 | Блок `select`, `order` или `pagination` сформирован неверно. В `batch` `INVALIDSELECTEXCEPTION` возникает и у элемента запроса без `method` или `query`. | Проверьте `error.message`; случай с пакетом называет требование прямо. |
| `UNKNOWNDTOPROPERTYEXCEPTION` | 400 | Названия поля нет у сущности. | Прочитайте настоящие названия через `<entity>.field.list`. Поле, которое *есть*, но не имеет нужного для применения атрибута, отвечает `VALIDATION_REQUESTVALIDATIONEXCEPTION` — см. строку выше. |
| `UNKNOWNAGGREGATEFUNCTIONEXCEPTION` | 400 | Агрегатная функция вне `sum` / `avg` / `min` / `max` / `count` / `countDistinct`. | `AggregateV3` в SDK отклоняет их до отправки. |
| `ENTITYNOTFOUNDEXCEPTION` / `ENTITYALREADYEXISTSEXCEPTION` | 400 | Строки нет или она уже есть. | Обычные результаты на уровне приложения; ветвитесь по ним. |
| `WRONGHTTPREQUESTMETHODEXCEPTION` | 400 | Метод вызван HTTP-глаголом, который он не публикует. | SDK всегда использует POST; это проявляется, когда необработанный клиент вызывает GET для метода только с POST. |
| `INTERNAL_INTERNALEXCEPTION` | 500 | Портал столкнулся с тем, чего не будет описывать, — сообщение фиксированное, «что-то пошло не так». | В ответе нечего использовать. Стоит сообщить о проблеме вместе с запросом, который её вызвал. |

Всё, что не переопределено, отвечает **400**: `RestException::STATUS` равен `400 Bad Request`, и меняют его только строки выше.

::warning
**В v3 один код охватывает все сбои аутентификации.** `ACCESSDENIEDEXCEPTION` с **401** — это то, чем портал отвечает на неверные учётные данные, на отсутствующие учётные данные и на совершенно корректные учётные данные, отправленные по обычному HTTP: на одном портале измерены три причины и побайтно одинаковые ответы. Собственное объяснение сервера отбрасывается на выходе: `RestApiServer::getRequestAccess()` сводит любой сбой `checkAuth()` к этому одному исключению и сохраняет только статус. Тот же запрос в `restApi:v2` отвечает `INVALID_CREDENTIALS` или `INVALID_REQUEST` / *Https required.* и сообщает, в чём дело.

Поэтому `ACCESSDENIEDEXCEPTION` в v3 означает «запрос не авторизован» и ничего более точного. Прежде чем браться за области доступа, проверьте банальное, о чём код не скажет, — схему URL и то, дошли ли учётные данные до запроса вообще.

SDK доставляет её как **мягкую** ошибку при обоих статусах — она есть во встроенном списке мягких, который проверяется раньше любого статуса, — поэтому она приходит в `Result`, а не выбрасывается, и 401 здесь **не** запускает обновление токена (для этого пути дополнительно нужен `expired_token` или `invalid_token`). Статус меняет то, что вам следует заключить, а не то, как ошибка до вас доходит.
::

## Шаблоны обработки

### Отличайте ошибки SDK от сбоев на стороне портала

`AjaxError` наследует `SdkError`, поэтому располагайте проверки `instanceof` от более конкретной к менее:

::rest-api-version-only
#rest-api-ver2
<!-- @check-ignore: top-level try/catch with return, not valid at module scope -->
```ts
import { AjaxError, SdkError } from '@bxshefby/b24jssdk'

try {
  await $b24.actions.v2.call.make({ method: 'crm.deal.get', params: { id: 1 } })
}
catch (error) {
  if (error instanceof AjaxError) {
    // Portal-side: error.code is the Bitrix24 code (e.g. expired_token)
    if (error.code === 'expired_token') return refreshAndRetry()
    if (error.code === 'AUTHORIZE_ERROR') return showPermissionDenied()
    throw error
  }
  if (error instanceof SdkError) {
    // SDK-side: error.code starts with JSSDK_
    throw error // these are programmer errors, surface them
  }
  throw error
}
```

#rest-api-ver3
<!-- @check-ignore: top-level try/catch with return, not valid at module scope -->
```ts
import { AjaxError, SdkError } from '@bxshefby/b24jssdk'

try {
  await $b24.actions.v3.call.make({ method: 'tasks.task.get', params: { id: 1 } })
}
catch (error) {
  if (error instanceof AjaxError) {
    // Portal-side: error.code is the Bitrix24 code (e.g. expired_token)
    if (error.code === 'expired_token') return refreshAndRetry()
    if (error.code === 'AUTHORIZE_ERROR') return showPermissionDenied()
    throw error
  }
  if (error instanceof SdkError) {
    // SDK-side: error.code starts with JSSDK_
    throw error // these are programmer errors, surface them
  }
  throw error
}
```
::

### Используйте `isSuccess` для методов без исключений

`Call`, `CallList`, `Batch`, `BatchByChunk` возвращают `Result` / `AjaxResult`, а не выбрасывают исключение при сбое на стороне REST. `CallList` и `CallTail` всё же отклоняют промис при защитах обхода, перечисленных выше (`JSSDK_ACTION_V3_LIST_FILTER_NOT_ARRAY`, `JSSDK_ACTION_V3_TAIL_FILTER_INVALID`, `JSSDK_ACTION_CURSOR_STALLED`, `JSSDK_ACTION_CURSOR_WENT_BACKWARDS`), поэтому добавьте `try`/`catch`, если они для вас важны:

::rest-api-version-only
#rest-api-ver2
<!-- @check-ignore: top-level return in callList error-handling illustration -->
```ts
const response = await $b24.actions.v2.callList.make({ /* … */ })
if (!response.isSuccess) {
  console.error(response.getErrorMessages().join('; '))
  return
}
const items = response.getData()
```

#rest-api-ver3
<!-- @check-ignore: top-level return in callList error-handling illustration -->
```ts
const response = await $b24.actions.v3.callList.make({ /* … */ })
if (!response.isSuccess) {
  console.error(response.getErrorMessages().join('; '))
  return
}
const items = response.getData()
```
::

Для пакетов с `isHaltOnError: false` значение `isSuccess` становится `false` при сбое **любого** вложенного вызова, но `getData()` по-прежнему содержит успешные записи. Если нужно узнать, какие вызовы прошли, переберите записи и проверьте `.isSuccess` у каждой.

### Перехватывайте ошибки вокруг `for await` для `FetchList`

::rest-api-version-only
#rest-api-ver2
<!-- @check-ignore: top-level for-await in fetchList error-handling illustration -->
```ts
try {
  for await (const chunk of $b24.actions.v2.fetchList.make({ /* … */ })) {
    await persist(chunk)
  }
}
catch (error) {
  if (
    error instanceof SdkError
    && error.code === 'JSSDK_CORE_B24_FETCH_LIST_METHOD_API_V2'
  ) {
    // a page request failed; persisted chunks before this point are still good
    return resumeFromLastSavedId()
  }
  if (
    error instanceof SdkError
    && (error.code === 'JSSDK_ACTION_CURSOR_STALLED' || error.code === 'JSSDK_ACTION_CURSOR_WENT_BACKWARDS')
  ) {
    // not the same situation: the walk was repeating pages, so the chunks
    // already persisted contain duplicates and have to be rolled back
    return discardAndReportStalledCursor()
  }
  throw error
}
```

### Решите, что повторять

| Условие ошибки | Можно ли безопасно повторять? |
|---|---|
| `QUERY_LIMIT_EXCEEDED`, `OVERLOAD_LIMIT` | Да — встроенный лимитер уже это делает. |
| `expired_token`, `invalid_token` (401) | Да — SDK автоматически обновляет токен и повторяет запрос один раз в каждой точке входа. |
| `AUTHORIZE_ERROR`, `WRONG_AUTH_TYPE` (403) | Нет — нужно вмешательство человека (повторная авторизация, исправление областей доступа). |
| `ERROR_METHOD_NOT_FOUND`, `INVALID_REQUEST` | Нет — запрос сформирован неверно; повтор даст ту же ошибку. |
| Сеть / 5xx без конкретного кода | Да — лимитер повторяет до `maxRetries`; при окончательном сбое выбрасывается нижележащая ошибка (с её настоящим кодом). Увеличьте `restrictionParams.maxRetries`, если нужно больше попыток. |
