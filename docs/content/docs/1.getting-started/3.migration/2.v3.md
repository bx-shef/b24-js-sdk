Здесь перечислено всё, что было помечено **`@deprecated` в линейке `2.x`** и **удалено в `3.0.0`**, и для каждого символа указана рекомендуемая замена.

::warning
**Этих символов больше нет.** В `2.x` они продолжали работать и при каждом вызове выводили
предупреждение об устаревании, а в `3.0.0` удалены. Код, который их вызывает,
не скомпилируется — это хороший случай. В обычном JavaScript такого предупреждения нет,
и код упадёт во время выполнения с ошибкой `is not a function`, поэтому выполните
[поиск ниже](#как-найти-все-места-вызова) до обновления, а не после.
::

::note
Пошаговые примеры `diff` для каждого метода есть в [руководстве v0 → v1](/docs/getting-started/migration/v1/) в разделе «Устарело». Эта страница — краткий список удалений.
::

::warning
**SDK подключён с CDN?** Тег `<script>` с адресом
`@bitrix24/b24jssdk@latest` уже сам перешёл на 3.0.0. Если приложение сломалось,
зафиксируйте `@2`, чтобы оно снова заработало, затем выполните миграцию и зафиксируйте `@3`
([#586](https://github.com/bitrix24/b24jssdk/issues/586)).
::

## Что удалено в 3.0.0

### Устаревшие сокращения REST в `AbstractB24`

Эти сокращения экземпляра не учитывали разделение `restApi:v2` / `restApi:v3`. Их заменяет явный набор действий:

| Удалено | Замена |
| --- | --- |
| `b24.callMethod(method, params, start)` | `b24.actions.v{2,3}.call.make(options)` |
| `b24.callListMethod(method, params, progress, customKeyForResult)` | `b24.actions.v{2,3}.callList.make(options)` [^idkey] — **замена не один в один, [см. ниже](#calllistmethod-замена-не-один-в-один)** |
| `b24.fetchListMethod(method, params, idKey, customKeyForResult)` | `b24.actions.v{2,3}.fetchList.make(options)` [^idkey] |
| `b24.callBatch(calls, isHaltOnError, returnAjaxResult)` | `b24.actions.v{2,3}.batch.make(options)` |
| `b24.callBatchByChunk(calls, isHaltOnError)` | `b24.actions.v{2,3}.batchByChunk.make(options)` |

[^idkey]: Передавайте правильный `idKey`: `'ID'` для классических списочных методов, `'id'` для `crm.item.*` / `restApi:v3`. Если его не указать, результат может оказаться пустым без каких-либо ошибок.

```diff
- await b24.callMethod('crm.deal.list', { filter: { '>id': 123 } }, 100)
+ await b24.actions.v2.call.make({
+   method: 'crm.deal.list',
+   params: { filter: { '>id': 123 }, start: 100 },
+   requestId: 'unique-request-id'
+ })
```

### `callListMethod`: замена не один в один

Четыре из пяти удалённых методов были тонкими обёртками: они приводили аргумент
к нужному виду и вызывали замену, поэтому заменить их можно механически. `callListMethod`
был другим: у него был собственный цикл постраничного обхода, а замена обходит данные иначе.
Меняются три вещи.

**1. Колбэка `progress` нет.** Третий аргумент `callListMethod`
сообщал процент выполнения, а у `callList.make` аналога нет, потому что заранее
общее количество неизвестно. Сообщайте о ходе выполнения самостоятельно через
[`fetchList.make`](/docs/working-with-the-rest-api/fetch-list-rest-api-ver2/),
который отдаёт по одной странице. Если нужен процент, а не счётчик
уже полученных строк, возьмите знаменатель из одного вызова `call.make`:
[`getTotal()`](/docs/working-with-the-rest-api/core-ajax-result/) по-прежнему
единственный способ посчитать строки в `restApi:v2`:

```ts
// @check-ignore: partial snippet — $b24 declared elsewhere
const first = await $b24.actions.v2.call.make({
  method: 'crm.deal.list',
  params: { filter: { '>id': 0 } }
})
const total = first.getTotal() // v2 only; 0 under restApi:v3

const rows: unknown[] = []
for await (const chunk of $b24.actions.v2.fetchList.make({ method: 'crm.deal.list' })) {
  rows.push(...chunk)
  const percent = total > 0 ? Math.round((100 * rows.length) / total) : 100
  console.log(`${percent}%`)
}
```

**2. Переданный `order` игнорируется.** `callListMethod` обходил данные по смещению
`start`, поэтому ваш `order` сохранялся. `callList` / `fetchList` обходят данные
по курсору `>id`, который *требует* сортировки именно по этому курсору, поэтому `order` убран
из типа, а если вы обходите типизацию из JavaScript, он отбрасывается во время выполнения
с записью `warning` в журнале. Сужайте выборку через `filter`. Если нужен определённый порядок строк,
отсортируйте их после сбора или листайте вручную через `call.make`
и `getNext()`.

**3. Обход идёт по курсору, поэтому важно имя поля id.** Обход по смещению
не зависел от названия id, а по курсору зависит. Передавайте `idKey` в том виде, как его пишет **ответ**,
а `cursorIdKey` — как его ждёт **запрос**. Для `tasks.task.list`
это `idKey: 'id', cursorIdKey: 'ID'`. Если ошибиться, условие страницы
ничего не найдёт. Теперь SDK это ловит: обход останавливается
с ошибкой `JSSDK_ACTION_CURSOR_STALLED`, а не зацикливается навсегда.

```diff
- const result = await b24.callListMethod(
-   'crm.deal.list',
-   { filter: { '>id': 0 }, order: { DATE_CREATE: 'DESC' } },
-   (percent) => console.log(`${percent}%`),
-   'items'
- )
+ // `order` has no equivalent — sort after collecting, and report progress
+ // from `fetchList` as shown above.
+ const result = await b24.actions.v2.callList.make({
+   method: 'crm.deal.list',
+   params: { filter: { '>id': 0 } },
+   idKey: 'ID',
+   customKeyForResult: 'items'
+ })
```

### `AbstractB24.batchSize`

> Максимальная длина ответа пакетного запроса (batch).

Статическая константа удалена. Если вы на неё опирались, подставьте значение `50`.

```diff
- if (size < AbstractB24.batchSize) {
+ if (size < 50) {
  // some code ...
}
```

### Вспомогательные методы постраничного обхода `AjaxResult` всё же не удалены

Все пять читают поля конверта `restApi:v2` — `next` / `total`. Ранее планировалось удалить их в `3.0.0` вместе с остальным устаревшим API, но **от этого плана отказались.** Все пять остаются:

| | `3.0.0` | |
| --- | --- | --- |
| `result.isMore()` / `hasMore()` | **сохранены**, только `restApi:v2` | читают `next` |
| `result.getTotal()` | **сохранён**, только `restApi:v2` | читает `total` |
| `result.getNext(http)` / `fetchNext(http)` | **сохранены**, только `restApi:v2` | повторяют запрос со смещением `next`; на клиенте `restApi:v3` **выбрасывают исключение** |

Их планировали удалить по критерию «читает поле конверта `restApi:v2`». Этот критерий описывает протокол, а не пользователя: `restApi:v2` не исчезнет ещё долго, большая часть REST-API Битрикс24 по-прежнему в нём, а удаление работающего метода сломало бы действующий код без какой-либо выгоды. Особенно показателен `getTotal()`: это **единственный** способ посчитать строки в `restApi:v2` (списочные помощники обходят данные, не раскрывая `total`, `SuccessPayload` намеренно его не содержит, а действие `actions.v3.aggregate.make` работает только в `restApi:v3` *и* помечено `@experimental`: его контракт измерен, но ни один выпущенный модуль не публикует `*.aggregate` ни на одном проверенном портале, так что считать им пока нечего). Удаление стало бы потерей возможностей под видом уборки.

**Ничего переносить не нужно.** Если вы уже перешли на списочные помощники, оставайтесь на них: это по-прежнему лучший инструмент и единственный, который работает в `restApi:v3`. Если не перешли, делать это не обязательно.

Это решение с условием пересмотра, а не бессрочное обещание, и условие зависит от метода:

- `getTotal()` / `isMore()` / `hasMore()` — пересматриваются, когда выпущенный модуль опубликует действие `*.aggregate`, а `actions.v3.aggregate` перестанет быть `@experimental` (тогда на практике появится счёт в v3 и у `getTotal()` впервые будет замена), **или** когда объявят дату отключения `restApi:v2`.
- `getNext()` / `fetchNext()` — только дата отключения `restApi:v2`. Рабочая замена у них уже есть, поэтому зрелость `aggregate` ничего не меняет.

::warning
Все пять работают **только в `restApi:v2`**, и так было всегда. В `restApi:v3`:

- `getTotal()` возвращает `0`{lang="ts-type"}, а `isMore()` возвращает `false`{lang="ts-type"} — **потому что поле отсутствует**, а не потому что строк ноль или они закончились. Не ветвите логику по этим значениям.
- `getNext()` / `fetchNext()` **выбрасывают** `SdkError({ code: 'JSSDK_CORE_METHOD_NOT_SUPPORT_IN_API_V3' })`{lang="ts-type"}. Это сделано намеренно: возврат `false` нельзя было бы отличить от «последней страницы».
::

В новом коде по-прежнему рекомендуются списочные помощники: [`callList.make`](/docs/working-with-the-rest-api/call-list-rest-api-ver2/) (собрать всё) или [`fetchList.make`](/docs/working-with-the-rest-api/fetch-list-rest-api-ver2/) (асинхронный генератор, одна страница на итерацию). Они скрывают работу со смещением и работают в обеих версиях протокола:

```diff
- // manual paging: yours to maintain, and v2-only
- const res = await b24.actions.v2.call.make({ method: 'crm.deal.list' })
- let list = res.getData()!.result
- while (res.isMore()) { res = await res.getNext(http); list.push(...res.getData()!.result) }
+ // the list helper iterates for you — `chunk` is the next array of items
+ for await (const chunk of b24.actions.v2.fetchList.make({ method: 'crm.deal.list' })) {
+   // handle chunk
+ }
```

### `LoggerBrowser` и `LoggerType`

Заменены универсальной системой [`Logger` / `LoggerFactory`](/docs/working-with-the-rest-api/logger/). Перечисление `LoggerType` удалено без замены: уровнями управляет `LoggerFactory`, поэтому просто уберите импорт:

```diff
- import { LoggerBrowser, LoggerType } from '@bitrix24/b24jssdk'
+ import { LoggerFactory } from '@bitrix24/b24jssdk'

- const $logger = LoggerBrowser.build('MyApp', import.meta.env?.DEV === true)
+ const $logger = LoggerFactory.createForBrowser('MyApp', import.meta.env?.DEV === true)

- $logger.info('response', dataList)
+ $logger.info('response', { someInfo: dataList })
```

## `Result<T>` по умолчанию `unknown`, а не `any`

**Что изменилось.** У `Result<T>`{lang="ts-type"} и `IResult<T>`{lang="ts-type"}
было объявлено `T = any`{lang="ts-type"}. Теперь объявлено
`T = unknown`{lang="ts-type"}. То же сужение коснулось
`TypeCallParams`: его универсальная индексная сигнатура теперь
`[key: string]: unknown`{lang="ts-type"} вместо `any`, вложенное поле
`params` — `Record<string, unknown>`{lang="ts-type"}, а `filter` — это
`TypeFilterV2 | TypeFilterV3`{lang="ts-type"}. Типы для отдельных версий
`TypeCallParamsV2`{lang="ts-type"} / `TypeCallParamsV3`{lang="ts-type"}
по-прежнему сужают `filter` до своего диалекта, так что если вы уже ими пользовались, ничего не меняется.

**Кого это затрагивает.** Всех, кто писал `Result`{lang="ts-type"} без аргумента типа,
а затем читал из него поле. Раньше это молча компилировалось, потому что
`any` распространяется дальше:

```diff
- const batch: Result = await b24.actions.v2.batch.make({ calls, options })
- const list = batch.getData().CompanyList.items // any — no check, no help
+ const batch = await b24.actions.v2.batch.make<{ items: Company[] }>({ calls, options })
+ const data = batch.getData() as { CompanyList?: { items?: Company[] } } | undefined
+ const list = data?.CompanyList?.items ?? []
```

**Что делать.** Укажите тип данных. У каждого действия есть обобщённый параметр:
`call.make<T>`, `batch.make<T>`, `callList.make<T>`. Это лучшее решение,
потому что тип тогда проходит через всё чтение. Если форма данных
действительно неизвестна до выполнения, одно приведение типа в месте чтения
сохраняет проверку остального кода.

::note
**Индексная сигнатура осталась.** Сузился только тип значения. Убрать
`[key: string]` совсем рассматривали, но отвергли, посчитав наши собственные
примеры: `crm.item.get` **это** `{ entityTypeId, id }`, и эти ключи — полезная нагрузка,
а не лазейка; закрытый тип перестал бы компилировать большую часть
документации. `unknown` убирает `any` из типа, не запрещая привычный способ
вызова API.
::

::note
**Результат `batch` больше не нужно сужать вручную.** Он действительно приходит
в одной из четырёх форм, в зависимости от того, переданы ли команды именованным объектом
или массивом, и от `returnAjaxResult`. Но теперь у `batch.make` есть перегрузки
ровно по этим аргументам (#518), и компилятор сам выбирает нужную. Приведения типов,
написанные под прежний union, можно убрать. См.
[таблицу возвращаемых значений](/docs/working-with-the-rest-api/batch-rest-api-ver2/#возвращаемое-значение).
::

## Среда выполнения: Node 20 больше не поддерживается в 3.0.0

`3.0.0` повышает минимальную версию Node. `engines.node` меняется с `^20.0.0 || >=22.0.0` на
`>=22.0.0`, поэтому **Node 20 больше не поддерживается**.

Поддержка Node 20 закончилась 2026-04-30: исправления безопасности для неё больше не выходят.
При этом CI давно тестирует только Node 22 и 24, так что `2.x` заявлял
версию, которую никто не проверял. `3.0.0` устраняет это расхождение.

Что это значит для вас:

- На **Node 22 и новее** ничего не меняется.
- На **Node 20** `npm install` выводит предупреждение `EBADENGINE`, а при
  `engine-strict=true` (в pnpm это значение по умолчанию внутри workspace) установка
  завершается ошибкой. Перейдите на Node 22 (LTS) или новее до обновления.

Это требование к окружению, а не изменение API: код менять не нужно, только версию
Node, на которой вы работаете. В вашем исходном коде переносить нечего.

## Поведение: ошибки v3 классифицируются по категории ответа

Это единственное изменение в `3.0.0`, которое меняет работу кода **без ошибки компиляции**,
поэтому прочитайте этот раздел, даже если сборка проходит чисто.

В `restApi:v3` ошибка, пришедшая в конверте ошибок v3 с HTTP-кодом
**4xx, кроме 401, 408 и 429**, теперь возвращается внутри `AjaxResult` (мягкая ошибка)
независимо от своего кода. В линейке `2.x` это поведение включалось параметром ограничений
`classifyV3ErrorsByCategory`, по умолчанию `false`. В `3.0.0`
это правило стало обычным поведением, а параметр удалён.

### Если вы передавали параметр

Удалите эту строку. TypeScript сообщит о неизвестном свойстве, а нужное вам поведение
теперь включено по умолчанию.

```diff
  await $b24.setRestrictionManagerParams({
    ...ParamsFactory.getDefault(),
-   classifyV3ErrorsByCategory: true,
    hardErrorCodes: ['MY_APP_BAD_PAYLOAD']
  })
```

### Если не передавали

Тогда доставка части ошибок v3 изменится, а **компиляция не сломается**. Ошибка v3 с кодом 4xx,
которая раньше отклоняла промис, теперь его завершает успешно. Поэтому
`try / catch` вокруг вызова перестаёт срабатывать, управление уходит в ветку успеха,
где `response.getData()` равен `undefined`, а следующая строка читает из него поле.

```ts
// Before 3.0.0 this caught an unlisted v3 4xx. It no longer does.
try {
  const response = await $b24.actions.v3.call.make({ method: 'main.eventlog.list', params: {} })
  console.log(response.getData()!.result)
}
catch (error) {
  console.error(error)
}
```

```ts
// The shape that works on both: check the result, then catch what is left.
const response = await $b24.actions.v3.call.make({ method: 'main.eventlog.list', params: {} })
if (!response.isSuccess) {
  console.error(response.getErrorMessages().join('; '))
}
else {
  console.log(response.getData()!.result)
}
```

Проверять `isSuccess` и раньше требовалось для каждого кода, закреплённого как мягкий: это девять
встроенных кодов v3 и всё, что есть в вашем `softErrorCodes`. Так что если вы проверяли,
вы уже обрабатывали этот путь для части ошибок, а теперь обрабатываете для большего их числа.
**Всё, что в `2.x` было мягким, не становится выбрасываемым.** Изменение идёт только в одну сторону.

### Если нужно прежнее поведение для конкретного кода

Закрепите его. `hardErrorCodes` проверяется раньше правила по категории, поэтому
указанный там код по-прежнему выбрасывается:

```ts
import { ParamsFactory } from '@bitrix24/b24jssdk'

await $b24.setRestrictionManagerParams({
  ...ParamsFactory.getDefault(),
  hardErrorCodes: ['BITRIX_REST_V3_EXCEPTION_INVALIDPAGINATIONEXCEPTION']
})
```

Переключателя, который целиком вернул бы старую классификацию, нет, и это сделано намеренно:
флаг с двумя режимами без срока удаления — это способ, которым слой совместимости становится
постоянным. Поэтому у этого флага и был запланированный срок окончания
(#480).

### Что не затронуто

5xx, 401, 408 и 429; весь `restApi:v2`, плоское тело ошибки которого не является
конвертом v3; и каждый код, закреплённый во встроенном списке жёстких ошибок, включая
`…INSUFFICIENTSCOPEEXCEPTION` с кодом 403. Подробнее в разделе
[Коды ошибок](/docs/working-with-the-rest-api/error-codes/#classification-by-category-restapiv3).

## Поведение: браузер теперь использует адаптер `fetch`

Ещё одно изменение, которое меняет работу кода **без ошибки компиляции**.

Axios выбирает адаптер, перебирая `['xhr', 'http', 'fetch']` и беря первый поддерживаемый.
Поэтому везде, где есть `XMLHttpRequest` (в окне или воркере), выбирался **XHR** —
из-за порядка в списке, а не по достоинствам. В `3.0.0` SDK в браузерной среде
запрашивает `fetch`. Node это не затрагивает: там XHR нет, выбирается адаптер `http`,
и так остаётся.

«Браузерная среда» означает браузер **или воркер**, то есть тот же набор, что
определяет [`isBrowserLikeRuntime()`](#поведение-воркер-больше-не-считается-сервером)
ниже: именно этот предикат использует SDK.

Из этого следуют три вещи, и только в браузере.

**1. Заблокированный редирект теперь даёт ошибку.** `maxRedirects: 0` `fetch` читает
(как `redirect: 'manual'`), а XHR его полностью игнорировал. SDK задаёт его для одного запроса —
пакетного запроса `restApi:v3` по транспорту без вебхука, который несёт токен доступа,
и редирект на поддомен передал бы его дальше. Поэтому на этом пути развёртывание с редиректом
теперь завершается ошибкой `JSSDK_HTTP_REDIRECT_BLOCKED`, тогда как раньше переход
молча выполнялся. Обычные вызовы не затронуты, если только вы сами не задали
`maxRedirects: 0` в `httpOptions`: тогда любой ответ со статусом 0 попадает в одну категорию,
потому что непрозрачный ответ не отличить от оборванного соединения.

**2. Тестовая подмена `XMLHttpRequest` перестаёт перехватывать запросы.** `jsdom`
здесь считается браузером, поэтому набор тестов, мокающий XHR, больше не видит трафик SDK.

**3. `onUploadProgress` в ваших собственных запросах через `ajaxClient`** работает хуже
вне Chromium: axios привязывает его к потоковой отправке запроса, которой нет в Firefox и Safari,
тогда как XHR всегда отдавал события прогресса.

### Как отказаться

Каждая точка входа принимает `httpOptions` при создании, они объединяются с собственными
настройками axios по умолчанию, поэтому явно указанный адаптер побеждает:

```ts
import { B24Hook } from '@bitrix24/b24jssdk'

const $b24 = B24Hook.fromWebhookUrl(
  'https://your-portal.bitrix24.com/rest/1/SECRET',
  { httpOptions: { adapter: 'xhr' } }
)
```

`B24Hook`, `B24OAuth` и `B24Frame` принимают ту же опцию. Для приложения во фрейме, которого это изменение касается в первую очередь, передавайте её в [`initializeB24Frame()`](/docs/working-with-the-rest-api/frame-initialize-b24-frame/) — единственный поддерживаемый способ создать `B24Frame`: `initializeB24Frame({ httpOptions: { adapter: 'xhr' } })`. Это
узкая часть `AxiosRequestConfig`{lang="ts-type"} — `TypeHttpOptions`{lang="ts-type"} — намеренно:
ключи, нужные SDK для связи с порталом, там не предлагаются (ключ вне списка
отбрасывается при создании, а его имя пишется в журнал). Их можно менять через
[`ajaxClient.defaults`](/docs/working-with-the-rest-api/core-http/#configuring-the-axios-instance).

## Поведение: зацикленный или движущийся назад курсор теперь останавливает обход

В `2.3.0` каждый обход списка и хвоста научили останавливаться, когда курсор постраничного вывода
**повторяется** (`JSSDK_ACTION_CURSOR_STALLED`{lang="ts-type"}). Эта проверка сравнивает
значение с *непосредственно предыдущим*, а `3.0.0` закрывает два оставшихся пробела.

**Сервер, который чередует две страницы**: курсор `A`, `B`, `A`, `B`, … Он
никогда не повторяет только что отправленное значение, и обход шёл бесконечно: потоковые помощники
возвращали одни и те же строки по кругу, а жадные наращивали массив, пока процесс не падал.
Каждый обход запрашивает строки строго после курсора (`[cursorIdKey, '>', cursor]`
для обхода списка, `cursor: { field, value, order }` для обхода хвоста), поэтому
курсор должен на каждой странице двигаться в направлении самого обхода. Значение, которое идёт
в другую сторону, теперь даёт `SdkError`{lang="ts-type"} с кодом `JSSDK_ACTION_CURSOR_WENT_BACKWARDS`{lang="ts-type"}. Поскольку
любой цикл где-то обязан шагнуть назад, это ловит цикл **любой** длины, а также курсор,
который просто идёт назад: он теряет строки, а не зацикливается, и раньше его никто не искал.

**Остановка на странице короче предыдущей** завершала обход как конец данных
независимо от курсора, поэтому результат возвращался усечённым, со строками,
повторяющими более раннюю страницу, и считался успешным. Теперь курсор проверяется
**до** остановки по концу данных: строка, не превышающая курсор, не может
присутствовать в ответе, соблюдавшем условие «строго больше», как бы коротка ни была страница.
Значит, короткая страница с неподвижным курсором означает, что сервер игнорирует условие,
а не что данные закончились.

### Что это значит для вашего кода

Ничего, если ваши обходы завершаются: корректный обход двигает курсор на каждой
странице, это и проверяется. Измерения на живом портале: `callList` v3 по
`main.eventlog.list` возвращает 68 строк, все уникальны и строго возрастают,
а `callTail` с `order: 'DESC'` возвращает те же строки строго по убыванию.
Обе проверки проходят.

Если вы перехватываете код остановки, перехватывайте и парный к нему:

```ts
import { SdkError } from '@bitrix24/b24jssdk'

try {
  const response = await $b24.actions.v3.callList.make({
    method: 'tasks.task.list',
    customKeyForResult: 'items'
  })
  console.log(response.getData())
}
catch (error) {
  if (
    error instanceof SdkError
    && (error.code === 'JSSDK_ACTION_CURSOR_STALLED' || error.code === 'JSSDK_ACTION_CURSOR_WENT_BACKWARDS')
  ) {
    // Pagination is broken for this method — check `idKey` / `cursorIdKey`, or
    // `cursorField` for a tail walk. Nothing collected is worth keeping.
  }
  else {
    throw error
  }
}
```

::note
**Значения, которые SDK не умеет упорядочивать, не считаются движением назад.** Числа
оцениваются, когда оба конечны. Строки оцениваются только в двух формах, где порядок JavaScript
заведомо совпадает с серверным: обе одинаковой длины, и только как цифры (id с ведущими нулями)
или как даты ISO-8601, указывающие **одну и ту же** зону
с одним разделителем.

Всё остальное возвращается к прежней проверке на равенство: курсор, у которого сменился
тип (`100`{lang="ts-type"}, затем `'100'`{lang="ts-type"}), id разной
длины (`'9'`{lang="ts-type"}, затем `'10'`{lang="ts-type"}, где
лексикографический порядок расходится с числовым), значения в разном регистре, которые
портал с нечувствительной к регистру сортировкой может упорядочить иначе, чем JavaScript,
и метки времени, которые перевод на летнее время переставляет: те, у которых
меняется смещение UTC, и те, где смещение не указано вовсе (голое
`2024-10-27 02:15:00`{lang="ts-type"}, где повторяющийся час по настенным часам
ставит более поздний момент раньше). Защита отказывается судить, а не гадает:
ложное «назад» отвергло бы работающий обход, и это хуже, чем пропустить
неработающий.
::

## Поведение: воркер больше не считается сервером

У `getEnvironment()`{lang="ts-type"} появился четвёртый элемент, `Environment.WORKER`{lang="ts-type"}, и Web, Shared и
Service Workers теперь возвращают его вместо `UNKNOWN`{lang="ts-type"}.

Среда, которая сообщает версию Node, остаётся `NODE`{lang="ts-type"}, даже если она строится по образцу
Worker API: Deno worker и Cloudflare Worker с `nodejs_compat` ведут себя так,
потому что это серверы, и вебхуку место именно там. Bun worker сообщает
`NODE`{lang="ts-type"} по той же причине, а Cloudflare Worker *без* `nodejs_compat` —
`UNKNOWN`{lang="ts-type"}; подробности на
[странице Environment](/docs/working-with-the-rest-api/tools-environment/).

Элемент перечисления — видимая часть. Часть, меняющая поведение: SDK
больше не считает воркер сервером:

- он больше не задаёт там заголовок `User-Agent` по умолчанию: это **запрещённый заголовок**
  в любом браузерном контексте, и браузер его всё равно отбрасывал;
- предупреждение «вебхук только для сервера» теперь срабатывает и в воркере, где
  раньше не срабатывало. Код, отправленный в воркер, так же публичен, как код в основном потоке,
  и секрет попадает в сборку в обоих случаях;
- `TelegramHandler` больше не отправляет сообщения из воркера. Он выводит предупреждение в консоль, как
  в браузере, а `testConnection()` возвращает `false`{lang="ts-type"}, а не подставляет
  токен бота в URL. Раньше воркер попадал в тихий запасной путь,
  и проверка соединения отправляла запрос.

Это тот же набор сред, что и в
[изменении адаптера](#поведение-браузер-теперь-использует-адаптер-fetch) выше: один
предикат отвечает за оба случая, поэтому воркер и браузер обрабатываются одинаково
во всём, кроме DOM.

::warning
**Определение среды — страховка, а не граница.** Браузерный воркер, собранный с
полифилом `process`, который сообщает версию Node (`unenv` за Nitro и Nuxt
отвечает `{ node: '22.14.0' }`), считается сервером, и три поведения
выше к нему не применяются. Это компромисс сделан намеренно (иначе настоящие серверы,
такие как воркеры Deno и Cloudflare, определялись бы неверно, и им выводилось бы
предупреждение об утечке секретов). Поэтому секрету вебхука или токену бота
по-прежнему не место в коде, который уходит клиенту, что бы ни определил SDK.
::

Если вы сами ветвите код по `getEnvironment()`{lang="ts-type"}, проверьте, какой вопрос
задаёт ваша ветка. `=== Environment.BROWSE`{lang="ts-type"} означает «есть DOM», а воркер
правильно **не** `BROWSE`{lang="ts-type"}: эта ветка продолжает работать. Ветка `default:`{lang="ts-type"} или `=== Environment.UNKNOWN`{lang="ts-type"},
которая раньше ловила воркеры, больше не ловит. Для всего, что не касается DOM
(CORS, запрещённые заголовки, публичность вашего кода), используйте новый
`isBrowserLikeRuntime()`{lang="ts-type"}, который `true`{lang="ts-type"} и для браузера, и для воркера.

```diff
- if (getEnvironment() !== Environment.BROWSE) {
-   // "must be a server" — this was wrong in a worker
+ if (!isBrowserLikeRuntime()) {
+   // a server, and only a server
    useWebhookSecret()
  }
```

## Поведение: настройки axios фильтруются, а не передаются целиком

`httpOptions` принимает именованную часть `AxiosRequestConfig`{lang="ts-type"} — `TypeHttpOptions`{lang="ts-type"}, — а ключ
вне неё **отбрасывается при создании**, при этом в журнал пишется его имя (но не значение). Одного
типа недостаточно: проверка лишних свойств не срабатывает для
значения, пришедшего через переменную, а в обычном JavaScript компилятора нет вовсе. Измерено на
неотфильтрованном пути: переданный так `transformRequest`
полностью заменял тело запроса, без ошибки на обеих сторонах, а сбой был только на стороне портала.

**Это сужает и поверхность, которая была выпущена.** `HttpV2`{lang="ts-type"} и `HttpV3`{lang="ts-type"} экспортируются, и
их второй аргумент конструктора типизирован как `object`. Поэтому в `2.x` прямой вызов
`new HttpV2(auth, { baseURL, responseType, transformResponse, … })` принимался
сигнатурой и доходил до axios без изменений. Начиная с `3.0.0` эти ключи
отбрасываются. Для тех, кто создаёт клиентов обычным способом, ничего не меняется: до появления `httpOptions`
точки входа ничего не передавали.

```diff
- const http = new HttpV2(auth, { baseURL: 'https://proxy.internal/rest/' })
+ const http = new HttpV2(auth)
+ http.ajaxClient.defaults.baseURL = 'https://proxy.internal/rest/'
```

`headers` — единственный ключ, который по-прежнему объединяется как раньше, и только на этом прямом пути;
в `httpOptions` он не предлагается.

## Поведение: тип содержимого JSON задаётся явно, а не наследуется

SDK всегда отправлял тела в формате JSON, но никогда не указывал тип содержимого: axios
сам подставляет `application/json` для тела-объекта. Начиная с `3.0.0`
SDK сам задаёт заголовок для каждого запроса.

Это важно, потому что экземпляр axios публичный. `Content-Type` в
`ajaxClient.defaults` раньше менял кодировку каждого запроса SDK, а портал читает булево значение в `filter` **только** из тела JSON: при
`application/x-www-form-urlencoded` значение `false`{lang="ts-type"} приходит как
строка `"false"`, условие отбрасывается, и вызов возвращает строки,
которые должен был исключить, без ошибки на обеих сторонах. См.
[Фильтрация](/docs/working-with-the-rest-api/filtering/).

Менять ничего не нужно, если вы не рассчитывали на этот механизм по умолчанию для
перекодирования трафика SDK. `ajaxClient.defaults.headers` больше на него не влияет; ваши
собственные запросы через тот же экземпляр не затронуты, включая `FormData`.

## Типизация: `placement.options` больше не `any`

`placement.options` у `B24Frame` раньше имело тип `any`{lang="ts-type"} для значения,
которое приходит с портала через границу `postMessage`{lang="ts-type"}. В
`3.0.0` это `Readonly<Record<string, unknown>>`{lang="ts-type"}.

Чтение ключа по-прежнему компилируется и даёт `unknown`{lang="ts-type"}. Перестаёт компилироваться
всё, что вы потом с ним *делаете*, пока не сузите тип. В этом и смысл: отчёт, с которого начались эти изменения,
был про условие, переданное в слайдер и прочитанное
как `options.payload.id`{lang="ts-type"}: это компилировалось без единого слова и во время выполнения
было `undefined`{lang="ts-type"}.

```diff
- const id = $b24.placement.options.payload.id
+ const payload = $b24.placement.options['payload']
+ const id = payload !== null && 'object' === typeof payload
+   ? (payload as { id?: unknown }).id
+   : undefined
```

Три вида поломок, чтобы вы знали, что искать:

| что вы написали | что происходит теперь |
|---|---|
| `options.payload.id` — обращение вглубь | ошибка: `payload` имеет тип `unknown` |
| `const s: string = options['place']` — присваивание конкретному типу | ошибка: `unknown` не является `string` |
| `helper(options)`, где `helper` принимает `Record<string, string>` | ошибка: значения имеют тип `unknown` |

Последний случай легко упустить: ошибка переезжает в место вызова, а не в обращение
к свойству.

::warning
**Если вы разбирали значение сами, перестаньте.** Раньше в документации советовали
осторожно применять `JSON.parse`{lang="ts-type"}, потому что одна из форм передачи — строка JSON.
Теперь эта форма разбирается за вас, поэтому старый совет выбрасывает
`SyntaxError`{lang="ts-type"} на объекте. TypeScript этого не поймает в кодовой базе на JavaScript:
это единственное изменение здесь, которое проявляется только во время выполнения.
::

Две вещи стали **проще**, а не сложнее:

- **`options` никогда не `undefined`.** Портал присылает объект, строку JSON
  или пустую строку, если у встройки (placement) не было параметров; все три приводятся к объекту
  до того, как вы их увидите, поэтому `?.`{lang="ts-type"}, который раньше был нужен, теперь лишний.
  (Лишний, но не ошибка: проект со `strict` по умолчанию по-прежнему компилирует `options?.place`.)
- **Строка JSON разбирается за вас.** Совет «разбирать осторожно», который раньше был
  в документации, ушёл вместе с этим.

Одно намеренно **потеряно**: пять форм передачи теперь сводятся к пустому
объекту, и потом их нельзя различить: отсутствующее значение, `''`, действительно
пустой объект, массив и строка, не являющаяся JSON. Доступа к исходному значению нет.
Если вам нужно их различать, создайте issue, а не обходите ограничение:
формы, теряющие информацию, не отправляет ни один известный источник.

Что **не** изменилось: **регистр ключей по-прежнему определяет портал.** Для встройки
по умолчанию объект буквально является строкой запроса URL фрейма, поэтому ключи
такие, как их записал тот, кто открыл фрейм; для зарегистрированной встройки — такие, как приложение
сохранило при привязке.

`isSliderMode`{lang="ts-type"} по-прежнему читает `IFRAME === 'Y'` — строку, потому что на пути
встройки по умолчанию она приходила из строки запроса. Ответ изменился в одном случае:
для формы со строкой JSON он раньше читал свойство у строки и возвращал `false`{lang="ts-type"}
при любом значении, а теперь возвращает `true`{lang="ts-type"}, если этот JSON содержит `"IFRAME":"Y"`. Булево
`true`{lang="ts-type"}, которое может сохранить зарегистрированная встройка, по-прежнему не
засчитывается, так задумано.

::note
Тип данных на проводе тоже изменился: `MessageInitData.PLACEMENT_OPTIONS`{lang="ts-type"} теперь
`unknown`{lang="ts-type"}, а не `Record<string, any>`{lang="ts-type"}, что никогда не было верным
для двух строковых форм. Если вы читаете этот тип напрямую, а не через
`b24.placement.options`{lang="ts-type"}, сужайте его или, лучше, перестаньте: менеджер
как раз делает это один раз за вас.
::

## Типизация: `openSliderAppPage` возвращает `unknown` и завершается при закрытии

`slider.openSliderAppPage()`{lang="ts-type"} имел тип `(params: any) => Promise<any>`{lang="ts-type"}.
В `3.0.0` это `(params: object) => Promise<unknown>`{lang="ts-type"}, в соответствии с тем,
что портал делает на самом деле, как измерено на живом облачном портале
([#486](https://github.com/bitrix24/b24jssdk/issues/486)):

- Промис завершается, когда слайдер **закрыт** (крестиком портала или
  `closeSliderAppPage()`{lang="ts-type"}), а не когда он открыт.
- Он разрешается пустой строкой `''`{lang="ts-type"}. Из открытого фрейма
  таким способом ничего не возвращается.

Поэтому единственное, что перестаёт компилироваться, — чтение поля из результата,
а читать там никогда было нечего. Любой объектный литерал или значение типа интерфейса
по-прежнему подходит как `params`.

```diff
- const result = await $b24.slider.openSliderAppPage({ place: 'deal', id: 42 })
- if (result.saved) reloadList()
+ $b24.slider.openSliderAppPage({ place: 'deal', id: 42 })
+   .then(() => reloadList()) // the user closed the slider
+   .catch(() => {})
```

Если вы делаете `await`, чтобы «открыть» слайдер, ваш код будет ждать, пока пользователь его закроет.
Передавайте результаты через свой бэкенд или `appOption`.

Одно изменение поведения в той же области: после `$b24.destroy()`{lang="ts-type"}
`initializeB24Frame()`{lang="ts-type"} теперь создаёт **новый** фрейм. Раньше он возвращал
уничтоженный, на котором любой вызов зависал без завершения. С этим сталкивалось SPA,
которое уничтожало `$b24` при размонтировании и инициализировало его снова в другом месте.

## Как найти все места вызова

В `2.x` эти символы заявляли о себе предупреждением `JSSDK_CORE_DEPRECATED_METHOD`
при каждом вызове. В `3.0.0` их нет, и предупреждать больше нечему:
**TypeScript** сообщает о каждом месте вызова как об ошибке, а обычный JavaScript
не жалуется, пока строка не выполнится. В любом случае сначала найдите их статически:

::tabs{class="mt-0"}

:::tabs-item{label="Linux / macOS (bash)"}

```bash
grep -rnE 'callMethod|callListMethod|fetchListMethod|callBatch|callBatchByChunk|LoggerBrowser|LoggerType|placement\.options|PLACEMENT_OPTIONS|openSliderAppPage|getEnvironment|Environment\.' src
```

:::

:::tabs-item{label="Windows (PowerShell)"}

```powershell
Get-ChildItem -Recurse src -Include *.ts,*.js |
  Select-String -Pattern 'callMethod|callListMethod|fetchListMethod|callBatch|callBatchByChunk|LoggerBrowser|LoggerType|placement\.options|PLACEMENT_OPTIONS|openSliderAppPage|getEnvironment|Environment\.'
```

:::

::

Когда поиск ничего не вернёт, кроме совпадений с `getEnvironment`, которые требуют прочесть и решить, а не исправить, вы готовы к `3.0.0`. Если вы пишете на TypeScript,
более надёжная проверка — `tsc --noEmit` после обновления: она находит места вызова,
которые поиск пропустит, например вызов через переменную типа `TypeB24`.

::warning
**`getEnvironment` в этом списке по обратной причине: здесь компилятор не поможет.**
Удалённые символы не компилируются, а ветвление по среде компилируется отлично
и просто отвечает иначе, потому что воркер теперь сообщает
[`Environment.WORKER`](#поведение-воркер-больше-не-считается-сервером)
вместо того, чтобы попасть в `UNKNOWN`. Прочитайте каждое совпадение и решите, какой вопрос
оно задаёт: «есть ли DOM» (`=== Environment.BROWSE`, без изменений) или «действуют ли
правила браузера» (теперь `isBrowserLikeRuntime()`).
::
