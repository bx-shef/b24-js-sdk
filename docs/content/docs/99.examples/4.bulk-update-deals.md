## Цель

Прочитать CSV-таблицу соответствий `dealId,newStageId` и применить смену стадии к каждой строке. Это могут быть сотни или десятки тысяч сделок: `BatchByChunkV2.make()` сам разбивает вызовы на блоки по 50 команд в пакете, ручная постраничная выборка не нужна.

## Стек и требования

- Node.js 20+, ESM
- `@bitrix24/b24jssdk@^1.0.0`
- Вебхук с правом доступа (scope) `crm`, заданный как `B24_HOOK`.
- CSV-файл `migrations.csv`:

  ```csv
  dealId,newStageId
  1234,WON
  1235,WON
  1240,LOSE
  ```

```bash
pnpm add @bitrix24/b24jssdk
export B24_HOOK="https://your-portal.bitrix24.com/rest/1/xxxxxxxxxxxxxxxx/"
```

## Полный пример

`scripts/migrate-deals.mjs`:

```js
import { readFile } from 'node:fs/promises'
import {
  B24Hook,
  EnumCrmEntityTypeId,
  ParamsFactory
} from '@bitrix24/b24jssdk'

const hookUrl = process.env.B24_HOOK
if (!hookUrl) {
  console.error('B24_HOOK is not set')
  process.exit(2)
}

const csv = await readFile(process.argv[2] ?? 'migrations.csv', 'utf8')
const rows = csv
  .split(/\r?\n/)
  .slice(1) // header
  .filter(Boolean)
  .map((line) => {
    const [dealId, newStageId] = line.split(',')
    return { dealId: Number(dealId), newStageId }
  })

console.log(`planned updates: ${rows.length}`)

const b24 = B24Hook.fromWebhookUrl(hookUrl, {
  restrictionParams: ParamsFactory.getBatchProcessing()
})

const calls = rows.map(({ dealId, newStageId }) => [
  'crm.item.update',
  {
    entityTypeId: EnumCrmEntityTypeId.deal,
    id: dealId,
    fields: { stageId: newStageId }
  }
])

const response = await b24.actions.v2.batchByChunk.make({
  calls,
  options: {
    isHaltOnError: false,
    requestId: `deal-stage-migration-${Date.now()}`
  }
})

if (!response.isSuccess) {
  console.error('partial failure:')
  for (const message of response.getErrorMessages()) {
    console.error(`  - ${message}`)
  }
  process.exit(1)
}

console.log(`updated: ${response.getData()?.length ?? 0} of ${rows.length}`)
```

## Запуск

```bash
node scripts/migrate-deals.mjs migrations.csv
# planned updates: 3450
# updated: 3450 of 3450
```

Если несколько строк завершатся ошибкой (удалённая сделка, нет права доступа, неверная стадия), `isHaltOnError: false` позволит остальным командам пакета выполниться, а скрипт после вывода списка ошибок завершится с кодом `1`.

## Как это работает

- `BatchByChunkV2.make({ calls })` принимает произвольное число команд и сам разбивает их на пакеты по 50 — это жёсткий предел на запрос. Порядок результатов совпадает с порядком входных данных.
- `Result.isSuccess` становится `false`, если в любой части была ошибка. `getErrorMessages()` возвращает по одному сообщению на каждый неудачный вызов. Успешные вызовы по-прежнему доступны в `getData()`, то есть частичный прогресс сохраняется.
- `ParamsFactory.getBatchProcessing()` делает клиент более осторожным, а не более либеральным: он вдвое снижает частоту запросов (`drainRate` 2 → 1, `burstLimit` 50 → 30) и **снижает** пороги, при которых выдаётся предупреждение и начинает добавляться задержка (оба 80% → 50%). Поэтому долгая миграция отступает раньше и не мешает очереди портала отвечать на живой трафик интерфейса. Сам бюджет времени операций не меняется.
- Имя запроса через `options.requestId` упрощает фильтрацию логов на стороне портала. Оно **не** защищает от случайного повторного запуска: это метка для отслеживания, и портал спокойно запишет данные дважды. На `restApi:v3` от этого защищает [`idempotencyKey`](/docs/actions/call/#idempotency-key).

## Ограничения

- Нужна форма `calls` в виде кортежей из двух элементов: `BatchByChunkV2` намеренно отклоняет команды с именованными объектами, потому что границы частей разорвали бы имена.
- Каждая команда расходует дневной бюджет вызовов методов. Для десятков тысяч обновлений запускайте скрипт в часы наименьшей нагрузки и подумайте о разбиении по ответственным пользователям.
- `crm.item.update` в Битрикс24 проверяет `stageId` на соответствие воронке сделки. Опечатка в `newStageId` даёт ошибку для отдельного вызова — она видна в `getErrorMessages()`, — но весь скрипт не прерывается благодаря `isHaltOnError: false`.
- Атомарный откат **не** поддерживается. Если нужно транзакционное поведение, сначала выгрузите текущие значения в отдельный CSV и запустите вторую миграцию для восстановления.
