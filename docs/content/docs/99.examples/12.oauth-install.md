## Что делает пример

Это недостающее звено между «у меня есть `clientId`/`clientSecret`» и «у меня есть рабочий клиент `B24OAuth`». Приложение Битрикс24, установленное через OAuth, получает события `ONAPPINSTALL`, `ONAPPUPDATE` и `ONAPPUNINSTALL` на настроенный вами URL обработчика. Этот рецепт:

1. Принимает событие установки и **сохраняет токены OAuth по порталам** (ключ — `member_id`).
2. Предоставляет `clientForMember(memberId)` — создаёт экземпляр `B24OAuth` из сохранённых токенов и подключает колбэк обновления, чтобы следующая обновлённая пара токенов автоматически записывалась обратно в хранилище.
3. Удаляет учётные данные при удалении приложения.
4. Показывает REST-вызов для конкретного портала (`profile`) через полученный клиент.

Используйте его как каркас многоарендного бэкенда, который обслуживает много порталов Битрикс24 из одного OAuth-приложения.

::note
**Безопасность.** URL установки и удаления доступны публично. Примените два приёма защиты из раздела [Безопасность приложений-получателей событий](/docs/tools/security/): отвечайте `200` до проверки и проверяйте `application_token` за постоянное время **до удаления учётных данных** при деинсталляции.
::

::warning
**Эндпоинт установки не может аутентифицировать вызывающего, и никакой код этого не изменит.** `application_token` *выдаётся* самим событием установки, поэтому у обработчика при первой установке нечего сверять. Любой, кто достучится до `/install` и знает `member_id`, может отправить установку для этого портала.

Рецепт управляет другим: тем, чего *стоит* поддельная установка. Сохранённый `client_endpoint` определяет, куда пойдут REST-вызовы приложения, а `server_endpoint` — куда SDK отправляет `client_id`, **`client_secret`** и `refresh_token` при каждом обновлении токена. Поэтому непроверенная подделка не просто испортит запись одного портала, а выдаст секрет всего приложения. Рецепт проверяет все три URL перед сохранением (см. `B24_ALLOWED_PORTAL_HOSTS` ниже), и поддельная установка в худшем случае может сломать вызовы одного портала — и только.

Это снижение риска, а не исправление. **Закройте `/install` сетевым ограничением** — списком разрешённых исходящих адресов Битрикс24 или секретным сегментом пути, — как любой неаутентифицированный эндпоинт, который пишет в вашу базу данных.
::

## Стек

Node.js 20+, `express`.

## Установка

```bash
pnpm add express
```

## Окружение

```bash
export PORT=3001                             # default
export B24_CLIENT_ID='local.abc123'          # from your Bitrix24 dev console
export B24_CLIENT_SECRET='...'

# Optional. Where the OAuth tokens are written. Defaults to
# .oauth-store.json in the working directory, which is rarely where you
# want portal credentials to live on a real server.
export B24_OAUTH_STORE='/var/lib/myapp/tokens.json'

# Optional, and required for self-hosted portals. Which hosts an install event
# may name, comma-separated. An entry starting with a dot is a suffix.
#
# The defaults cover the cloud: `.bitrix24.com`, `.bitrix24.ru` and the other
# regional suffixes for the portal, and `oauth.bitrix.info` /
# `oauth.bitrix24.tech` for the token server. A boxed Bitrix24 lives at
# whatever domain its owner chose and is its own token server, so it is
# rejected until you name it — and naming one known host is *stronger* than
# the cloud default, not weaker.
export B24_ALLOWED_PORTAL_HOSTS='intranet.example.com'
export B24_ALLOWED_OAUTH_HOSTS='intranet.example.com'
```

`server_endpoint` — это не портал. В облаке это общий сервер токенов для всех порталов, поэтому у него отдельный список, а не требование совпадать с `domain`.

В консоли разработчика Битрикс24:

- **URL обработчика установки**: `https://your-server.example.com/install`
- **URL обработчика удаления**: `https://your-server.example.com/uninstall`

Для локальной разработки откройте доступ командой `npx ngrok http 3001`.

## Запуск

```bash
npx tsx 12-oauth-install.ts
```

Затем запустите рукопожатие, установив приложение на портал Битрикс24. Проверьте результат так:

```bash
curl https://your-server.example.com/portal/<memberId>/profile
```

## Примечания

- **Хранилище — JSON-файл** (`.oauth-store.json`), только для демонстрации. В продакшене замените его на Postgres, Redis или ваше настоящее хранилище.
- **`application_token`** Битрикс24 присылает и с событием установки, и с событием удаления. Рецепт запоминает его при установке и за постоянное время сравнивает перед тем, как что-либо удалить при деинсталляции, поэтому подделанный вызов удаления не сотрёт учётные данные портала. В событии установки сверять не с чем — именно там `application_token` выдаётся, — поэтому считайте `/install` неаутентифицированным и закройте его теми сетевыми ограничениями, которые допускает ваше развёртывание.
- **`setCallbackRefreshAuth`** подключается при каждом вызове `clientForMember()`. Это гарантирует, что в хранилище всегда лежит свежая пара токенов после того, как SDK автоматически обновил токен после ответа 401.
- **Всегда сначала возвращайте `2xx`** на эндпоинтах установки и удаления, а потом обрабатывайте. В Битрикс24 нет автоматического повтора (неудавшиеся или медленные доставки отбрасываются, а медленные обработчики получают более низкий приоритет) — см. [Приёмы безопасности](/docs/tools/security/).
- Если один портал обслуживают несколько воркеров, используйте транзакционное хранилище (Postgres `ON CONFLICT UPDATE`), чтобы одновременные обновления не теряли токены.
- **`member_id` — это ключ, который выбрал кто-то другой.** `/install` не может аутентифицировать вызывающего, поэтому идентификатор приходит недоверенным, а затем становится ключом объекта, строкой журнала и — в вашем развёртывании — ключом базы данных. Рецепт делает с этим две независимые вещи, потому что одна не заменяет другую: проверяет **форму** идентификатора на границе (это не даёт символу перевода строки подделать вторую строку журнала и ограничивает длину ключа) и хранит данные в `Object.create(null)` (это не даёт `__proto__` проглотить запись, а `constructor` / `toString` — найтись при поиске как унаследованные функции). Сохраните обе привычки в том, чем замените JSON-файл: у `Map` или параметризованного запроса второе свойство уже есть.
- Для более широкого многоарендного шаблона «по порталам» (стратегия кеширования, жизненный цикл, отозванные установки) этот рецепт — основа: для часто используемых порталов оберните `clientForMember` в LRU-кеш с ключом `memberId` (подходит LRU на основе `Map`: см. примечание выше).
