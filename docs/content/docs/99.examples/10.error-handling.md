## Что делает пример

Показывает каноническую схему обработки ошибок для тех, кто вызывает SDK:

1. **`SdkError`** — программная ошибка (например, вызов метода не из v3 через `actions.v3.*`).
2. **`AjaxError`** — REST вернул ошибку (`ERROR_NOT_FOUND`, `INVALID_CREDENTIALS`, `EXPIRED_TOKEN`, `QUERY_LIMIT_EXCEEDED`, …).
3. **Сетевой уровень** — `NETWORK_ERROR` / `REQUEST_TIMEOUT`. Для неидемпотентных вызовов это принципиально другая ситуация.
4. **Мягкие ошибки** — коды, которые возвращаются как `isSuccess: false`, а не выбрасываются: либо они зафиксированы во встроенном списке, либо вы добавили их через `softErrorCodes`, либо — на `restApi:v3` — их покрывает [правило по категории](/docs/working-with-the-rest-api/error-codes/#классификация-по-категории-restapiv3).

Также показано применение `setRestrictionManagerParams` с новыми параметрами:
- `hardErrorCodes` — дополняет список SDK «выбросить сразу, без повтора» кодами, специфичными для вашего приложения.
- `softErrorCodes` — дополняет список «вернуть как мягкую ошибку в AjaxResult».
- `retryOnNetworkError: false` — отключает сетевые повторы для `*.add` / `*.update` / загрузки файлов, чтобы не плодить дубликаты.

На `restApi:v3` разделение на мягкие и жёсткие ошибки определяется по ответу, а не по списку кодов, поэтому ошибка, о которой SDK никогда не слышал, всё равно доставляется так же, как соседние — см. [Коды ошибок](/docs/working-with-the-rest-api/error-codes/#классификация-по-категории-restapiv3). В `2.x` это включалось отдельным параметром; начиная с `3.0.0` параметр не нужен.

## Примечания

- `setRestrictionManagerParams` обновляет политику для **всех** HTTP-клиентов этого экземпляра `$b24` (и v2, и v3).
- Он **заменяет названные вами параметры и сохраняет остальные**, поэтому для возврата значений по умолчанию нужно явно назвать то, что требуется очистить: `ParamsFactory.getDefault()` не содержит ключей `hardErrorCodes` / `softErrorCodes`, и если передать только его, эти списки останутся в силе. Блок `finally` в рецепте передаёт `hardErrorCodes: []` именно поэтому.
- `hardErrorCodes` и `softErrorCodes` **аддитивны**: встроенные списки (коды авторизации и фатальные) всегда считаются жёсткими. Их можно расширять, но нельзя убирать.
- Для неидемпотентных вызовов оборачивайте каждый вызов в `try/finally`, который потом возвращает `retryOnNetworkError: true`. Рецепт показывает этот приём.
- Если для неидемпотентного вызова произошёл сетевой тайм-аут, безопасное действие — **сверка** (запросить только что созданную сущность по идемпотентной метке на стороне клиента), а не повтор.
