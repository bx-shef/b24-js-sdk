# Ревью PR: уровень по путям, `/code-review`, двое проверяющих и панель из пяти

> Последняя сверка: 2026-11-24

Правила — [AGENTS.md](../../../AGENTS.md), раздел «Ревью PR». Этот навык — порядок действий.
Расходятся — прав файл правил, а навык правится в том же PR.

**Основная проверка** (дальше — «проверка»): `pnpm install --frozen-lockfile`, затем `pnpm run lint`,
`pnpm run typecheck`, `pnpm run package-jssdk:test:run-unit`, `node --test "scripts/__tests__/**/*.test.mjs"`.
Один прогон на PR; по ходу работы — точечные запуски нужных тестов.

## 1. Подготовка

1. `git fetch origin main && git merge origin/main` в ветку PR — проверяем то, во что PR вольётся.
   Чужую ветку не перебазируем.
2. Простыми словами, 3–6 строк: что PR делает и зачем. Не пишется коротко — PR делает слишком много.
3. Проверка — зелёная. В ней же сверка правил уровней (`scripts/__tests__/review-tier.test.mjs` зовёт
   `tools/review-tier.sh --self-test`).

## 2. Уровень ревью

`tools/review-tier.sh --action` — уровень по путям изменённых файлов, `--explain` — по файлам и правилам,
`--levels` — легенда уровней. Правила — `tools/review-tier.rules`. Уровень PR — наибольший из уровней его файлов.

| уровень | что меняется | что делаем | примеры |
| --- | --- | --- | --- |
| 0 | документы и переводы (`*.md`, `docs/content`, навыки `skills/`), тесты, версии, `.gitattributes` | ревью нет: основная проверка | перевод главы, строка в CHANGELOG, подъём версии, новый тест |
| 1 | мелкое поведение: всё, что не 0 и не 2 | `/code-review medium --max-findings 5`. Уровень пишем явно: скилл запоминает прошлый. `max` и `ultra` запрещены | исправление в одном хелпере, страница сайта документации, playground |
| 2 | деньги, лицензия, безопасность, транспорт и авторизация, сборка, CI, Docker, публичный API | двое проверяющих параллельно, панель из пяти — для денег и лицензий и по правилу панели на задачу (п. 3); `/code-review` не зовём | `core/http`, `oauth`, `actions` (batch), `index.ts`, `package.json`, воркфлоу, сервер сайта |

- **Ручной уровень** главнее автоматического. Его задаёт слово владельца («уровень 2», «панель», «без ревью»)
  или строка «Уровень ревью: N» в описании PR: тогда `tools/review-tier.sh --level N --action` (или
  `REVIEW_TIER=N`). Вывод показывает оба: «вручную N, по путям M».
- Агент вправе **поднять** уровень сам: сомнение; правка выросла из рассуждения, а не из замера; в тексте
  цена или условия лицензии. **Понизить** вправе только владелец: ручной уровень ниже автоматического
  печатает предупреждение.
- Пути с пометкой «слово владельца» (`LICENSE`) меняются только по слову владельца.
- Какая модель и усилие, сколько агентов за раз — режим «экономия» или штатный, раздел «Ревью PR».

Если `/code-review` недоступен, сообщить владельцу и согласовать замену; не называть ручную проверку запуском скилла.

## 3. Ревью уровня 2 — агенты одним сообщением, параллельно

Двое: **Безопасность** и **Инженер/QA** (роли «Инженер» и «QA» таблицы — в одном агенте). Пятеро — если PR трогает деньги или лицензии (`license-manager.ts`, `payment-manager.ts`), а также на последнем PR задачи, если панель из пяти ещё не проводилась. Для задач только уровня 0 ревью не требуется. В панели все роли таблицы, по агенту на роль.

| роль | модель, усилие | смотрит |
| --- | --- | --- |
| **Документация** (только в панели из пяти) | `gpt-6.2-sol`, среднее | документация (`docs/content`, `skills/`, `AGENTS.md`) верна против кода `packages/jssdk/src`, ссылки открываются, примеры компилируются, методы REST сверены с `b24-rest-docs` |
| **Инженер** | `gpt-6.2-sol`, среднее | верность решений и канон репозитория (AGENTS.md); стек лимитеров не обходится; совместимость публичного API и типов; сборка пакетов и сайта |
| **QA** | `gpt-6.2-sol`, среднее | краснеет ли тест, если сломать код; всё ли заявленное в PR проверено; что можно проверить только на портале или стенде — так ли и названо |
| **Безопасность** | `gpt-6.2-sol`, высокое | токены и OAuth, вебхуки в логах и ошибках, редиректы и SSRF в HTTP, ввод из `postMessage` во frame, CSP сайта, supply chain (зависимости, воркфлоу); у Docker — ключи только в .env, порты, пользователь не root |
| **CTO** (только в панели из пяти) | `gpt-6.2-sol`, высокое | изменение целиком: объём, цена, направление, расхождение с bitrix24/b24jssdk (стоимость еженедельной синхронизации), что оно обещает пользователям; публикация и домен — по команде владельца; не решение ли это владельца |

Для Codex модели и усилие указаны в таблице; в Claude Code применять доступные модели по действующим правилам проекта, не выдавая их за Codex. Модель — параметр запуска агента. Усилие — как позволяет среда запуска; **максимум усилия — никогда**. Если указанные модель или усилие недоступны, явно сообщить об этом и фактически использованной конфигурации; не объявлять требуемое ревью проведённым без согласованной замены. Замечания фиксировать с файлом, строкой и проверяемым последствием; после исправления тот же проверяющий перепроверяет именно своё замечание.

Запускающий называет каждому файлы и строки диффа, которые смотреть. Каждому в задании — дословно по смыслу:

- Проект большой. Смотри файлы и строки из задания (список — `git diff origin/main...HEAD --stat`), не грузи всё дерево.
- Дерево общее. Чужая правка — сосед, не откатывать и не строить на ней теорий.
- Код меняет только QA (в паре — «Инженер/QA») и только чтобы проверить, что тест краснеет, — в отдельном
  `git worktree`, мутаций не больше 3 на PR. Откат мутации — из копии во временном каталоге, **никогда**
  `git checkout --`.
- Внешний API и REST Битрикс24 сверять с источником (`.bitrix-docs/b24-rest-docs`, MCP `b24-dev-mcp`), не по памяти.
- Ключи, вебхуки и данные клиентов в отчёте не цитировать.
- Сообщать находки — не больше 8, по существу: файл:строка, что, почему важно, как чинить, насколько
  уверен. Не чинить.

## 4. Отчёт владельцу — по-русски, коротко

Блок на проверяющего: **кто — что — почему важно — как чинить**. Без стенограмм. Отдельно — что берёшь
в работу и что нет, с причиной и замером.

## 5. Исправления и повтор

- Всё — **в этом же PR**. Просится в отдельный issue или PR — не выносить молча, сказать и обсудить.
- Исправленный гард — с тестом, который краснеет при мутации.
- После правок: проверка, пуш. Перепроверяет **только нашедший** замечание — продолжением того же
  агента (сообщением ему), а не новым.
- Ревью заново целиком — только если PR переписан. Серия связанных PR — **одно ревью (двое или панель) на
  общий дифф** серии.
